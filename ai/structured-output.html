Structured Output

Get replies a program can read: specify the exact JSON shape, allowed values and what to do with missing data, then parse and check every reply in code.

You have 300 customer emails and want each one as a row in a spreadsheet: name, order number, type of problem. You write a prompt, run it on the first email, and the reply opens with a cheerful "Sure, here are the details" followed by bold labels and a bulleted list. A person reads that fine. Your script, which expected three clean fields, crashes on the first line.

When a program reads the reply, the reply is no longer prose. It is data, and the program can only read it if the format is exactly what the code expects.

#Specify the shape, not just the content

Asking a model to "extract the name, order number and issue" tells it what to find. It says nothing about how to write it down, so the model picks the format a helpful chat reply usually has.

For a program, everything about this is wrong: the friendly opener, the markdown, the # added to the number, and an issue written as a free sentence that cannot be counted. A good structured-output prompt settles five things:

  1. The format. Usually JSON, because every language can parse it.
  2. The exact field names and types. order_id as a string of digits, not "Order number".
  3. The allowed values for any field you will group or count by.
  4. What to do when something is missing. Use null; never guess.
  5. Nothing else. No text before or after the JSON.

The template does the work of an example, as in Show Examples, while the rules around it set the limits. Asking for null matters most: without it, a missing order number tends to come back as something plausible-looking, which is far worse than an empty field.

Key idea

A model is good at following a format and not perfect at it. Specify the shape exactly in the prompt, then check every reply in code before you use it.

#Check every reply

Even with a clear prompt, across hundreds of calls you will see the occasional reply wrapped in a markdown code fence, with a value outside your list, or with a missing field. Treat model output like input from a user: parse it, check it, and only then trust it.

Here is the same check in code. It returns either the clean data or a list of errors you can show to a person or send back to the model.

const FIELDS = ["name", "order_id", "issue_type"];
const ISSUE_TYPES = ["damaged", "late", "wrong-item", "other"];
 
function parseTicket(reply) {
  const text = reply.trim().replace(/^```(json)?\s*/, "").replace(/\s*```$/, "");
  let data;
  try { data = JSON.parse(text); } catch { return { ok: false, errors: ["not valid JSON"] }; }
  if (typeof data !== "object" || data === null || Array.isArray(data)) {
    return { ok: false, errors: ["expected one JSON object"] };
  }
  const missing = FIELDS.filter((f) => !(f in data));
  if (missing.length) return { ok: false, errors: missing.map((f) => "missing " + f) };
  const errors = [];
  const { name, order_id: orderId } = data;
  if (name !== null && typeof name !== "string") errors.push("name must be a string or null");
  if (orderId !== null && !(typeof orderId === "string" && /^[0-9]+$/.test(orderId))) {
    errors.push("order_id must be digits or null");
  }
  if (!ISSUE_TYPES.includes(data.issue_type)) errors.push("issue_type must be one of " + ISSUE_TYPES.join(", "));
  return errors.length ? { ok: false, errors } : { ok: true, value: data };
}
 
const reply = '```json\n{"name": "Sam Ortiz", "order_id": null, "issue_type": "late delivery"}\n```';
console.log(parseTicket(reply)); // { ok: false, errors: [ 'issue_type must be one of ...' ] }
import json, re
 
FIELDS = ["name", "order_id", "issue_type"]
ISSUE_TYPES = ["damaged", "late", "wrong-item", "other"]
 
def parse_ticket(reply):
    text = re.sub(r"^```(json)?\s*|\s*```$", "", reply.strip())
    try:
        data = json.loads(text)
    except json.JSONDecodeError:
        return {"ok": False, "errors": ["not valid JSON"]}
    if not isinstance(data, dict):
        return {"ok": False, "errors": ["expected one JSON object"]}
    missing = [f for f in FIELDS if f not in data]
    if missing:
        return {"ok": False, "errors": ["missing " + f for f in missing]}
    errors = []
    if data["name"] is not None and not isinstance(data["name"], str):
        errors.append("name must be a string or null")
    order_id = data["order_id"]
    if order_id is not None and not (isinstance(order_id, str) and re.fullmatch(r"[0-9]+", order_id)):
        errors.append("order_id must be digits or null")
    if data["issue_type"] not in ISSUE_TYPES:
        errors.append("issue_type must be one of " + ", ".join(ISSUE_TYPES))
    return {"ok": False, "errors": errors} if errors else {"ok": True, "value": data}
 
reply = '```json\n{"name": "Sam Ortiz", "order_id": null, "issue_type": "late delivery"}\n```'
print(parse_ticket(reply))  # {'ok': False, 'errors': ['issue_type must be one of ...']}

Missing fields are caught before any value is checked. Note that null and missing are different: "order_id": null is the model saying "not in the email", which you asked for; no order_id key at all means it skipped part of the format.

In the real world

Many model APIs offer a structured output or JSON mode, where you pass a schema and the reply is constrained to match it. Use it when you have it: it removes most format errors. It cannot check meaning, though. A reply can match the schema perfectly and still put the wrong value in a field, so keep checking values that matter.

#Designing a shape that works

  • Keep it flat and small. Five clear fields beat twenty nested ones. Each extra field is another chance for a mistake.
  • Name fields plainly. delivery_date tells the model what goes there; dd does not.
  • Give every category field a catch-all. An "other" value gives odd inputs somewhere honest to go.
  • If you need reasoning, give it a field. Put a "reasoning" field before the answer fields, for the reason Give the Model Room to Think explains: the model writes the fields in order, so reasoning placed first can shape the answer fields after it.

#Common mistakes

Trusting the reply because it looks right

Ninety-nine good replies do not make the hundredth safe. Parse and check every reply, and decide in advance what happens when one fails: retry with the error, or set it aside for a person.

Leaving no way to say &quot;missing&quot;

If every field must be filled, the model fills it, sometimes with a guess. Allow null and say when to use it.

Free text where you need categories

A field like "issue": "the lid was cracked" is fine to read and useless to count. If you will group by a field, give it a fixed list of values.

#Check yourself

Quick check

An email has no order number. Your prompt does not mention missing values. What is the risk?

  1. Not quite. The JSON will usually be valid. The problem is the value inside it.
  2. Right. A required field invites a value. Say "use null if it is not in the text" so missing stays missing.
  3. Not quite. Refusal is unlikely. Quietly filling the gap is the common failure.

You use an API mode that guarantees replies match your JSON schema. Do you still need to check replies?

  1. Not quite. It guarantees shape, not truth. A field can be well-formed and wrong.
  2. Right. Right. Schema modes remove format errors, not mistakes in content.
  3. Not quite. They generally do work for format. The remaining risk is meaning.

You want the model to reason before picking a category, inside the JSON. Where should the reasoning field go?

  1. Right. Fields are written in order, so reasoning that comes first can inform the category.
  2. Not quite. Then the category is chosen before any reasoning exists, and the reasoning only justifies it.
  3. Not quite. For a parser it does not. For a model writing one token at a time, it does.
