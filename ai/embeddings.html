Embeddings

Turn words, documents and products into lists of numbers where similar meanings sit close together, and measure closeness with cosine similarity.

A customer types "warm jacket" into a clothing shop's search box. The shop sells an "insulated winter coat", which is exactly what they want. A keyword search misses the coat, because the two phrases do not share a single word. Meanwhile it returns a "jacket potato" recipe card from the café section.

The fix is to stop comparing letters and start comparing meanings. To do that, a computer needs meaning in a form it can calculate with: numbers. That is what an embedding is.

#Meaning as a position

An embedding is a list of numbers that represents a piece of content, chosen so that things with similar meanings get similar lists. A list of numbers like this is also called a vector. You can think of each one as a point in space. "Insulated winter coat" and "warm jacket" land near each other. "Linen shirt" lands somewhere else, and "jacket potato" far away.

Real embeddings have hundreds or thousands of numbers per item, not two. You cannot picture that many dimensions, but the arithmetic is the same as in two or three, so small examples are enough to learn the method.

#Where the numbers come from

Nobody types embeddings in by hand. They come out of a neural network trained on a task that forces similar things to look similar inside it. Two common tasks:

  • Predict the context. Train a network to guess a word from the words around it. Words that appear in similar sentences, like "coat" and "jacket", must produce similar hidden values to make similar guesses.
  • Match pairs. Show the network pairs that belong together, like a question and its answer, or a search and the product people clicked. Train it so matching pairs get close vectors and random pairs get distant ones.

After training, you keep the network and use one of its layers as the embedding: feed in any text and read off the list of numbers.

#Measuring closeness

To use embeddings, you need one number that says how similar two lists are. The standard choice is cosine similarity. It looks at the direction the two vectors point in, ignoring how long they are. It is 1 when they point the same way, 0 when they are at right angles (in embedding terms, unrelated), and −1 when they point in opposite directions.

It takes two ingredients, both school algebra:

  • The dot product: multiply matching positions and add. For [4, 1, 1] and [5, 2, 2] it is 4×5 + 1×2 + 1×2 = 24.
  • The length of a vector: Pythagoras in more dimensions. For [4, 1, 1] it is √(16 + 1 + 1) = √18 ≈ 4.24.

cosine(a, b) = dot(a, b) / (length(a) × length(b))

Dividing by the lengths is what makes it about direction only. A long document and a short one about the same thing still score as similar.

#Trace a search

To keep the numbers small, give each item a hand-made 3-number embedding: how warm it is, how dressy, how waterproof. The query "warm jacket" becomes [4, 1, 1]. Real embedding dimensions do not have tidy names like these, but the search works the same way.

function dot(a, b) {
  let total = 0;
  for (let i = 0; i < a.length; i++) total += a[i] * b[i];
  return total;
}
 
// Cosine similarity: 1 means same direction, 0 means unrelated.
function cosine(a, b) {
  return dot(a, b) / (Math.sqrt(dot(a, a)) * Math.sqrt(dot(b, b)));
}
 
// Item names with their scores, most similar first.
function search(query, items) {
  return Object.entries(items)
    .map(([name, vec]) => [name, cosine(query, vec)])
    .sort((x, y) => y[1] - x[1]);
}
 
search([4, 1, 1], {
  "insulated winter coat": [5, 2, 2],
  "wool overcoat": [4, 4, 0],
  "rain shell": [1, 1, 5],
  "linen shirt": [0, 3, 0],
}); // coat 0.985, overcoat 0.833, shell 0.454, shirt 0.236
import math
 
def dot(a, b):
    return sum(x * y for x, y in zip(a, b))
 
def cosine(a, b):
    """Cosine similarity: 1 means same direction, 0 means unrelated."""
    return dot(a, b) / (math.sqrt(dot(a, a)) * math.sqrt(dot(b, b)))
 
def search(query, items):
    """Item names with their scores, most similar first."""
    scored = [(name, cosine(query, vec)) for name, vec in items.items()]
    return sorted(scored, key=lambda pair: pair[1], reverse=True)
 
search([4, 1, 1], {
    "insulated winter coat": [5, 2, 2],
    "wool overcoat": [4, 4, 0],
    "rain shell": [1, 1, 5],
    "linen shirt": [0, 3, 0],
})  # coat 0.985, overcoat 0.833, shell 0.454, shirt 0.236

Key idea

An embedding turns meaning into a position. Once content is a position, "find similar things" becomes "find nearby points", which is just arithmetic.

#What embeddings are used for

  • Search by meaning. Embed every document once. At query time, embed the query and return the nearest documents, as in the trace.
  • Recommendations. "People who liked this also liked" becomes "items near this one".
  • Grouping and duplicates. Near-identical support tickets or product listings sit almost on top of each other.
  • Feeding language models. Language models turn every token into an embedding before doing anything else. And retrieval systems use embedding search to find the passages a model should read before answering, covered in RAG Basics.

#Common mistakes

Mixing embeddings from different models

Each embedding model builds its own space. Position 17 in one model's list has nothing to do with position 17 in another's. If you switch models, re-embed everything, documents and queries alike.

Treating similar as correct

"Refunds are accepted within 30 days" and "Refunds are not accepted" are about the same topic, so their embeddings are close. Similarity finds related text; it does not check whether that text agrees with the query or is true. Read what you retrieve.

Using the dot product without normalizing

The raw dot product grows with vector length, so long or repetitive items can outscore better matches. Use cosine similarity, or scale every vector to length 1 first, after which the dot product and cosine give the same answer.

#Try it yourself

Try it: Direction beats length

A query has the embedding [1, 2]. Document A is [2, 4] and document B is [3, 1]. Compute the dot product and the cosine similarity of the query with each. Which document is the better match, and why do the two measures disagree on how strong the match is?

Show a sample answer
  • A: dot = 1×2 + 2×4 = 10. Lengths are √5 and √20, so cosine = 10 / √100 = 10 / 10 = 1.0.
  • B: dot = 1×3 + 2×1 = 5. Lengths are √5 and √10, so cosine = 5 / √50 ≈ 0.71.

A is the better match: it points in exactly the same direction as the query, just twice as far. Cosine says so with a perfect 1.0. The dot product also ranks A first here, but its values (10 and 5) depend on lengths too, so you cannot tell from them that A is a perfect match in direction. That is why cosine is the usual choice: its scale is fixed from −1 to 1, whatever the vectors' lengths.

#Check yourself

Quick check

Two vectors point in exactly the same direction, but one is three times longer. What is their cosine similarity?

  1. Right. Cosine only cares about direction. Scaling a vector does not change it.
  2. Not quite. That would be true if length mattered. Dividing by both lengths removes it.
  3. Not quite. Cosine similarity is never above 1.

You switch to a new embedding model for queries but keep the old document embeddings. What happens?

  1. Not quite. The query and documents now live in different spaces. Comparing them is meaningless.
  2. Right. Positions in one model's space mean nothing in another's. Re-embed the documents with the new model.
  3. Not quite. Same length does not mean same meaning for each position.

A search for "can I cancel my order" returns a passage saying "orders cannot be cancelled once shipped" as the top match. What does that tell you?

  1. Not quite. The passage is on exactly the topic asked about. That is a correct retrieval.
  2. Right. Embeddings measure topic similarity, not agreement. The passage is relevant, and the answer it gives may be no.
  3. Not quite. High similarity says nothing about whether the passage says yes or no.
