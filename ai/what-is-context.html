What Is Context

A model only knows what it reads on each call. See what goes into that text, where it comes from, and why it decides the quality of every answer.

You call a support line about a delivery. The person who answers has never spoken to you. Everything they know about your problem comes from the notes on their screen: your order, the last agent's comments, the company's refund rules. If the notes are good, the call takes two minutes. If the last agent wrote "customer called, sorted", you start from zero.

A language model is in that position on every request. It has broad general knowledge from training, but about you and this task it knows only what is on its screen right now. That screen is called the context.

#Two kinds of knowing

A model has two sources of information, and they behave very differently.

  • Training. Everything it absorbed while it was built: language, facts about the world, how code usually looks. This is broad, but frozen at some date, and it contains nothing private: not your files, your company's rules or yesterday's news.
  • Context. The text sent to it on this call. This is narrow, but it is current and specific, and you control it.

When an answer is generic, out of date or wrong about your situation, the cause is usually the same: the fact it needed was not in the context, so it filled the gap from training. That is the pattern behind hallucinations and behind the generic answers in Prompting Basics.

Key idea

A model only knows about your situation what is in its context on this call. Deciding what goes in, and what stays out, is the main skill of working with it.

#What goes into the context

When you type a message into an AI app, your message is only one piece of what the model reads. The app assembles a larger block of text around it.

  • Instructions from whoever built the app: the role, the rules, the tone. See System Prompts.
  • Tool descriptions, if the model can search, run code or call other services. Covered in Tools and MCP.
  • Retrieved documents: pages the app looked up because they seemed relevant to your question. That is RAG.
  • Saved notes about you or the project, carried over from earlier sessions. That is memory.
  • The conversation so far: every earlier message and reply in this chat.
  • Your new message, plus anything you pasted or attached.

From the model's side there are no separate channels. It is all one long piece of text, read top to bottom, with markers saying who wrote what. Everything in this module is about choosing those pieces well.

#Watch a chat being resent

The model keeps nothing between calls. A chat feels continuous because the app sends the whole conversation again every time. Step through two turns of a bakery chat, then see what happens in a fresh chat.

Same model, same question, different context, different answer. The model did not "forget" Lena in the new chat. It never remembered her; it only ever read her.

#The same thing in code

Here is the app's side of that tracer. The history list is the only memory there is, and it lives in the app.

// The app keeps the conversation. The model keeps nothing.
function buildRequest(system, history, newMessage) {
  return [
    { role: "system", content: system },
    ...history,
    { role: "user", content: newMessage },
  ];
}
 
const system = "You take orders for a small bakery.";
const history = [];
 
const first = buildRequest(system, history, "I'm Lena. 12 rolls for Friday.");
history.push(first.at(-1), { role: "assistant", content: "Noted: 12 rolls, Friday." });
 
const second = buildRequest(system, history, "Can I make it 20?");
console.log(second.length); // 4: system, two saved turns, new message
 
const freshChat = buildRequest(system, [], "Can I make it 20?");
console.log(freshChat.length); // 2: nothing says what "it" is
# The app keeps the conversation. The model keeps nothing.
def build_request(system, history, new_message):
    return (
        [{"role": "system", "content": system}]
        + history
        + [{"role": "user", "content": new_message}]
    )
 
system = "You take orders for a small bakery."
history = []
 
first = build_request(system, history, "I'm Lena. 12 rolls for Friday.")
history += [first[-1], {"role": "assistant", "content": "Noted: 12 rolls, Friday."}]
 
second = build_request(system, history, "Can I make it 20?")
print(len(second))  # 4: system, two saved turns, new message
 
fresh_chat = build_request(system, [], "Can I make it 20?")
print(len(fresh_chat))  # 2: nothing says what "it" is

Real apps send the list through an API instead of printing its length, but the shape is the same: a list of messages, rebuilt and resent on every call.

#Context beats cleverness

Compare two ways of asking the same question. The wording barely changes. What changes is the information on the screen.

The first reply is not a bad model. It is an honest model with nothing to work with.

#Common mistakes

Assuming it remembers other chats

A new chat starts with an empty history. Unless the app has a memory feature that loads notes into the context, nothing from yesterday's chat is there. Paste in what matters.

Assuming it can see what you see

The model does not see your screen, your open files, today's date or the email you are replying to, unless the app puts them in the context. When an answer seems oddly unaware, ask: was that fact actually in the text it read?

Leaving old, wrong information in

Context works both ways. If an outdated price list sits in the conversation next to the new one, the model may use either. Removing wrong information matters as much as adding right information.

#Try it yourself

Try it: What would it need to know

Someone asks an assistant: "Should I accept this meeting invite?" List every piece of information the model would need in its context to give a useful answer, and where each piece could come from (the user, a calendar, a document, earlier conversation).

Show a sample answer

One reasonable list:

  • The invite itself: who sent it, topic, time, length. From the user pasting it, or a calendar tool.
  • The user's calendar that day: is there a clash? From a calendar tool.
  • The user's priorities: "I'm protecting mornings for focus work this month." From the user or saved notes.
  • Who the sender is to them: their manager, a vendor, a stranger. From the user or a contacts lookup.
  • Whether they are actually needed: the agenda, and whether a colleague is already going. From the invite or the user.

Without these, the only possible answer is generic advice about meetings. Notice that most of the useful facts are not in the question at all. That is normal: the question is usually the smallest part of a good context.

#Check yourself

Quick check

In a long chat, the assistant correctly refers to something you said 10 messages ago. Why can it do that?

  1. Not quite. A model's weights do not change while you chat. Nothing is written into the model.
  2. Right. Right. The app rebuilds the full conversation on every call, so the old message is in the text the model reads now.
  3. Not quite. Your message was never in its training data. It can only know it from the current context.

An assistant gives an outdated answer about your company's holiday policy. What is the most likely cause?

  1. Right. Training is frozen and has nothing private. Without the current policy in the context, a generic or old answer is the best it can do.
  2. Not quite. Temperature changes how varied the wording is. It cannot supply a fact the model never saw.
  3. Not quite. A longer question would not help unless it included the policy itself.

Which of these does the model not see unless the app adds it to the context?

  1. Not quite. Your message is always part of the request. That is the one piece you can count on.
  2. Right. The model has no clock. Many apps add the date to the instructions for exactly this reason; if they do not, the model can only guess.
  3. Not quite. That comes from training. It does not need to be in the context.
