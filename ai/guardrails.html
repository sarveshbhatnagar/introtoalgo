Guardrails

How permissions, argument checks, human approval and careful handling of untrusted text limit the damage when an AI agent makes a mistake.

A guardrail is a check that runs in ordinary code before an agent's action is carried out, and it applies whatever the model has written. Guardrails exist because a model can misread a request, follow reasoning that sounds right but is wrong, or be steered by text it read in a tool result, and better instructions cannot bring the chance of that to zero.

Suppose you tell a coding agent in capital letters to delete files only inside tmp/. The agent builds the path from two parts, one of them is empty, and the delete runs on the whole project folder. The instruction was clear, but it was only a request, and the delete tool accepted any path. A delete tool that refuses every path outside tmp/ would have stopped the damage, no matter what the model wrote.

#The four places to put a limit

You can limit an agent at four points, and they work best together. Each one is covered in its own section below.

  1. Permissions decide which tools the agent has at all and what its credentials can reach.
  2. Argument checks decide which paths, amounts and recipients a tool will accept.
  3. Human approval holds risky actions until a person says yes.
  4. Handling of untrusted text decides how much power the agent keeps after it has read content that someone else wrote.
Key idea

A rule that is only written in the prompt is a suggestion to the model. A rule that is checked in code before the action runs is a guardrail.

#Permissions

The safest tool is one the agent does not have. An agent that answers questions about orders needs a tool that reads orders, and it has no need for a tool that deletes customers. If you leave the delete tool out and connect the agent to the database with a read-only account, then even an attack that completely fools the model leaves it nothing to call.

The same applies to credentials. If the agent uses an API key that can do everything your own admin account can do, then every bug in the agent becomes an admin-level bug. Give the agent its own key with only the scopes it needs. A separate key also makes the agent's actions easy to find in the logs and easy to revoke without affecting anything else.

#Checking the arguments of a tool

Allowing a tool does not make every call to it safe, because the harm usually depends on the arguments. A tool that sends email is harmless with one recipient and a data leak with another. The place to enforce limits is inside the tool, the same place where Tool Use showed validation of bad input. Here the checks are aimed at dangerous input rather than malformed input. Typical checks are:

  • A file tool resolves the path, including .. segments and symbolic links, and only then checks that the result is inside the allowed folder. Checking the text of the path before resolving it can be bypassed.
  • A refund tool accepts an amount only up to the value of the order it refers to.
  • An email tool sends only to addresses that appear on the customer's record.
  • A tool that runs code does so in a sandbox with no network access and no view of your files.

Rate limits are a useful addition. A limit of ten refunds per hour will not stop a single bad refund, but it stops a confused agent from repeating the same mistake a hundred times before anyone notices.

#Human approval

Some actions are too costly or too hard to undo to leave to the model, and for those the system should pause and show the request to a person. The way to decide is to sort each tool by what happens when it is used wrongly. The table summarises a common sorting.

RiskExamplesDefault
Read onlylook up an order, search documentsrun automatically
Small or easy to undoa refund under 50, a draft replyrun and log it
Costly, external or permanenta large refund, sending email, deleting, publishingask a person first
Not needed for this jobdeleting a customerno tool at all

Approval only works if the person can make a real decision. The request has to show the exact recipient, amount or list of files, and not a summary written by the model, and the default answer should be no. If the agent asks about everything, including harmless lookups, the person soon approves without reading, and then the one dangerous request is approved as well. For that reason the automatic category should be as large as safety allows.

A policy gate applies the sorting to every tool request before anything runs. The tracer below follows five requests through one.

#The gate in code

The gate takes the place of the direct tool call in the agent loop. In the code below, askHuman shows the request to a person and returns yes or no.

const policy = {
  getOrder: { risk: "read" },
  refundOrder: { risk: "money", autoLimit: 50 },
  sendEmail: { risk: "external" },
};
 
function checkAction(call) {
  const rule = policy[call.tool];
  if (!rule) return { decision: "block", reason: `${call.tool} is not on the allowed list` };
  if (rule.risk === "read") return { decision: "allow" };
  if (rule.risk === "money" && call.input.amount <= rule.autoLimit) {
    return { decision: "allow" };
  }
  return { decision: "ask" };
}
 
function guardedRun(call, runTool, askHuman) {
  const { decision, reason } = checkAction(call);
  if (decision === "block") return { error: `Blocked: ${reason}.` };
  if (decision === "ask" && !askHuman(call)) {
    return { error: "A person declined this action. Do not retry it." };
  }
  return runTool(call);
}
policy = {
    "get_order": {"risk": "read"},
    "refund_order": {"risk": "money", "auto_limit": 50},
    "send_email": {"risk": "external"},
}
 
def check_action(call):
    rule = policy.get(call["tool"])
    if rule is None:
        return {"decision": "block", "reason": f"{call['tool']} is not on the allowed list"}
    if rule["risk"] == "read":
        return {"decision": "allow"}
    if rule["risk"] == "money" and call["input"]["amount"] <= rule["auto_limit"]:
        return {"decision": "allow"}
    return {"decision": "ask"}
 
def guarded_run(call, run_tool, ask_human):
    check = check_action(call)
    if check["decision"] == "block":
        return {"error": f"Blocked: {check['reason']}."}
    if check["decision"] == "ask" and not ask_human(call):
        return {"error": "A person declined this action. Do not retry it."}
    return run_tool(call)

Two details of this code matter. The policy lists the tools that are allowed, so a tool nobody has classified yet is blocked until someone decides what to do with it. If the policy listed forbidden tools instead, forgetting to add one would leave it open. The second detail is that a block or a refusal comes back to the model as an error message it can read, so the agent can tell the user what happened instead of retrying the same call.

#Untrusted text and prompt injection

The sendEmail request in the tracer came from text inside a customer message, not from the user. This is the attack described in Prompt Injection. When an agent reads text that you do not control, such as a web page, an incoming email or an uploaded document, whatever it does next may be steered by the author of that text, and the model cannot reliably tell the difference.

You can use the gate to react to this. After the agent has read untrusted content, require approval for any action that sends a message or touches private data, even if the same action would run automatically at the start of the session. The attack that does the most damage needs three things at once: untrusted text, access to private data, and a way to send data out. Removing or gating any one of the three makes the attack much harder.

#Checking what the model says

The sections above limit what an agent can do. Many products also check what the model writes to the user, because a reply can contain private data, a link the model made up, or text that breaks your policy. These output checks usually run after generation and are either simple rules, such as a pattern that detects card numbers or a list of allowed link domains, or a second model call that classifies the reply. They help, but they are weaker than the limits on actions: a classifier can be wrong in both directions, and a rule can only catch what its author thought of. Use output checks for what the user sees, and use permissions and argument checks for anything that changes the world.

#Pitfalls

A rule that exists only in the prompt

An instruction such as "never delete files outside tmp/" makes a mistake less likely but does not prevent it, and an injected instruction can argue the model out of it. Write the same rule into the tool itself, and keep the instruction as a way to make the agent behave well in the normal case.

Approval requests for every action

A person who approves every lookup stops reading after about ten requests and will approve the dangerous one too. Ask only for risky actions, show the exact recipient, amount or file list, and make no the default answer.

Allowing a tool without checking its arguments

Allowing sendEmail without checking the recipient means allowing email to anyone, and allowing a file tool without checking the path means allowing access to every file the process can read. Most useful limits are on arguments, so write them in the tool.

Checking a path before resolving it

A check that the path text starts with tmp/ passes tmp/../src, which points outside the folder. Resolve the path first, including links, and then compare the result with the allowed folder.

Letting the agent work around a block

If a block message is vague, or if the agent has a second tool that does the same thing, it may find another route to the blocked action. Name the reason in the error, say whether retrying is pointless, and apply the same limit to every tool that can do the same job.

#What to do in practice

Start from the tool list, not from the prompt. For each tool, write down the worst thing it could do with the worst arguments the model could produce. Remove tools the job does not need, narrow the credentials of the ones that remain, and put argument checks inside the tools. Then assign each remaining tool to automatic, logged or approval according to the table above, and make approval requests show exact details.

Log every action together with the decision made, so that you can see what the agent tried and what the gate stopped. A pattern of blocked calls is often the first sign that a prompt is being attacked or that the instructions confuse the model. Finally, turn each worst case you wrote down into a test in your evals, so that a later change to a prompt or a tool cannot quietly remove a limit.

Try it: Set the policy for an assistant

An assistant manages a person's calendar and email using the tools below. For each tool, choose one of run automatically, run and log, ask first, or remove, and give one reason.

Show a sample answer
  • readCalendar: run automatically. Reading changes nothing.
  • createEvent: run and log. It only touches the user's own calendar and is easy to undo.
  • sendEmail: ask first. It reaches other people and cannot be unsent, so the request should show the recipients and the full text.
  • deleteEmail: ask first, or make it reversible by moving mail to a trash folder that is emptied after 30 days.
  • readWebPage: run automatically, but treat the rest of the session as untrusted and require approval for any send.
  • forwardAllEmail: remove. No everyday task needs it, and it gives an attacker a silent and permanent copy of everything the user receives.

The decision follows what a wrong call would cost, not how often the tool is useful.

Quick check

An agent only answers questions about orders. What most reliably prevents it from ever deleting data?

  1. Not quite. This is a request that the model can misread or be talked out of.
  2. Right. With no way to delete, nothing the model writes can make it delete.
  3. Not quite. This is costly, and approval fatigue sets in. Removing the ability is simpler and stronger.

Why should the policy list the tools that are allowed instead of the tools that are forbidden?

  1. Not quite. Length is not the reason for the choice.
  2. Right. Forgetting to add a rule then fails safe instead of failing open.
  3. Not quite. The model never sees this list. Ordinary code checks it.

A file tool checks that a path starts with tmp/ and then deletes it. Which input gets past the check?

  1. Not quite. This is a file inside the allowed folder, so allowing it is correct.
  2. Right. The text starts with tmp/, but the path resolves to a file outside the folder. The check has to run after the path is resolved.
  3. Not quite. The text does not start with tmp/, so the check already rejects it.

An agent reads a web page and then asks to send an email. What is the safest default?

  1. Not quite. The page may contain instructions that made the agent send this message, so the request may not be the user's.
  2. Right. After reading untrusted text, an outgoing action needs a person's check.
  3. Not quite. This is too strong. Sending only needs approval when untrusted text may be steering the agent.

#What to practise next

List your agent's tools with the worst thing each could do, add those cases to your evals, and read Privacy and Security for what to keep out of AI tools in the first place.
