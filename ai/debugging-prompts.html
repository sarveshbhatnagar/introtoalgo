Debugging Prompts

How to find why a prompt gives bad replies, fix it with one change at a time, and check every test case so a fix does not break other inputs.

Debugging a prompt means finding out why it produces bad replies and changing it so that they stop, without breaking the replies that were already good. A single prompt handles every input your application receives, so a change that fixes one input can quietly change the answers for others. The method that avoids this is to keep a set of test cases and run all of them after every change.

Without that set, you edit the prompt, retry the one bad input, see a good reply, and move on. A week later three other inputs have started failing, and nobody can tell which edit caused it.

#The debugging loop

The loop has five steps, and you repeat steps 3 to 5 until the failures are gone.

  1. Collect test cases. Gather 5 to 20 real inputs. Include the ones that fail and a spread of ones that already work, and write down the correct answer for each.
  2. Run every case with the current prompt and record which ones pass.
  3. Read the failures next to the prompt and decide on one likely cause.
  4. Change one thing that addresses that cause.
  5. Run every case again. Keep the change only if more cases pass than before and no important case that used to pass now fails.
Key idea

Step 5 is the one people skip. Judging a change on the single example you were fixing tells you nothing about the other inputs, which the same prompt also controls.

#Example: a ticket priority prompt

A support team uses a prompt that labels each incoming ticket as urgent, normal or low. They collected six tickets with the correct label for each, then tried three versions of the prompt. The tracer shows the results of each version across the whole set.

The tempting fix would have been to add the rule "If the ticket mentions payroll, label it urgent." That passes the test ticket, but it fails on the next ticket, which will be about invoices instead. A fix should address what the failing cases have in common, not the wording of one case.

#Finding the cause

Most prompt failures come from a short list of causes. Each one has a typical symptom and a typical fix, and the fix is a change to one part of the prompt.

#Missing context

The symptom is a reply that is correct in general but generic or aimed at the wrong audience. The model only knows what is in the prompt, so if it does not know who the reply is for or what it will be used for, it produces something average. The fix is to state the audience, the purpose and any constraints, as described in Prompting Basics.

#An undefined term

When a prompt uses a word like "urgent", "short" or "technical" without defining it, different inputs get different readings of that word, and the replies look inconsistent. The ticket example above is this case. The fix is to define the term and give the reason behind the definition, so the model can apply it to inputs you did not anticipate. Be Clear and Specific covers this.

#A format that is described but not shown

If the content of the reply is right but the layout varies, the prompt probably describes the format in words. Models follow a worked example much more closely than a description, so add one or two examples of the exact output you want. See Show Examples.

#No room for working

On problems with several steps, such as arithmetic or comparing options, a model that must give the answer first has no chance to work through the steps. Ask for the reasoning before the final answer, and ask for the answer in a fixed place so that your code can read it. Give the Model Room to Think explains the technique.

#Rules that conflict or are buried

If the model follows a rule on most inputs but ignores it on some, look at the other rules around it. Two rules may pull in different directions, such as "always answer briefly" and "always explain your reasoning", or the rule may be one line in the middle of a long prompt. Say which rule wins when they conflict, and move the important rule to the beginning or end of the prompt.

#A prompt that was assembled wrongly

In an application the prompt is usually a template that code fills in with the user's input and other data. If a reply makes no sense, print the exact text that was sent before you edit anything. A common finding is that a variable was empty, a document was cut off, or the user's text landed in the wrong place, and no rewording of the instructions would have helped.

#Missing facts

When the reply contains confident details that are wrong, the prompt usually asks for facts it never provided. The model fills the gap with plausible text. Put the facts in the prompt, and say what to write when the answer is not in them, for example "If the policy does not cover the question, say you do not know." The background is in Why Models Hallucinate.

If you cannot see the cause, you can ask the model to explain a single wrong reply, for example "Before the label, say in one sentence which words in the ticket decided it." The explanation is not a reliable account of how the model actually decided, but it often points to the phrase it focused on.

#A small test runner

Once you have more than a few cases, run them with code instead of by hand. In real use the getLabel function would send the prompt and the ticket to a model. In this sketch it is a stand-in that returns fixed answers, so you can see the output format.

function runTests(cases, getLabel) {
  const failures = [];
  for (const c of cases) {
    const got = getLabel(c.ticket);
    if (got !== c.expected) failures.push(`${c.ticket}: expected ${c.expected}, got ${got}`);
  }
  console.log(`passed ${cases.length - failures.length} / ${cases.length}`);
  for (const f of failures) console.log("  " + f);
}
 
const cases = [
  { ticket: "Calm: no one can pay", expected: "urgent" },
  { ticket: "FURIOUS about typo", expected: "low" },
  { ticket: "Reports page slow", expected: "normal" },
];
// Stand-in for a real model call, behaving like prompt v1:
const v1 = { "Calm: no one can pay": "normal", "FURIOUS about typo": "urgent", "Reports page slow": "normal" };
runTests(cases, (ticket) => v1[ticket]); // passed 1 / 3
def run_tests(cases, get_label):
    failures = []
    for c in cases:
        got = get_label(c["ticket"])
        if got != c["expected"]:
            failures.append(f'{c["ticket"]}: expected {c["expected"]}, got {got}')
    print(f"passed {len(cases) - len(failures)} / {len(cases)}")
    for f in failures:
        print("  " + f)
 
cases = [
    {"ticket": "Calm: no one can pay", "expected": "urgent"},
    {"ticket": "FURIOUS about typo", "expected": "low"},
    {"ticket": "Reports page slow", "expected": "normal"},
]
# Stand-in for a real model call, behaving like prompt v1:
v1 = {"Calm: no one can pay": "normal", "FURIOUS about typo": "urgent", "Reports page slow": "normal"}
run_tests(cases, lambda ticket: v1[ticket])  # passed 1 / 3

Replies vary from run to run because of sampling (see Sampling and Temperature), so with a real model you should run each case several times. A case that passes two times out of three is a real failure. Evals extends this runner into a proper test suite.

#Pitfalls

Changing several things at once

If one edit adds an example, rewords the task and moves a rule, you cannot tell which change helped and which one hurt. Make one change per run. If a change does nothing, you can undo it without wondering what else you touched.

Adding a rule for each failing input

A rule such as "if the ticket mentions payroll, mark it urgent" makes the prompt longer and more fragile, and it does not help with the next unseen input. Look for what the failing cases share and fix that.

Tuning the prompt to the test set

After many rounds of edits, the prompt may pass every case you have only because you shaped it around them. Keep a few cases aside that you never look at while editing, and run them at the end. If they fail, the prompt has learned your test set and not the task.

A test set with only failures

If every case in the set is a past failure, a change that fixes them can break the ordinary inputs without anyone noticing. Include plenty of cases that already work.

Blaming the model too early

Before you decide that a model cannot do the task, reread the prompt as a stranger would, with no knowledge of your product. Switching models is a fair test only once the prompt is clear, because a vague prompt fails on any model.

#What this changes in practice

Save every bad reply you see in production, together with the correct answer, and add it to the test set. Over time the set becomes a record of what has gone wrong, and any later change to the prompt, or to the model behind it, can be checked against it. Write down each prompt version next to its results so you can go back to a version that worked.

Try it: Find the cause, then fix it

This prompt translates app text for a Spanish release of a product called Bloom. Some replies translate the name as "Florecer", which confused testers. Name the likely cause in one sentence, then rewrite the prompt so that it fixes the cause and not just this one word.

Show a sample answer

The cause is that the prompt never says some words are names, so "Bloom" looks like an ordinary English word that should be translated.

This works because a general rule plus a list addresses the cause, and the reason lets the model treat other feature names the same way. After the change, rerun your other translation cases to check that ordinary words are still translated.

Quick check

Your change fixes the failing case. What should you do before keeping it?

  1. Not quite. It works on one input, but the same text controls every input.
  2. Right. A change can break cases that used to pass, as version 2 did to the locked-out user.
  3. Not quite. That is useful for a flaky case, but it tells you nothing about the other cases.

Tickets written angrily are labelled urgent even when the problem is minor. What is the most likely cause?

  1. Not quite. It reads tone well, and it relies on tone because nothing else was defined.
  2. Right. Without a definition, tone is the most obvious signal. Define urgency by impact and say that tone does not count.
  3. Not quite. Randomness would cause inconsistent labels, not a steady bias toward angry tickets.

A case passes on one run and fails on the next with the same prompt. What does that tell you?

  1. Not quite. The test is fine. The reply is varying between runs.
  2. Right. Replies are sampled, so a borderline case can go either way. Treat it as a failure and make the prompt clearer.
  3. Not quite. Varying replies are normal sampling behaviour and are not a sign of load.
