Common Mistakes

The mistakes people most often make when working with an AI assistant, why each one happens, and the habit that prevents it.

Most problems with AI assistants come from how the assistant is used and not from the model itself. The same few mistakes appear again and again: asking too little, trusting the answer too much, pasting too much private material, and handing over decisions that should stay with you. This lesson describes each of them, explains why it happens, and gives the habit that prevents it.

Each mistake is cheap to make because the assistant always answers fluently. A vague request still gets a confident reply, a wrong number is written in the same tone as a right one, and a pasted secret is accepted without complaint. Nothing in the tool warns you, so the checks have to come from you.

#The four patterns behind most mistakes

Almost every everyday mistake belongs to one of four patterns. Under-asking means giving the model too little to work with, so it fills the gaps with the most typical guess. Over-trusting means accepting fluent text as true without checking it. Over-sharing means pasting more data than the task needs. Over-delegating means letting the assistant make decisions or do the learning that you should be doing. Earlier lessons cover each one in depth, and the table below links to them.

PatternWhat it looks likeThe habit that prevents it
Under-askingA one-line request for a large job, with no goal or definition of doneWrite a brief
Over-trustingNumbers, quotes and links accepted without checkingVerify claims in proportion to the stakes
Over-sharingWhole files, logs or exports pasted "for context"Paste less and redact the rest
Over-delegatingVery large changes accepted unread, or the thinking outsourcedWork in small steps and do the thinking yourself

#Common mistakes and how to avoid each one

#Regenerating instead of changing the request

When a draft is disappointing, it is tempting to press regenerate until a better one appears. With an unchanged prompt, every attempt is drawn from the same spread of likely answers (see Sampling and Temperature), so a problem that is consistent across attempts will stay. If two attempts have the same flaw, stop regenerating, say what is wrong, and change one thing about the request.

You should still check the result yourself. Growth from 412,000 to 470,000 is about 14.1%, so a draft that reports a different growth figure has made an error.

#Asking the model to do exact arithmetic or data processing

A language model produces text that looks like a correct answer, and for sums, sorting, counting and date conversion it is often slightly wrong. A figure such as 18% growth where the real value is 14% reads just as confidently as the correct one. For exact work, ask the assistant to write the spreadsheet formula or a short script, and let the spreadsheet or the interpreter do the calculation. Then recompute any number that will be quoted to someone else.

#Trusting citations and quotes without opening them

When you ask for a statistic "with a source", the model can produce a plausible sentence and a plausible link whether or not either exists (see Why Models Hallucinate). Open every source you intend to rely on and find the exact sentence that supports the claim. If you cannot find it, remove the claim or find a real source yourself.

#Pasting more than the task needs

A full customer export, a whole config folder or a complete log is easy to paste and gives the model information it does not need. The extra material can contain personal data or secrets such as API keys in a .env file, and it also makes the answer less focused. Paste only the part that matters, replace names and keys with placeholders, and rotate any real secret that has already been pasted.

#Accepting large changes and asking for green tests

When an assistant changes many files at once, nobody can review the result properly, so mistakes go in unnoticed. Ask for the smallest change that fixes the problem and read the whole diff. Also be careful with the request "make the tests pass": the quickest way for the model to do that may be to edit the tests, and the tests are the specification of what the code should do. After any such change, check which test files were modified before trusting a green result.

#Continuing a long conversation after it has gone wrong

In a long chat the model has to work from everything that was said, including the earlier wrong turns and rejected ideas, and its answers tend to get worse as that material builds up (see Context Rot). If the assistant keeps repeating a mistake you have already corrected, start a new conversation and put a short summary of the current state and the decisions made so far in the first message.

#Asking the model to confirm its own answer

Asking "are you sure?" or "is this correct?" does not check anything, because the model answers from the same understanding that produced the first reply. It may defend a wrong answer or drop a right one just because you questioned it. Verify against something outside the conversation instead, such as running the code, opening the source, or recomputing the number (see Verifying AI Output).

#Setting up an automation and never looking at it again

An automated workflow that worked in testing can drift. The inputs change, the model behind the service is updated, or new kinds of request arrive that nobody tried. Read a sample of real outputs on a regular schedule, and rerun your test set whenever the prompt, the model or the input source changes.

#Trusting everything or nothing

Some people trust the assistant fully after a few good answers, and others stop using it after one bad answer. Reliability depends on the task: an assistant can be very dependable at rewording an email and unreliable at quoting case law. Find out where it is strong by checking its output in each kind of task, and then adjust how much checking each task gets.

Blaming the tool for a missing brief

When a result disappoints, reread your request before blaming the model. If a capable person who knew nothing about your project could not have done better from the same words, the request is what needs fixing.

Not saying that AI was used

For anything other people will rely on, such as figures, legal text or production code, tell the reader what was AI-assisted and what you checked. This tells reviewers where to look, and many workplaces and schools require it.

#Who is responsible for the result

The assistant produces drafts, and you own the goal, the inputs, the checks and the decision to use the result. Whoever sends or merges the output is responsible for it, whatever tool produced it. The same applies when an assistant acts on its own, which is why Guardrails matter for agents.

Try it: Spot the mistakes

List every mistake in this story and the habit that would prevent it.

Show a sample answer
  1. She pasted the .env file. It usually holds secrets. Paste only the code involved, with secrets replaced, and rotate any real key that went in.
  2. "Fix the discount bug" gave no detail. A brief should say what is wrong, give an example input with the expected output, and name the files to change.
  3. She accepted a 14-file change. That is too much to review. Ask for the smallest fix and read the diff.
  4. "Make the tests pass" invited edits to the tests. The tests are the specification, so ask for a fix to the code and say that the tests must not change.
  5. She treated green tests as done. Tests that were changed to pass prove little. Check what changed in the test files first.
  6. She merged with no time to watch the result. AI-assisted changes need the same care as any other. Merge when someone is available to notice a problem and fix it.

#Check yourself

Quick check

You regenerated a reply four times and every version is off in the same way. What should you do next?

  1. Not quite. With the same prompt the answers come from the same spread, so more attempts rarely fix a consistent problem.
  2. Right. A consistent flaw means the request is missing something. Naming it changes what the model aims for.
  3. Not quite. An unclear request usually gets the same kind of answer from a different assistant.

You need the average of 400 spreadsheet values. How should you use an AI assistant?

  1. Not quite. The model may be slightly wrong, and checking its answer means doing the sum anyway.
  2. Right. The spreadsheet calculates exactly, and the assistant is good at knowing the formula.
  3. Not quite. This is too broad. Assistants are useful for formulas and code, but they should not act as the calculator.

An AI-drafted summary that you sent to a client contains a wrong date. Who is responsible?

  1. Not quite. Sending the output was your decision.
  2. Right. Using an assistant does not transfer responsibility, which is why you check before sending.
  3. Not quite. Because mistakes are expected, checking for them is part of your job.

#What to practise next

Write the habits from this lesson as a short checklist and keep it next to your assistant for a week. Then read Guardrails before letting an agent act on its own.
