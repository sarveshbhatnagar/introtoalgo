Be Clear and Specific

How to replace vague words in a prompt with instructions you can check, and why giving the reason for a rule covers cases you did not list.

Being specific means writing a prompt so that only one kind of reply satisfies it. Words such as "short", "simple", "professional" and "improve" feel clear to the person who writes them, but each one leaves a decision open, and the model fills it with the most common guess. A specific prompt reduces the number of attempts you need before the reply is usable.

If you ask a colleague to make a slide deck "a bit shorter", they might cut 30 slides to 26 when you wanted 10. A model does the same thing, because the number you had in mind was never written down.

#Replacing vague words with checkable ones

"Keep it short" means you decided how short, but the model does not know your decision and has no access to your reasons. The fix is to replace each vague word with something you could check against the reply. If you cannot tell whether a reply followed the instruction, the model could not tell either.

VagueSpecific
Keep it shortUse fewer than 80 words
Make it simpleWrite it so a 12-year-old could follow it, and explain any technical word in brackets
Sound professionalUse a formal tone, with no jokes and no exclamation marks
Give me some ideasGive 5 ideas, one line each
Improve this paragraphFix grammar and spelling only, and keep my wording and length

"Improve" could mean fixing typos, restructuring the paragraph, cutting it in half or making it sound fancier. "Fix grammar and spelling only" allows exactly one of those.

#Techniques for making a prompt specific

#Say why, not only what

You can never list every case, so each rule should come with its reason. The model can then apply the reason to cases you did not think of. In the first prompt below, the rule is followed but the model has no way of knowing whether a return is allowed.

Because the model knew the goal, it gave a helpful answer and handled the refund request honestly, which the bare rule never covered. Use this whenever a rule starts with "never" or "always": add one clause that says why.

#Name the reader

A phrase such as "for a new hire in their first week" sets the vocabulary, the depth and the tone in one step. Without it, the model writes for an average reader who does not exist. Name the reader whenever the reply is meant for someone other than you, and add what they already know.

#Give numbers

Word counts, item counts and reading levels are the easiest instructions for a model to follow and for you to check. Use a number for length and quantity. Use a range, such as "50 to 70 words", when an exact count is not needed. Models follow length targets only approximately, so if a limit is strict, check the length of the reply yourself instead of trusting it.

#Describe what done looks like

Say what the finished reply must contain, for example "it should end with one action the reader can take today". This is also how you handle format: if you want a table, bullet points or JSON, say so. For output that a program will read, see Structured Output.

#Say what to do when the answer is missing

Suppose the instruction is "Extract the invoice date" and one invoice has no date. The model will often write a plausible date anyway, because the prompt implies that one exists. Add "If the date is not in the text, write unknown and do not guess." This is one of the main ways to prevent made-up details.

#Pitfalls with emphasis, conflicting rules and long prompts

Adding emphasis instead of detail

An instruction such as "VERY IMPORTANT: be concise!!" is still vague, because capital letters show that you care but do not say what concise means. Write "under 60 words" instead. Heavy emphasis can also make a model overcorrect and leave out things you wanted.

Instructions that contradict each other

If a prompt says both "be thorough" and "keep it brief", the model has to choose one, and you cannot predict which. State which instruction wins, for example "Keep it under 100 words, even if that means skipping minor points."

Putting the request at the end of a long background

A task that appears only in the last sentence of a long background paragraph is easy for the model to underweight. State the task first, then the context, then the material. If the material is long, repeat the question after it.

#When more detail does not help

Specific does not mean long. Extra detail helps only when it removes a decision that would otherwise be left to the model. A rule that restates what the model would do anyway, such as "write in correct English", adds length without changing the reply, and a prompt with many rules makes it more likely that two of them conflict.

Be careful about constraints the model cannot follow reliably. Exact word counts and strict character limits are checked poorly by a model, so verify them in code if the limit matters. It is also usually better to describe the result you want than to prescribe every step, unless the steps themselves are the requirement.

#Checking a prompt before you send it

Read the prompt as if you were a capable colleague who is new to the project, and put the answer to every question that person would ask into the prompt. If a prompt that works on one example fails on others, run it on a few different inputs and look for the vague word that each failing reply interpreted differently. Debugging Prompts covers how to find it.
