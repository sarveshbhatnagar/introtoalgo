Context Rot

Why answers get worse as a conversation with an AI assistant grows, how to recognise it, and how to recover with handoff summaries and notes files.

Context rot is the gradual drop in answer quality that happens when a conversation with a language model gets long and fills up with material that is no longer true or no longer relevant. It matters to anyone who works with an assistant for hours at a time, because the symptoms look like the model getting worse, when the actual cause is the text you keep sending it.

In a long session the assistant starts to forget a rule you gave it early on, bring back a fix you already rejected, or edit an old version of a file instead of the latest one. Once you can recognise this, the remedy is usually to start a new session with a short summary, not to keep correcting the old one.

#Why long sessions degrade

On every call, the assistant reads the whole context again: every message, every reply and every tool result so far. Nothing is removed unless you or the application removes it, so a long session carries all of its history into every reply, and quality can drop well before the context limit is reached. That has four consequences.

#Dead ends stay in the context

An approach you abandoned is still there in full detail. It looks as authoritative as the approach you kept, and the model has no reliable way to know which one you meant unless you said clearly that the first one failed. A long failed attempt can also be far more detailed than the one-line message that rejected it.

#Old versions pile up

If three drafts of the same function are in the context, a request such as "change the function so it also handles empty input" may be applied to the wrong draft, or to a blend of two of them.

#Early instructions get less weight

A rule from message 3 sits under everything that came after it. Models tend to use information in a very long context less reliably than information in a short one, as described in The Context Window. When the conversation reaches the limit, the application may also drop the oldest messages, and that is exactly where your rules usually are.

#Earlier mistakes become examples

The model continues the text it is given, and that text includes its own earlier wrong replies. A mistake that appeared three times in the history is more likely to appear a fourth time, because the history now shows it as normal.

Key idea

As a session grows, the share of the context that is still true shrinks, and answer quality follows that share.

#Signs that a session has rotted

One of these on its own can have other causes, such as an unclear request. Two or more together are a strong sign of rot.

  • The assistant forgets or breaks a rule that you set early in the session.
  • It brings back an approach or a bug that you already rejected.
  • It edits an old version of the work instead of the latest one.
  • You are writing more corrections than new requests.
  • Replies become longer, vaguer and more hedged.

When you see several of them, change the context instead of arguing with the assistant. Further corrections only add more text to the context that is causing the problem.

#How to recover and prevent it

#Start a fresh session with a handoff

Ask the assistant to summarise the session, read the summary and correct it, then paste it into a new conversation. A useful handoff contains the goal, the current state of the work, the decisions and rules that apply, the approaches that failed and the reason each one failed, and the next step. This is the most reliable fix, because the new session contains only current material.

#Keep a notes file

For work that lasts several days, keep the handoff in a file such as NOTES.md. Load it at the start of each session and update it whenever you reach a milestone. Some coding tools load a file like this automatically. It works as memory that you control, because you decide what is in it and you can read it.

A notes file that survives sessions
# Date bug fix: notes
 
Goal: dates entered as DD/MM must not be read as MM/DD.
Rules: keep the public API unchanged. All tests must pass.
 
Current state: parser fixed in parseDate() (attempt B). Tests pass.
Tried and failed:
- Rewriting the parser (attempt A): changed the public API.
 
Next: add tests for 29 Feb and for two-digit years.

#Edit your message instead of adding a correction

If a bad reply was caused by an unclear message, most chat tools let you edit that message and regenerate the reply. The bad reply then leaves the context, which is better than adding a correction after it, because the correction leaves the bad reply in place for the model to read.

#Use one session for each task

Open a new conversation when the topic changes. The side question about logging in the example above would have been better asked in its own chat, where it could not add 600 tokens of unrelated text to the debugging session.

#Repeat rules that a late request depends on

If a request near the end of a long session depends on a rule from the beginning, state the rule again in that request. It costs one sentence and does not rely on the model weighing a distant message correctly.

#Keep bulky material out of the main session

Large pasted files, long logs and big search results are the fastest way to fill a context with text that is only needed once. Do the work that needs them in a separate conversation, or in a sub-task that has its own context, and bring back only the conclusion. Some agent tools do this with sub-agents.

#Automatic compaction

Some applications do part of this for you. Near the context limit they replace older turns with a summary and may clear old tool results. This helps, but the summary is written by the model, and it decides what to keep. A rule that mattered to you may be left out, so for important work a handoff that you wrote or checked is more dependable.

#Pitfalls

Correcting a session that has already drifted

Each correction adds more text to the context, and each wrong reply that remains in the history is another example the model may copy. After two or three failed corrections, stop and start a fresh session with a handoff.

A handoff that leaves out the failures

If the summary lists only what works, the fresh session has no way to know that some approaches were already tried, and it will suggest them again. Keep one line for each dead end with the reason it failed.

Using a summary you did not read

A model-written summary can state confidently that something was decided when it was only discussed, or leave out a rule you gave. Read it and fix it before you paste it into a new session.

A handoff that is almost the whole transcript

Pasting a very long summary recreates the problem in the new session. A handoff is useful because it is short and every line in it is still true, so cut anything that does not affect the next step.

Try it: Write the handoff

After 60 messages planning a team offsite, replies are getting muddled. Here is what happened, in no order. Write a handoff for a fresh session in under 120 words.

  • Porto was considered, then dropped because flights were too expensive. Lisbon was chosen.
  • Dates: 12 to 14 May. Budget: 400 per person, 9 people.
  • Three people are vegetarian.
  • Hotel 1 was over budget. Hotel 2 had no meeting room. Hotel 3 has not replied yet.
  • A long side discussion about team T-shirts went nowhere.
  • Next: chase Hotel 3, then draft a day-by-day agenda.
Show a sample answer

This handoff puts the decisions and constraints first. Each rejected option keeps one line with its reason, so the new session will not suggest Porto or the first two hotels again. The T-shirt discussion is left out because it does not affect any later step, and the handoff ends with one clear task to start on.

#Check yourself

Quick check

Late in a long session, the assistant keeps reusing an approach you rejected an hour ago. What is the most likely cause?

  1. Not quite. The model has no intent. It continues the text it reads, and the rejected approach makes up a large part of that text.
  2. Right. Dead ends stay in the context and look as authoritative as current material.
  3. Not quite. A larger window would keep even more stale history, so the problem would not go away.

Which handoff summary is the most useful for a fresh session?

  1. Not quite. That moves the rot into the new session.
  2. Right. It is short, everything in it is current, and it records dead ends so they are not tried again.
  3. Not quite. Without the rules and the failed attempts, the new session may break a constraint or repeat a mistake.

A project spans two weeks of sessions. What keeps each new session on track with the least effort?

  1. Right. It is memory you control, and it stays short, current and readable by both you and the model.
  2. Not quite. That is the situation that produces context rot.
  3. Not quite. This is slow, and you will forget details. Writing it once and keeping it updated is more reliable.

#What to practise next

The next time a session drifts, write the handoff, start a fresh session and compare the first reply with the last one from the old session. Then read What Is an Agent, where a model runs long tool loops on its own and managing the context becomes a central part of the design.
