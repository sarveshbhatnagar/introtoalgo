Coding With AI

How to work with a coding assistant: giving it the right context, keeping each change small, using tests as the definition of done, and reviewing diffs.

Working with an AI coding assistant means giving it a small, well-specified task, checking what it produces, and repeating. The model can write code much faster than you can read it, so the amount you can review, not the amount it can generate, sets the pace at which you can work safely.

If you ask for "CSV export on the reports page" and accept 300 changed lines across six files after a quick skim, you have no way of knowing what else changed. Suppose the change also rewrote a date helper, and invoices showed the wrong month a week later because of it. Nobody had read the whole change, so nobody noticed.

#The loop for one change

Size each step to something you can read and test in a few minutes. For CSV export, that means asking first for a function that turns rows into CSV text, together with its tests, then for the button, then for the download. Every step follows the same five parts.

  1. State the goal and attach the files. The model only knows what is in its context, so include the code it will change and the code it has to fit with.
  2. Ask for one small change. That is one function or one fix, and ideally one file.
  3. Read the diff, which is the list of lines added and removed, before you run anything.
  4. Run the tests. If one fails, paste the exact error message and the failing test back to the model, because "it doesn't work" gives it nothing to act on.
  5. Commit. That gives you a safe point to return to if the next step goes wrong.

#Tests as the definition of done

A test turns "this looks right" into "this does what I specified". Either write the tests before the implementation, or read the ones the model wrote with care, because a wrong test makes wrong code look correct. The final version and its contract
const assert = require("node:assert");
 
function median(nums) {
  if (nums.length === 0) throw new Error("median of empty list");
  const sorted = [...nums].sort((a, b) => a - b); // copy: callers reuse nums
  const mid = Math.floor(sorted.length / 2);
  if (sorted.length % 2 === 1) return sorted[mid];
  return (sorted[mid - 1] + sorted[mid]) / 2;
}
 
assert.strictEqual(median([3, 1, 2]), 2);
assert.strictEqual(median([4, 1, 3, 2]), 2.5);
assert.strictEqual(median([7]), 7);
const times = [120, 80, 95];
median(times);
assert.deepStrictEqual(times, [120, 80, 95]); // input not changed
assert.throws(() => median([]));
def median(nums):
    if not nums:
        raise ValueError("median of empty list")
    ordered = sorted(nums)  # copy: callers reuse nums
    mid = len(ordered) // 2
    if len(ordered) % 2 == 1:
        return ordered[mid]
    return (ordered[mid - 1] + ordered[mid]) / 2
 
assert median([3, 1, 2]) == 2
assert median([4, 1, 3, 2]) == 2.5
assert median([7]) == 7
times = [120, 80, 95]
median(times)
assert times == [120, 80, 95]  # input not changed

except ValueError:

In Python, the equivalent of the in-place bug is calling nums.sort() instead of sorted(nums), and the same test catches it.

#Reading the diff

Read every line of the diff, and read it with specific questions in mind.

  • Did it change anything you did not ask for? Renames, reformatting and small improvements in other files are where unwanted behaviour changes hide.
  • Did it touch the tests? A test that was loosened or deleted makes the run green without fixing anything.
  • Did it add a dependency? Check that the package exists and is the one you intended. Models sometimes suggest plausible package names that do not exist, and Privacy and Security explains why attackers register such names.
  • Does it hide errors? An empty catch block, or a default value that swallows bad input, turns a loud failure into a silent one.
  • Can you explain every line? If you cannot, ask the model to explain it, and then check the explanation against the code instead of trusting it.

#Choosing how to start a task

#Tests first

Ask the model to write the tests and show them to you before it writes any code. You review a short list of expected behaviours, which is much easier than reviewing an implementation, and the tests then judge the code that follows. Use this when the behaviour is clear and can be checked automatically, such as a pure function, a parser or a validation rule. It works poorly for visual layout or anything else that is hard to assert on.

#Plan first

For a change that spans several files, ask for a short plan before any code: which files will change, what each change does, and what could break. Correct the plan, and then ask for the steps one at a time. A wrong plan costs you one sentence to fix, while a wrong 300-line change costs you a full review. The risk is accepting a plan that sounds sensible without checking it against the codebase, so name the files and functions the plan refers to and verify they exist.

#Exploring and then discarding

When you do not know how something should work, such as an unfamiliar library or an approach you have not tried, it is reasonable to let the model write a quick prototype that you plan to throw away. Keep it on a separate branch and do not merge it. Once you understand the approach, start again with a precise request, because prototype code is rarely written to the standard you would accept in the main codebase.

#Pitfalls: large changes, edited tests and long sessions

A change too large to read

If a change is too long to read carefully, it is too long to accept. Discard it and ask for only the first piece. Regenerating code costs little, whereas finding a bug in 300 lines you skimmed costs a lot.

Tests edited to make them pass

When a test fails, a model sometimes changes the expected value in the test instead of fixing the code. Treat any edit to a test as a change to the specification, and accept it only if you can say why the old expectation was wrong.

One long session for everything

In a long session, early instructions get lost and earlier wrong attempts keep influencing the answers. Start a fresh session for each task, and begin it with a short note of what is already done and what the conventions are. Context Rot explains why this happens.

Passing tests that do not cover the change

A green test run only shows that the cases someone wrote pass. If the model wrote both the code and the tests from the same misunderstanding, both can be wrong in the same way. Check that the tests cover the edge cases from your own request, such as empty input and the case where the caller reuses its data.

#Assistants that edit files and run commands

Many coding assistants do more than answer in a chat window. They read your repository, edit several files and run commands such as the test suite. This removes the copy and paste, but it does not change the rule that you review what was produced. The assistant can now change many files in one step, so the diff you read is larger and an unrelated change is easier to miss.

Three habits keep this manageable. Work on a branch, so that the whole attempt can be thrown away with one command. Allow the assistant to run commands that only read or test, and approve anything that deletes files, installs packages or touches the network one command at a time. Keep secrets such as API keys out of the files the assistant can read, because their contents become part of its context. Privacy and Security covers what happens to that context.

It also helps to keep a short file of project conventions that the assistant reads at the start of each session, for example how to run the tests, which folders are generated, and which style rules the team uses. This replaces repeating the same rules in every request. Keep it short and correct it when a rule changes, because an outdated rule is followed just as faithfully as a current one.

  1. Not quite. Its return values were all correct.
  2. Right. The return values were right, but the input changed. Only a test that checks the input afterwards catches this.
  3. Not quite. That test was right, and v2 passed it.

After you report a failing test, the model's next diff changes assert.strictEqual(median([4, 1, 3, 2]), 2.5) to expect 3. What does that tell you?

  1. Not quite. The median of 1, 2, 3 and 4 is 2.5, so the test was right.
  2. Right. The model changed the specification instead of fixing the code, so you should reject the change.
  3. Not quite. A green run against a wrong test proves nothing.

#What to practise next

On your next task, write or read the tests before you look at the implementation, and commit after each step that passes. Then continue with Verifying AI Output, which covers checking facts, numbers and sources as well as code.
