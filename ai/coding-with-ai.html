Coding With AI

Get real work out of an AI coding assistant: small steps, the right files and goal, a careful read of every diff, and tests that define what done means.

You ask an AI assistant to "add CSV export to the reports page". A minute later it hands back 300 changed lines across six files. You skim it, it looks reasonable, and the page works when you click the button. You merge it.

A week later a colleague finds that the change also rewrote a date helper in another file, and invoices now show the wrong month. The assistant did not do anything strange. It made a big change, and nobody read all of it. The model types faster than you can check, so the limit on safe progress is how much you can review, not how much it can write.

#Work in steps you can check

The fix is to size each step to what you can read and test in a few minutes. Instead of "add CSV export", you ask for one piece at a time: first a function that turns rows into CSV text, with tests. Then the button that calls it. Then the file download.

Each step follows the same loop:

  1. Say the goal and give the files. The model can only use what is in its context. Paste or attach the code it will touch and the code it must fit with.
  2. Get one small change. One function, one bug fix, one file if you can.
  3. Read the diff. Every line, before you run anything.
  4. Run the tests. If something fails, paste the real error back.
  5. Commit. Now you have a safe point to return to if the next step goes wrong.
Key idea

An AI assistant makes writing code cheap. It does not make checking code cheap. Work in steps small enough that you actually check each one.

#Tests are the contract

Tests turn "it looks right" into "it does what I said". Write them first, or have the model write them first and then read them carefully, because a wrong test makes wrong code look correct. Each test is one promise the code must keep.

The final version and its contract
const assert = require("node:assert");
 
function median(nums) {
  if (nums.length === 0) throw new Error("median of empty list");
  const sorted = [...nums].sort((a, b) => a - b); // copy: callers reuse nums
  const mid = Math.floor(sorted.length / 2);
  if (sorted.length % 2 === 1) return sorted[mid];
  return (sorted[mid - 1] + sorted[mid]) / 2;
}
 
assert.strictEqual(median([3, 1, 2]), 2);
assert.strictEqual(median([4, 1, 3, 2]), 2.5);
assert.strictEqual(median([7]), 7);
const times = [120, 80, 95];
median(times);
assert.deepStrictEqual(times, [120, 80, 95]); // input not changed
assert.throws(() => median([]));
def median(nums):

        raise ValueError("median of empty list")
    ordered = sorted(nums)  # copy: callers reuse nums
    mid = len(ordered) // 2
    if len(ordered) % 2 == 1:
        return ordered[mid]
    return (ordered[mid - 1] + ordered[mid]) / 2
 
assert median([3, 1, 2]) == 2
assert median([4, 1, 3, 2]) == 2.5
assert median([7]) == 7
times = [120, 80, 95]
median(times)
assert times == [120, 80, 95]  # input not changed
try:
    median([])
    raise AssertionError("expected an error")
except ValueError:
    pass

In Python the in-place bug looks different (nums.sort() versus sorted(nums)), but it is the same mistake, and the same test catches it.

#Read every diff

Reading a diff is faster than writing the code, but only if you read with questions in mind. These catch most problems:

  • Did it change anything I did not ask for? Renamed variables, reformatted files and "small improvements" elsewhere are where surprises hide.
  • Did it touch the tests? A loosened assertion or a deleted test makes the run go green without fixing anything.
  • Did it add a dependency? Check that the package really exists and is the one you think. Models sometimes invent plausible package names.
  • Does it hide errors? An empty catch block or a default value that swallows bad input turns a loud bug into a quiet one.
  • Could I explain every line to a colleague? If not, ask the model to explain it, then check the explanation against the code.
Paste the real error

"It doesn't work, fix it" gives the model nothing to go on. Paste the exact error message, the failing test and what you expected. That is the same information you would want if a teammate asked you for help.

#Common mistakes

Accepting a change too big to read

If a diff is too long to read carefully, it is too long to accept. Throw it away and ask for the first piece only. Regenerating is cheap; finding a bug in 300 lines you skimmed is not.

Letting it edit the tests to pass

When tests fail, a model will sometimes change the expected value instead of the code. Treat any edit to a test as a change to the contract. Approve it only if the old test was actually wrong.

Running one long session for everything

After hours of back and forth, early instructions get lost and old wrong attempts sit in the context. Start a fresh session per task, with a short note of what is done. Context Rot explains why.

#What to practise next

Next time you use an assistant on real code, write the tests (or read its tests) before you look at the implementation. Then continue with Verifying AI Output, which covers checks for facts, numbers and sources as well as code.
