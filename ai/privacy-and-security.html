Privacy and Security

Know where pasted text goes, keep secrets and other people's data out of prompts, redact before you paste, and check AI-written code for security holes.

A login bug has you stuck, so you paste the config file and the last fifty lines of the server log into an AI assistant. It spots the problem in seconds. What you did not notice is that the log also held a customer's email address and the config held the production database password.

Maybe nothing bad ever comes of it. But that password now sits in a chat history on a server you do not run, kept for as long as that service keeps things, and visible to whoever can open your account. You gave away control of it to fix one bug.

#Pasted text leaves your hands

When you send a prompt to a hosted assistant, the text travels to the provider's servers to be processed. What happens next depends on the provider, your plan and your settings. It can be kept in your chat history, kept in logs for a while for abuse monitoring or debugging, and in some setups used to improve future models.

You do not need to fear this. You need to know the answers for the tools you use, once:

  • Is this tool approved for this kind of data? At work, your employer may allow some tools for code and forbid them for customer data. Ask before you find out the hard way.
  • Is my data used for training, and can I turn it off? This often differs between personal and business plans.
  • How long are conversations kept, and does deleting a chat delete it everywhere?
  • Who else can see my history? Shared workspaces, admins and shared devices all count.
Key idea

Treat every prompt as something you are sending to someone else. If you would not email it to an outside contractor, do not paste it in as it is.

#What to keep out

  • Secrets: passwords, API keys, access tokens, private keys, connection strings.
  • Other people's personal data: names with contact details, health, financial or student records. They did not agree to share it with a third party, and laws in many places say you need a reason to.
  • Confidential work: unreleased plans, contract terms, code your employer has not cleared for the tool.

The model rarely needs the real value. To debug a login, it needs to know that a password is set, not what it is. Replace sensitive values with placeholders like [EMAIL] or [SECRET], and the help you get is the same.

#Redact before you paste

For logs and config files, a small script does this faster and more reliably than your eyes. Each rule replaces one known shape of sensitive text, in order.

A simple redactor
// Rules run in order. Each replaces one known shape of sensitive text.
const RULES = [
  [/[\w.+-]+@[\w-]+\.[\w.]+/g, "[EMAIL]"],
  [/\b(\w*(?:password|secret|token|key))\s*[=:]\s*\S+/gi, "$1=[SECRET]"],
  [/\b[A-Za-z0-9_-]{32,}\b/g, "[TOKEN]"],
];
 
function redact(text) {
  for (const [pattern, replacement] of RULES) {
    text = text.replace(pattern, replacement);
  }
  return text;
}
import re
 
# Rules run in order. Each replaces one known shape of sensitive text.
RULES = [
    (r"[\w.+-]+@[\w-]+\.[\w.]+", "[EMAIL]"),
    (r"(?i)\b(\w*(?:password|secret|token|key))\s*[=:]\s*\S+", r"\1=[SECRET]"),
    (r"\b[A-Za-z0-9_-]{32,}\b", "[TOKEN]"),
]
 
def redact(text):
    for pattern, replacement in RULES:
        text = re.sub(pattern, replacement, text)
    return text

Paste less

The safest data is data you never sent. The error message and the ten lines around it usually beat the whole file, and they also give the model less to get distracted by.

#Security risks that come back out

Privacy is about what goes in. Security is also about what comes out, because AI output often ends up running on your machine.

  • Insecure fixes. Asked to "make the error go away", a model may suggest turning off certificate checks, opening permissions wide, or building a database query by gluing strings together. Each one works, and each one opens a hole. When a fix disables a safety check, find out why the check failed instead.
  • Packages that do not exist. Models sometimes suggest plausible package names that were never published. An attacker can register such a name and publish a harmful package under it. Before you install anything new, check that it is the real, maintained project.
  • Commands you have not read. Read a command before you run it, especially anything that deletes, changes permissions, or downloads and runs a script in one line.
  • Assistants with access. An assistant that can read your files or act on your accounts can be steered by text hidden in what it reads. Prompt Injection covers how, and why you should give such tools only the access the task needs.

#Common mistakes

Deleting the chat instead of rotating the secret

If you pasted a real password or key, deleting the conversation does not undo it: it may already be in logs or backups. Change the password or revoke the key. That is the only fix that works.

\

Test keys often have more access than people think, and test databases often hold copies of real data. Apply the same rule to every secret: placeholders only.

Forgetting screenshots and attachments

A screenshot of a dashboard can show customer names in the sidebar. A shared document can carry comments and earlier versions. Look at the whole thing before you upload it.

Quick check

You realise you pasted a live API key into a chat an hour ago. What should you do first?

  1. Not quite. Good to do, but the key may already be in logs. The key itself is still valid.
  2. Right. Once a secret has left your control, the only reliable fix is to make it useless.
  3. Not quite. The model cannot remove your text from the provider's storage.

In the tracer, why did line 5 survive redaction?

  1. Not quite. Rule 2 works as written. Line 5 has no name=value shape for it to match.
  2. Right. Pattern rules only catch shapes you predicted. Always read what you paste, too.
  3. Not quite. No order would help: none of the three rules matches that line.

An assistant fixes your HTTPS error by adding an option that skips certificate checks. What is the right response?

  1. Not quite. The error is gone because the safety check is gone. Anyone in the middle of the connection could now read or change your traffic.
  2. Right. Right. A fix that disables a safety check hides the problem instead of solving it.
  3. Not quite. Code written on laptops tends to end up in production. Fix the cause.
