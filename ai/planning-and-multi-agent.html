Planning and Multi-Agent Systems

Help an agent with a big task by making it plan first, and split work across agents with fresh context, plus the costs and when one agent is better.

An agent compares how three open-source web frameworks handle security updates: how fast they ship fixes, how they announce them, and how long old versions get patches. It reads A's docs, then B's, then C's. With dozens of pages in its history, the report says Framework A supports old versions for two years. That was Framework C.

No single step was wrong; the history got too long to keep three similar sets of facts apart (see Context Rot). Two fixes: make the agent plan, and split the work across several agents that each see less.

#Plan first, then act

An agent in the agent loop picks one step at a time, so on a long task it drifts: it follows a lead, forgets part of the request, and runs out of steps with one framework unread.

The cheap fix: before any tool call, ask for a short plan, kept in the history as a checklist the agent ticks off and rewrites.

The checklist guards against forgetting part of the task, lets a person correct it early, and shows progress. It is a guess, not a contract: if Framework B has no security page, the agent should rewrite the remaining steps.

#Several agents, each with a fresh context

Planning does not stop all three frameworks' pages piling up in one context. Splitting does. An orchestrator agent breaks the task into parts and hands each to a worker agent. Each worker starts with an empty history and only its part, does the reading, and sends back a short summary. The orchestrator never sees the raw pages.

The numbers are illustrative: the single agent holds the task (100 tokens) plus 12,000 tokens per framework. Totals count what agents hold, not what they re-read each call (see The Agent Loop); shorter histories re-read less, but briefs, summaries and repeated searches often cost more. Each worker is just the agent loop with its own goal:

// runWorker(brief) runs one agent loop and returns its final answer.
function orchestrate(goal, parts, runWorker) {
  const summaries = parts.map((part) =>
    runWorker(`Overall goal: ${goal}\nYour part: ${part}\n` +
      "Reply with at most 5 bullet points, each with a source link."));
  return summaries; // in a real app, run the workers in parallel
}
 
const fakeWorker = (brief) => `summary of: ${brief.split("\n")[1]}`;
console.log(orchestrate("Compare security updates",
  ["Framework A", "Framework B", "Framework C"], fakeWorker));
// [ 'summary of: Your part: Framework A', ... ]
# run_worker(brief) runs one agent loop and returns its final answer.
def orchestrate(goal, parts, run_worker):
    summaries = [
        run_worker(f"Overall goal: {goal}\nYour part: {part}\n"
                   "Reply with at most 5 bullet points, each with a source link.")
        for part in parts
    ]
    return summaries  # in a real app, run the workers in parallel
 
fake_worker = lambda brief: f"summary of: {brief.splitlines()[1]}"
print(orchestrate("Compare security updates",
                  ["Framework A", "Framework B", "Framework C"], fake_worker))
# ['summary of: Your part: Framework A', ...]

The brief is all the worker knows, so it must carry the goal, the part's boundaries and the reply's shape. "Research Framework B" gets back a vague essay.

#When one agent is better

Multi-agent systems are popular to draw and often no better in practice: they cost more, handoffs lose unwritten context, and errors have more places to hide.

Good splits are separate topics, separate files, or separate approaches where you keep the best. Research assistants often use workers to read sources in parallel; coding agents more often stay single, because edits to one codebase depend on each other.

Key idea

Split a task across agents only when the parts can be done without talking to each other. Otherwise, one agent with a plan is simpler, cheaper and easier to debug.

#Common mistakes

Splitting work that is not independent

Two workers writing halves of one program each make reasonable choices about names, data formats and error handling, and the choices will not match. Use one agent, or make the shared decisions first and put them in both briefs.

Following a stale plan

Tell the agent that rewriting the plan is expected, or it may stick to the original after a result proves it wrong.

Trusting summaries without sources

The orchestrator cannot check what a worker read. Ask for a source per claim so someone can follow it back.
