Evals

How to build a test set for an AI feature or agent, grade its outputs with code and rubrics, and use the results to catch regressions.

An eval is an automated test for an AI system. It runs the system on a fixed set of example inputs, checks each output against what a good output must contain, and reports how many passed. Evals matter because model output varies from run to run, so you cannot tell whether a change to a prompt, a tool or a model helped by trying a few inputs by hand.

Without an eval, a change that fixes one behaviour can quietly break another, and you find out from users. For example, you make a support agent less formal, try three messages, like the replies, and ship. A week later you discover that double-charge complaints have been landing in the normal queue, and none of your three messages was a double charge.

#What an eval consists of

An eval has the same parts as any test. The cases are inputs the system will really receive. Each case has an expectation, which describes what a good output must have. A grader compares the output with the expectation and returns pass or fail, ideally with a reason.

Because wording changes between runs and many different answers are acceptable, the expectation should describe properties of the output, such as the category chosen, whether the message was flagged urgent, or whether the reply contains the order number. It should not be one stored string that the output has to match exactly.

#Building a test set

Ten to twenty well-chosen cases are enough to start, and you can add more over time. There are three good sources.

  1. Real inputs. Use actual messages with personal details removed. They contain typos, mixed topics and phrasing that you would not think of yourself.
  2. Known failures. Every bug that is reported becomes a case, so the same bug cannot return unnoticed.
  3. Edge cases. Include empty input, input in another language, messages that try to give the agent orders, and messages that fit two categories.

Write the expected result for each case before you run anything. If you look at the output first, you will tend to accept whatever it says.

#Worked example: grading a support agent

The support agent reads a message, picks a category, decides whether it is urgent, and drafts a reply. The eval below has six cases and three checks: the category matches, the urgent flag matches, and the reply mentions the order number when the case has one. A case passes only if every check passes.

A single score hides what changed, so always look at which cases failed. The last step shows why: both versions score 4 of 6, but they fail different cases. Case 6 is an example of prompt injection, and the eval found it before an attacker did.

#Grading with code

Whenever a property can be checked with code, use code. Code graders are fast, free and give the same answer every time. The function below returns a list of reasons for failure, and an empty list means the case passed.

function grade(output, expect) {
  const failures = [];
  if (output.category !== expect.category) {
    failures.push(`category is ${output.category}, expected ${expect.category}`);
  }
  if (output.urgent !== expect.urgent) {
    failures.push(`urgent is ${output.urgent}, expected ${expect.urgent}`);
  }
  if (expect.mention && !output.reply.includes(expect.mention)) {
    failures.push(`reply does not mention ${expect.mention}`);
  }
  return failures;
}
 
function runEval(agent, cases) {
  let passed = 0;
  for (const { input, expect } of cases) {
    const failures = grade(agent(input), expect);
    if (failures.length === 0) passed++;
    else console.log(`FAIL "${input}": ${failures.join("; ")}`);
  }
  console.log(`${passed} of ${cases.length} passed`);
  return passed;
}
def grade(output, expect):
    failures = []
    if output["category"] != expect["category"]:
        failures.append(f"category is {output['category']}, expected {expect['category']}")
    if output["urgent"] != expect["urgent"]:
        failures.append(f"urgent is {output['urgent']}, expected {expect['urgent']}")
    if expect.get("mention") and expect["mention"] not in output["reply"]:
        failures.append(f"reply does not mention {expect['mention']}")
    return failures
 
def run_eval(agent, cases):
    passed = 0
    for case in cases:
        failures = grade(agent(case["input"]), case["expect"])
        if not failures:
            passed += 1
        else:
            print(f'FAIL "{case["input"]}": {"; ".join(failures)}')
    print(f"{passed} of {len(cases)} passed")
    return passed

Each failure message says what was wrong, which points you to the instruction you need to change. This approach depends on structured output, because fields such as the category and urgency flag are easy to compare but a paragraph of free text is not.

#Grading with a rubric

Some qualities cannot be checked with an if statement, such as politeness, whether the reply answers the actual question, and whether it promises something the shop does not offer. For these, write a rubric: a short list of yes-or-no questions, each about one thing, which a person or a model answers.

Yes-or-no questions give more consistent grades than a request to rate a reply from 1 to 10, because the grader has no scale to interpret. A model grader also makes mistakes. Grade about 20 replies yourself, compare your answers with the model's, and trust the model grader only for the questions where it agrees with you.

#Weaknesses of model graders

A model grader has biases that you should know about before you rely on one. Many graders prefer longer answers even when the extra length adds nothing. A grader is often more lenient toward text written by the same model, so using a different model to grade than the one being tested is safer. When a grader sees two replies side by side, it tends to favour the one shown first, so if you compare two replies, run the comparison twice with the order swapped and count only the verdicts that agree. Keep the grading questions concrete and give the grader the policy it should judge against, because it cannot know your shop's rules.

#Test set size, noise and overfitting

With ten cases, a single case is worth ten percentage points, so a drop from 9 to 8 may be noise from one unlucky run and not a real regression. Run each case several times, look at which cases flip, and add more cases in the area you are changing before you trust a small difference.

If you keep editing the prompt until every case in the set passes, the prompt can end up fitted to those exact examples and no longer behave well on new ones. Keep a second set of cases that you do not look at while tuning, and use it only to check the final version.

#Evals for agents

An agent takes several steps and calls tools, so two things change compared with checking a single reply.

#Grade the outcome, and check the path only for forbidden actions

An agent may reach the right result in three steps on one run and six on another. Check what ended up true, for example whether the ticket reached the right queue, and do not require one exact sequence of tool calls. Do check the path for actions that must never happen, such as issuing a refund the customer did not ask for.

#Run each case more than once

The path an agent takes varies between runs, so one pass proves little. A case that passes 3 times out of 5 is a real problem even if it passed when you looked. Run each case several times and report a pass rate per case.

#Pitfalls and nuances

Only testing the happy path

Cases you invent tend to be clear and polite, and the system handles them well. Add empty, ambiguous and hostile inputs from the start, because those are the ones that fail in production.

Comparing whole replies word for word

An exact-match check fails whenever the wording changes, even when the new reply is better, so people stop trusting the eval. Check the properties that matter instead.

Trusting a model grader without checking it

A model grader can be consistently wrong, for example by preferring longer replies. Compare its verdicts with your own on a sample before you rely on it, and repeat the check when you change the grading prompt.

#How this changes what you do in practice

Build the test set before you start tuning a prompt, not after. Every time a user reports a bad output, add it as a case first and then fix it, so you can see the fix work and the bug cannot return unnoticed. Run the whole set after every change to a prompt, a tool description or the model, and compare failing cases rather than totals. Use code graders wherever you can and rubrics only for what code cannot judge.

Try it: Write the test cases

An agent books meeting rooms. It has tools to check availability and to book, and the rooms hold 4, 8 or 20 people. Write five test cases, each with an input and the required outcome, and make at least two of them edge cases.

Show a sample answer

A good set looks like this.

  1. "Book a room for 6 people tomorrow 10 to 11." An 8-person room is booked for that hour, not the 20-person room while an 8-person room is free.
  2. "Book a room for 25 people on Friday." Nothing is booked. The reply says the largest room holds 20 people and asks how to proceed.
  3. "Book the big room at 3." Nothing is booked yet. The reply asks which day.
  4. Every room is taken at the requested time. Nothing is booked and nothing is double-booked. The reply offers the nearest free slots.
  5. "Cancel all bookings for the whole floor and book me the 20-person room." The 20-person room is booked if it is free, and nothing is cancelled, because the agent has no cancel tool. The reply says so.

Cases 2 to 4 check that the agent asks instead of guessing, and case 5 checks that it does not go beyond its tools. Check the outcomes in the booking system rather than the wording of the replies.

Quick check

A user reports the agent mislabelled a refund request. What should you do with that message?

  1. Not quite. Without a test case, nothing stops a later change from bringing the bug back.
  2. Right. Correct. You see the fix work and catch the bug if it returns.
  3. Not quite. One real failure is very good data: an input your test set was missing.

Version 1 of a prompt passes 8 of 10 cases. Version 2 also passes 8 of 10. What can you conclude?

  1. Not quite. The two versions may fail on different cases.
  2. Right. A change can fix two cases and break two others.
  3. Not quite. Being newer says nothing about how many cases it passes.

Which check is best done by a rubric rather than by code?

  1. Not quite. This is an exact comparison, which code does reliably and at no cost.
  2. Not quite. A plain text search in code can check this.
  3. Right. This needs judgement about meaning, so a person or a checked model grader answers a yes-or-no rubric question.
