A team keeps readings from 50,000 sensors in a relational table. Each reports every 10 seconds: 50,000 ÷ 10 = 5,000 inserts a second, 5,000 × 86,400 = 432 million rows a day, kept 30 days. Each night a job deletes the oldest day row by row, updating every index, and dashboards time out while it runs.

The database was built for a different job. A time-series store writes in chunks by time and expires a day by dropping one chunk. The access pattern picks the database.

The idea

Ask three questions, in order, and the category usually falls out:

  1. How is the data read and written? By key, by time range, by following relationships, or with joins and ad hoc filters? Write down the top three queries, as in data modeling.
  2. What must never go wrong? Two writes that must succeed or fail together (take stock, create the order) need transactions. If a second-old read is fine, you have more choices.
  3. How big and how fast? Rows, bytes, writes a second.

The default is relational: transactions, constraints, joins, and queries you did not plan for. Leave it only when a question above gives a reason, and say it.

The six categories

Each is good at one access pattern and pays elsewhere. Products blur the lines; treat these as shapes.

One system, several stores

Real systems often use several stores. Each is another thing to run, back up and keep in sync, so add one only with a reason.

Scale changes less than people think

"It needs to scale" is not a reason; do the arithmetic. As a rough rule, one relational server handles thousands to tens of thousands of simple writes a second and several terabytes, and read replicas multiply reads.

Leave it when the numbers say so: writes beyond one primary, or data many times one machine, read mostly by key. A self-partitioning store (key-value or wide-column) then saves you sharding by hand, at the cost of cross-partition transactions and joins.

In the interview

Choose right after listing access patterns. Name the category, give a one-sentence reason citing a query, guarantee or number, and say what would change your mind.

Where do you store the messages? The main read is "latest 50 messages in this chat", at an estimated 20,000 writes a second. So a wide-column store partitioned by chat id, sorted by time: one partition read per page, writes spread across nodes. Users, billing and membership need constraints and transactions, so they go in a relational database. Why not put everything in the relational database? At this write rate I'd be sharding it by hand within a year. At a tenth of the load I would, to run one store. It names the query, the number, the cost, and when the simpler choice wins.

Follow-ups to expect:

  • "Can a relational database scale?" Yes: replicas, partitioning, caches, at the cost of operations work and harder cross-shard queries.
  • "Couldn't the sensor table stay relational?" Often: partition by day and expiry becomes dropping one partition, not 432 million deletes. A time-series store does that for you, plus compression and roll-ups.

Common mistakes

"NoSQL scales" is a slogan, not a reason, and "NoSQL" covers four different categories. If you cannot name the query the store makes fast and the guarantee you need, you have not chosen yet.

A document store does not check your data's shape, so the schema moves into your code and every reader must handle every old shape.
