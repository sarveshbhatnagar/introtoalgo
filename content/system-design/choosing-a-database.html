A team stores readings from 50,000 sensors in a relational table. Each sensor reports every 10 seconds, so that is 50,000 ÷ 10 = 5,000 inserts a second, 5,000 × 86,400 = 432 million rows a day. They keep 30 days. Every night a job deletes the day that just turned 31 days old, 432 million rows one by one, updating every index as it goes, and the dashboards time out while it runs.

The database is not broken; it was built for a different job. A time-series store writes data in chunks by time and expires a whole day by dropping one chunk. The access pattern picks the database.

The idea

Ask three questions, in this order, and the category usually falls out:

  1. How is the data read and written? By one key, by time range, by following relationships, or with joins and ad hoc filters? Write the top three queries down, as in data modeling.
  2. What must never go wrong? If two writes must succeed or fail together (take stock, create the order), you need transactions. If a stale read for a second is fine, you have more choices.
  3. How big and how fast? Rows, bytes and writes a second.

The default is a relational database: transactions, constraints, joins, and queries you did not plan for. Move away from it only when a question above gives you a reason, and say it.

The six categories

Each category is good at one access pattern and pays for it elsewhere. Products blur the lines; treat these as shapes.

One system, several stores

Real systems often use several stores. Each extra store is one more thing to run, back up and keep in sync, so add one only with a reason.

Scale changes less than people think

"It needs to scale" is not a reason by itself. Do the arithmetic. One relational server on good hardware handles thousands to tens of thousands of simple writes a second and several terabytes (a rough rule of thumb), and read replicas multiply read capacity.

Leave it when the numbers do: writes beyond one primary, or data many times one machine, read mostly by one key. Then a store that partitions itself (key-value or wide-column) saves you sharding by hand, and costs you cross-partition transactions and joins.

In the interview

Choose the database right after you list the access patterns. Name the category, give the reason in one sentence that cites a query, a guarantee or a number, then say what would change your mind.

Where do you store the messages? I'd use NoSQL, because it scales better than SQL. No access pattern, no number, no cost. "NoSQL" is four different categories. Where do you store the messages? The main read is "the latest 50 messages in this chat", and we estimated 20,000 writes a second. So I'd use a wide-column store partitioned by chat id and sorted by time: one partition read per page, and writes spread across nodes. Users, billing and group membership go in a relational database, because those need constraints and transactions. Why not put everything in the relational database? At this write rate I'd be sharding it by hand within a year. If the numbers were 10 times smaller, I would, and keep one store to operate. It names the query, the number, the cost, and the condition under which the simpler choice wins.

Follow-ups you should expect:

  • "Can a relational database scale?" Yes: replicas for reads, partitioning for writes, and caches in front. The cost is operational work and harder cross-shard queries.
  • "Document or relational for a product catalogue?" Document if products are read whole and fields vary by type; relational if they join orders and stock in transactions.
  • "When would you add a graph database?" When the core query walks three or more hops over a large graph. For "my friends", a join table is enough.
  • "Couldn't the sensor table stay relational?" Often, yes: partition it by day, and expiring a day becomes dropping one partition instead of 432 million deletes. A time-series store does that for you and adds compression and roll-ups.

Common mistakes

"NoSQL scales" is a slogan, not a reason. If you cannot name the query the store makes fast and the guarantee you need, you have not chosen yet.

A document store does not check the shape of your data, so the schema moves into your code, and every reader must handle every old shape ever written.
