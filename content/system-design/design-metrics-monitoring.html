Every server reports numbers every few seconds: CPU, memory, requests, errors, latency. Engineers watch dashboards, and rules page someone when error rates climb. When production is on fire, everyone opens this system at once, so it must work best when everything else is failing.

Think of an in-house Datadog. It hides a write-heavy store that must compress well, a cardinality problem that can take it down, and a rule most candidates miss: the monitor must not fail with what it monitors. Observability covers what to measure; this lesson builds the machine, following A Framework for Any Design.

Clarify the problem

Design a metrics monitoring system. Metrics only, meaning numeric time series, or logs and traces too? Metrics only. How many servers, how many series per server, and how often do they report? 100,000 servers, about 500 series each, every 10 seconds. How long do we keep data, and at what detail? Full detail for a week, coarser data for two years. So writes are steady and dominant, and reads spike during incidents. Priorities: alerts fire even when parts of production are down, a 1-hour dashboard loads in about a second, and losing a few seconds of samples is fine. Losing alerting is not. Ranking alerting above data completeness drives the failure design later.
  • Functional: collect labelled metrics (service, host, status) from every server; query by time range and labels, with sums, rates and percentiles; evaluate alert rules and notify on-call.
  • Non-functional: ingest 5 million samples a second; queryable within 30 seconds; a 1-hour panel loads in about 1 second; alerts fire within a minute of their hold duration and survive partial outages; raw data for 7 days, rollups for 2 years.
  • Out of scope: logs, traces, anomaly detection, agent install tooling.

Estimate the scale

  • Series: 100,000 × 500 = 50 million active time series.
  • Samples: 50 million ÷ 10 s = 5 million samples a second, nearly constant. At about 20 bytes each on the wire: 100 MB/s in.
  • Raw storage: a sample (timestamp and value) is 16 bytes uncompressed. 5 × 106 × 86,400 = 432 billion samples a day, 6.9 TB a day uncompressed. Time-series compression gets a sample to one or two bytes; assume 2: 864 GB a day.
  • Queries: in an incident, 2,000 dashboards × 20 panels refreshing every 30 seconds ≈ 1,300 queries a second. 100,000 alert rules every 30 seconds add a steady 3,300 a second.

Write the write endpoint the agents call, the query endpoint dashboards call, and how an alert rule is defined.

Agents send compressed batches, many series per request. Dashboards send a query, a time range and a step. A rule is a query, a threshold, a hold duration and who to notify.

Define the API

POST /v1/write                     from agents, every 10 s, compressed
  body: [ { "labels": {"__name__": "http_requests_total", "service": "checkout",

  204 No Content

                   &start=...&end=...&step=60s
  200 { "series": [ { "labels": {"status": "500"}, "points": [[t, v], ...] } ] }
  422 Unprocessable   query would touch more than 100,000 series

Alert rule
  expr:  error ratio for checkout > 5%
  for:   5m                 the condition must hold this long before firing
  notify: team-checkout

The decision worth arguing is step. A panel 1,000 pixels wide shows about 1,000 points, yet a week at a 10-second step returns 60,480 per series. With step in the API, the server picks the coarsest rollup tier that fills the panel and refuses queries that touch too many series.

What identifies a series, how are samples stored, and how does a query find the series matching service="checkout"?

A series is its metric name plus labels, hashed to an id. Samples sit per series in compressed time-range chunks. An inverted index maps each label pair to its series ids; a query intersects those lists.

Model the data

series      id = hash(metric name + sorted labels)
            labels  {__name__="http_requests_total", service="checkout", host="web-17", status="500"}

chunk       series_id, start_time, end_time, compressed bytes   (120 samples, 20 minutes)
            only the open chunk stays in memory; full ones go to local disk

index       "service=checkout" -> [series ids, sorted]
            "status=500"       -> [series ids, sorted]
            query {service="checkout", status="500"}  =  intersect the two lists

blocks      every 2 hours: chunks + index for that window, written as immutable
            files to object storage; compaction merges blocks and builds rollups

Writes are append-only, always at "now", for every series at once. Reads ask for a time range over a set of series. Nothing is updated. A time-series database (such as Prometheus, M3 or VictoriaMetrics) keeps each open chunk in memory and the last two hours on local disk, then writes immutable, compressed blocks to cheap object storage.

Sketch the path from a server's counters to a dashboard and to a page on someone's phone. Which parts must survive an outage?

Host agents, ingest, a log, a time-series store, a query service, and an alert evaluator feeding a notifier that pages through an outside provider. Alerting must run apart from what it watches.

High-level design

Deep dives

Push or pull

When ingest is slow or returns 429, the agent buffers a few minutes on disk and backs off with jitter, so 100,000 agents do not retry in lockstep. Each agent also sends an up series; alerting on it going absent tells a dead host from a quiet one.

Storing time series

Compression works because neighbouring samples look alike. Timestamps arrive every 10 seconds: 1000, 1010, 1020, 1031. Store the first, then the difference of differences: 10 − 10 = 0, 11 − 10 = 1. Mostly zeros, one bit each. Values change slowly, so store each XOR-ed with the previous one: an unchanged value is a single 0 bit. That is how 16 bytes becomes one or two, and why samples are compressed per series in time order.

Downsampling. Old data is viewed coarsely, so compaction rewrites it into the tiers above. Each rollup point keeps min, max, sum and count, not just an average, so it still answers "the highest CPU in that hour" and longer averages stay correct (total sum ÷ total count). Percentiles cannot be rebuilt from those four values, so record latency as a histogram (counts per bucket), whose buckets roll up by adding.

The cardinality problem. Each unique combination of label values is a series, so labels multiply. 200 services × 50 endpoints × 10 status codes is 100,000 series, fine. Add user_id and 1 million users × 5 endpoint and status combinations is 5 million series, 5 GB of ingester memory, from one line of code. Memory, index size and query cost all scale with series; this is how such systems usually fall over.

  • Limit per tenant: cap active series per team and refuse new ones beyond it; existing series keep working.
  • Make it visible: show each team its series count and its biggest labels.
  • Send unbounded values elsewhere: user ids, request ids and URLs belong in logs and traces, not labels.

Sizing by samples per second and ignoring series count. More samples over fixed series is plannable; a stream of new series is not, since each holds index entries and memory until it goes stale.

The query path

A query such as "checkout error rate by status, last hour" runs in four steps:

  1. Find series: intersect the index lists for __name__=http_requests_total and service=checkout. If more than 100,000 match, refuse with 422 before reading data.
  2. Pick a tier: the coarsest tier still finer than the step. A 7-day panel 1,000 points wide has a step of about 10 minutes, so over 1,000 series it reads 10 million 1-minute points, not 60 million raw ones.
  3. Fan out: series are sharded across ingesters by id, so ask every shard holding matches for recent data, and object storage for older blocks, in parallel.
  4. Aggregate early: each shard returns partial sums by status, a few series instead of thousands; the query service adds them.

In an incident, hundreds of engineers open the same dashboards. Align start and end to the step and cache by (query, step, time range): older points never change, so a refresh computes only the newest few.

Alerts that survive the outage

The hard problem is shared fate. If monitoring shares production's cluster, network and service discovery, the outage that needs an alert takes out alerting too, and silence reads as "all fine".

  • Separate failure domain: run monitoring on its own machines and network path, depending on nothing it watches (not their database, auth or deploy system).
  • No data is a signal: a rule whose series vanish fires instead of quietly resolving.
  • Watch the watcher: a small second stack in another region checks the main one is scraping, storing and evaluating.
  • Dead man's switch: an always-firing alert sends a heartbeat to the outside paging provider every minute. If heartbeats stop, the provider pages.

Bottlenecks and failures

At 10x (500 million series), ingest and the log scale by adding nodes, and ingesters need 500 GB of memory before replication. Index and query fan-out break next: put large tenants on separate shard groups so one team's huge query cannot slow everyone. Storage grows to about 300 TB, cheap in object storage.

What a strong answer sounds like

LevelWhat the answer does
JuniorSamples go into a database table; a cron job checks thresholds and sends email.
MidA time-series database, push or pull with a reason, estimates of samples and storage, downsampling.
SeniorSizes by series too, plans for cardinality explosions, explains compression and rollups, builds the query path around step and fan-out, and keeps alerting alive when production and the monitor fail.
Monitoring runs in production's data center, and the data center loses its network. What happens? As described, nothing pages. So I'd run alerting outside production's failure domain, treat "no data" as an alert, and send a heartbeat to an outside paging provider every minute; if the stack goes dark, the provider pages on-call. The cost is a second small stack and an outside dependency. Why not just run two copies of everything? Two copies in one failure domain fail together. What pages must depend on nothing the outage can take down.

Follow-up questions

How do you compute p99 latency across 1,000 servers?

Never average each server's p99. Add every server's latency histogram buckets and read the 99th percentile from the sum.

How do you support many teams fairly?

Per-tenant limits on sample rate, active series and query cost, plus separate shard groups for the largest tenants.

What about very short-lived jobs?

A 3-second job can finish between collections, so it pushes its final values to the local agent before exiting.
