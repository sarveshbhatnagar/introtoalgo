A profile service keeps its database leader in an East data center and a read replica in the West. A West user changes her bio, refreshes 200 ms later, and sees the old bio: the replica is one second behind. The save button looks broken.

Then the link between data centers drops for 90 seconds. The West can refuse writes until it returns, or accept them and risk two versions of a row. That choice is CAP.

The idea

Once data lives on several machines, copies can disagree. A consistency model promises what a read can return after a write. Stronger promises are easier to build on but cost latency or availability; weaker ones are fast but serve stale data.

CAP says: when the network splits the replicas into groups that cannot talk (a partition), each group must either refuse some requests or answer without the latest writes. C means linearizable: every read sees the latest completed write, as if there were one copy. A means every request to a working node gets an answer. With a healthy network you get both.

PACELC adds the rest: if Partition, choose Availability or Consistency; Else, Latency or Consistency. A strongly consistent write waits for other replicas: around 100 ms across continents, on every write. That everyday cost usually matters more than the rare partition.

Lag, then a partition

West reads chose availability; writes chose consistency. CAP is decided per operation, not per database.

Four promises, as users see them

  • Strong (linearizable). Once a write returns, every read sees it. With a conditional write ("book 14C only if free"), two people cannot both get it.
  • Eventual. Copies converge once writes stop. Until then a like count may read 42, then 41.
  • Causal. Dependent writes are seen in order: a reply never appears before its comment.
  • Read-your-writes. Users always see their own changes, even if others see them later.

What a quorum does and does not give you

Leaderless stores write to W of N replicas and read from R. If R + W > N, every read set overlaps every write set, so a read reaches a replica with the latest acknowledged write. With N = 3, W = 2, R = 2: 2 + 2 = 4 > 3.

That is not linearizability. Concurrent writes can land in different orders on different replicas, a half-failed write may show on one, and some stores fall back to "any W nodes" during failures. Say "quorum reads see the latest acknowledged write in the normal case", not "quorums make it strongly consistent".

Numbers worth remembering

  • Replica lag in one region: usually milliseconds, seconds or minutes under load. Design for "unbounded but usually small".
  • Round trip: about 0.5 ms within a data center, tens of ms between regions on one continent, around 100 ms between continents.
  • N replicas with majority quorums tolerate (N − 1) ÷ 2 failures, rounded down: 3 tolerate 1; 5 tolerate 2.

In the interview

Bring consistency up when you add replicas, caches or a second region, or when two users can race for one thing. Skip "this is an AP system"; state the need per feature, with the reason: "Seat booking must be strongly consistent: two people paying for one seat is the failure we cannot have. The seat map can lag."

Your design has a leader and replicas in two regions. Is it consistent? Per feature. Usernames and payments go to the leader: strongly consistent. Feeds and like counts read local replicas and can lag a second unnoticed. After a user posts, their reads go to the leader for 10 seconds. It splits the system by feature and names a mechanism for each promise. And if the regions lose contact? Reads keep working in both regions. Writes in the region without the leader get a retryable error until the link returns. Right for payments; likes I could queue and apply later.

Follow-ups:

  • "Is your database CP or AP?" Usually it is set per operation. Say which refuse during a partition and which serve stale.
  • "Why not promote the West replica when the link drops?" That makes two leaders: split brain. Promotion needs a majority vote, so put a tiebreaker in a third site (see consensus).
  • "How else do you get read-your-writes?" Remember the log position of the user's last write; read only from a replica that has reached it.

Common mistakes

You cannot give up partition tolerance; networks fail anyway. The real choice, only during a partition, is refuse or serve stale data.

Sending every read to the leader wastes replicas and adds cross-region latency. Start from eventual plus read-your-writes. Spend strong consistency only where a stale read breaks a rule across users: one winner, never below zero.
