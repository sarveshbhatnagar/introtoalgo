A retrieval-augmented generation (RAG) system answers questions from a large set of documents. For each question it searches the documents, selects the few passages that are most relevant, and gives them to a language model with an instruction to answer only from those passages and to cite them. See RAG basics and chunking and retrieval for the building blocks.

The model call is the easy part. The hard parts are keeping millions of changing documents searchable, finding the right passages quickly, never showing someone a document they are not allowed to read, and measuring answer quality. The steps below follow A Framework for Any Design.

Clarify the problem

Design a system that answers employees' questions from company documents. Which documents does it cover, for example a wiki, tickets and shared drives, and can every employee read all of them? All three, about 10 million documents in total. Permissions vary a lot, and the HR, legal and some engineering spaces are restricted. Then permission checks are a hard requirement. How many employees will use it, and how soon after an edit should the answers reflect it? There are 20,000 employees, and a changed page should show up within minutes. My priorities are these. The system must never show content that the asker cannot open. Every answer must cite its sources. It should say it does not know instead of guessing. The first words should appear within about 2 seconds, and the cost per question must be controlled. Asking about permissions in the first minute shows that you have thought about running such a system.
  • Functional requirements: answer questions with citations using only documents the asker may read, say when the documents do not contain the answer, ingest document changes, and collect feedback on answers.
  • Non-functional requirements: no permission leaks at all, first words within 2 seconds and the full answer within about 10 seconds, edits searchable within 10 minutes, removed access effective within 5 minutes, bounded cost per question, and availability during working hours in every region.
  • Out of scope: actions such as filing tickets, fine-tuning models, and customers outside the company.

Estimate the scale

  • Chunks: 10 million documents with about 5 passages (chunks) each give 50 million chunks.
  • Questions: 20,000 employees asking 10 questions a day give 200,000 questions a day. Over an 8-hour working day (28,800 seconds) that is about 7 a second, or about 20 a second at a 3x peak.
  • Tokens: each question sends 8 chunks of about 500 tokens plus about 500 tokens for instructions, the question and the answer, which is 4,500 tokens. Over 200,000 questions that is 900 million tokens a day, and this figure drives the cost.
  • Changes: if 1% of the documents change each day, that is 100,000 documents and about 500,000 chunks to embed again, which is about 6 a second over a full day.

Write the endpoints for the chat window and for the connectors that report document changes. Decide whether the answer comes back as one response or as a stream.

The API needs an ask endpoint that streams the answer and ends with the citations, a feedback endpoint, and an internal endpoint where connectors report changes.

The decision worth arguing is streaming. A full answer takes several seconds, but the first words can arrive after about one second, so server-sent events are what meets the 2-second target. The citations come last because the model decides which sources it uses while it writes. If the model is down, the 503 response still contains the top documents.

Decide what an indexed chunk must hold so that it can be searched, cited, filtered by permission and embedded again only when its text changes.

A chunk needs its text, its vector, the document id, a title and link for citations, the groups allowed to read it, and a hash of its text so that unchanged chunks are not embedded again.

Model the data

documents                         -- source of truth for what is indexed
  doc_id          VARCHAR(64) PRIMARY KEY     -- "wiki-4410"
  source          VARCHAR(16)
  title, url      TEXT
  allowed_groups  TEXT[]          -- copied from the source system
  content_hash    CHAR(64)
  updated_at      TIMESTAMP

chunks                            -- lives in the search index
  chunk_id        VARCHAR(80)     -- "wiki-4410#3"
  doc_id          VARCHAR(64)
  text            TEXT            -- about 500 tokens, about 2 KB
  embedding       VECTOR(1024)
  allowed_groups  TEXT[]          -- filter field
  text_hash       CHAR(64)        -- skip re-embedding unchanged chunks
  index_version   INT             -- which chunker and embedding model made it

The query that runs on every question is "find the nearest vectors and the best keyword matches among the chunks this person may read". That needs a search index that supports vector search, keyword search and filters in one query. A search engine with vector support or a vector database with keyword support both work. Vector search is approximate, so its recall has to be measured.

Sketch both paths: how a document becomes searchable chunks, and how a question becomes a cited answer. Say where the permission check happens.

For ingestion, workers fetch, chunk and embed changed documents and write them to the index with their allowed groups. For a question, the service embeds it, runs a filtered hybrid search, reranks the results and sends the best chunks to the model. The permission check is a filter inside the search.

High-level design

Both paths use the same embedding model, because vectors produced by different models cannot be compared with each other.

Deep dives

The ingestion pipeline

The index has to follow the documents, which are edited, moved and deleted all the time. Each source system sends change events to a connector, and the connector also crawls the source on a schedule to catch any events that were lost. Every change becomes a message on a queue, and workers process the messages in four steps.

  1. The worker fetches the document and extracts its text, including from PDFs and slides. Extraction failures often go unnoticed, so count them for each source.
  2. The worker splits the text into chunks of about 500 tokens along the headings, with a little overlap between neighbours. It puts the document title and section heading at the top of each chunk so that it makes sense alone.
  3. The worker embeds, in batches, only the chunks whose hash is new. Most edits change only a few chunks.
  4. The worker writes the new and changed chunks to the index by doc_id and deletes the chunks that no longer exist.

Changing the embedding model or the chunking rules is a larger event, because the old and new vectors cannot be compared. The approach is to build a second index tagged with a new index_version and write every live change to both. When it is complete and checked against the evaluation set below, the answer service switches to it. At 1,000 chunks a second, backfilling 50 million chunks takes about 14 hours.

Choosing the retrieval method

The retrieval step decides which 8 chunks the model sees, so it limits the quality of every answer. There are three options.

Vector search compares the embedding of the question with the embedding of each chunk and returns the nearest ones. It finds passages with the same meaning in different words, so "reset my login" matches a page about password recovery. Its weakness is exact terms: an embedding model gives an error code or ticket number little meaning, so such a query can return vaguely related chunks.

Keyword search scores chunks by the words they contain,. It is excellent for exact identifiers, and it misses a passage that uses different words from the question. Company questions contain both exact terms and paraphrases, so neither method is enough alone.

Hybrid search runs both searches and merges the two ranked lists. A common way is reciprocal rank fusion, where each list gives a chunk 1 ÷ (60 + rank) points and the chunks are sorted by their total, so a chunk that both lists rank well beats one that only a single list ranks first.

Hybrid search returns 50 candidates cheaply, but its scorers judge the question and chunk separately, so the order is approximate. A reranker is a model that reads the question and one candidate chunk together and gives a more accurate relevance score. It is too slow for millions of chunks, but takes about 200 ms for 50 candidates. Its 8 chunks are better than the first 8 of the fused list, which lets the prompt hold 8 chunks instead of 20.

This design uses hybrid search plus a reranker, because 200 ms is small next to the second the model needs to start answering.

Enforcing permissions

Text that the asker may not read must never reach the prompt, because anything in the prompt can appear in the answer. Every chunk therefore carries the groups allowed to read its document, copied from the source system, and the question is answered only from chunks that match the asker's groups. There are three places to apply that check.

Filtering after the search means searching everything and then dropping the chunks the user cannot read. It is simple to build but fails in practice. For someone in a small team, most of the top 50 results may be restricted, so few or none remain and the answer is poor although readable documents exist.

Filtering inside the search applies the group condition as part of the query, so the engine returns the 50 best chunks among the readable ones. This is the choice for this design. It requires an index with efficient filtered vector search.

A separate index for each group gives strong isolation, but chunks readable by many groups are stored many times and a permission change means rewriting copies, so it suits only a few large, strictly separate tenants.

The filter is only as good as the permission data behind it, so three more rules apply. A permission change only has to update the allowed_groups field and does not need any embedding, which makes it cheap, so it runs on its own path and more often than content sync to meet the 5-minute target. The asker's groups come from the directory with a cache of about a minute, not from a login token that lives for hours. For highly sensitive sources such as HR and legal, the service also asks the source system at answer time whether the user can still open each cited document, which closes the gap before the next sync.

Retrieved text is untrusted as well, because a page can contain text written to steer the model; the prompt must treat it as data (see prompt injection).

Caching and controlling cost

The cost is driven by the 900 million tokens a day. The first lever is to send fewer and better chunks: with 6 chunks instead of 8, the prompt drops from 4,500 to 3,500 tokens. The second is to cache answers to repeated questions. The cache key must contain the normalized question and the asker's group set, because without the groups an answer built from restricted documents could be served to someone without access. An entry is evicted whenever a document it cites is changed or has its permissions changed.

A cache that answers merely similar questions is risky: "parental leave in France" and "parental leave in Germany" are close in meaning but have different answers.

Evaluating quality

The team builds a golden set of a few hundred real questions, each labelled with the documents that answer it, and scores every change against it before release (see evals). Three measurements matter.

  • Retrieval recall at 8 is how often a correct chunk is among the 8 sent to the model. When it is low, no prompt can rescue the answer, so this is checked first.
  • Faithfulness is whether every claim in the answer is supported by a cited chunk. A model can grade this at scale, with a sample checked by people.
  • Correct refusals are measured with questions the documents cannot answer, scoring whether the system says it does not know.

Bottlenecks and failures

At 10 times the questions, about 200 a second at peak, the language model and the reranker run out of capacity first. The fixes are more model capacity, more caching and fewer tokens per question. At 10 times the documents, the vectors take 2 TB at 4 bytes per number, so the index is split into shards by chunk, the shards are queried in parallel, and the numbers are stored in 1 byte each.

Follow-up questions

How do you handle follow-up questions in a conversation?

The system rewrites the follow-up into a standalone question using the recent turns, so "And for production?" becomes "How do I rotate the production database password?", and retrieves with that. The raw follow-up has no topic words to match.

The answer is wrong but the right document exists. How do you debug it?

Start with retrieval. Check whether the right chunk was among the 50 candidates and among the final 8. If it was not, the problem is in chunking, search or ranking, and the fix is there. If it was, the problem is in the prompt or the model.

Why not put all the documents in the context window?

Ten million documents do not fit in any context window. Even a set that fits would cost tokens on every question, and models use long contexts unevenly. Retrieval sends only a few thousand relevant tokens.
