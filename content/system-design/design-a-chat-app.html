Ana sends Ben a message and his phone shows it a moment later: one tick for sent, two for delivered, a colour change when read. If Ben is in a tunnel, the message waits and arrives when he comes out, in the right place.

It tests what request-and-response designs never touch: millions of open connections, routing to the recipient's server, ordering, and what "delivered" promises. Read Realtime Communication first if WebSockets are new. The steps follow A Framework for Any Design.

Clarify the problem

"Chat app" can mean team chat or a phone messenger. Pin it down.

Design a chat app like the ones on your phone. One-to-one and groups? How big a group? Read receipts and online status? Groups up to 200 people. Yes to receipts and to "online" or "last seen". Several devices per user? Media? And how many daily users and messages? One device, text only for now. 50 million daily active users, around 40 messages each a day. Then my priorities: an acknowledged message is never lost, everyone in a conversation sees one order, and online delivery takes well under a second. Presence can lag a few seconds. No end-to-end encryption, search or media storage. The last turn ranks the guarantees. The rest of the design must earn the first two.
  • Functional: one-to-one and group messages (up to 200); offline messages; history; sent, delivered and read receipts; online and last-seen.
  • Non-functional: an acknowledged message is never lost; one agreed order per conversation; online delivery under 500 ms; 99.99% availability for sending; presence may be a few seconds stale.
  • Out of scope: end-to-end encryption, search, media, multiple devices (see follow-ups).

Estimate the scale

  • Messages: 50 million × 40 = 2 billion a day ÷ 86,400 s ≈ 23,000 a second; about 70,000 at a 3x evening peak.
  • Deliveries: if 80% of messages are one-to-one and the rest reach 20 group members on average: 0.8 × 1 + 0.2 × 20 = 4.8 per message, so 23,000 × 4.8 ≈ 110,000 a second, about 330,000 at peak.
  • Connections: with 20% of daily users online at peak, 10 million WebSockets. At an assumed 100,000 per server (10 KB each, 1 GB), that is 100 servers; plan 200 for failures and deploys.
  • Heartbeats: a ping every 30 seconds per client is 10 million ÷ 30 ≈ 330,000 a second, as many as peak deliveries. They must never leave the connection servers.

List what goes over the open connection and what stays plain HTTP. How does a client retry a send without a duplicate?

Sends, deliveries, acks, receipts and presence go over the WebSocket; history and catch-up are HTTP with a cursor. The client's own id on each send lets the server spot retries.

Define the API

Client to server, over the WebSocket
  send     { client_msg_id: "c-7f3a", conv_id: "c_123", body: "lunch?" }
  ack      { conv_id: "c_123", up_to_seq: 1044 }       "I have everything up to 1044"
  read     { conv_id: "c_123", up_to_seq: 1044 }       "I have seen everything up to 1044"
  ping     every 30 s

Server to client
  sent     { client_msg_id: "c-7f3a", conv_id: "c_123", seq: 1044, ts: ... }
  message  { conv_id: "c_123", seq: 1044, sender: "ana", body: "lunch?", ts: ... }
  receipt  { conv_id: "c_123", user: "ben", kind: "delivered" | "read", up_to_seq: 1044 }
  presence { user: "ben", online: false, last_seen: ... }
  error    { client_msg_id: "c-7f3a", code: "not_member" | "too_large" | "rate_limited" }

HTTP
  GET  /v1/conversations/{conv_id}/messages?before_seq=1000&limit=50   history, newest first
  GET  /v1/sync?since={user_cursor}                                    what changed while offline
  POST /v1/conversations   { members: [...] }                          create a group
       403 not allowed, 404 no such conversation, 429 rate limited

The decision worth arguing is who names a message. The client's client_msg_id is an idempotency key, so a retried send is stored once. The server's seq is its position in the conversation, and clients sort by that, never their own clock. Acks and receipts say "up to seq N", confirming a whole batch at once.

What does a stored message look like, which queries must be fast, and what is the partition key? Think about a group of 200.

Once per conversation, ordered by seq, partitioned by conversation id in a wide-column store. Per-member cursors hold delivered and read positions.

Model the data

messages                       -- about 200 bytes a row
  conv_id        BIGINT        -- partition key (with bucket)
  bucket         INT           -- month number, keeps partitions bounded
  seq            BIGINT        -- clustering key: order inside the conversation
  sender_id      BIGINT
  client_msg_id  VARCHAR(36)
  body           TEXT          -- up to 4 KB
  created_at     TIMESTAMP
  PRIMARY KEY ((conv_id, bucket), seq)

dedupe                         -- PRIMARY KEY (conv_id, client_msg_id) -> seq
                               --   kept 1 day; a retried send gets the stored seq back
conversations                  -- conv_id, kind (direct | group), members, last_seq
members                        -- PRIMARY KEY (user_id, conv_id):
                               --   last_delivered_seq, last_read_seq, last_activity

The access patterns are narrow: append to one conversation, 23,000 times a second, and read "the newest 50" or "everything after seq N". Nothing joins. A wide-column store (such as Cassandra or HBase) keeps a partition's rows together, sorted by the clustering key, so both reads are one sequential scan. A relational database works too, but at 146 TB a year you would shard it by hand. The members table, keyed by user, serves the inbox and sync.

Sketch it: where do sockets live, how does a message on Ana's server reach Ben's, where is it stored, and what if Ben is offline?

Connection servers hold sockets; a stateless chat service orders, stores and forwards each message; offline recipients get a push and catch up from the store.

High-level design

Split the system by what each part remembers. Connection servers hold sockets, so they run no business logic and deploy rarely; the chat service holds nothing and deploys freely; the session cache holds who is connected where.

Deep dives

Connection servers and routing between them

With 10 million sockets on 100 to 200 servers, Ana and Ben are rarely on the same one.

Keep registry entries honest with a TTL: each connection server refreshes its entries every 30 seconds in one batch, and they expire after 90. Anything routed to a dead server meanwhile falls back to push; the message is already stored.

Deploys are the quiet danger: a restart drops 100,000 sockets. Drain servers one at a time, and have clients reconnect after a random delay; spread over 30 seconds, that is about 3,300 a second.

Delivery guarantees and ordering

Weak answers say "exactly once". Delivery is at least once: the server resends anything unacknowledged, so a lost ack means a duplicate. The client drops any (conv_id, seq) it has, so on screen it looks like exactly once; client_msg_id does the same for retried sends.

The sequence must come from one place per conversation: route every send for c_123 to one chat server (by consistent hashing on the conversation id) that keeps the counter, or keep it in a store with atomic increment or compare-and-set. Plain quorum reads and writes are not enough: two servers can both read 1043 and write 1044. A number whose write fails leaves a harmless gap; clients treat gaps as "fetch from the store".

Offline delivery and sync

The store is the delivery mechanism; sockets and pushes only say "something is new". On reconnect the client calls /v1/sync: the server reads the user's conversations from members, batch-reads each last_seq, and returns those ahead of the client, which pulls each missing range. After a week away, it fetches each chat's messages only when opened.

Phone push can delay, drop or collapse notifications, so "push sent" never means "delivered". Sockets can die unnoticed too: if Ben does not ack within about 10 seconds, push anyway. The notification system case study covers that pipeline.

Receipts and presence

Receipts are cursors, not rows per message: two numbers in Ben's members row, so "read up to 1045" is one write. In one-to-one chats, push each cursor change to the other person. In a group of 200, pushing every read cursor to every member is 200 × 199 ≈ 40,000 messages when everyone reads one message; instead, compute "read by 37" when someone opens the message info.

Presence quietly costs the most. It lives only in the session cache, with the 90-second TTL. The trap is fan-out: 20 online/offline changes per user a day is 50 million × 20 ÷ 86,400 ≈ 11,600 a second; pushed to 100 contacts each, 1.16 million presence messages a second, ten times the message deliveries. So push presence only to people with that chat on screen; others fetch it on open.

Storage and the partition key

Without the month bucket, a busy conversation's partition grows forever on the same nodes: a full group of 200 sending 40 messages each a day writes 200 × 40 × 200 B = 1.6 MB a day, about 3 GB in five years. Monthly buckets cap it near 48 MB, at the cost of a second query across a month boundary.

Bottlenecks and failures

At 10x (500 million daily users), peak deliveries reach about 3.3 million a second and stored writes 230,000 a second on average. Connection servers grow past 1,000; the store adds nodes, and conversation ids hash evenly. First to strain is the session cache, 100 million entries refreshed every 30 seconds: shard it by user id. Presence fan-out is next, hence the open-chat limit.

Forwarding before storing feels faster, but a crash in between means Ben saw a message that no longer exists, and Ana's retry creates a second copy. Store, acknowledge, then deliver.

If the catch-up read hits a replica a second behind the write, Ben reconnects and the newest message is missing. Use majority writes and reads (with 3 replicas, 2 + 2 > 3, so they overlap), or read from the leader.

What a strong answer sounds like

LevelWhat the answer does
JuniorWebSockets and a database. Orders by timestamp; says "exactly once" without saying how.
MidSeparate connection servers, registry or pub/sub routing, store before delivering, sync for offline users.
SeniorAt least once plus dedupe, a per-conversation sequence with a named source, a partition key from the group arithmetic, and sees that heartbeats and presence outweigh messages.
Why not order messages by timestamp? Clocks drift, so two people could see different orders. Each conversation gets a sequence number from one owner, the chat server it hashes to. Everyone sorts by it, and a gap shows a missed message. And if that owner crashes mid-conversation? Another instance takes over, reads the highest stored seq and continues. In case two servers briefly both think they own it, the store write is conditional on that seq not existing; the loser retries with the next number. It names where the number comes from and what goes wrong when the owner changes. Interviewers listen for the second part.

Follow-up questions

How do you support several devices per user?

The registry maps a user to (device, server) pairs, each device with its own delivered cursor. A message goes to every connected device; "delivered" means one device acked. Read state syncs through the read cursor.

Where do photos and videos go?

The client uploads to blob storage with a short-lived signed URL, then sends a message holding the file's id. Files never touch the chat path.

What changes with end-to-end encryption?

The server forwards ciphertext it cannot read: no server-side search or moderation, and groups need key distribution. Routing, ordering and storage are unchanged.

How do edits and deletes work?

As a new message with its own seq, pointing at the original. Clients apply it in order, so everyone ends with the same history, and offline users catch up through sync.

How would you run this across regions?

Users connect to their nearest region. Each conversation's home region owns its sequence, so senders elsewhere pay one cross-region round trip. Messages replicate everywhere for history.
