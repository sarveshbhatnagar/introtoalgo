You paste a long link and get back something like sho.rt/008sudj. Anyone who opens the short link lands on the long one. It looks like a weekend project, which is why interviewers like it: a small surface hides a read-heavy workload, an ID scheme that works across many servers, a cache that does most of the work, and a database that must never lose a row.

This case study follows A Framework for Any Design. Try each "Your turn" box before you read on.

Clarify the problem

The one-sentence prompt tests whether you pin down scope before drawing boxes. Ask about features, then scale, then what matters most when things fail.

Design a URL shortener. Users submit a long URL, get a short one, and opening it redirects. Can users pick a custom alias? Do links expire? Do we need click counts? Custom aliases, yes. Links live forever unless the user sets an expiry. A click count per link is enough; no dashboards. How many links are created, and how often is each one opened? Around 100 million new links a month. Reads are about 100 times the writes. Then it's read-heavy, and the redirect is the path to protect. Redirects should add under 20 ms on our side and stay up even when link creation is down. A created link must never be lost. I'll leave out accounts, spam scanning and dashboards unless you want them. The last answer turns facts into priorities: which path is hot, what "fast" means, which part may fail and which must not.

Write it down where the interviewer can see it:

  • Functional: create a short link for a long URL, with an optional custom alias and expiry; redirect a short code to its long URL; count clicks per link.
  • Non-functional: redirects are fast (under 20 ms added) and highly available; created links are never lost; codes are short.
  • Out of scope: user accounts, abuse scanning, analytics dashboards.

Estimate the scale

Turn the interviewer's numbers into per-second rates and bytes. A month has about 30 × 86,400 ≈ 2.6 million seconds.

  • Writes: 100 million ÷ 2.6 million ≈ 40 links a second on average. Assume peaks of 5x: 200 a second.
  • Reads: 100 × 40 = 4,000 redirects a second on average, 20,000 at peak.
  • Code length: with 62 characters (0-9, a-z, A-Z), 6 characters give 626 ≈ 57 billion codes and 7 give 627 ≈ 3.5 trillion. Five years is 6 billion links, so 7 leaves plenty of room.

Two more numbers. A redirect response is about 500 bytes, so 20,000 a second is only 10 MB/s. If the hottest 10 million links get most clicks, caching them takes 107 × 500 B = 5 GB, which fits on one cache node.

Write the two endpoints: method, path, request body, and what each returns, including errors.

A create endpoint (POST /api/links with the long URL and optional alias and expiry, returning the code) and the redirect (GET /{code}, returning a redirect status with a Location header). The real choice is which redirect status.

Define the API

POST /api/links
  body: { "long_url": "https://...", "alias": "spring-sale"?, "expires_at": "2027-01-01"? }
  201 Created   { "code": "008sudj", "short_url": "https://sho.rt/008sudj" }
  400 Bad Request   the URL is not valid
  409 Conflict      the alias is taken

GET /{code}
  302 Found   Location: https://the-long-url...
  404 Not Found     no such code, or it has expired

A 301 (moved permanently) lets browsers cache the redirect, so repeat clicks never reach you: less load, but you cannot count those clicks or change the target. A 302 (found) is not cached, so every click comes through. We need click counts, so use 302; the estimate says the extra traffic is small.

Protect POST with a per-client rate limit, or spammers will own the shortener within days.

What does one record hold, how is it looked up, and which kind of database fits?

One record per code. Every read is "the row for this code", every write is an insert, nothing joins: a key-value access pattern.

Model the data

code        CHAR(7)   PRIMARY KEY   -- "008sudj" or a custom alias
long_url    TEXT                    -- up to 2 KB
created_at  TIMESTAMP
expires_at  TIMESTAMP NULL
clicks      BIGINT                  -- updated in batches, not per click

The hot path is a lookup by primary key: no joins, no range scans, and rows never change except the click count. A key-value or wide-column store (such as DynamoDB or Cassandra) fits: it partitions by key out of the box, which we want at 3 TB and beyond. A relational database with read replicas also works at this size, and is a fine pick if the team already runs one. Give the reason: single-key reads, no joins, easy partitioning by code.

Custom aliases live in the same table. Because code is the primary key, "insert if absent" makes alias claims safe: two users racing for spring-sale cannot both win.

Sketch both paths: what sits between a browser and the database on a redirect, and where does a new code come from?

Split reads from writes so each scales on its own: a stateless redirect service with a cache in front of the store, and a create service that hands out codes.

High-level design

Redirects outnumber creates 100 to 1, so they get their own service and cache. Each new link needs a code no other server will hand out; a small ID allocator gives each create server a block of numbers.

Deep dives

Interviewers almost always push on three parts: making codes, keeping redirects fast, and counting clicks without slowing redirects.

Generating short codes

Every server must hand out unique codes without a slow check on each request.

For the random option: with 6 billion links stored and 3.5 trillion possible codes, a new code collides with probability 6 × 109 ÷ 3.5 × 1012 ≈ 0.2%. One retry in 500 creates is fine. If counter codes being guessable worries the interviewer, scramble the number with a reversible function before encoding: still no collisions, no longer sequential.

Keeping redirects fast

A few links get most of the clicks. A cache with LRU eviction in front of the store serves most redirects in about a millisecond. Links never change, so writes need no invalidation. The exceptions: delete the cache key when a link is deleted, and check expires_at on every redirect so an expired link is never served from cache. See caching for stampedes, which matter when a link goes viral.

Counting clicks without slowing redirects

Updating a counter on every click puts a write on the hot path, and a viral link makes one row the hottest spot in the database. Instead, the redirect service publishes a click event to a queue and returns. A worker sums events per code and writes one update per link every few seconds.

Say the trade-off out loud: counts lag by a few seconds, and lost queue events make them slightly low. Fine for click counts; for billing per click you would make events durable and processing idempotent.

Bottlenecks and failures

At 10x (200,000 redirects a second at peak, 30 TB over five years):

  • Redirect servers hold no state, so add more.
  • The cache becomes a cluster split by consistent hashing, so adding a node moves only a small share of keys.
  • The store is partitioned by code, which spreads evenly because codes do.
  • The allocator barely notices: blocks of 1,000 at 2,000 writes a second is 2 requests a second.

Without a cache, all 20,000 peak redirects a second hit the database, and a viral link hammers one partition. The cache is part of the design, not a later optimisation.

What a strong answer sounds like

Every level reaches a working design. What differs is how far the numbers drive it and how the trade-offs are argued.

LevelWhat the answer does
JuniorA service and a database, a hashed URL for a code, and a working path once prompted about collisions.
MidEstimates traffic and storage, separates reads from writes, adds a cache with a reason, compares two code schemes.
SeniorLeads with the read/write ratio, picks 302 for click counts, takes counting off the hot path, says what fails first at 10x and what they leave out.
Why not just hash the URL? 7 characters of a hash collide, so I'd still need check-and-retry on every insert, and two users would share a code. Counter blocks never collide and cost one allocator call per thousand links. The cost is guessable codes; if that matters, I'd scramble the number before encoding. A strong answer names the cost of the option it picks, not only the flaws of the one it rejects.

Follow-up questions

How would you run this in several regions?

Serve redirects in every region from a local cache and store replica; replication lag only delays brand-new links by a second or two. Give each region its own ID ranges so creates never coordinate across regions.

The same long URL is submitted twice. Same code?

Not by default. Deduplication needs an index on the long URL and lets one user's expiry or deletion affect another's link. Offer it per user if asked.

How do you stop abuse?

Rate limit creates per API key and per IP, check new URLs against a blocklist, and scan them asynchronously so a bad link can be disabled later.

How do you delete a link quickly?

Mark it deleted in the store and delete the cache key. With 302, browsers have not cached it, so the next click sees the change.

What if one link gets a million clicks a minute?

That is about 17,000 a second on one key. Keep a copy in each redirect server's memory for a few seconds so the cache node holding it is not overloaded.
