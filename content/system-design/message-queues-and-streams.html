A signup endpoint creates the account, then calls an email provider to send a welcome message before responding. One afternoon the provider slows from 100 ms to 3 seconds. At 50 signups a second, 50 × 3 = 150 requests are stuck waiting, the worker pool fills, and signups fail though the database is fine.

The email did not need to happen before the response. Put it on a queue, answer in milliseconds, and let a worker send it later.

The idea

A producer writes a message to a durable broker and moves on. A consumer reads it later and does the work. A burst now waits in the broker instead of crushing the consumer, and a dead consumer delays work instead of failing requests.

The costs: work happens later, there is one more system to run, and messages can arrive twice.

Queue or log

A queue (such as RabbitMQ or SQS) hands each message to one consumer and deletes it once acknowledged. A log (such as Kafka) appends messages and keeps them for days; each consumer group tracks its own position (an offset) and can rewind.

One job type, one kind of worker: a queue. A second team wants the same events, or you need replay: a log.

Delivery guarantees

A consumer does the work and sends an acknowledgement. A crash can land between them; the order decides what it costs.

  • At-most-once: ack, then work. A crash after the ack loses the message. Fine for droppable metrics.
  • At-least-once: work, then ack. A crash before the ack means the message comes back and the work runs again. The usual choice.
  • "Exactly-once": no broker can stop a consumer doing an external action twice. You build exactly-once effect: at-least-once delivery plus idempotent processing. Some brokers offer exactly-once within their own reads and writes; that does not cover your email provider.

A message that always fails blocks its partition in a log, or burns workers in a queue. Cap attempts, dead-letter it, and alert.

Ordering, partitions and consumer groups

A log is split into partitions, and order holds only inside one. The producer hashes a key to pick the partition, so key by whatever must stay in order: with order_id, one order's "created", "paid" and "shipped" arrive in sequence.

A consumer group is one logical subscriber. Inside a group, each partition has one consumer at a time, so 12 partitions allow at most 12 busy consumers. Different groups (email, analytics) each read every message. Size partitions for future parallelism: adding them later remaps keys and breaks per-key order during the change.

A hot key, such as one huge customer, lands on one partition. To spread it, add a suffix and give up its ordering.

Backpressure

A queue absorbs bursts; it does not fix consumers slower than producers on average. At 1,200 messages a second in and 1,000 out, the backlog grows by 200 a second, 720,000 an hour. Watch consumer lag (messages or seconds behind) and act on it:

  • Scale consumers, up to the partition count.
  • Bound the queue and push back: return 429 or 503 and let clients retry later.
  • Shed or sample low-value messages (debug events) before high-value ones (payments).

Numbers worth remembering

  • Publishing to a broker in the same data center: a few ms, including replication.
  • One partition: thousands to tens of thousands of small messages a second. Throughput scales with partitions.
  • Little's law: messages waiting = arrival rate × wait time. 50 a second × 3 s = 150, the hook's stuck requests.

In the interview

Bring in a queue when work is slow, flaky or not needed for the response, when traffic is bursty, or when several systems react to one event. Then state the guarantee and its cost: "Delivery is at-least-once, so the counter worker dedupes by event id."

After checkout we send a confirmation email and update analytics. Where does that happen? Not in the checkout request. Checkout publishes OrderPlaced to a log keyed by order id. Email and analytics are separate consumer groups, so a slow email provider delays neither analytics nor checkout. Can a customer get two emails? Under at-least-once, yes, unless I prevent it. The email worker passes the event id to the provider as an idempotency key, so a redelivery sends nothing. Messages that fail five times go to a dead-letter queue with an alert. The candidate raises the duplicate before being cornered.

Follow-ups:

  • "The API crashes after creating the account but before publishing. Now what?" No welcome email, ever. Write the message to an outbox table in the account's transaction (see transactions).
  • "What if the provider has no idempotency key?" Record sent job ids in your own table. A crash between sending and recording can still send twice, so keep that window short.

Common mistakes

Duplicates are normal under at-least-once. Say how the consumer makes them harmless: a dedupe table, an idempotency key, or an operation safe to repeat.
