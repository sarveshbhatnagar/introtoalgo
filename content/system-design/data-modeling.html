A team splits the reservation system's reservations across 8 partitions by a hash of the reservation id, so rows spread perfectly evenly. Two diners book table 7 at 19:30 at the same moment. Their reservations hash to different partitions, each checks only its own rows, both find no conflict, and both commit. The table is double-booked, the one thing the requirements forbade.

Nobody first asked which queries run, and which must see each other's writes.

Access patterns first

Entities are the easy part: restaurants, tables, slots, reservations, diners. Before choosing any key, list every way the system reads and writes them, with a rate from the estimates.

Almost everything starts from a restaurant, one pattern from a diner, and the last belongs in a search index.

A worked schema

restaurants (restaurant_id PK, name, city, cuisine, timezone)

tables      (restaurant_id, table_id, seats,
             PRIMARY KEY (restaurant_id, table_id))

slots       (restaurant_id, slot_date, slot_time, table_id, seats,
             reservation_id NULL,          -- NULL means free
             PRIMARY KEY (restaurant_id, slot_date, slot_time, table_id))

reservations (restaurant_id, reservation_id, table_id, slot_date, slot_time,
              user_id, party_size, status, created_at,
              PRIMARY KEY (restaurant_id, reservation_id))

user_reservations (user_id, slot_date, slot_time, reservation_id,
                   restaurant_name,        -- copied on purpose
                   PRIMARY KEY (user_id, slot_date, slot_time, reservation_id))
  • A row per slot. "Is table 7 free at 19:30?" is one row, and booking is a conditional update: set reservation_id only where it is still NULL. If no row changes, someone else won: return 409. Check and write are one step, so no race.
  • Every restaurant table starts with restaurant_id. The slot update and reservation insert share a partition key, so they commit in one local transaction, and an open-slots query reads one contiguous range.
  • user_reservations repeats data. The diner's page lists reservations by time, with restaurant names. Keyed by user_id, that is one range read, no join.

Size it. Slots come to about 24 GB (the first quiz question works it out); reservations, 1 million a day × 365 × 200 bytes = 73 GB a year. Both fit one server, and 1,050 operations a second at peak suits one primary with read replicas. You may never shard, but pick the partition key anyway: it decides which transactions stay on one machine if you do.

Normalize, then copy on purpose

Normalized: each fact lives in one place (the restaurant's name only in restaurants), so reads join. Denormalized: facts are copied to where they are read, so reads are one lookup, but every change must reach every copy.

Start normalized. Denormalize one access pattern at a time, each with a reason and a way to keep the copy in step.

Choosing the partition key

The partition key decides which machine holds each row (see sharding and partitioning). A good key keeps everything a frequent query or transaction needs on one partition, and spreads load evenly. The two goals conflict.

A venue taking thousands of bookings a second (a stadium) would run its partition hot; you would split its slots by date or section. At 50 bookings a second in total, that is not this problem.

How a booking flows through the model

In the interview

Spend about 3 minutes here and let the access patterns pick the store: single-key lookups suggest a key-value store, transactions a relational database (see choosing a database). A booking is a conditional update plus an insert in one transaction, so relational. Useful phrases:

  • "Before picking keys, here are the five queries and their rates."
  • "The diner's list is a denormalized view, updated from events. It can lag; the booking cannot."
How would you partition the reservations? By restaurant. The booking check, open-slot query and restaurant's view all start there, so each hits one partition. The diner's list starts from the user, so I keep a separate copy keyed by user id. What about a hugely popular restaurant? A few hundred slots a night is small volume; the issue is contention on the same rows when bookings open. The conditional update keeps it correct, and a queue in front of its booking page smooths the burst.

Expected follow-ups:

  • "Why not a secondary index on user_id?" Fine on one node. On a partitioned store, a global index is a separately partitioned copy, updated either asynchronously (the same lag, less control) or in a cross-partition transaction (slower bookings).
  • "How do you handle time zones?" Store local date and time plus the restaurant's time zone.

Common mistakes

A tidy entity diagram says nothing about keys. List the access patterns with rates first; the keys fall out of them.

A hashed id spreads load perfectly and scatters related rows. First check that every transaction and frequent query stays on one partition, then the spread.
