Most designs in this track end with "the bytes go in an object store". Here you build that box, an Amazon S3. A user sends PUT photos/2026/cat.jpg with 4 MB; years later, after thousands of disks have died, a GET must return exactly those bytes.

The user's side is in Blob Storage. The steps follow A Framework for Any Design.

Clarify the problem

Design an object storage service. I'll assume buckets of objects by key, with put, get, delete and list by prefix, and objects replaced whole, never edited. How big can one be? Versioning? From zero bytes up to 1 TB. Versioning is a stretch goal. How much data, and how busy is it? 100 PB in about 100 billion objects, growing 10 PB a month. About 4,000 writes and 40,000 reads a second. Then durability first, since a lost object can never be fixed; then read availability; then cost per byte, because at 100 PB the storage overhead is the bill. Saying why cost matters sets up storage overhead as a deep dive.
  • Functional: buckets; put, get (whole or a byte range) and delete objects; list keys by prefix, in pages; multipart upload.
  • Non-functional: eleven nines of durability per object per year; reads available 99.99%; a successful put is visible to every later get and list; first byte within about 100 ms; storage overhead well under 3x.
  • Out of scope: access policies, billing, storage classes, cross-region replication, versioning.

Estimate the scale

The average object is 100 PB ÷ 100 billion = 1 MB.

  • Ingest: 4,000 puts a second × 1 MB = 4 GB/s. Over a month (about 2.6 million seconds): ≈ 10 billion objects, 10 PB, matching the growth given.
  • Egress: 40,000 gets a second × 1 MB = 40 GB/s, 120 GB/s at a 3x peak: about 120 front ends at 1 GB/s each. Bandwidth is the limit.

Write put, get, delete, list and multipart upload. How does the client know the bytes arrived intact?

Put, get and delete on /{bucket}/{key}, list with a prefix and page token, and start, part and complete for multipart. The put carries a checksum; mismatched bytes are refused.

Define the API

PUT    /{bucket}/{key}          x-checksum: sha256=9f2c...
  200 { "etag": "9f2c...", "version": "v2" }
  400 Bad Digest            bytes do not match the checksum; nothing stored
  412 Precondition Failed   If-Match / If-None-Match did not hold

GET    /{bucket}/{key}          Range: bytes=0-1048575 (optional)
  200 or 206 + bytes         404 no such key

DELETE /{bucket}/{key}
  204 No Content             also when the key did not exist

GET    /{bucket}?prefix=photos/2026/&delimiter=/&limit=1000&after=...
  200 { "keys": [...], "prefixes": ["photos/2026/01/"], "next": "token" }

POST   /{bucket}/{key}?uploads                start  -> { "upload_id": "u7" }
PUT    /{bucket}/{key}?upload_id=u7&part=3   one part -> { "etag": "..." }
POST   /{bucket}/{key}?upload_id=u7          complete, body: [{part, etag}, ...]
DELETE /{bucket}/{key}?upload_id=u7          abort

Argue what happens when two clients put the same key at once. Default to last writer wins, ordered by the metadata commit, plus conditional puts: If-None-Match: * ("only if the key does not exist") and If-Match: <etag> ("only if unchanged since I read it"). That is compare-and-swap without locks. Delete returns 204 for a missing key, so retries are safe (see idempotency and retries).

What records describe an object, and where do its bytes live? What must change when a dead disk is rebuilt elsewhere?

An object row maps a key to chunks in large volumes; a volume map says which disks hold each volume. A rebuild changes the volume map, never billions of object rows.

Model the data

objects                       -- sorted by (bucket_id, key)
  bucket_id    BIGINT
  key          VARCHAR(1024)  -- "photos/2026/cat.jpg"
  version      BIGINT
  size_bytes   BIGINT
  checksum     CHAR(64)       -- sha256 of the bytes (multipart: of the parts' sums)
  chunks       LIST           -- [(volume_id, chunk_id, length, crc32c), ...]
  PRIMARY KEY (bucket_id, key)

volumes                       -- the volume map, about 10 million rows
  volume_id    BIGINT PRIMARY KEY
  state        VARCHAR(8)     -- open | sealed | coded
  layout       LIST           -- 3 disks while open; 14 fragment disks once coded
  generation   INT            -- bumped when compaction rewrites it

multipart_parts
  upload_id, part_number, chunks, checksum

The indirection is key → chunks → volume → disks. A volume is a 10 GB append-only file of many objects' chunks: 100 PB ÷ 10 GB = 10 million volumes, a 2 GB map at about 200 bytes each that every front end can cache. Each storage node indexes chunk id to offset.

Gets and puts are strongly consistent single-key lookups; list scans sorted keys from a prefix, which rules out hash partitioning. Use a range-partitioned, sorted key-value store, such as TiKV: each range is replicated three ways under consensus, and busy ranges split.

Sketch the boxes. What picks the disks, what commit makes an object visible, and what runs in the background?

Front ends, metadata, placement, storage nodes, and background workers for scrub, repair, coding and GC. The object exists at the metadata commit.

High-level design

Metadata is small, strongly consistent and touched by every request; data is huge, written once and mostly cold. So they are separate services. Bytes go first and metadata second, so an object never points at missing bytes.

Deep dives

Durability: copies or erasure coding

Eleven nines is a 1 in 1011 yearly chance of losing an object: about 1 of our 100 billion a year. Assume 2% of disks fail a year and a lost piece is rebuilt within 24 hours.

  • Chance a given disk fails in a 24-hour window: p = 0.02 × 24 ÷ 8,760 ≈ 5.5 × 10−5.
  • 3 copies. One of the 3 disks fails 3 × 0.02 = 0.06 times a year; the object is lost only if both others fail before the rebuild: p² ≈ 3.0 × 10−9. Yearly loss ≈ 0.06 × 3.0 × 10−9 = 1.8 × 10−10, just under ten nines: about 18 objects a year.
  • 10 + 4 coding. One of 14 disks fails 14 × 0.02 = 0.28 times a year; the object is lost only if 4 of the other 13 fail before the rebuild: 715 × p⁴ ≈ 6.4 × 10−15. Yearly loss ≈ 0.28 × 6.4 × 10−15 ≈ 1.8 × 10−15, almost fifteen nines. Data is coded once its volume fills, so this figure is the one that counts.
  • Faster repair pays twice. Repair in 1 hour and p falls 24 times, so the 3-copy loss falls 24² = 576 times, to about 3 × 10−13.

Real failures correlate: a rack loses power, a disk batch shares a firmware bug, a release deletes the wrong files. So spread each volume across racks, roll out software slowly, and wait days before erasing deleted data.

Repair is the price of coding. 7,000 disks at 2% a year fail every 2.6 days. Rebuilding a 20 TB disk under 10 + 4 reads 200 TB: over 24 hours, 200 TB ÷ 86,400 s ≈ 2.3 GB/s of background traffic, against 0.23 GB/s for copies. Normal reads do not pay: the code is systematic, so the 10 data fragments hold the original bytes and a 1 MB read usually touches one fragment.

Durability also needs detection: a rotted copy is a copy you do not have. Every read checks the chunk's CRC, and a scrubber reads every disk end to end: a 20 TB disk every 14 days is 20 TB ÷ 1.2 million s ≈ 17 MB/s.

Huge objects and multipart upload

A 1 TB object arrives as parts, say 10,000 of 100 MB, in parallel. Each part is a small put: chunks plus a multipart_parts row.

Complete moves no bytes. It checks every listed part's etag, then writes one object row listing the parts' chunks in order, in one transaction. A 1 TB object appears atomically, in milliseconds. Abort, or expiry of uploads idle for a week, deletes the part rows and leaves the chunks to garbage collection.

Listing by prefix

There are no folders. Listing photos/2026/ scans the sorted store from the prefix until keys stop matching, touching one or two ranges.

  • Pages: at most 1,000 keys plus a token holding the last key.
  • Delimiter: with delimiter=/, keys under photos/2026/01/ collapse into one entry, and the scan seeks past them.
  • Hot ranges: timestamp-prefixed keys all land at the end of one range, and splitting cannot help. Suggest a short hash prefix.

List reads the same consistent store as get, so a key is listed the moment its put returns. An asynchronous listing index would break jobs that write files and then list them.

Deleting and reclaiming space

Delete removes the object row at once. Its bytes stay in the volume until a slower job reclaims them.

Use both, with two safety rules:

  • Grace period: never erase a chunk younger than a few days, since its put may not have committed yet. The commit refuses chunks older than a day, so a stalled put fails rather than point at erased bytes.
  • Compaction keeps chunk ids: when a sealed volume is over 40% dead, a worker copies its live chunks into a new generation of that volume and updates the volume map. Object rows still say "volume 5,120,331, chunk 88". The old generation stays readable for a day.

Synchronous erasure slows requests, races with puts and compaction, and lets a delete bug destroy data instantly. A few days between "unreferenced" and "erased" is your undo window.

Bottlenecks and failures

At 10x (40,000 puts and 400,000 gets a second), add storage nodes and front ends; new volumes go to the emptiest disks, so nothing old moves. The metadata store strains first, since every put is a consensus write: split busy ranges and cache hot rows in front ends.

Follow-up questions

How would you add versioning?

Put the version in the key so each put adds a row; delete adds a "delete marker" row. A plain get reads the newest non-marker row. GC treats every version's chunks as live.

How do you survive losing a whole data center?

No zone may hold more fragments than the code can lose: with 3 zones, 12 data + 6 parity, 6 per zone, survives a zone at 18 ÷ 12 = 1.5x. With a zone down there is no margin, so repair fast.

What about billions of tiny objects?

Coding is per volume, so a 1 KB object costs 1.4 KB of disk, but its 500-byte metadata row rivals the data: metadata is the limit.

One object gets 50,000 gets a second. What breaks?

The disk holding it. Cache hot objects in front ends or a CDN; objects never change in place, so caches cannot go stale.
