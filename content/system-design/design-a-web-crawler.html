A search engine can only find pages it has seen. A web crawler sees them: it starts from a few URLs, downloads each page, pulls out the links and adds new ones to its to-do list. Run that loop a billion times a month and you have the raw material for a search index.

The loop is easy; everything around it is not: be polite to other people's servers, avoid fetching a page twice, survive sites with endless URLs, keep hundreds of downloads in flight. The steps follow A Framework for Any Design.

Clarify the problem

Design a web crawler. What is it for: a search index, an archive? HTML only, or PDFs too? A general search index. HTML only. How many pages, and how fresh must they be? About a billion pages a month. Popular pages refreshed more often. Then my priorities: never overload a website, never waste fetches on duplicates, and spend the budget on pages that matter most. I'll hand raw HTML to the indexing team. Politeness comes first. A crawler that hammers a small site gets blocked, and shows you forgot the people on the other end.
  • Functional: start from seed URLs; fetch HTML; extract and add new links; store each page; recrawl, important pages more often.
  • Non-functional: polite (one request at a time per site, with a gap, robots rules obeyed); about 1 billion pages a month; each URL scheduled once per cycle (a lease retry may rarely fetch twice); survives slow and hostile sites; a crash loses no frontier state.
  • Out of scope: indexing, ranking, JavaScript rendering, media, pages behind logins.

Estimate the scale

A month is 30 × 86,400 ≈ 2.6 million seconds. The crawler sets its own pace, so plan a target rate plus headroom, not a peak.

  • Fetch rate: 109 ÷ 2.6 × 106 s ≈ 385 a second. Call it 400; plan for 800 to catch up after a bad day.
  • Bandwidth: 400 × 100 KB a page = 40 MB/s, about 320 Mbit/s. One data center link.
  • Connections in flight: assume 1 second per fetch. By Little's law (in-flight = rate × time), 400 × 1 s = 400 open downloads, 800 with headroom.
  • The politeness ceiling: at one request a second per site, a 1-million-page site takes 106 ÷ 86,400 ≈ 11.6 days. Large sites, not bandwidth, limit freshness.

A crawler has no public users. Write the messages between its parts and to the indexing team.

Add URLs (seeds and parsed links, same call), get the next URL a fetcher may fetch now, and an output record per page. The frontier picks "next" by politeness and priority.

Define the API

frontier.add(urls: [ { url, priority, discovered_from } ])
  -> accepted count; URLs already seen are dropped silently

frontier.lease(fetcher_id) -> { url, host, lease_id, lease_until }
  -> or "nothing ready, retry in N ms" when every host is cooling down

frontier.complete(lease_id, result)
  result: fetched(status, content_hash) | not_modified | failed(reason, retry_after?)
  -> an expired lease is handed out again, so a dead fetcher loses no URL

event PageFetched { url, fetched_at, status, content_hash, blob_key }
  -> published to a stream that the indexer consumes

The decision worth arguing is lease, not pop. A popped URL whose fetcher crashes is lost for good: it is marked seen and never added again. A leased URL goes back out after lease_until. The cost: a slow (not dead) fetcher may duplicate a download, which wastes a fetch but breaks nothing.

What records does the crawler keep about URLs, hosts and page content? What does it ask of each, and how often?

A URL record keyed by URL hash (seen? next fetch?), a host record (robots rules, next allowed request), and page bytes in object storage. "Have I seen this URL?" is asked about 50 times per page, so it gets its own structure.

Model the data

-- one row per known URL, partitioned by host hash
urls:   url_hash      BIGINT PRIMARY KEY  -- 8-byte hash of the normalised URL
        url           TEXT                -- up to ~2 KB
        host          TEXT
        priority      SMALLINT
        next_fetch_at TIMESTAMP
        last_status   SMALLINT
        content_hash  BIGINT NULL         -- fingerprint of the last body

-- one row per host
hosts:  host            TEXT PRIMARY KEY
        robots_rules    TEXT              -- parsed robots.txt, refreshed daily
        crawl_delay_ms  INT               -- 1,000 unless the site asks for more
        next_allowed_at TIMESTAMP
        ip_cache        TEXT, ip_expires TIMESTAMP

-- page bodies: object storage, key = url_hash + fetch date, gzip-compressed

The URL table gets lookups and inserts by hash and a scan for "what is due", with no joins: a wide-column or key-value store (such as Cassandra) partitioned by host, so the machine that schedules a host owns its URLs. Page bodies are large, written once and read in bulk: blob storage.

Normalise URLs before hashing, or one page looks like many: lowercase scheme and host, drop the default port and #fragment, sort and prune query parameters. HTTP://Example.com:80/a?b=2&a=1#top and http://example.com/a?a=1&b=2 are one page.

A frontier hands URLs to fetchers, which download, store the body and pass it to parsers. Parsers extract links, drop seen ones and add the rest to the frontier.

High-level design

The crawl is a breadth-first search: the frontier is the queue, ordered by priority and politeness; the seen-URL set is the visited set.

Deep dives

The URL frontier: politeness and priority

A plain first-in, first-out queue fails twice. Pages link mostly within their own site, so runs from one host hit it all at once. And it treats a news home page like an old forum thread.

Use two layers. The front is a few priority queues, high for pages that change often or rank well. The back is one queue per host, held by at most one fetcher at a time, refilled from the front favouring high priority. A min-heap keys each host by when it may next be fetched.

Split the frontier by host with consistent hashing over, say, 10 machines. Each host lives on one machine, so politeness needs no coordination. Queues live on disk with a small in-memory head. Score priority by how often a page changed on past fetches and how many known pages link to it.

Deduplicating URLs

At 50 links a page and 400 pages a second, the seen set answers 20,000 lookups a second, nearly all "seen". Two details make it correct. The check is insert-if-absent, one atomic step, so two parsers cannot both add the same link. And a URL counts as seen only once the frontier has stored it, so a crash never leaves it seen but unqueued.

A Bloom filter is a bit array plus k hash functions. Adding a URL sets k bits; checking reads them. Any 0 means new; all 1s means probably seen. A 1% false-positive rate needs about 9.6 bits per item and 7 hash functions: 1010 × 9.6 bits ≈ 12 GB.

The catch to say out loud: a false positive is sticky. The same new URL hits the same bits every time, so it is skipped for as long as that filter lives. At 100 billion URLs (800 GB against 120 GB) the filter wins; rebuild it each cycle with fresh hash seeds so the unlucky URLs change.

Deduplicating content

Mirrors and ?ref= variants serve the same page. Store a 64-bit fingerprint of each body (8 bytes × 1 billion pages = 8 GB) and skip parsing known ones. Near-copies differing by a timestamp or an ad need a similarity hash; mention it, design it only if asked.

DNS and fetch throughput

A fetch is mostly waiting. With non-blocking I/O, ten machines with 80 open connections each cover the planned 800. CPU goes to parsing, so parsers are a separate fleet.

DNS is the classic hidden bottleneck: standard resolver calls often block a thread, and an uncached lookup takes 10 to 200 ms. Run a caching resolver beside the fetchers, keep each IP for its time to live, and resolve a host just before its turn. If one lookup serves 20 fetches, 400 fetches a second need 20 lookups a second.

Robots rules and traps

Fetch each host's /robots.txt first and cache the rules for a day. Obey Disallow paths and any longer delay. A server error means off limits for now; a 404 means no rules.

Some sites generate endless URLs: a calendar with "next month" forever, session IDs in links, filters that combine into millions of pages. Cap URL length (say 2,000 characters), path depth and pages per host per cycle; strip session parameters; flag hosts where most pages are duplicate fingerprints.

"At most 400 pages a second" could all hit one small server. Politeness is per host: one request at a time, with a gap, enforced in the frontier, not in each fetcher.

Bottlenecks and failures

At 10x (about 4,000 fetches a second), fetchers and parsers scale out and bandwidth reaches 3.2 Gbit/s. The seen set nears 100 billion URLs, where a Bloom filter pays off. The real limit is politeness: large sites cannot be fetched faster, so freshness comes from smarter priority and conditional requests (If-Modified-Since), where a 304 Not Modified costs almost nothing.

What a strong answer sounds like

LevelWhat the answer does
JuniorA queue, fetchers and a database; a set for visited URLs; a global rate limit when asked about overloading sites.
MidEstimates fetch rate and storage, uses per-host queues, hashes URLs for the seen set, respects robots rules.
SeniorBuilds a frontier from priority plus per-host scheduling, partitioned by host; weighs a hash set against a Bloom filter's sticky false positives; leases, not pops; names politeness as the limit on freshness.
Why not just use a Bloom filter? It's much smaller. About 12 GB against 80 GB. But one in a hundred new URLs is reported as seen and, hitting the same bits every time, never crawled this cycle. 80 GB over ten machines is cheap, so I'd rather be exact. At 100 billion URLs I would switch. Both sizes, a precise failure ("sticky"), and the number that flips the decision.

Follow-up questions

How do you decide when to recrawl a page?

Schedule around how often its fingerprint changed in past fetches, sooner for important pages. Conditional requests make an unchanged page cost a 304.

How would you crawl pages that need JavaScript to render?

Send only those pages to a pool of headless browsers. Rendering costs far more CPU than parsing, so keep it a per-site exception.

A site asks you to stop crawling it. What changes?

Add the host to a blocklist the frontier checks before leasing, and purge its queue. It takes effect at the next lease.

How would you crawl from several regions?

Give each host to the region nearest it: short fetches, one owner per host. Only new URLs cross regions.

How do you know the crawler is healthy?

Watch fetches per second, duplicate share, error rates per host, and the age of the oldest due high-priority URL: it shows if important pages go stale.
