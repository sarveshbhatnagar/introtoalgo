A concert has one ticket left. Two fans press "buy" in the same 10 ms. Both requests read remaining = 1, both charge a card, both write remaining = 0. Two people paid for one seat, and the database reported no error. Each request was correct alone; the bug is how they overlapped.

The idea

A transaction groups reads and writes into one unit. ACID names its four promises:

  • Atomic: all writes happen, or none. A crash halfway leaves nothing behind.
  • Consistent: your rules hold before and after. Mostly your job; constraints like UNIQUE and CHECK (stock >= 0) help.
  • Isolated: concurrent transactions do not see each other's half-done work. The isolation level sets how strictly.
  • Durable: committed data survives a crash; it is in a log on disk, often on replicas too.

Stricter isolation means more waiting or retries. Choose the weakest level that stops your races.

Snapshot gives each transaction a frozen view as of its start. Some databases abort a transaction whose row changed underneath it; others let the later write win, so check yours. Serializable means the result equals some one-at-a-time order, at the cost of more aborts to retry.

Stopping a lost update

-- read: title = 'Draft', version = 7
UPDATE docs
SET    title = 'Final', version = 8
WHERE  id = 42 AND version = 7;
-- 1 row updated: you won.
-- 0 rows updated: someone wrote first. Re-read and retry, or show a conflict.

For write skew, make the transactions collide on purpose: lock something both touch, such as the team row (SELECT … FOR UPDATE on teams), before counting admins, or run that transaction as serializable.

Across services: 2PC and sagas

An order touches the orders database, payments and inventory. No one transaction spans them.

Two-phase commit (2PC) adds a coordinator. First every participant prepares: does the work, holds locks, promises to commit. If all vote yes, the coordinator says commit; otherwise abort. It is atomic, but if the coordinator dies after "prepare", participants hold their locks until it returns.

A saga gives up atomicity: a chain of local transactions, each publishing an event that triggers the next. If a step fails, compensating actions undo earlier steps: refund the card, release the seat. Others can see middle states ("paid, not yet reserved"), so design for them.

Each step must update its database and publish an event; a crash between two separate writes loses one. The outbox pattern writes the event into an outbox table in the same local transaction, and a relay publishes outbox rows afterwards.

Across services, default to a saga with outboxes and idempotent consumers. Use 2PC only for a few databases that support it, in one data center, when a visible in-between state is unacceptable.

Numbers worth remembering

  • A short transaction on one database: about 1 to 10 ms. Locks held that long are cheap; across a network call or user think time, they are not.
  • 2PC: at least two round trips per transaction, plus a durable log write at each step.

In the interview

Bring this up when two users can change the same thing (stock, seats, balances) or one action spans services. Name the race, then the fix: "Two buyers can read the same stock, so I decrement with a conditional update."

Orders, payments and inventory are separate services. How do you keep them consistent? A saga, not a distributed transaction. Each service commits locally and publishes through an outbox, so a crash cannot lose the event. If inventory fails after payment, payment refunds. Consumers dedupe by order id, since events can arrive twice. It names what the outbox prevents and what the dedupe handles. The user sees "paid" and then "cancelled". Is that okay? That is the cost of a saga. I would reserve stock before charging, so the common failure happens before money moves.

Follow-ups:

  • "What if the compensation fails?" Retry it; it must be idempotent. After several failures, alert a human.

Common mistakes

Reading a counter, adding one in code and writing it back is the lost update. Do the arithmetic in the database, or check a version.

Many databases default to read committed. Write skew and lost updates pass through it silently.
