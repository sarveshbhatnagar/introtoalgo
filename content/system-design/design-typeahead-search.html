You type "pi" into a search box and a list drops down: "pizza near me", "pie crust recipe", "pilates". Each keystroke is a request, the answer must beat the next keystroke, and the list must reflect what millions of people search for.

The obvious answer, a trie on a server, is half right. The real work is precomputing answers offline and spending a 100 ms budget across the client, the network and an edge cache. The steps follow A Framework for Any Design. If tries are new, read Tries first.

Clarify the problem

Design the autocomplete for a search box. Do we suggest past queries ranked by popularity, not documents? How many? Past queries by popularity. Show five. How fresh must popularity be? And are suggestions personal? A day is fine; trending within an hour would be nice. Not personalised. How many users, and how fast? 50 million daily users, about 6 searches each. It should feel instant. I'll take "instant" as under 100 ms from keystroke to list for most users. English first, prefix matches only, no spelling correction, and offensive suggestions removable quickly. Turning "instant" into 100 ms gives the design a budget to spend. "A day" of freshness allows an offline build.
  • Functional: for a prefix, return the 5 most popular past queries starting with it, weighted to recent searches; bad suggestions can be removed.
  • Non-functional: under 100 ms for most users; very high availability (an empty list is the fallback, the search box never breaks); popularity at most a day old, trending within an hour as a stretch.
  • Out of scope: personalisation, spelling correction, other languages, searching documents (see Search Systems).

Estimate the scale

  • Searches: 50 million × 6 = 300 million a day.
  • Suggestion requests: a 20-character query could send 20 requests, but people pick a suggestion early, the client skips quick bursts of keystrokes (debouncing), and its cache answers repeats. Assume 6 per search: 1.8 billion a day, 1.8 × 109 ÷ 86,400 s ≈ 21,000 a second. With a 3x peak, about 62,500 a second.
  • Query log: 300 million × 100 bytes ≈ 30 GB a day for the offline build.

Write the suggestion endpoint. What makes it cacheable by a CDN?

A plain GET with the prefix in the query string and a Cache-Control header, nothing personal, and a prefix normalised by the client (lowercase, trimmed) so equal prefixes share one cache entry.

Define the API

GET /v1/suggest?q=pi&limit=5
  200 OK
  Cache-Control: public, max-age=3600
  { "q": "pi", "version": "2026-11-14",
    "suggestions": ["pizza near me", "pie crust recipe", "pilates",
                    "pineapple upside down cake", "piano lessons"] }

  q is empty            200 with an empty list
  q longer than 50      400 Bad Request
  service overloaded    503; the client shows no list and the user keeps typing

The decision worth arguing is making the response public and cacheable. No cookie, no user id: everyone typing "pi" in the same hour hits one cached response at the edge. A user id would make every response unique and kill the cache. The cost is no personalisation in the API; the client merges your recent searches instead. A one-hour max-age is fine for data rebuilt daily.

What do the serving and offline sides each store? Which is read 62,500 times a second?

Serving holds one read-only table, prefix → five best suggestions, rebuilt each build. Offline holds daily query counts, read only by the build. The hot path never computes anything.

Model the data

-- serving: read-only, rebuilt each build, held in memory on every server
prefix_top5
  prefix       VARCHAR(20)   PRIMARY KEY   -- "pi"
  suggestions  [ (query, score) x 5 ]       -- about 150 bytes a row with the key
  version      DATE

-- offline: written by the log pipeline, read only by the build
query_counts
  query        VARCHAR(100)
  day          DATE
  count        BIGINT
  PRIMARY KEY (query, day)

blocklist      -- queries and patterns never to suggest; small, edited by people

Serving is a single-key lookup on a table that never changes between builds: an in-memory hash map loaded from a file on every server, with no database on the hot path. If it outgrew memory, the next step is a key-value store partitioned by prefix. The offline counts are large, append-only and scanned in bulk, so they belong in files in blob storage or a data warehouse.

Sketch two paths: a keystroke that becomes a list, and a search that later changes the list. Where do caches sit?

Read path: the client's cache, a CDN edge, then identical suggest servers holding the table in memory. Write path: searches are logged; a batch job counts and ranks them and writes a versioned table to blob storage; servers load it and swap. The paths share only that file.

High-level design

Deep dives

A trie, or a precomputed top five per prefix

A trie puts all queries starting with "pi" under one node, reached in one step per character. The trap: the subtree under "p" may hold a million queries, too many to search per keystroke. Search once, at build time, and store each node's top five on it.

The 30 GB bound fits in memory, so every server holds the whole map, unsharded. If it stops fitting, shard by prefix hash, never by first letter: far more queries start with "s" than "x".

Updating popularity offline

Counting on the hot path means a write per search and re-sorting up to 20 prefix lists. Do it in a daily batch instead.

Weight each day's count by 0.8 per day of age. A query searched 1,000 times a week ago scores 1,000 × 0.87 ≈ 210; one searched 300 times today scores 300 and ranks higher. Also drop rare queries (mostly typos and private details like names or addresses) and anything blocklisted.

The latency budget and where caching happens

Light in fibre travels about 200 km per millisecond, so a server 6,000 km away costs at least 2 × 6,000 ÷ 200 = 60 ms per round trip. A plan for a user near an edge:

StepBudget
Wait for a pause in typing (debounce)30 ms
Round trip to a nearby edge15 to 30 ms
Edge to suggest server and back, on a miss30 ms if the region is near
Lookup on the serverunder 1 ms
Draw the list10 ms

An edge hit lands at 55 to 70 ms, a miss to a nearby region at 85 to 100 ms, a miss to a far region blows the budget. Caching does most of the work:

  • In the client. Keep every response for the session, so backspacing costs nothing. Drop out-of-order replies whose prefix no longer matches the box. If the "pi" list had fewer than five entries, it is complete: filter it for "piz" without asking.
  • At the edge. Short prefixes are few and hot: only 26 + 262 + 263 = 18,278 letter prefixes of up to three characters. Assume the edge answers 60%: 62,500 a second at peak becomes 25,000 at the servers. See CDNs.
  • On the server. The table is already in memory.

Run suggest servers in several regions so misses stay near.

Bottlenecks and failures

At 10x (625,000 requests a second at peak), the edge takes 60%, leaving 250,000 a second. Suggest servers share nothing; at an assumed 10,000 a second each (the HTTP stack, not the lookup, is the limit), that is 25 servers plus spares. The build is the slower wall: 300 GB of log a day needs a distributed batch job split by query. Many languages get a table each, sharded by prefix hash when one outgrows memory.

Collecting and sorting everything under a short prefix is slow, and short prefixes are the most frequent requests. Precompute the top five per prefix.

LevelWhat the answer does
JuniorSearches a trie per request; updates counts on each search.

SeniorTurns "instant" into a 100 ms budget and spends it; makes responses edge-cacheable on purpose; builds versioned tables offline with decay and filtering; removes bad suggestions at serve time; sizes the table and skips sharding.
An offensive suggestion is showing for a common prefix. How fast can you remove it? Within about a minute. Each server refreshes the blocklist every minute and filters results at serve time. The edge may hold the old response for an hour, so I'd purge that prefix from the CDN. App copies go when the session ends. The next build drops the query for good. Filtering only at build time takes a day. The strong answer knew where every copy of the data lives.

Follow-up questions

How would you personalise suggestions?

The client stores the user's recent searches and puts matches first; the shared path stays cacheable.

How do you show trends within an hour?

A stream job compares each query's last-hour count with its usual rate and publishes spiking queries every few minutes. Servers merge them in at serve time, and the edge TTL drops to a few minutes for short prefixes.

How do you handle typos?

Fuzzy matching per keystroke is expensive. Mine misspellings from the logs (typed X, then searched Y) and add them as prefixes pointing to Y's list.

What about other languages?

A table per language, chosen by locale, which joins the cache key. Normalisation (accents, scripts without spaces) lives in one library shared by build and client.

Why not use a search engine's prefix queries?

Fine for a small catalogue. At 62,500 requests a second, ranking per query costs far more than a map lookup for answers that change daily.
