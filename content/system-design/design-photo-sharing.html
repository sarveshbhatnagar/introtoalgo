A photo sharing app lets users upload photos with a caption, follow other users, and scroll a feed of the newest photos from the people they follow. It also shows a profile grid for each user and lets people like posts. Instagram is the usual example.

The design is hard because the system stores two very different kinds of data. Photos are large, never change and are read constantly, so they belong in object storage behind a CDN. Metadata such as posts, follows and likes is tiny and changes constantly, and accounts with millions of followers create hot spots. Interviewers ask this to see whether you keep the two apart and can handle a viral post. The steps follow A Framework for Any Design, and the feed itself is covered in Design a News Feed.

Clarify the problem

Design a photo sharing app. I'll assume users can upload a photo with a caption, follow people, see a feed, view a profile grid, and like posts. Are comments, stories, video or direct messages in scope? Leave out stories, video and messages. Likes are in scope. How many users are there, and how uneven are the follower counts? Assume 200 million daily users and about 50 million new photos a day. Most people have a few hundred followers, but some accounts have 50 million. Then almost all of the bytes are images. I'll treat a posted photo as something we must never lose, and I'll allow the feed to be a few seconds stale and the like counts to be approximate. Separating what must never be lost from what may be stale shows where strong consistency is worth paying for and where it is not.
  • Functional: upload a photo with a caption, follow and unfollow users, show a home feed with the newest posts first, show a profile grid, and like and unlike posts.
  • Non-functional: a photo is never lost once the user has posted it, the feed loads in under 200 ms, images appear within about a second, a post reaches followers within 10 seconds, and reads stay available when parts of the system fail.
  • Out of scope: video, stories, messages, search, ads and feed ranking.

Estimate the scale

A day has 86,400 seconds, and peak traffic is assumed to be three times the average.

  • Uploads: 50 million photos a day is about 580 photos a second on average and about 1,700 at peak.
  • Feed loads: at 10 app opens per user per day, 2 billion feed loads a day is about 23,000 a second.
  • Bytes per photo: a 2 MB original plus three resized copies of 30 KB, 120 KB and 250 KB, which is 2.4 MB in total.

Write the endpoints for uploading and posting a photo, reading the feed, following a user and liking a post. Say where the image bytes travel.

The client asks the API for a signed URL, sends the bytes directly to object storage, and then creates the post. The feed returns metadata with CDN URLs, so image bytes never pass through the API servers.

The decision worth arguing is that creating a post returns 202 with the status processing. The API servers never saw the image bytes, so no post is usable until a worker has checked the file and produced the resized copies. Follow and like are PUT requests, so repeating one after a timeout has no extra effect.

Sketch the records for posts, follows and likes. Choose a partition key for each one and say which reads it serves.

Posts are partitioned by author and sorted by a time-ordered id. Follows are stored in both directions, and likes are partitioned by the user who liked, with a separate count per post.

Model the data

posts               PRIMARY KEY ((author_id), post_id)   -- post_id DESC
  author_id   BIGINT
  post_id     BIGINT      -- 64-bit, time-ordered
  photo_id    VARCHAR(16)
  caption     TEXT        -- up to 2,200 chars
  status      VARCHAR(10) -- processing | ready | failed | deleted
  width, height, image_version INT

followers           PRIMARY KEY ((followee_id, bucket), follower_id)
following           PRIMARY KEY ((follower_id), followee_id)

photos              PRIMARY KEY (photo_id)
  post_id     BIGINT NULL, processed BOOLEAN           -- see "upload"

likes               PRIMARY KEY ((user_id), post_id)     -- did I like it?
like_counts         PRIMARY KEY (post_id)
  count BIGINT,  last_offset BIGINT                     -- see "hot posts"

Every read asks for the rows under one key, newest first, and no query joins tables. That access pattern fits a wide-column store such as Cassandra, which partitions data by key, keeps the rows of a partition sorted, and handles a high write rate.

Post ids come from a time-ordered ID generator, so sorting by id is the same as sorting by time and a cursor simply means "posts older than this id". The store keeps 3 replicas and uses a quorum of 2 for both reads and writes. Because 2 + 2 is greater than 3, every read overlaps with the latest acknowledged write.

Sketch the boxes. Where do the bytes go on upload, what makes the three sizes, where are images served from, and when does a post reach followers?

Bytes go to a photo store, and its upload event wakes resize workers, which mark the post ready and trigger fan-out. A CDN serves the images and the API serves only metadata.

High-level design

Deep dives

Uploading photos safely

Sending photos through the API servers ties up a connection for as long as a slow mobile network takes and makes the API fleet carry every image byte. A signed URL avoids that: the API checks the request and returns a URL that allows one upload to one key, with a maximum size and content type, for a short time, and the phone sends the bytes directly to the photo store. See Blob Storage.

Those bytes skipped your code, so the client could upload something that is not an image. The post therefore stays in the status processing until a worker has decoded the file. A file that does not decode is deleted and the post is marked failed. A cleanup job deletes posts that stay in processing for 24 hours, and a storage rule deletes originals that no post refers to.

The worker can also finish before the post request arrives and find no post to mark as ready. To handle this, both sides write to the photo's row in the photos table with a compare-and-set. The post request sets post_id only if it is empty, which also produces the 409 for a reused photo, and the worker sets processed. Whichever write lands second marks the post ready and starts fan-out, so fan-out runs exactly once.

Creating the resized copies

Phones need small images, so each photo is stored in several sizes, and the question is when to create them. Creating every size eagerly after upload means each size exists before anyone views the photo, but the post is delayed by a few seconds and adding a size later means reprocessing every photo. Creating sizes on demand at the edge allows any size and wastes nothing on unviewed photos, but the first viewer waits and a viral post sends a burst of resize work to the origin. Shrinking on the phone saves server CPU, but the result cannot be trusted, so it only supplements server-side processing.

Eager resizing at 0.2 CPU-seconds per photo needs about 120 cores on average (580 × 0.2) and about 340 at peak (1,700 × 0.2). Scale the workers on queue depth, which is what delays posts.

Serving images from the CDN

Each image URL contains the photo id, the size and a version, for example /p7001/t.v1.jpg. The content behind a URL never changes, so the CDN can cache it for a year. If a photo is processed again, the worker writes v2 and the post points to the new URL, so nothing has to be purged. A regional origin shield, a CDN layer in front of the store, turns hundreds of edge locations missing on a new photo into one request to the store. See CDNs.

Choosing the partition key for posts

The key has to serve a profile grid (one author's posts, newest first) and a feed page (10 posts from different authors).

By post id. Posts spread evenly, and a feed page is 10 direct lookups, but one author's posts are scattered, so a profile grid needs a second table kept in step. By author, sorted by post id. A profile grid is one partition read, and a feed entry that stores the author id as well as the post id still needs only 10 lookups. The cost is heavy reads on a famous author's partition, which is a caching problem because posts never change. By day. Archiving is easy, but all writes and all reads of fresh posts hit today's partition.

Follows are written twice, in followers and following, because the two questions need different partitions. Fan-out asks who follows Mia, and pulling posts from big accounts asks whom Leo follows. A follower list of 50 million entries at 16 bytes each is 800 MB, which is too large for one partition. The followers table therefore adds a bucket number for every 1 million followers.

Hot posts and like counts

When an account with 50 million followers posts, four different things become hot. The image is handled by the CDN, so three remain.

Fan-out. Writing 50 million feed entries at 200,000 inserts a second takes 250 seconds, which is far over the 10-second goal. Use the hybrid from the news feed design: for accounts above about 100,000 followers, do not push the post into feeds, and let each follower's feed fetch it at read time.

The post record. If 20% of the followers open the post within an hour, that is 10 million reads over 3,600 seconds, or about 2,800 reads a second for one key. The post never changes, so cache it.

Likes. If 5% of the followers like the post within 10 minutes, that is 2.5 million likes over 600 seconds, or about 4,200 likes a second on one post.

The simplest design keeps a counter in the post row and runs count = count + 1 on every like. All 4,200 writes a second then compete for the lock on one row, and the row becomes the bottleneck. Splitting the counter into several rows spreads the writes, but every read must sum them.

The third option is to batch the updates. The likes table is partitioned by the user who liked, so those writes spread evenly. Each like is also sent to a stream partitioned by post id. The aggregator that owns a partition counts the likes it receives for one post over one second and then writes count = count + n once, so 4,200 updates a second become one update a second. This is the design to propose, because the like records stay exact and only the displayed count lags by about a second.

The stream delivers each event at least once, so after a crash the aggregator may see the same events again. To avoid counting them twice, the aggregator stores the stream offset of the last event it applied in the same row and in the same write as the count, and it ignores any event at or below that offset. A nightly recount from the likes table repairs other drift.

Bottlenecks and failures

At 10 times the load (500 million photos a day) the problems are bytes and cost. Storage grows by about 440 PB a year, so originals move to cold storage after 30 days. Image traffic averages 280 GB/s, which makes the CDN the largest cost. The resize fleet grows to about 1,200 cores on average and 3,400 at peak.

What a strong answer sounds like

Interviewers watch whether image bytes stay out of the API servers, whether the partition key follows from the access patterns, and whether you can say what happens to a viral post.

Why partition posts by author? Doesn't that create hot spots? Partitioning by author makes a profile grid one sorted partition read, and because feed entries carry the author, a feed page can still fetch its posts directly. The hot spot is reads of a famous author's posts, but those posts never change, so caches absorb the reads. Likes are partitioned by the user who liked, and the counts are updated in batches. The answer ties the key to an access pattern, admits the cost, and fixes it with a tool that fits because the data does not change.

Follow-up questions

A user deletes a photo. What has to happen?

First mark the post deleted, so that every read skips it immediately. Then delete the stored objects and purge the CDN in the background.

The phone retries a post after a timeout. Do you get two posts?

No. The client sends an idempotency key with the request, so the second request returns the post that the first one created. The 409 response also prevents the same photo from being attached to two different posts.

How would you add content moderation?

Add a second consumer of the upload events that scores each image. Flagged posts stay out of feeds until a reviewer approves them. Posts already wait until they are ready, so moderation is one more condition.
