Your public API is sized for 3,000 requests a second in total. One customer's script has a retry bug and sends 2,500 a second alone. Latency climbs for everyone and the database times out. Nobody was malicious; the client just had no ceiling.

The idea

Pick a key (API key, user id or IP), count its requests over time, and reject those over the limit with 429 Too Many Requests and a Retry-After header. Limits protect capacity and fairness, enforce plans, and slow attacks such as password guessing.

The cost: a check per request, shared state across servers, and rejected good traffic if the limit or key is wrong.

Five ways to count

  • Fixed window. One counter per key per minute, reset each minute. Edges leak: with a limit of 100 a minute, a client can send 100 at 0:59 and 100 at 1:00.
  • Sliding window log. Store each request's timestamp, drop those older than a minute, count the rest.
  • Sliding window counter. Weight last minute's count by its overlap with the last 60 seconds. Limit 100, 80 last minute, 30 so far, 15 seconds in: 30 + 80 × 45/60 = 90, so the request passes.
  • Token bucket. A bucket holds up to capacity tokens and refills at rate a second. A request takes a token or is rejected.
  • Leaky bucket. Requests join a queue drained at a fixed rate; when it is full, new ones are rejected.

A token bucket, step by step

Capacity 5, refill 1 token a second. No timer refills the bucket: each request computes how many tokens arrived since the last.

class TokenBucket {
  constructor(capacity, ratePerSec) {
    this.capacity = capacity;
    this.rate = ratePerSec;
    this.tokens = capacity;   // start full
    this.last = 0;            // time of the last refill
  }

  allow(now) {
    const elapsed = now - this.last;
    this.tokens = Math.min(this.capacity, this.tokens + elapsed * this.rate);
    this.last = now;
    if (this.tokens >= 1) {
      this.tokens -= 1;
      return true;
    }
    return false;
  }
}

class TokenBucket:
    def __init__(self, capacity, rate_per_sec):
        self.capacity = capacity
        self.rate = rate_per_sec
        self.tokens = capacity   # start full
        self.last = 0            # time of the last refill

    def allow(self, now):
        elapsed = now - self.last
        self.tokens = min(self.capacity, self.tokens + elapsed * self.rate)
        self.last = now
        if self.tokens >= 1:
            self.tokens -= 1
            return True
        return False

Where the limiter lives

  • At the edge, by IP: cheap flood protection.
  • At the API gateway, by API key or user: plan quotas and fairness. The usual answer.
  • Inside a service: guarding one dependency, like a payment provider capped at 50 calls a second.

Counting across many servers

Ten gateway nodes counting alone let a limit of 100 a minute become 1,000. Three fixes:

  • A central counter store, an in-memory store such as Redis. Exact, but adds a hop (about 0.5 ms) and a dependency. Check and update must be atomic (see the mistakes).
  • Split the limit: each of 10 nodes allows 10 a minute. No shared state, but right only if each client's traffic spreads evenly.
  • Local counts, synced every second. Fast; overshoots by what slips through between syncs.

Use the central store for quotas, local counters for floods. If the store is down, fail open (allow everything) for a general API, so a limiter outage is not a full outage. Fail closed, or use strict local limits, for login and other attack targets.

Numbers worth remembering

  • Token bucket: two numbers, about 16 bytes, per key.
  • Sliding log: 8 bytes per request in the window, per key.

In the interview

Mention a rate limit for a public API, an expensive endpoint, or a third party with limits. Name the key, algorithm and response: "Per API key, token bucket of 100 with a refill of 10 a second, enforced at the gateway with counters in a shared store, returning 429 with Retry-After."

How would you stop one customer from overloading the API? A per-API-key token bucket at the gateway: brief bursts, capped average, two numbers per key. With several gateway nodes, counters live in a shared in-memory store and check-and-take is atomic. And if that store goes down? Fail open, each node falling back to a local limit of total ÷ node count. Inexact limits beat rejecting everyone. It names key, algorithm, placement, race and failure mode, where a weak answer stops at "add a rate limiter".

Follow-ups to expect:

  • "Why not limit by IP?" Offices and mobile networks share IPs, and attackers rotate them. Use IP before login, the account or key after.
  • "And across regions?" Each region gets its own counter store and a share of the limit. A global store adds a cross-region round trip to every request.
  • "What should a client do with a 429?" Wait for Retry-After, then back off with jitter.

Common mistakes

If two nodes both read 99 and both write 100, the client got 101. Use an atomic increment, or a small script that refills and takes a token in one step.
