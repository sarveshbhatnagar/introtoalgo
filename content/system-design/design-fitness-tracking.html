You start a run and lose signal on a forest trail for 40 minutes. When you stop, the app shows your route, pace and climb. Back on Wi-Fi it uploads, and friends see it in their feed.

The hard part is not the server. Data is born on a phone, often offline, so a late, repeated or half-finished upload must be safe. Around that sit trace storage, live location and a social feed. The steps follow A Framework for Any Design. Try each "Your turn" box before reading on.

Clarify the problem

Design a fitness tracking app, for runs and bike rides. The core: record an activity with GPS, see its stats, share it to friends' feeds. Must recording work with no signal? Is there live tracking, where a friend watches me move? Yes to both. Recording must work fully offline. Live sharing is opt-in, mostly for safety. Scale? Activities a day, their length, typical follower counts? About 10 million activities a day, 45 minutes on average. Most users have tens of followers; a few pro athletes have millions. Then the top priority is never losing an activity or storing it twice, despite bad networks and retries. A feed a minute behind is fine; live positions at most about 15 seconds old. I'd skip heart-rate sensors, training plans and payments. Segment leaderboards? In outline. The candidate finds the real risk, data born offline, and makes it a requirement: no loss, no duplicates.
  • Functional: record with GPS offline; upload when online; show stats (distance, time, pace, climb) and a map; a feed of followed people's activities; share a live position; segment leaderboards in outline.
  • Non-functional: an activity is never lost or duplicated; recording never needs the network; feeds within about a minute of upload; live positions at most about 15 seconds old; activity pages under 300 ms.
  • Out of scope: sensors beyond GPS, training plans, payments, messaging.

Estimate the scale

  • Points per activity: one a second for 45 minutes: 45 × 60 = 2,700. At about 20 bytes each (time, latitude, longitude, altitude, accuracy): 54 KB raw.
  • Uploads: 10 million ÷ 86,400 ≈ 116 a second. Weekend mornings bunch up; assume a 5x peak, about 580 a second.
  • Feed writes: 50 followers per activity: 10 million × 50 = 500 million entries a day, about 5,800 a second.
  • Live sharing: 50,000 people at peak, an update every 15 seconds: about 3,300 writes a second. Small.

Write an upload call the phone can retry any number of times without creating two activities. Add the feed and live-sharing calls.

The phone makes the id when recording starts and uploads with PUT /activities/{id}; a repeat is a no-op. The feed is a paginated GET; live sharing is a small POST of recent points and a GET for viewers.

Define the API

PUT  /activities/{activity_id}           id = UUID made on the phone at start
  headers: Content-SHA256: 9c1e...
  body: compressed trace file + { "type": "run", "title": "...", "visibility": "followers" }
  201 Created     { "activity_id": "a7f3...", "status": "processing" }
  200 OK          same id, same file: already stored, returns the same activity
  409 Conflict    same id, different file (a bug on the phone; never overwrite)

GET  /activities/{activity_id}           stats, simplified route line, segment efforts
GET  /feed?cursor=...&limit=20           friends' activities, newest upload first

POST /live                               start sharing   -> { "live_id": "lv_81", "viewer_link": "..." }
POST /live/{live_id}/points              batch of the last 15 s of points
GET  /live/{live_id}                     latest position + short trail, for viewers
  200 { "pos": [...], "updated_at": "...", "ended": false }

The decision worth arguing is who creates the id. With an id made on the phone at the start, the upload is a PUT to a known name, and every retry lands on the same record: an idempotency key born before any network call.

No resumable uploads: a 10-hour ride is 36,000 points × about 4 compressed bytes ≈ 144 KB, so retry the whole file.

Where do GPS points live, and what goes in the database? Think about what each screen reads.

One compressed file per activity in object storage, read whole. One summary row per activity with stats and a simplified route line for feed cards. Feeds hold activity ids. Live positions are short-lived in-memory keys.

Model the data

activities                              -- partitioned by user_id
  activity_id   UUID PRIMARY KEY        -- made on the phone
  user_id       BIGINT
  file_sha256   CHAR(64)                -- detects "same id, different file"
  trace_key     TEXT                    -- "traces/u42/a7f3-9c1e.gz": id + hash
  status        VARCHAR(12)             -- processing | ready | failed
  started_at    TIMESTAMP               -- from GPS time, not the phone clock
  uploaded_at   TIMESTAMP
  distance_m, moving_s, climb_m INT
  route_line    TEXT                    -- about 100 points, for cards and thumbnails
  visibility    VARCHAR(10)             -- only_me | followers | everyone

follows         (follower_id, followee_id)       -- both directions indexed
feed_items      (user_id, uploaded_at, activity_id)   -- ids only, newest first
segment_efforts (segment_id, user_id, elapsed_s, activity_id)   -- every effort
segment_bests   (segment_id, user_id, elapsed_s)   -- index (segment_id, elapsed_s)

live:{live_id}  -> last 20 points, expires 10 min after the last update

A trace is written once and read whole, so it is a file in object storage. Feeds, profiles and stats pages read the summary row: 10 million × 2 KB = 20 GB a day, about 7 TB a year, so the table is partitioned by user_id, since "my activities" is the commonest query. Relational or wide-column both work; the unique key on activity_id is what matters.

Sketch the path from "the phone gets signal" to "a friend sees the run". Which steps happen before the phone's answer, and which after?

Before: store the file, insert the row if absent, publish an "uploaded" event. After: workers compute stats, match segments and fan out to feeds. Slow work after the answer keeps uploads quick and retries cheap.

High-level design

The upload does the minimum that makes the activity safe, then answers; retryable workers do the rest.

Deep dives

Recording offline and syncing

The phone is the source of truth until the server confirms. Four rules:

  • Write locally first. GPS needs no data connection. Points go to an append-only local file, flushed every few seconds; a killed app reopens it and continues.
  • Name it at the start. The phone makes a random UUID when recording starts.
  • Upload from a queue. A local queue retries with growing delays. The phone deletes a file only after a 200 or 201.
  • Make every server step repeatable. File key includes its hash; row inserted only if absent; feed entries keyed by follower and activity.

With a server-made id, a lost reply leaves two bad choices: retry and maybe duplicate, or give up and maybe lose the run. Deduplicating by "same user, same start time" is fragile. Make the id on the phone, before any network call.

A subtler race: the user edits the title on the website while the phone still queues the old one. Send edits as separate small updates; the upload never overwrites a field edited on the server.

Storing GPS traces

Every reader takes a trace whole; nobody asks for "point 1,734 of activity a7f3".

Delta encoding makes the file small: consecutive points are metres apart, so storing differences turns 4-byte coordinates into a byte or two. Keep the original upload beside the cleaned version, so better cleaning code can recompute.

Live sharing

Live sharing is a separate, lossy path that can never break recording.

The phone sends the last 15 seconds of points while still writing its local file. The live service overwrites a key holding the latest 20 points, and viewers poll every 15 seconds: 3,300 writes a second and a few times that in reads, easy for one in-memory store with a replica. For a few viewers at a 15-second rate, polling is simpler than push (see realtime communication).

The safety detail interviewers like: show how old the position is. If the runner loses signal, the viewer sees "last update 6 minutes ago", not a dot that looks current.

The friends feed

The mechanics match Design a News Feed: fan-out on write into per-user id lists, fan-out on read for the few athletes with millions of followers. What differs:

  • Posts arrive late. A Saturday run may upload on Monday. Order by upload time so friends see it, and show the activity date on the card.
  • Fan-out waits for processing. The card needs distance and the route line, so fan out after stats are ready.
  • Visibility changes after fan-out. Feeds store ids only; the read path drops activities the reader may not see, so making a run private takes effect at once.
  • Privacy zones. Users hide the few hundred metres near home. Apply it when making the route line, so no public copy holds the real endpoints.

Segment leaderboards, in outline

A segment is a named stretch of road or trail. A worker finds segments in the map cells the trace crosses, checks the trace passes the start, follows it and reaches the end, and records the time between as an effort. Each board keeps every athlete's best time, smallest first. Design a Leaderboard covers ranking at scale; most boards are small enough for an index on (segment_id, elapsed_s).

Bottlenecks and failures

At 10x (100 million activities a day, 5,800 uploads a second at peak), the stateless activity service scales out, object storage absorbs about 400 TB a year, and the table adds partitions. The first real strain is feed fan-out: 5 billion entries a day, about 58,000 a second. Lower the follower count above which posts are fetched on read, and let fan-out lag a little at peaks.

Publish first, and a failed insert leaves a worker processing a missing activity; commit first, and a crash before publishing leaves it unprocessed. Commit, then publish, with a sweeper for rows left in processing, or write the event in the row's transaction (an outbox table) and relay it.

The upload reply times out. What does the phone do? It retries the same PUT /activities/a7f3. The id was made at the start, so the server either creates the activity or finds it and returns 200, and only then does the phone delete its copy. Every step behind it is repeatable. What if two phones upload the same run, a watch and a phone? Different ids, so we store two. I'd detect overlap after processing, same user and mostly the same time range, and ask the user which to keep rather than guess.

Follow-up questions

The phone's clock is wrong. Does it matter?

Use each point's GPS time, which is accurate, for pace and ordering. The phone clock is for display only; the server sets uploaded_at.

How do you handle GPS noise?

Drop points with poor accuracy, reject jumps implying impossible speed, and smooth the rest. Compute distance from the cleaned line; raw noise adds distance on every wiggle.

How would you show a heatmap of popular routes?

A nightly batch job reads public traces from object storage, counts passes per small map cell, and renders tiles. It never touches the live path.

How do you delete an account?

Delete the rows and trace files, and remove feed entries in the background. Readers already drop missing activities, so feeds look right at once.

Can you tell a cyclist from a runner logging a ride as a run?

Flag activities whose speed does not fit the type, such as a "run" with long stretches at 35 km/h, and keep them off running boards until the user confirms.
