A ticket booking system lets people browse events, choose seats on a seat map, pay, and receive tickets. Its central rule is that each seat is sold to exactly one buyer, and everyone who pays must end up with a ticket or a refund.

Interviewers ask this question because three hard problems appear together: several buyers can try to take the same seat at once, demand for a popular event arrives in one spike, and a seat must stay reserved for minutes while the buyer pays. The steps below follow A Framework for Any Design.

Clarify the problem

Design a ticket booking system for concerts and sports. Are the seats assigned, like row C seat 12, or is it general admission with no specific seat? The seats are assigned, and fans choose them from a seat map. How big is the largest on-sale, in seats and in people arriving at the same time? The biggest shows have about 50,000 seats and two million people waiting when sales open. The platform sells about 5 million orders a month. Then the normal load is small and the on-sale is the real problem. My priorities are that no seat is sold twice, that we never take money without giving a ticket, and that the site stays up during the spike, even if people have to wait in a line. I will also assume a fan gets about ten minutes to pay after choosing seats. Ranking correctness above speed, and saying that a waiting line is acceptable, shapes the whole design.

Functional requirements:

  • Fans can browse events, see a live seat map, hold seats for a few minutes, pay, and receive tickets.
  • Seats that are held but never paid for are released automatically.

Non-functional requirements:

  • A seat is never sold twice, so inventory needs strong consistency, and a paid order always ends with tickets or a refund.
  • The system stays available when demand is about 80 times the supply of seats.
  • A hold lasts 10 minutes.

Out of scope: resale, dynamic pricing, event creation and scanning tickets at the door.

Estimate the scale

On a normal day, 5 million orders a month is 5,000,000 ÷ 2,600,000 seconds, about 2 orders a second. Browsing at 100 times that is 200 reads a second, which one database handles easily. The numbers that matter are the ones for an on-sale.

A 50,000-seat show sells about 25,000 orders at 2 seats per order, so with two million people waiting there are about 80 fans for every order. If each of those fans refreshed the page every 5 seconds without any control, the load would be 2,000,000 ÷ 5 = 400,000 requests a second, all aimed at the same 50,000 seat rows. Storage is small, so the difficulty is contention on a few rows and not size. If waiting fans check their place every 10 seconds, two million fans send 2,000,000 ÷ 10 = 200,000 requests a second, which is far too much for a database, so the waiting room must answer without one.

Write the endpoints to join the line, load the seat map, hold seats and pay. What should come back when the seats have already been taken?

Joining returns a place in line, holding seats creates an order with an expiry time, and paying confirms it. When seats are gone, the error should include current availability so the fan can choose again.

The API decision worth arguing about is the waiting-room status endpoint. The server publishes a single number per event, such as "admitted up to 40,500", and each fan compares it with the position in their own ticket. Every fan receives the same small response, so a CDN that caches it for one second absorbs nearly all of the 200,000 requests a second.

The pay endpoint uses an idempotency key, the order id, so a double-click or a client retry never charges the card twice.

Sketch the records for seats and orders. How can a hold disappear on its own if the fan walks away?

Store the hold on the seat row as a status, the holding order and a held_until time. The claim query treats an expired hold as free, so no background job has to run for the hold to lapse.

Claiming two seats must succeed or fail as a unit, so the inventory belongs in a relational database with transactions, partitioned by event_id when one machine is not enough. A key-value store can do a conditional write on one row, but it cannot claim two seats atomically.

The hold is stored in the seat row instead of being a database lock, because a database lock lasts for milliseconds while a fan takes minutes to pay.

Sketch the boxes. Where do fans wait, what checks that they were admitted, where does the seat map come from, and where are holds and sales written?

A waiting room served from a CDN, a gateway that checks a signed pass, a booking service in front of a seat map cache and the inventory database, and a payment processor.

High-level design

Deep dives

Preventing double booking

Suppose two requests for C-13 arrive within a millisecond of each other. If each one reads the seat as available and then writes it as held, both succeed and the seat is sold twice, so the database has to make exactly one of them fail. There are three ways to do that, and a fourth that moves the hold out of the database. The mistake to avoid in all of them is checking in one statement and writing in another, because the check and the write must be one atomic step.

Pessimistic locking. The transaction runs SELECT … FOR UPDATE on the seat rows, which makes every other transaction that touches those rows wait. It then checks the status and writes. This works when a decision needs several reads, but buyers queue behind the lock, so the transaction must be short and must never stay open while a fan decides or pays.

Optimistic version check. Each row has a version number. The code reads the row, and later writes with WHERE version = 7, so the write changes nothing if another transaction wrote first, and the code retries. This is good when conflicts are rare, but during an on-sale most attempts hit the same rows, so most writes fail and retry.

Conditional update. A single UPDATE statement claims the seats only if they are free, and the caller checks how many rows changed. It takes one round trip, and the row lock lasts only for that statement. It fits whenever the rule can be written in a WHERE clause, as it can for claiming a known set of seats.

Holds in an in-memory store. A store such as Redis can create a hold with "set if absent, expire in 10 minutes", which is fast and expires on its own. It is a second source of truth, though: if a failover loses a recent write, two fans can hold one seat, so the database must still confirm the sale.

I would choose the conditional update, because it needs one round trip and no lock is held while anyone is thinking. The seats are claimed like this:

BEGIN;
UPDATE seats
   SET status = 'held', order_id = 9001,
       held_until = now() + interval '10 minutes'
 WHERE event_id = 77 AND seat_id IN ('C-12', 'C-13')
   AND (status = 'available'
        OR (status = 'held' AND held_until < now()));
-- rows changed = 2: COMMIT.  fewer than 2: ROLLBACK and report 409.
COMMIT;

This is safe because the second transaction to update a row waits for the first one's row lock. At the read-committed level in databases such as PostgreSQL, it then re-checks its WHERE clause, sees the seat is held, and changes nothing. At repeatable read or serializable it fails with a serialization error, which you treat like a 409. Databases differ here (see transactions and isolation), so name the isolation level you rely on. Two orders that claim overlapping seats in opposite order can deadlock, and sorting the seat ids before claiming avoids that.

Surviving the on-sale spike

Adding booking servers does not help, because all 50,000 seats live in one partition and more servers only send it more conflicting writes. Returning a 429 error to the excess traffic protects the database, but it rewards whoever retries fastest, which usually means bots. A virtual waiting room limits how many fans reach booking and gives the rest a fair place in line.

The waiting room works in five parts:

  • When a fan joins, they receive a number in a signed ticket. Numbers handed out before 10:00 are shuffled at 10:00, so arriving early at the page gains nothing, and after that numbers are assigned in order of arrival.
  • While waiting, the browser reads only the cached "admitted up to N" value, so 200,000 checks a second cost almost nothing.
  • A controller keeps at most 10,000 fans in the booking flow and raises N as orders complete or passes time out. The database therefore sees about 33 new fans a second, however large the crowd is.
  • An admitted fan exchanges their ticket for a signed 15-minute pass tied to their account, and the gateway verifies it without any shared state.
  • When no seat is available or held, the event is announced as sold out and waiting fans are told at once.

The seat map cache is rebuilt about once a second. The map is only advice and the conditional update is the source of truth, so a stale map costs a fan one 409 and never causes a double sale.

Holds, payment and releasing seats

Most bugs in a booking system live between "held" and "sold". Storing the hold in the seat row, with an expiry time, means an abandoned hold becomes claimable without any cleanup, because the claim query already treats it as free. The cleanup job only refreshes the seat map and the order status.

The second problem is that a hold must outlive the payment. If a hold lapses at 10:31:04 and the charge succeeds at 10:31:05, another fan may already have claimed the seat. So when the fan presses pay, the order moves to paying and held_until is extended beyond the longest time the processor can take. The sale then runs as UPDATE seats SET status = 'sold' WHERE order_id = 9001 AND status = 'held' and must change both rows. If it does not, the order is refunded automatically.

The third problem is that a timeout is not a failure. After a timeout the charge may still have succeeded, so the order stays in paying, the booking service asks the processor for the result using the idempotency key, and only then sells or releases the seats. Design a Payment System covers this in more detail.

Bottlenecks and failures

If demand grows 10 times to twenty million fans, the waiting room answers 2 million checks a second for one cached number, which is a CDN problem and not a database problem. The booking side does not change, because the admission cap fixes its load. When many big on-sales overlap, partition the inventory by event_id so each show has its own partition.

Two million people arrive at 10:00. What do you do? All of that demand lands on one event's rows, so I cannot scale it out. I would use a waiting room that admits about 33 fans a second and keeps 10,000 in the booking flow. It publishes only an "admitted up to N" number, so the 200,000 checks a second are served by a CDN. Why not just return a 429 when you are overloaded? That protects the database, but it rewards whoever retries fastest, which is usually bots. A line is fairer to real fans and gives the database a predictable load.

Follow-up questions

How would you handle general admission?

Keep a count of remaining tickets per section and decrement it with a conditional update such as SET remaining = remaining - 2 WHERE remaining >= 2. All claims then wait for the lock on that one row, so split the count across about 10 rows and have each request try a random row that still has tickets.

How do you stop bots from buying everything?

Allow one place in line per verified account and add a challenge when joining the line.

A group wants six seats together. What changes?

Offer a "best available" option in which the booking service searches for six adjacent free seats and claims them with the same all-or-nothing update. If one was taken in the meantime, fewer than six rows change, so it rolls back and searches again.

Could you push seat changes to the map instead of polling?

Yes, with server-sent events. That reduces 409 responses, but it adds 10,000 open connections and a fan-out for every seat change. A map that is one second stale does little harm, so I would add push only if fans see too many 409s.
