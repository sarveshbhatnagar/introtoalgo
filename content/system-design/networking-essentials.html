Your server builds the product page in 30 ms. A shopper 8,000 km away still waits about 270 ms for the first byte, and that is with the address already cached. Almost 90% of that wait is three trips across the ocean and back.

Interviewers rarely ask about packets, but where that time goes decides where servers live and whether you need a CDN.

The idea

For small requests, distance costs more than bandwidth. You pay in round trips: a message out, a reply back. Light in fibre covers about 200 km per millisecond, so a round trip over 8,000 km takes at least 2 × 8,000 ÷ 200 = 80 ms. Real routes bend, so that is a lower bound.

A fresh HTTPS request needs three round trips before the first byte comes back: one to open the connection, one to set up encryption, one for the request. That is 3 × 80 = 240 ms, plus 30 ms on the server: the 270 ms from the hook. Most tricks in this module cut round trips or shorten them.

What happens when you open a URL

So the address in DNS should belong to something that survives one machine dying, such as a pair of load balancers sharing a floating IP.

Four layers, briefly

DNS turns a name into an IP address, and every layer caches the answer for the record's TTL. GeoDNS returns a different address depending on where the resolver is, which is how users reach the nearest region.

TCP gives a reliable, ordered byte stream: lost packets are resent and bytes arrive in order. The price is the handshake and head-of-line blocking: one lost packet holds up everything behind it. UDP has no handshake and no guarantees. Use it when late data is worthless (voice, video calls, game state) and let the app handle loss.

TLS encrypts the connection and proves the server's identity. TLS 1.3 takes one round trip to set up; the older TLS 1.2 takes two. Most designs terminate TLS at the load balancer, so app servers do not each manage certificates.

HTTP is request and response: method, path, headers, body, status code. HTTP/1.1 sends one request at a time per connection. HTTP/2 runs many requests as streams over one TCP connection, though a lost packet still stalls them all. HTTP/3 runs over QUIC, which is built on UDP: streams are independent and connection plus encryption setup takes one round trip.

HTTP, gRPC or WebSockets

The default to say: "REST over HTTPS for clients, gRPC between services." Change your mind on the client side when the server must push; Realtime Communication compares the push options.

Numbers worth remembering

  • Light in fibre: about 200 km per ms, so every 1,000 km adds at least 10 ms of round trip.
  • Round trip inside one data center: about 0.5 ms. Across a continent (4,000 km): 40 ms or more. Across an ocean (8,000 km): 80 ms or more.
  • New HTTPS connection: 3 round trips to the first byte with TLS 1.3, 4 with TLS 1.2. Reused connection: 1.
  • 1 Gbit/s is 125 MB/s, because a byte is 8 bits.

In the interview

Bring networking up when distance matters: users on several continents with a latency target, mobile clients, or a feature where the server pushes. Phrases that show judgement: "Every round trip costs at least 80 ms from there, so I want fewer round trips, not faster servers." "TLS ends at the load balancer." "Clients get REST, services talk gRPC."

Users about 8,000 km from our only region say the app is slow. What do you do? First I'd check where the time goes. If the server takes 30 ms but users wait a second, it's round trips: each costs at least 80 ms from there, and a new connection plus a few sequential API calls adds up fast. So what's the fix? Cheapest first: static files on a CDN, connections terminated at edge locations near users so handshakes are short, and one batched call for the home screen instead of five. If that's not enough, a read replica region near them, since most of this traffic is reads. It measures first, counts round trips and orders fixes by cost. A weak answer says "add more servers", which does nothing for distance.

Follow-ups to expect:

  • "TCP or UDP for a video call?" UDP, or a protocol built on it. A late frame is useless, so resending it only adds delay.
  • "Is traffic behind the load balancer encrypted?" Inside a private network it often is not. If compliance or a zero-trust policy asks for it, re-encrypt to the servers or use mutual TLS between services, at some cost in CPU and certificates.
  • "Why not fail over by changing DNS?" Cached answers live until the TTL runs out, sometimes longer. DNS moves traffic between regions over minutes; it does not survive a machine failure.

Common mistakes

A screen that makes 5 API calls one after another, at 80 ms per round trip, waits 400 ms before any server work. Call in parallel, or add one endpoint that returns what the screen needs.

A changed record moves nobody until cached answers expire. Lower the TTL a day before a planned move, and never rely on DNS alone to route around a dead machine.
