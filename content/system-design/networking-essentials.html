Your server builds the product page in 30 ms. A shopper 8,000 km away still waits about 270 ms for the first byte, even with DNS cached. Almost 90% of that is three trips across the ocean and back.

Where that time goes decides where servers live and whether you need a CDN.

The idea

For small requests, distance costs more than bandwidth. You pay in round trips: a message out, a reply back. Light in fibre covers about 200 km per millisecond, so a round trip over 8,000 km takes at least 2 × 8,000 ÷ 200 = 80 ms (real routes bend, so more).

A fresh HTTPS request needs three round trips: open the connection, set up encryption, send the request. 3 × 80 = 240 ms, plus 30 ms on the server, is the 270 ms above. Most tricks in this module cut or shorten round trips.

Four layers, briefly

  • DNS turns a name into an IP address, cached at every layer for the record's TTL. GeoDNS answers by the resolver's location, sending users to the nearest region.
  • TCP gives a reliable, ordered byte stream. The price is the handshake and head-of-line blocking: one lost packet holds up everything behind it. UDP has neither handshake nor guarantees; use it when late data is worthless (voice, video calls, game state).
  • TLS encrypts the connection and proves the server's identity: one round trip to set up with TLS 1.3, two with 1.2. Most designs terminate TLS at the load balancer, so app servers need no certificates.
  • HTTP/1.1 sends one request at a time per connection. HTTP/2 runs many streams over one TCP connection, though a lost packet stalls them all. HTTP/3 runs over QUIC, built on UDP: streams are independent and setup with encryption takes one round trip.

Numbers worth remembering

  • Every 1,000 km adds at least 10 ms of round trip.
  • Round trip in one data center: about 0.5 ms. Across a continent (4,000 km): 40 ms or more. Across an ocean (8,000 km): 80 ms or more.
  • First byte on a new HTTPS connection: 3 round trips with TLS 1.3, 4 with TLS 1.2. Reused connection: 1.
  • 1 Gbit/s is 125 MB/s, because a byte is 8 bits.

In the interview

Bring networking up when distance matters: users on several continents, a latency target, mobile clients, or server push. Say: "Every round trip costs at least 80 ms from there, so I want fewer round trips, not faster servers."

Users about 8,000 km from our only region say the app is slow. What do you do? First I'd check where the time goes. If the server takes 30 ms but users wait a second, it's round trips: at least 80 ms each, and a new connection plus sequential API calls adds up fast. So what's the fix? Cheapest first: static files on a CDN, connections terminated at edge locations near users, and one batched call for the home screen instead of five. If that's not enough, a read replica region near them, since most traffic is reads. It measures, counts round trips and orders fixes by cost. "Add more servers" does nothing for distance.

Expected follow-ups:

  • "TCP or UDP for a video call?" UDP, or a protocol built on it. Resending a late frame only adds delay.
  • "Is traffic behind the load balancer encrypted?" Often not. If policy requires it, use mutual TLS between services.
  • "Why not fail over by changing DNS?" Cached answers live until the TTL runs out. DNS shifts traffic between regions over minutes, too slowly for a machine failure.

Common mistakes

Five API calls one after another, at 80 ms per round trip, wait 400 ms before any server work. Call in parallel, or add one endpoint that returns what the screen needs.

A changed record moves nobody until cached answers expire. Lower the TTL a day before a planned move.
