Ana in New York books a weekly Monday 9:00 meeting with Ben in London and Chen in Singapore. It reaches their phones in seconds at the right local time, reminds them ten minutes before, and stays at 9:00 for Ana after the March clock change.

The boxes are ordinary; the data is not. "Every Monday, forever" cannot be rows, local time is not UTC, and "when are these eight people free?" touches eight shards. The steps follow A Framework for Any Design; try each "Your turn" box before reading on.

Clarify the problem

Design a calendar service like those in office suites. I'll assume the core is events, invites with replies, repeating events, free/busy for finding a slot, and reminders. Do we include meeting rooms or other providers' calendars? Rooms are people with a calendar. Skip other providers. How many users, and how many meetings each? 100 million users, 50 million active each day, about four meetings a day each. Then reads dominate and reminders burst on the hour. Priorities: a saved event is never lost and shows on my devices at once; invitees may see it seconds later; no reminder skipped or over a minute late; every occurrence at the right local time. Separating what must be instant (your write) from what may lag (others' copies) decides the design.
  • Functional: create, edit and delete events; invites and replies; repeating events with per-occurrence changes; day, week and month views; free/busy for many people; reminders; sync to every device.
  • Non-functional: durable, read-your-writes for the owner; attendees see changes within 5 seconds; week view under 200 ms; reminders within 60 seconds, never skipped; correct local times.
  • Out of scope: other providers, video calls, room rules beyond "a room has a calendar".

Estimate the scale

A day has 86,400 seconds; assume peaks of 3 times the average.

  • Writes: 2 a day per active user: 100 million ÷ 86,400 ≈ 1,200 a second, 3,500 at peak.
  • Reads: 20 a day per active user: 1 billion ÷ 86,400 ≈ 12,000 a second, 35,000 at peak.
  • Free/busy: if half the 50 million daily new events use the scheduling view, about 870 lookups a second at peak; at 5 people each, 4,300 per-person lookups.
  • Reminders: 50 million × 4 meetings = 200 million a day, about 2,300 a second on average.

Write endpoints to create, read a week, edit one occurrence, reply, query free/busy and sync. How does a client avoid overwriting another edit?

Times are local time plus a zone name. Reads take a window and return occurrences. Edits carry the version (If-Match) and a scope: this, following, or all. Sync is "changes since token".

The decision worth arguing is who expands repeating events. The view endpoint expands on the server, so a web page gets plain occurrences. Sync sends the raw rule and exceptions, so a phone can expand any month offline. Both must share one expansion library, or they disagree on edge cases.

Sketch the records. How do you store "every Monday, forever" with one Monday cancelled and another moved? How do you find Ben's events this week with one index lookup?

The rule once, plus exceptions keyed by original start. Each attendee gets an entry on their own shard with the event's span ("forever" is a far-future date), so one index on the span's end finds every event.

Model the data

events                       -- on the organizer's shard
  event_id      BIGINT PRIMARY KEY
  organizer     BIGINT
  title, description, location   TEXT
  start_local   TIMESTAMP        -- 2027-03-01 09:00, no zone attached
  tz            VARCHAR(40)      -- "America/New_York"
  duration_min  INT
  rrule         TEXT NULL        -- "FREQ=WEEKLY;BYDAY=MO"
  version       INT

exceptions                   -- one row per changed occurrence
  event_id, original_start       PRIMARY KEY
  cancelled     BOOLEAN
  new_start_local, new_duration, new_title   NULL = unchanged

entries                      -- one per attendee, on THEIR shard
  calendar_id, event_id          PRIMARY KEY
  span_start_utc, span_end_utc   -- span_end = 9999-12-31 if no end
  start_local, tz, duration_min, rrule, title   -- copied from the event
  exceptions    JSON             -- copied, plus this person's own declines
  response      VARCHAR(10)      -- needs-action | accepted | declined
  reminders     JSON
  INDEX (calendar_id, span_end_utc)

changes                      -- per calendar, for device sync
  calendar_id, seq               PRIMARY KEY
  event_id, op

The hot read is "Ben's events overlapping this week": WHERE calendar_id = ? AND span_end_utc > week_start AND span_start_utc < week_end. The index skips everything that ended earlier, so years of history cost nothing; what remains is this week's events plus a few dozen open-ended series to expand. Entries copy the times, rule and exceptions, so the read stays on Ben's shard.

A relational database, sharded by calendar, fits: an edit changes event, exceptions and change log in one transaction, and the read is an indexed range scan.

Sketch where an edit is written, how it reaches attendees and devices, and where free/busy and reminders live.

One transaction on the organizer's shard, then a change stream to workers that update attendees, nudge devices and plan reminders. Free/busy reads a per-person cache.

High-level design

Deep dives

Repeating events and time zones

"Every weekday at 9:00, no end date" has infinitely many occurrences. Storing years of them hurts the moment someone edits the series.

Store the rule in iCalendar RRULE format, the start as local time plus a zone, and exceptions keyed by the original start time, which stays fixed even when the occurrence moves. Ana's March 2027, with March 8 cancelled and March 22 moved to 10:00:

Original start (New York)ExceptionUTCBen in London
Mon Mar 1, 09:00none14:0014:00
Mon Mar 8, 09:00cancellednonenone
Mon Mar 15, 09:00none13:0013:00
Mon Mar 22, 09:00moved to 10:0014:0014:00
Mon Mar 29, 09:00none13:0014:00

Edit scopes map to the data: "this occurrence" adds an exception; "all" changes the series row; "this and following" ends the old rule before that occurrence and starts a new series. Reads cap the window at a year, bounding expansion.

Look at the UTC column. Ana's 9:00 moves an hour in UTC when New York changes clocks on March 14, 2027. London changes on March 28, so for two weeks Ben sees 13:00. That is correct, and it only happens if you expand in the event's own zone, then convert.

  • Repeating events store a zone name such as America/New_York, never an offset like −05:00, which is right for only half the year.
  • All-day events are dates with no zone: a March 3 birthday is March 3 everywhere.
  • Missing and doubled times: 2:30 on spring-forward night does not exist; 1:30 on fall-back night happens twice. Use one rule everywhere, such as iCalendar's: move a missing time forward by the gap, take the first of a doubled one.
  • The rules change. Governments change daylight saving at short notice. A time zone database update fixes future occurrences on the next expansion; rebuild anything derived in UTC for that zone.

Storing 14:00 UTC and adding 7 days looks fine until March 15, when Ana's 9:00 meeting shows at 10:00 New York time. Repeat in local time; convert last.

Free/busy for many people

Chen asks when Ana, Ben and five others are free next week: seven shards, each with series to expand. The answer needs only busy intervals: free/busy reveals when, not what.

The lookup reads 7 entries in parallel, merges sorted intervals (the intervals pattern) and returns gaps in working hours. The cache is 100 million × 3.6 KB ≈ 360 GB, a modest cluster; seconds of lag is fine for suggesting slots.

Reminders at scale

A repeating event has no last reminder, so use a rolling horizon on a job scheduler:

  • Plan: a daily planner expands each calendar's next 48 hours; fan-out workers add changes inside that window. Jobs are keyed by (calendar, event, original start, offset), so planning twice creates one job.
  • Re-check on fire: drop the reminder if the event was cancelled, moved or declined; no hunting for jobs.
  • Survive the burst: the scheduler loads each minute's jobs a minute early and hands them to the notification system, built for bursts of 100,000 a second.
  • Use the device: a synced phone raises the alarm itself, so a server outage does not silence most reminders.
  • Duplicates: jobs run at least once. A "sent" record per job key catches most; a rare double beats a missed meeting.

Edits from many devices

Every edit sends If-Match with its starting version; a conditional update applies it only if unchanged. A stale edit gets 412 and the current event; the client merges field by field and retries, or asks the user if both changed one field.

Devices sync from the per-calendar change log. Each change takes the next number from a per-calendar counter in the same transaction, so numbers commit in order and "everything after 1,042" misses nothing; that number is the sync token. Rows older than about 30 days are trimmed; an older token gets 410 and a full resync. A lost push just waits for the next app open.

Bottlenecks and failures

At 10x (35,000 writes and 350,000 reads a second at peak), add servers and read replicas (owners read their own calendar from the primary) and split shards. The real pain is a huge guest list: a 50,000-person all-hands is 50,000 entry writes per edit. Above about 1,000 guests, give each guest a pointer row, written once, and read times from the shared event: the hybrid a news feed uses for celebrity accounts.

Follow-up questions

How do you book a meeting room without double booking?

A room is a calendar that auto-accepts if nothing confirmed overlaps. Check and accept run in one transaction that bumps the room's change counter, so two bookings cannot interleave; the loser is declined.

How do invites to people at other companies work?

By email with an iCalendar attachment; replies come back the same way, matched by the event's unique ID and sequence number.

An attendee declines one occurrence. Where is that stored?

As an exception on that attendee's entry, keyed by original start; the shared event is untouched.
