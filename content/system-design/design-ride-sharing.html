You tap "Request" on a street corner. Seconds later the app shows a driver two minutes away, and a little car moves toward you. Behind it, a million drivers report their position every few seconds, and the system must find the right one near you and make sure no other rider gets the same car.

It has three hard parts that request-and-response designs lack: writes far above reads, searching by location, and riders racing for the same driver. The steps follow A Framework for Any Design.

Clarify the problem

Design a ride-sharing service. I'll focus on the core: request, match a nearby driver, follow the trip on a map. Are pricing, payments and shared rides in scope? No. Another team quotes the price. How many drivers online at peak, and rides a day? About a million drivers at peak, 10 million rides a day. Then my priorities: a driver is never assigned to two riders, a match takes a few seconds, and map positions are at most a few seconds old. Losing a location update is fine; losing a trip record is not, because we bill from it. Locations are disposable; trips are not. That one sentence shapes the storage for the whole design.
  • Functional: drivers report location; riders request rides; a nearby driver accepts or declines an offer; both see progress live; trips move through clear states and can be cancelled.
  • Non-functional: no driver on two trips (strong consistency for assignment); match within about 5 seconds; locations at most about 5 seconds stale; durable trip records; matching survives a location node dying.
  • Out of scope: payments, pricing, shared rides, ratings, onboarding.

Estimate the scale

  • Location updates: 250,000 writes a second at peak (below); at about 100 bytes each, 25 MB/s.
  • Ride requests: 10 million ÷ 86,400 s ≈ 116 a second; about 350 at a 3x rush-hour peak. Writes outnumber matches about 700 to 1.
  • Latest positions: 1 million × 100 bytes = 100 MB. The live map fits in one machine's memory.
  • Trip history: a 20-minute trip with a point every 4 seconds has 1,200 ÷ 4 = 300 points, 30 KB. 10 million × 30 KB = 300 GB a day, about 110 TB a year.
  • Riders watching a car: 5 minutes waiting plus 20 riding gives 10 million × 25 ÷ 1,440 ≈ 174,000 watchers, each updated every 4 seconds: about 43,000 pushes a second.

Write the driver's location update, the rider's request, and how an offer reaches a driver and is accepted. How do the apps stay connected?

Drivers keep a persistent connection: locations up, offers down. Riders create a trip with an idempotency key. Accepting names the offer ID, so a late accept is refused and a repeat is harmless.

Define the API

Driver connection (WebSocket), app -> server:
  location { lat, lng, heading, speed, sent_at }      every 4 s, no reply
  status   { "available" | "offline" }

Driver connection, server -> app:
  offer { offer_id, trip_id, pickup, expires_in_s: 15 }
Driver connection, app -> server:
  accept { offer_id }
    -> accepted { trip }  |  refused: offer expired or already answered

POST /v1/trips   Idempotency-Key: 7f3a...
  body { pickup, dropoff, quote_id }
  202 { trip_id, state: "MATCHING" }
POST /v1/trips/{id}/cancel     200 | 409 trip already completed
Rider connection, server -> app: trip state changes, driver position

The decision worth arguing is how location updates travel. An HTTP request every 4 seconds from a million phones is 250,000 requests a second, each with headers and often a new connection. A persistent connection carries small messages cheaply, and the server needs it anyway to push offers. Locations get no reply and no retry: the next one, 4 seconds later, is fresher than a retry. The realtime communication lesson covers the connection servers behind this.

Which data is disposable and which must be durable? Sketch where driver positions, driver status and trips live.

Latest positions are disposable: in memory, indexed by map cell, expiring if a driver goes quiet. Driver status decides assignments, so it needs conditional writes. Trips are the durable record in a database.

Model the data

-- in memory, sharded by region; rebuilt from updates within seconds
driver_pos:  driver_id -> { lat, lng, cell, updated_at }   expires after 30 s
cell_index:  cell -> set of available driver_ids

-- durable, strongly consistent per row
drivers:     driver_id PK, state,        -- offline | available | offered | on_trip
             offer_id NULL, trip_id NULL, version INT
trips:       trip_id PK, rider_id, driver_id NULL, state, pickup, dropoff,
             created_at, updated_at, version INT

-- append-only, partitioned by trip_id
trip_points: (trip_id, sent_at) PK, lat, lng

Three stores for three kinds of data. Positions: an in-memory store (such as Redis); nothing lost there that the next update will not restore. Driver status and trips: a relational database or any store with per-row conditional writes, because correct assignment depends on "update only if the state is still X". Trip points: a high-volume append-only log read by trip ID, suiting a wide-column store (such as Cassandra).

Draw the location and ride request paths. Where does matching read, and where does it write?

Driver updates flow through a driver gateway into an in-memory geo index. A request goes to a trip service; a matching service reads candidates from the geo index and claims one with a conditional write on the driver's row. The offer goes out through the gateway.

High-level design

Deep dives

Location updates at 250,000 a second

Each update replaces the last, so live positions need no durability, history or replicas, only a fast overwrite. If a geo index node dies, its drivers reappear within 4 seconds on the replacement. Say that out loud; it is why this part can be simple.

Shard the geo index by region, so a ride request touches one shard. Most updates do not change cell: at 50 km/h a car covers 50 ÷ 3.6 × 4 ≈ 56 metres between updates, and a cell is about 600 metres across, so it changes cell at most once every 10 or so updates.

Only trip points need durability. For drivers on trips, the gateway appends each point to a stream feeding the trip-points store and the rider's screen: a fraction of the 250,000 a second.

Finding nearby drivers

Computing the distance to a million drivers is slow. Divide the map into cells, keep a set of available drivers per cell, and look only at cells near the pickup.

A geohash interleaves the bits of latitude and longitude in base 32, so each extra character makes the cell 32 times smaller. (Cells narrow east-west away from the equator; the numbers above ignore that.)

The trap is the neighbour-cell problem. A rider near a cell's edge may have the nearest driver 50 metres away, across the border, in a cell with a completely different string. Always search the cell plus its 8 neighbours: 9 × 1.2 × 0.6 ≈ 6.5 km². Too few drivers? Step out a ring or to a coarser precision. Straight-line distance is only a filter: a driver 300 metres away across a river may be 10 minutes out, so rank the top few by driving time from a routing service.

Matching without double assignment

Two riders across the street both see D7 as closest. If both matchers read "available" and both write "assigned", D7 gets two trips. This read-then-write race is the part interviewers care about most.

UPDATE drivers
SET    state = 'offered', offer_id = 'o-981', version = version + 1
WHERE  driver_id = 'D7' AND state = 'available';
-- 1 row updated: we own the offer.  0 rows: someone else got there first.

Quorum reads and writes alone do not make "read, check, write" atomic: two clients can each read "available" from a quorum before either writes.

The offer is a lease with a 15-second expiry. Accepting is two conditional writes in a fixed order, not one transaction: the driver row (offered to on_trip, only if the offer is live), then the trip (MATCHING to DRIVER_ASSIGNED, only if still matching). If the trip write fails because the rider cancelled, release the driver. After a crash between the two, the app retries the accept with the same offer_id, and a sweeper releases any driver whose trip_id points at a trip that is not theirs.

The trip state machine

Many actors can change a trip at once: the rider cancels as the driver accepts, a timeout fires as the driver taps "arrived". Allow only these moves:

FromToTriggered by
MATCHINGDRIVER_ASSIGNEDdriver accepts a live offer
MATCHINGNO_DRIVERSno accept within 60 seconds
DRIVER_ASSIGNEDDRIVER_ARRIVEDdriver taps "arrived" near the pickup
DRIVER_ARRIVEDIN_PROGRESSdriver starts the trip
IN_PROGRESSCOMPLETEDdriver ends the trip
any state before IN_PROGRESSCANCELLEDrider or driver cancels

Each move is a conditional update on (trip_id, state, version). If cancel and accept land together, exactly one finds the expected state; the other gets a conflict and the app shows the true state. Changes are published as events from the database's change log, so none is lost, and drive both apps and billing.

The geo index is a fast, slightly stale copy: use it to find candidates, never to assign. Claim in the driver-state store with a condition, or sooner or later two riders get the same car.

Bottlenecks and failures

At 10x (2.5 million updates a second) the geo index needs smaller regional shards; a dense city may split by cell prefix. Update throughput, not memory, is the limit. Matching grows to about 3,500 requests a second at peak; partition driver state by region so claims stay local.

What a strong answer sounds like

LevelWhat the answer does
JuniorPositions in a database table queried by distance; handles the race once it is pointed out.
MidEstimates the update rate, keeps positions in memory, uses geohash cells and their neighbours.
SeniorSeparates disposable positions from durable assignments; claims with a conditional write and names the store guarantee; models a trip state machine; ranks by driving time.
Two matchers pick the same driver. What happens? Both try the same conditional update: set offered only if still available. The store applies them one at a time on that row, so one gets "1 row updated", the other 0, and it moves on. That needs a single authority for the row, a leader or a consensus group. A store that merges writes from several replicas later would let both succeed, so driver state does not go there. The answer names the mechanism and the store property it depends on. "Use a lock" would invite a question about lock expiry.

Follow-up questions

How would you do surge pricing?

Count open requests and available drivers per cell every minute and publish a multiplier per area. The pricing team owns the formula; we supply fresh counts.

How do you estimate arrival time?

A routing service over the road graph with live traffic: a shortest-path search like Dijkstra's algorithm with heavy precomputation. Call it only for candidates that pass the straight-line filter.

Could you match better by waiting?

Yes. In dense areas, batch requests for a second or two and assign them together to minimise total pickup time.

How do riders see the car move smoothly?

The server pushes a position every 4 seconds and the app animates between points along the road.

What if a driver's GPS jumps a kilometre?

Reject updates that imply an impossible speed, and snap positions to roads before matching or billing.
