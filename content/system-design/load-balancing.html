Launch day: the API expects 3,000 requests a second at peak, and one app server handles about 1,000 before latency climbs. So you need at least three servers. But clients know one address, and when a server crashes mid-afternoon, something has to stop sending it traffic.

The idea

A load balancer owns the public address and picks one of many identical servers for each request or connection. That gives capacity (add servers behind it) and availability (a dead server leaves the pool).

It costs an extra hop (under a millisecond in a data center), one more component that must not fail, and a rule: any server must handle any request ("stateless").

Spreading requests and surviving a crash

Run four servers, not three, so losing one still leaves enough. Each gets 3,000 ÷ 4 = 750 requests a second.

Active health checks call an endpoint on a timer, as above. Passive checks watch real traffic and eject a server that errors or times out, which is faster.

Choosing a server

With a plain hash % n, going from 4 to 5 servers moves about 4 keys in 5; consistent hashing fixes that.

Sticky sessions and stateless servers

If server A keeps your shopping cart in memory, every request from you must reach A. Balancers can do that with sticky sessions, usually a cookie naming the server. But load gets uneven, and when A dies its carts are gone.

Better: stateless servers, with session data in a shared store (such as Redis) or a signed token the client sends. Any server handles any request, and a crash loses nothing.

When the balancer is the weak point

One balancer is a single point of failure. The usual fix is the pair in the first diagram: active and standby share a virtual IP, and the standby takes it when heartbeats stop. At larger scale, run several active balancers behind DNS with several addresses, or one address announced from many places (anycast). Managed cloud balancers do this already; say so rather than drawing it.

A reverse proxy receives requests for servers: it terminates TLS, compresses and caches. A layer 7 balancer is a reverse proxy that spreads load; an API gateway adds authentication, rate limiting and routing by path to different services. One box labelled "API gateway / load balancer" is fine.

Numbers worth remembering

  • Worst-case detection time is check interval × failures needed: 5 s × 2 = about 10 s.
  • Servers: peak ÷ per-server capacity, rounded up, plus at least one spare.

In the interview

Draw a load balancer as soon as you have two servers, and name the choices: "Layer 7, round robin, health checks every few seconds, and stateless app servers with sessions in a shared store, so I can scale them freely."

Users keep getting logged out. Why might that be? Sessions probably live in each server's memory, and the balancer sends the next request elsewhere. I'd move them to a shared store, so any server can read them and a restart loses nothing. Stickiness can stay as a cache-warmth hint. It fixes the cause. "Turn on sticky sessions" would patch the symptom: a deploy or crash would still log users out.

Expected follow-ups:

  • "What if the load balancer dies?" A standby takes over its virtual IP (see above).
  • "How do you deploy without dropping requests?" Take a server out of the pool, let in-flight requests finish (draining), update it, put it back.
  • "WebSockets behind a balancer?" Least connections, and expect clients to reconnect when a server goes away.

Common mistakes

Three servers for a load that needs three: one crash overloads the other two, and they fall over too. Add spare capacity for the failure you expect.

If /health fails whenever any dependency is slow, one shared hiccup marks every server down at once. Check only that this server can work; dependencies get their own alarms.
