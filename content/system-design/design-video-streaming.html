Someone uploads a 10-minute video from a phone on a shaky train connection. Minutes later it plays in full HD on a TV, and on a phone in a lift that drops to lower quality for a few seconds instead of freezing.

The bytes dominate everything. One popular video moves more data in an hour than the metadata database handles in a year, so split the two: a small, careful system for titles and status, and a huge, dumb, cached system for bytes. The steps follow A Framework for Any Design.

Clarify the problem

Design a video streaming service. Uploads and on-demand playback, or live too? Search and recommendations? Uploads and on-demand playback only. How many uploads a day, how long, and how much do people watch? About 100,000 uploads a day, 10 minutes on average. 50 million daily viewers, about 30 minutes each. Then playback is the system: start in about 2 seconds, rarely stall. Uploads must survive bad connections. Most of the cost will be bandwidth, so I'll design around the CDN. "Most of the cost will be bandwidth" is a senior instinct, stated before any numbers.
  • Functional: resumable upload; processing into formats every device plays; playback that adapts to the network; title, status and view count.
  • Non-functional: playback starts in about 2 seconds, stalls rarely and is highly available; videos ready within minutes; uploads never lost; metadata eventually consistent (a view count can lag).
  • Out of scope: live streaming, search, recommendations, comments, copy protection.

Estimate the scale

  • Concurrent viewers: 50 million × 30 minutes ÷ 1,440 minutes ≈ 1 million on average; 2 million at a 2x evening peak.
  • Uploads: 100,000 ÷ 86,400 s ≈ 1.2 a second. At 1 GB per original: 100 TB a day, about 1.2 GB/s in.
  • Processed copies: five qualities, 240p to 1080p, at 0.4 + 0.8 + 1.5 + 3 + 6 = 11.7 Mbit/s together. For 10 minutes: 11.7 × 106 × 600 ÷ 8 ≈ 0.88 GB per video, about 88 TB a day.
  • Storage per year: (100 + 88) TB × 365 ≈ 69 PB before replication; rarely read originals go to cheaper storage.
  • Metadata: 36.5 million new rows a year at about 1 KB: 36.5 GB. Tiny.

Write upload endpoints where a drop at 90% does not mean starting over, and the player's playback calls.

Upload in three steps: start a session, send numbered chunks, complete. A status call lists arrived chunks so the client resumes. Playback is one metadata call, then plain file requests for a manifest and segments that a CDN can cache.

Define the API

POST /v1/uploads   { "filename", "size_bytes", "sha256" }
  201 { "upload_id", "chunk_size": 8000000, "chunk_urls": [signed URLs...] }
PUT        (8 MB of bytes, goes straight to object storage)
  200 { "etag" }    400 checksum mismatch
GET  /v1/uploads/{id}        -> { "received": [0..111] }   resume from here
                                (the API asks storage which parts landed)
POST /v1/uploads/{id}/complete      safe to repeat: same video_id
  202 Accepted { "video_id", "status": "processing" }
  409 Conflict   chunks missing

GET  /v1/videos/{id}  -> { title, status, duration_s, "manifest_url" }
GET  cdn/v/{id}/master.m3u8             manifest: the qualities on offer
GET  cdn/v/{id}/720p/seg_00042.ts       one 4-second segment

The decision worth arguing is where the bytes go. Proxying 1.2 GB/s through API servers ties each up for minutes. Instead the API hands out signed URLs: short-lived links that let the client write one chunk directly to object storage. The cost: the API never sees the bytes, so at complete storage confirms every part's checksum, and the split job, which reads the whole file anyway, verifies the sha256. complete returns 202 because the video is not playable yet.

List the records for videos, uploads and processing work. Which belong in a database and which are files?

Video rows, upload sessions and transcode jobs are small: a database. Originals, segments and manifests are files in object storage, keyed by video ID. Never put video bytes in a database.

Model the data

videos:   video_id BIGINT PRIMARY KEY, owner_id BIGINT, title TEXT,
          status TEXT,          -- uploading | processing | ready | failed
          duration_s INT, renditions TEXT, jobs_left INT, created_at TIMESTAMP
uploads:  upload_id, video_id, size_bytes, storage_upload_id, expires_at
          -- which parts arrived is asked of object storage, not stored here
jobs:     job_id, video_id, segment_no INT, rendition TEXT,
          status TEXT, attempts INT, lease_until TIMESTAMP

-- object storage keys
originals/{video_id}
v/{video_id}/master.m3u8, v/{video_id}/{rendition}/index.m3u8
v/{video_id}/{rendition}/seg_{n}.ts

The metadata is small, relational and read-heavy: a relational database with read replicas. It gives an atomic counter: each finished job decrements jobs_left, and the job that reaches 0 writes the manifests, then sets ready. Batch view counts through a queue, as in the URL shortener's click counting, so a viral video does not turn one row into a hot spot.

Draw the upload path and the playback path. Which boxes see video bytes?

Bytes flow client to object storage, to transcoders and back, and out through the CDN to viewers. The API, database and job queue only see IDs and status. That split is the design.

High-level design

Deep dives

Chunked, resumable upload

A single 1 GB PUT that fails at 90% throws away 900 MB, and on a phone it will fail. Split it into 125 chunks of 8 MB, each uploaded and checksummed on its own, so a failure costs only the chunks in flight. Object storage offers this as a multipart upload: parts arrive in any order and a final call joins them.

Too small a chunk (256 KB) means 4,000 requests, each paying a round trip; too large (100 MB) means a retry on a slow phone takes minutes. 4 to 16 MB is a sound middle; I'd pick 8 MB. Expire unfinished sessions after a day or two so abandoned parts do not pile up.

Transcoding as a queue of jobs

Phones record in formats many devices cannot play and networks cannot carry, so each upload becomes five qualities: about 100 CPU-minutes for a 10-minute video. On one machine, the uploader waits over an hour and a half.

A 4-second segment takes 4 ÷ 60 × 10 CPU-minutes = 40 CPU-seconds for the whole ladder. With 150 workers free, the video takes about 40 seconds of wall time, plus queueing, splitting and the final step: minutes, not hours.

Make jobs safe to repeat. Outputs go to fixed names, so a job that runs twice replaces the same file. A job decrements jobs_left only when its own row moves from running to done, so it cannot count twice. With that idempotency, at-least-once delivery is enough: exactly one effect, not one run. Give the queue priorities so a big creator does not wait behind test uploads.

Adaptive bitrate streaming

Each quality is cut into the same 4-second segments, listed in a manifest: a small text file naming the qualities and every segment's URL (HLS and DASH are the common formats). Before each segment, the player picks the quality its measured bandwidth and buffer can sustain. So a slow network means lower quality, not a frozen picture.

Say it out loud: adaptation lives in the player, so servers hold plain static files a CDN can cache.

CDN delivery and cost

500 GB/s cannot come from one place, and the bill scales with bytes. A CDN keeps segments near viewers. At a 95% hit rate, origin serves 5% of 500 GB/s = 25 GB/s; at 99%, 5 GB/s. Each point of hit rate is a large saving.

Views are lopsided. Popular videos sit in every edge. The long tail misses almost every time, so serve it from fewer, larger regional caches. Pre-warm edges for videos you expect to be popular, and keep segment URLs identical for every viewer so one cached copy serves all.

It puts 500 GB/s on machines built for small JSON and gives the CDN nothing to cache. Segments are static files at fixed URLs; let the CDN and object storage serve them.

Bottlenecks and failures

At 10x viewing (10 million concurrent, 5 TB/s), delivery is the whole problem: more CDN capacity, a higher hit rate, a regional cache tier to protect origin. At 10x uploads, transcoding needs about 70,000 busy cores: an elastic fleet, with the queue absorbing bursts. The metadata database feels it last: at 20 page loads per viewer a day, 109 ÷ 86,400 ≈ 11,600 reads a second today, 116,000 at 10x, which replicas plus a cache cover.

Follow-up questions

How would live streaming change this?

Transcoding must keep up in real time and the manifest grows as segments appear. Shorter segments cut delay but add requests and compress worse.

How do you count views?

The player sends a view event after a few seconds, through a queue to a batching counter. Counts lag by seconds, fine for display.

How do you stop people downloading paid videos?

Expiring signed URLs stop link sharing; the edge checks the signature but leaves it out of the cache key. Real protection needs encrypted segments and separate licence keys (digital rights management), which you buy, not build.

Can you save storage on old videos?

Move originals to archive storage, and drop unused qualities of unwatched videos, regenerating them on demand.

What if a creator deletes a video?

Mark it deleted so the API stops returning it, then purge the CDN and delete the objects in the background. Short-lived signed URLs cover the gap before the purge.
