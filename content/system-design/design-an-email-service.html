An email service receives messages from other mail servers over SMTP, stores them in each user's mailbox, lets users read, label and search them from several devices, and sends outgoing mail to other providers. Interviewers ask about it because it combines a strict durability requirement (an accepted message must never be lost) with large storage, per-user partitioning, search, and communication with servers that you do not control.

The steps below follow A Framework for Any Design. Try each "Your turn" box before you read the section that follows it.

Clarify the problem

Design an email service like a big web mail provider. I'll assume the core features are sending and receiving mail, labels, search and attachments. Do we also need to support desktop clients over IMAP? Our own apps only. IMAP is a stretch goal. How many users are there, and how much mail does each one get? There are 100 million users. Each receives about 40 emails a day after spam is rejected, and sends about 5. Then my priorities are these. Once we tell the sender's server that a message is accepted, we never lose it. New mail reaches every device within a few seconds. A user's own actions show up immediately. Search results can lag by a few seconds. The candidate names the one promise that must never be broken and says where delay is acceptable.
  • Functional requirements: receive mail over SMTP, filter spam and viruses, list mail by label, open messages and attachments, send mail with retries and bounces, change labels, search a user's own mail, and sync devices.
  • Non-functional requirements: no accepted message is lost, new mail is visible within 5 seconds, the inbox opens in under 200 ms, search answers in under 500 ms, and receiving keeps working when reading is degraded.
  • Out of scope: calendar, contacts, chat, ads, end-to-end encryption, and IMAP (which comes up as a follow-up question).

Estimate the scale

Assume that an average email takes 30 KB of storage. Headers and body take about 10 KB, and one email in 20 has a 400 KB attachment, which adds 400 KB ÷ 20 = 20 KB on average. Peak traffic is about twice the average.

  • Received mail: 100 million users × 40 emails = 4 billion emails a day. That is about 46,000 a second on average and about 92,000 a second at peak.
  • Sent mail: 100 million × 5 = 500 million a day, about 5,800 a second on average.
  • Reads: at 20 opened messages per user a day, 2 billion reads a day, about 23,000 a second.
  • Inbound bandwidth: 4 billion × 30 KB = 120 TB a day, which is 120 TB ÷ 86,400 s ≈ 1.4 GB/s on average. Over a year that is about 44 PB before replication, so bodies and attachments go to object storage, and only about 500 B of metadata per email (2 TB a day) goes in a database.

Write the endpoints the mail apps need: list a label, open a message, send, change labels, search, and sync. What should "send" return when delivery can take days?

Listing is a GET by label with a cursor. Send returns 202, meaning queued and not yet delivered. Sync asks for "changes since sequence number N".

The decision worth arguing is how devices sync. Re-downloading the first 50 inbox messages on every wake-up transfers 50 rows when one changed, and misses label changes on older mail. Instead, each user has a change log, and a device asks for everything after the last sequence number it has seen, for example "everything after 81,237". Label changes are sent as operations ("add Receipts, remove INBOX"), so two devices that edit different labels on one message both succeed.

Sketch the records. Where do bodies and attachments live? What is the partition key, and how do you list "Inbox, newest first" quickly when a message can have many labels?

Metadata is partitioned by user_id, and bodies and attachments live in object storage. A per-label index ordered by time makes a listing one range scan.

A message can carry many labels. Inbox, Sent, Spam and Trash are system labels, and archiving a message removes its INBOX label without moving anything.

Almost every query is about one user's mail, so everything is partitioned by user_id. The label_index table has one row for each message and label, so "the newest 50 messages in the Inbox" is a single range scan. Mailbox metadata goes in a sharded relational database, and the deep dives explain why. Bodies and attachments never change after they are written, which suits object storage.

High-level design

Deep dives

Receiving mail and deciding when to reply 250

SMTP gives every reply a meaning. A 4xx reply means "try again later", and the sending server will retry. A 5xx reply means "permanently refused", and the sending server tells its own user that the message was not delivered. A 250 reply after the message body means that you now own the message and the sender may delete its copy.

There are three places to deal with unwanted mail. The first is to reject it during the SMTP conversation. The sender learns immediately and you store nothing, but the check runs while the sender waits, so only fast and certain checks belong here, such as an unknown recipient or a sending IP address with a bad reputation.

The second is to accept the message and file it in the Spam label. This leaves time for content classifiers and virus scans, which are too slow to run while the connection is open, and the user can rescue a false positive. The cost is storing the spam.

The third is to accept the message and then send a bounce to the sender. This is the option to avoid. Spam usually forges its sender address, so the bounce goes to an innocent person who never sent anything. That is called backscatter, and it can get your servers blocklisted. Bounces are only for undeliverable mail, from the send path described later.

The pipeline delivers each message at least once, and this is deliberate. A sender may retry after a 250 reply gets lost, and the queue may give one message to two workers. Exactly-once delivery is not practical, so the mailbox write is made idempotent with a per-recipient dedupe key, which is a hash of the Message-ID header and the content (see idempotency and retries). A message addressed to three of your users is stored once and queued as three deliveries.

The queue also provides back-pressure. If it is nearly full, SMTP in replies 451, a temporary failure, and senders retry later, so mail is delayed but never dropped.

Storing mailboxes, partitioned by user

Each user's mail is independent of everyone else's, so the partition key is user_id. The choice that matters is the kind of store, because one delivery changes several things at once: it adds a message row and label rows, raises the unread count, and appends a change-log entry.

A sharded relational database keeps one user on one shard, so a delivery is one transaction. The message, its labels, the counts and the change log cannot disagree, and the sync sequence number is simple to assign. The cost is operating the sharding yourself. This is the choice for mailboxes.

A wide-column store such as Cassandra also partitions by user and adds capacity by adding nodes, so it absorbs 46,000 writes a second without much effort. Its transactions only cover a single partition, so the label rows, counters and change log can drift apart and need repair jobs.

Users are mapped to shards through a directory and not with user_id modulo the number of shards. With a directory you can move a single user without redistributing everyone (see sharding and partitioning).

Attachments are stored under the SHA-256 hash of their bytes. A 5 MB file that is sent to 200 of your users then takes 5 MB of storage and not 1,000 MB. Users reach an attachment only through a message that they own, never by its hash. A background sweep deletes objects that nothing has referenced for a few days.

Searching one user's mail

Every search is limited to the mail of the person who asks, so the index is sharded by user. All of one user's documents sit on one shard, a query goes to a single machine, and it cannot return another user's mail. A user with millions of messages creates a hot shard, which you fix by moving the user, as with mailboxes.

The alternative is one global index, as a web search engine uses. Every query then goes to all shards and filters down to one user, and a bug in that filter shows people each other's mail. Mail search never crosses users, so a global index has no benefit.

The index covers headers, body text and attachment names. Operators such as from:, has:attachment and label: are filters on stored fields. The indexer reads the change log, which is why search lags by a couple of seconds, and results are checked against the mailbox so that a message deleted a second ago does not appear. Search systems explains the inverted index itself.

Sending mail with retries and bounces

Before the API returns 202, one transaction writes the message to the Sent label and an outbox row, and a relay process moves outbox rows to the outbound queue. Without the outbox row, a crash could leave a message in Sent that was never queued. The draft id is the idempotency key, so a double tap on Send results in one message.

For other recipients, an SMTP out worker takes the message from the queue and does the following:

  • Delivery: it groups the recipients by domain, looks up each domain's MX record, connects over TLS, and signs the message with DKIM so that the receiving server can verify that it came from you.
  • Temporary failures: a 4xx reply or a timeout means the message goes to the retry schedule. The gaps grow, for example 5 minutes, then 15, then hourly, for at least four to five days as the SMTP standard suggests.
  • Permanent failures: a 5xx reply such as "no such user", or running out of retries, produces a bounce message in the sender's inbox with the address and the reason. This is the only path that creates bounces.

Syncing devices

Each user has a counter, which is an ordinary column on the user's shard. Every change to the mailbox takes the next number and writes a row to the changes table in the same transaction. Taking the number locks the counter row until commit, so changes commit in order and a reader cannot skip one. A device only has to remember the last number it has seen.

Three situations need explicit handling:

  • Telling devices that something changed: web clients keep an open connection and phones receive a push notification (see realtime communication). The notification only says that something changed, so a lost push causes a delay and nothing worse.
  • Offline edits: the device queues operations such as "mark m_9f2 read" and replays them when it reconnects. If two devices set conflicting flags, the last write wins.
  • A device that is far behind: the change log is kept for 30 days. A request for older changes gets 410, and the device resyncs the newest 500 messages in each label.

Bottlenecks and failures

At 10 times the load, the system would receive about 460,000 messages a second on average and about 1.2 PB of new data a day. Storage cost is the first limit that is hit. You reduce it by compressing bodies, storing attachments once, moving old mail to cheaper tiers, and enforcing quotas. SMTP in and the filter workers are stateless, so you add more of them behind several MX records, and the mailbox and search tiers add shards.

A sender's server hands you a message. When do you say "accepted"? After the raw message is in object storage with three copies and a reference to it is on a replicated queue. Until then I can fail with a 4xx and the sender keeps its copy. After that point, losing the message is our fault. What if you crash after writing but before replying? The sender never saw the 250, so it retries. The mailbox insert is unique on a dedupe key built from the Message-ID and a content hash, so the second copy changes nothing. The answer ties durability to a protocol event and handles the duplicate that its own design can create.

Follow-up questions

How does undo send work?

The outbound message is queued with a delay of about 10 seconds, and pressing undo deletes it from the queue before it is released. After the message has been handed to another provider it cannot be recalled.

A mailing list sends one message to 1 million of your users. What happens?

You store the body once and queue 1 million deliveries, about 22 seconds of work at 46,000 a second. Bulk deliveries use a lower-priority queue so that personal mail keeps its normal delay.

How would you support IMAP clients?

You add an IMAP front end that maps labels to folders and maps the change log to IMAP's modification sequence numbers. A message with two labels appears in two folders, and deleting it from one folder must remove only that label.
