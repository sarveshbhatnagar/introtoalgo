You open a maps app, the city appears, you type an address, and a blue line says "10 min". You drive. A few minutes later: "Faster route found, saves 5 min", because a crash just blocked the motorway ahead.

Three systems hide behind one screen: static content (the map), an algorithm (shortest paths on a huge graph) and a stream (moving phones turned into traffic). A strong answer keeps them apart and goes deep on one. The steps follow A Framework for Any Design. Try each "Your turn" box before reading on.

Clarify the problem

Design a maps and navigation service. Three features: the map, a route with an arrival time, and turn-by-turn guidance with live traffic. Are place search, walking and transit in scope? Driving only. Assume address search exists and gives you coordinates. What scale? Daily users, routes a day, and peak navigating phones? 100 million daily users, 100 million routes a day including reroutes, 5 million phones navigating at peak. Then the map is CDN content, routing must be fast on a continent-sized graph, and traffic is a stream of about a million pings a second. If traffic fails, routing uses typical speeds. Three differently shaped systems, and what degrades gracefully: that is what interviewers want early.
  • Functional: a pannable, zoomable map; the fastest driving route with an ETA; while driving, live ETA updates and faster-route offers; reroute when the driver leaves the route.
  • Non-functional: tiles in under 100 ms from nearby; a route in under 200 ms at the server; new jams in ETAs within 2 to 3 minutes; routing works without live traffic; location data anonymised and kept briefly.
  • Out of scope: place search, walking and transit, map editing tools, street-level imagery.

Estimate the scale

  • Tiles: 100 per user a day: 10 billion ÷ 86,400 ≈ 116,000 a second, about 350,000 at a 3x peak. With 95% CDN hits, the origin sees about 17,000.
  • Routes: 100 million ÷ 86,400 ≈ 1,200 a second, about 3,500 at peak.
  • Pings: 5 million phones, one batch every 5 seconds: 1 million batches a second. At about 100 bytes each, 100 MB/s, useful for only a few minutes: a partitioned stream aggregated in memory, not database rows.
  • Road graph: assume 500 million junctions and 1.2 billion one-way segments. At 8 bytes a junction (two packed coordinates) and 12 bytes a segment (target, travel time, segment id): 4 GB + 14.4 GB ≈ 18 GB. It fits in one large server's memory.

Write the calls to load the map, ask for a route, and send location while driving. How does the phone learn of a faster route?

Tiles are cacheable GETs by zoom, x and y. A route is a POST with origin, destination and departure. Pings are a POST with a batch of points. The phone already calls every 5 seconds, so the ping reply can carry "a better route is ready".

  200  { "eta_s": 540, "better_route": null }

The decision worth arguing is how the phone hears of a faster route. A WebSocket per driver means 5 million open connections; the ping reply carries it instead, at most 5 seconds late. See realtime communication for when push is worth it.

The tile URL holds the map version (v812), so a rebuild changes URLs: no CDN purge, no mixed builds. The cost is a cold CDN sending all 350,000 requests a second to the origin, so push popular tiles before switching.

For tiles, the road graph, live speeds and pings: where does each live and how is it read?

Tiles: immutable files in a blob store behind a CDN. Graph: built offline, loaded whole into each routing server. Live speeds: a small segment-to-speed map. An active route per navigating phone. Pings: a stream kept for hours.

Model the data

-- road graph: built offline from map data, shipped as a file, loaded into RAM
junction   id INT, lat INT, lng INT                 -- 8 B packed coordinates (+ id by position)
segment    from INT, to INT, segment_id INT,
           length_m INT, road_class TINYINT, turn_rules ...   -- one row per direction

-- live speeds: key-value, overwritten every minute
live_speed       segment_id -> (speed_kmh, samples, updated_at)   -- about 16 B each

-- typical speeds: a weekly curve, 672 slots of 15 minutes. Segments share
-- a few thousand curve shapes, so each stores a curve id, not 672 numbers
typical_curve    segment_id -> curve_id                      -- 2 B each
curve            (curve_id, slot 0..671) -> speed_kmh

-- active routes: one per navigating phone, deleted when the trip ends
active_route     route_id -> (segments, eta_s, better_route)  -- a few KB

-- pings: a partitioned stream, kept for a few hours, no user id
ping       trip_token, t, lat, lng, speed, heading

Tiles are immutable, read by key: blob storage behind a CDN. The classic mistake is querying a database per search step: at 0.5 ms a round trip, 50,000 junctions take 25 seconds. The graph is read-only between builds, so it sits in each routing server's memory as compact arrays. Only main roads get enough pings for a live speed: 100 million segments × 16 B = 1.6 GB. Typical-speed curve ids add 1.2 billion × 2 B = 2.4 GB. Every routing server holds both. Pings are written and read once: a stream, with a random token per trip instead of a user id.

Sketch three flows: drawing the map, asking for a route, and turning pings into traffic the next route uses.

Tiles: phone, CDN, tile store. Routes: phone, gateway, routing servers holding the graph and live speeds; each route is saved as active. Pings: phone, gateway, stream, a traffic aggregator writing segment speeds. The ping reply checks the active route for a better one.

High-level design

The three flows share only the phone and gateway, so each fails alone.

Deep dives

Map tiles

At zoom 0 one square holds the world; each zoom level splits every square into four. A tile is named z/x/y, so the phone works out which tiles cover the screen by itself.

Routing on a huge road graph

A route is a shortest path where a segment's weight is its travel time. Dijkstra's algorithm is correct, but it grows a circle of settled junctions around the start until it reaches the destination. On a long trip, say 20 million junctions at about 1 µs each (a heap operation plus a memory miss): 20 seconds, against a 200 ms goal.

Searching from both ends, or A*, shrinks the circle only a few times; beyond one city, 3,500 routes a second would need tens of thousands of cores. Most work must happen before anyone asks.

Cut the graph into cells along natural borders, so each has few border junctions. Precompute the fastest time between every pair of a cell's border junctions: shortcut edges. A query runs Dijkstra on real roads in the end cells and on shortcuts elsewhere. With several cell levels, a long query settles tens of thousands of junctions, still exact for the current weights.

Capacity: 50,000 junctions at 1 µs is 50 ms of one core; 3,500 routes a second × 0.05 s = 175 busy cores, so about 20 servers of 16 cores run near half busy. Each holds the 18 GB graph: replicas, not shards, which would turn one search into many network hops.

From pings to traffic and ETAs

A GPS point says where a phone is, not which road. The aggregator map-matches each run of points to the likeliest chain of segments, using heading and speed to tell a motorway from the road under it, then keeps each segment's recent speeds.

  • Partition by area. The stream is keyed by map tile, so one aggregator owns an area.
  • Ignore noise. One car stopping for fuel is not a jam: publish only when several phones agree.
  • Blend with history. With few samples, use the typical speed for that 15-minute slot of the week.

Rerouting

  • The driver leaves the route. The phone sees several points in a row over, say, 50 m off the line and asks for a new route. Local detection is fast and survives a bad connection.
  • Traffic makes another route faster. Re-pricing all 5 million active routes every 90 seconds would be 55,000 searches a second, 15 times the route traffic. Re-price only routes crossing a changed segment, and offer a switch only if it saves, say, 2 minutes and 10% of the remaining time, so drivers are not flipped back and forth.

If every driver near the crash gets the same "faster" route at once, the side road jams within minutes. Offer it to a share of drivers at a time; the next minute of pings corrects the speeds.

Bottlenecks and failures

At 10x (10 million pings, 35,000 routes a second), the stream and aggregator add partitions by area. Routing adds replicas: 35,000 × 0.05 s = 1,750 cores. The awkward part is the shortcut refresh every replica repeats; at that size, compute it once and ship it.

What a strong answer sounds like

LevelWhat the answer does
JuniorDraws map and route services, says "Dijkstra", stores pings in a database.
MidServes zoom-level tiles from a CDN, sees plain Dijkstra is too slow and names a precomputation, streams pings into segment speeds.
SeniorSeparates the three systems, picks cell shortcuts for live traffic, replicates the in-memory graph, falls back to typical speeds, and handles rerouting hysteresis and herding.
How do you compute routes for 3,500 requests a second? Plain Dijkstra settles tens of millions of junctions on a long trip, so I precompute times between each cell's border junctions. A query then settles about 50,000: 50 ms, 175 cores at peak. Every server holds the whole 18 GB graph. Why cells and not a full hierarchy, which answers faster? Speeds change every minute. With cells I recompute shortcuts only where speeds changed; a basic hierarchy picks shortcuts from all the weights, so it needs a full rebuild.

Follow-up questions

How do you ship a new version of the map data?

Load the new graph beside the old, then switch. A reroute mid-switch uses its route's graph version.

How would offline navigation work?

The user downloads a region's tiles and graph with typical speeds; the phone runs the same search without live traffic.

How do you protect people's privacy?

Pings carry a random per-trip token, trip ends are trimmed so homes stay hidden, and raw pings are deleted after hours. Only segment averages are kept.

How do you know the ETAs are good?

Each finished trip gives a predicted and actual arrival. Track the error by region and hour, and tune the live/typical blend with it.

How do you handle road closures and turn restrictions?

A closure sets a weight to infinity and goes through the same per-cell shortcut refresh as traffic. Turn restrictions live in the graph (edges between segments), so the search never produces an illegal turn.
