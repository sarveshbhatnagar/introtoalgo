A cache cluster has 4 nodes holding 10 million keys and serves 50,000 reads a second. 95% are hits, so the database sees 50,000 × 0.05 = 2,500 reads a second. Each key's node is hash(key) mod 4. Traffic grows, so someone adds a fifth node and switches to mod 5.

A key stays put only if its hash leaves the same remainder for 4 and 5: 4 values in every 20. So 80% of keys point at a node that lacks them. The hit rate falls to about 0.95 × 0.2 = 19%, and the database goes from 2,500 to 50,000 × 0.81 = 40,500 reads a second. Adding capacity caused the outage.

The idea

Consistent hashing places keys so that when a node joins or leaves, only about 1/N of them move: the new fifth node takes its fair share, and every other key stays put.

Use it wherever keys spread over a changing set of machines: caches, partitioned key-value stores, sticky load balancing. The cost is a little bookkeeping in every client.

The ring

Hash server names and keys into one range of numbers, bent into a circle. Real rings use 0 to 232 − 1 or more; by hand, use 0 to 99. A key belongs to the first server clockwise from it, wrapping past 99 to 0.

Now watch what moves when a server joins, then leaves.

Virtual nodes

The fix: give each server many points, called virtual nodes, by hashing "A#0", "A#1", up to "A#99". Each server owns 100 small scattered arcs instead of one big one:

  • Even shares. Summing many random arcs, a share's deviation from average shrinks roughly as 1 ÷ √v for v points: about 10% at 100.
  • Even recovery. A leaving server's 100 arcs go to many neighbours, not one.
  • Weights. A server with twice the memory gets 200 points and about twice the keys.

A lookup binary-searches the sorted points for the first at or after the key's hash, wrapping to the start. The hash must mix well (here, the first 32 bits of MD5), or similar names like "A#0" and "A#1" can bunch. See also hash tables.

const crypto = require("crypto");

function hash(s) {                           // first 32 bits of MD5
  return parseInt(crypto.createHash("md5").update(s).digest("hex").slice(0, 8), 16);
}

class Ring {
  constructor(vnodes = 100) {
    this.vnodes = vnodes;
    this.points = [];                        // [position, node], sorted
  }
  add(node) {
    for (let i = 0; i < this.vnodes; i++) this.points.push([hash(`${node}#${i}`), node]);
    this.points.sort((a, b) => a[0] - b[0]);
  }
  remove(node) {
    this.points = this.points.filter(([, n]) => n !== node);
  }
  lookup(key) {
    const h = hash(key);
    let lo = 0, hi = this.points.length;     // first point at or after h
    while (lo < hi) {
      const mid = (lo + hi) >> 1;
      if (this.points[mid][0] < h) lo = mid + 1; else hi = mid;
    }
    return this.points[lo % this.points.length][1];  // past the end: wrap to 0
  }
}

import bisect
import hashlib

def ring_hash(s):
    # first 32 bits of MD5
    return int(hashlib.md5(s.encode()).hexdigest()[:8], 16)

class Ring:
    def __init__(self, vnodes=100):
        self.vnodes = vnodes
        self.points = []                    # (position, node), sorted

    def add(self, node):
        for i in range(self.vnodes):
            bisect.insort(self.points, (ring_hash(f"{node}#{i}"), node))

    def remove(self, node):
        self.points = [p for p in self.points if p[1] != node]

    def lookup(self, key):
        # first point at or after the key's hash; past the end: wrap to 0
        i = bisect.bisect_left(self.points, (ring_hash(key), ""))
        return self.points[i % len(self.points)][1]

When a cache node dies

Back to the 4-node cache, now on a ring with 100 virtual nodes each. Every app server holds the same ring.

Other ways to place keys

Numbers worth remembering

  • Adding the (N+1)th node moves about 1/(N+1) of keys with consistent hashing; with mod N, about N/(N+1).
  • Virtual nodes: 100 to 200 per server is common; spread shrinks as 1 ÷ √v.

In the interview

Bring it up when keys spread over nodes that come and go. State the problem in numbers, then name virtual nodes.

The cache needs a fifth node. Any problem? With hash mod N, 4 to 5 remaps 80% of keys and the database takes most reads at once. With consistent hashing and about 100 virtual nodes per server, the new node takes roughly a fifth of the keys, evenly from the others. Does that fix a single very hot key? No, one key still lives on one node. I'd cache the hot key in each app server's memory for a few seconds, or replicate it to several nodes and pick one at random. It quantifies the failure, picks the fix, and knows its limit.

Follow-ups to expect:

  • "How do clients agree on the ring?" Membership comes from a configuration service or gossip. During changes clients briefly disagree; a few requests miss.
  • "How does replication fit?" Store each key on the next 3 distinct servers clockwise, skipping repeat points of a chosen server.

Common mistakes

It balances key counts, not traffic. A key read 20,000 times a second still lands on one node.
