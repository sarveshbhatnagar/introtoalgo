An orders table outgrows one database and is split across 4, each with its own auto-increment counter. Within a day shard 1 and shard 3 have both created order 1001. Support finds two, and the analytics job that merges shards silently overwrites one with the other.

Across many machines, each server must hand out IDs no other will ever produce, ideally without asking anyone.

The idea

Three ways avoid a clash without a central counter per request: IDs so random that clashes are practically impossible (UUIDs); IDs built from parts unique on their own, such as time, machine number and counter (Snowflake-style); or a private block of numbers handed to each server in advance (range allocation).

Then ask: must it fit in 64 bits? Should IDs sort by creation time? Does it matter if outsiders can guess the next ID or count your orders?

The options

With range allocation, a server asks for "the next 1,000", gets 7,000 to 7,999, and hands them out from memory. A crash just skips the unused numbers.

A UUID v4 has 122 random bits. By the birthday estimate, n IDs collide with probability about n² ÷ 2123. For a trillion IDs: (1012)² ÷ (1.06 × 1037) ≈ 10−13. Treat it as never, given a good random generator.

A Snowflake-style ID, bit by bit

Split a 64-bit integer into fields. The timestamp sits in the highest bits, so sorting IDs as numbers sorts them by time.

  • Sign, 1 bit: always 0, keeping the ID positive in signed 64-bit integers.
  • Timestamp, 41 bits: milliseconds since an epoch you choose, such as your launch date. It lasts about 70 years (worked out below).
  • Machine, 10 bits: 210 = 1,024 generators at once.
  • Sequence, 12 bits: a counter that resets every millisecond. 212 = 4,096 IDs per ms per machine, about 4 million a second.

Build the example by shifting each field into place and adding: 1,000,000,000 × 222 = 4,194,304,000,000,000, plus 37 × 212 = 151,552, plus the sequence, 5. The ID is 4,194,304,000,151,557. To read it back, divide by 222 for the timestamp, and so on.

Tune the split: more sequence bits suit a few very busy generators; a timestamp in seconds lasts longer but sorts less finely.

JavaScript numbers are exact only up to 253. With 22 bits below the timestamp, any timestamp past 231 ms (about 25 days after the epoch) gives an ID a browser silently rounds. Send these IDs as strings in JSON.

Numbers worth remembering

  • 210 ≈ 1 thousand, 220 ≈ 1 million, 230 ≈ 1 billion, 240 ≈ 1 trillion.
  • A 64-bit ID is 8 bytes; a UUID is 16 bytes, or 36 characters as text. Over a billion rows and their indexes, that is many gigabytes.

In the interview

IDs come up whenever data is sharded or written from many servers, and in designs showing items in time order (feeds, chats). State the requirements first: "Unique across shards, 64 bits, roughly time-sorted, so a Snowflake-style generator in each service."

How do you assign message IDs? Messages are written on many servers and shown in time order, so 64-bit Snowflake-style IDs. Each server leases its machine number at startup, then makes IDs locally. Two messages in the same chat land on different servers in the same millisecond. Which comes first? The machine bits decide, so order is arbitrary within that millisecond, and server clocks differ by a few ms anyway. Fine for chat. If exact order inside a conversation mattered, one owner per conversation would assign sequence numbers. Strong answers admit time-ordered IDs are only roughly ordered across machines, and say what to do about it.

Follow-ups:

  • "What if the clock goes backwards?" Wait until it passes the last timestamp used; alert if the jump is large.
  • "Can outsiders learn anything from your IDs?" Yes: sequential IDs reveal volume, time-based ones reveal creation time. Where that matters, show users a separate random public ID.

Common mistakes

Random UUID v4 keys land all over the index, so each insert touches a different page and large tables slow down. Use a time-ordered ID when the key decides physical order.
