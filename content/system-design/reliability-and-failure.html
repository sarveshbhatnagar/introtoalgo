Reliability is the work of keeping a system useful while parts of it fail. It combines redundancy, so that a failed component has a replacement, with protective patterns such as timeouts, circuit breakers and load shedding, which stop a failing component from dragging down its callers. Availability, the share of time that the system does its job, is the number used to set the target.

Without these measures, a slow optional service makes its callers wait, the waiting callers use up their threads, and the callers of those callers start to fail as well.

Where reliability measures sit

Availability and the nines

Availability is usually written as a percentage and spoken as a number of nines. 99.9% is "three nines".

AvailabilityDowntime per 30-day monthDowntime per year
99%7.2 hours3.65 days
99.9%43 minutes8.8 hours
99.99%4.3 minutes53 minutes
99.999%26 seconds5.3 minutes

Each additional nine cuts downtime tenfold and costs more. At 99.99% a paged person cannot log in and fix a problem within the monthly budget, so recovery has to be automatic.

Components in series

When a request needs every component in a chain, the availability of the chain is the product of the availabilities. Three services that are each 99.9% available give 0.9993, about 99.7%, which is roughly 130 minutes of downtime a month instead of 43. Every dependency added to the critical path lowers availability.

Components in parallel

When any one of several copies can serve the request, the system is down only if all copies are down at once. Two copies that are each 99% available fail together 0.01 × 0.01 = 0.0001 of the time, so the pair is 99.99% available. This assumes independent failures. Two copies in one rack, or running the same bad release, do not fail independently, and their real availability is much lower.

Redundancy and failover

Redundancy means having a second component ready to do the work of one that fails. How the second component is used gives two designs, and both are common.

Active-passive

One component serves all traffic while a standby copy waits, kept up to date by replication. When the active one fails, a monitor notices, promotes the standby and redirects traffic to it. It is the normal design for a database with a single leader, because only one node accepts writes.

Downtime is the detection time plus the promotion time. Checks every 5 seconds with three misses required take 15 seconds to detect a failure. Checking more aggressively replaces a leader that is only slow while it is still running, and two nodes then both believe they are the leader, which is called split brain (see consensus and leader election). With asynchronous replication, writes that had not reached the standby are lost at failover.

Active-active

All copies serve traffic at the same time. Stateless servers behind a load balancer work this way, and when one fails the others simply take its share. There is no promotion step, so there is almost no failover time.

The cost is that the remaining copies must be able to carry the extra load. For stateful systems, active-active means more than one node accepts writes, so concurrent writes to one record can conflict and need a resolution rule or a single owner per record.

Cascading failure

A cascading failure is one in which a failure in a single component increases the load or the waiting time of other components until they fail too. It usually begins in one of four ways:

  • A dependency becomes slow rather than failing outright. Each waiting call holds a thread.
  • Callers retry failed requests, so a struggling service receives several times its normal load.
  • A server fails and its traffic overloads the remaining servers, which fail in turn.
  • A restarted service starts with an empty cache, so every request reaches the database until it warms up.

Protections against failure

Timeouts

A timeout limits how long a caller waits for a response before it gives up. Every network call needs one, because a dependency that hangs otherwise holds the caller's thread forever. Set it a little above the dependency's 99th percentile latency. A timeout that is too long does not protect anything, because the threads still fill up, and one that is too short turns ordinary slow responses into errors and extra retries.

Retries

A retry repeats a failed request, which hides short failures such as a dropped connection or a server that restarted. Retries are safe only for operations that can be repeated, so a payment needs an idempotency key first (see idempotency and retries). Wait between attempts with exponential backoff, doubling the delay each time, and add random jitter so that clients do not retry together.

Retries multiply load when they are done at every layer. If a web tier, a service and a database client each make three attempts, one user request can produce 3 × 3 × 3 = 27 queries at the database. Retry at one layer only, cap retries at a small fraction of normal traffic (a retry budget), and do not retry errors that will fail again, such as a 400.

Circuit breakers

A circuit breaker wraps calls to a dependency and counts failures. While it is closed, calls pass through. When the failure rate in a recent window passes a threshold, the breaker opens, and calls fail immediately or use a fallback without reaching the dependency. After a cool-down it lets a few trial calls through (half-open); if they succeed it closes, and if not it opens again.

A breaker protects the caller, because failing at once costs nothing, and the dependency, which receives no traffic while it recovers. A breaker that opens on normal noise is a nuisance, so most implementations require a minimum number of calls in the window.

Bulkheads

A bulkhead gives each dependency its own limited pool of threads or connections, the way a ship's compartments contain a leak. If recommendations becomes slow, it can use up only its own pool. The cost is that pools must be sized, and idle capacity cannot be borrowed.

Graceful degradation

Graceful degradation means that when a part fails, the system keeps working with reduced features instead of failing completely. A product page can show popular items when recommendations are down, and a feed can load without ads. Decide for each dependency whether it is critical or optional, and write and test the fallback in advance.

Load shedding

Load shedding means that a server that is over capacity rejects some requests immediately, usually with a 503 response, instead of accepting all of them and timing out on every one. This keeps the accepted requests fast. Shed the least valuable work first, such as browsing before checkout. Shedding differs from rate limiting, which gives each client a fair share, because shedding responds to the server's own overload.

Backpressure

Backpressure is the way a slow consumer tells its producer to slow down, so that work does not pile up without limit. The usual form is a bounded queue: when it is full, the producer is blocked or receives an error. Without a bound, the queue grows until memory runs out. Backpressure slows the sender down, while shedding rejects the excess. A consumer that fetches only as many messages as it can process is the common example (see message queues and streams).

Zones, regions, RPO and RTO

A zone is an isolated group of data centers with its own power and network, and a region is a group of zones in one area. Copies in separate zones survive a building failure, and synchronous replication between zones is practical because they are close. Copies in separate regions survive losing a whole region, at much higher cost.

Two objectives decide how much protection is needed. The recovery point objective (RPO) is how much recent data you can afford to lose, measured as a length of time. The recovery time objective (RTO) is how long the service may stay down before it must be working again. Synchronous replication gives an RPO of zero but makes every write wait for the second copy, while asynchronous replication loses whatever had not yet been copied.

One region, several zones

Copies in three zones survive a zone failure with automatic failover, and with synchronous replication no data is lost. A region-wide outage still takes the system down. It is enough for most systems.

Active-passive regions

A second region holds an asynchronous copy and takes over if the first is lost. Failover takes minutes, and the RPO is the replication lag. Use it when a region outage must cost minutes and a few seconds of lost writes are acceptable.

Active-active regions

Every region serves live traffic, so users reach a nearby region and there is no untested standby. Writes to one record in two regions can conflict, so records usually have a home region. Use it when users span continents and latency matters.

Problems that interviewers probe

Failover that sends all load to the survivors

When one zone fails, its traffic moves to the others. If two zones each run at 70% of capacity, the survivor would need 140%. Keep enough headroom to lose the largest failure domain, which for three zones means running each at about 66% or less.

Health checks that are too shallow or too deep

A check that only tests whether the process runs misses a server that cannot reach its database. A check that queries the database makes every server unhealthy when the database slows down, and the balancer removes all of them. Keep sending traffic to some servers if all of them fail the check.

In the interview

Interviewers usually point at a box in your design and ask what happens when it dies. For each component, say what the user sees, how the failure is detected and what takes over, and state the target as downtime: "99.9% allows about 43 minutes a month, so failover must be automatic". Use active-passive for single-writer state and active-active for stateless tiers.

Questions to expect:

  • "What happens if the database leader dies?" A monitor detects the missed health checks within seconds and promotes the standby. With asynchronous replication, writes not yet copied are lost, so say which RPO the data allows. Payments replicate synchronously to another zone.
  • "What happens if one app server dies?" The load balancer stops sending it traffic within seconds, and the other servers take its share. Requests in flight on it fail and are retried, which is safe only if they are idempotent.
  • "A dependency is slow. What happens to your service?" Without protection, calls pile up and use every thread. With a timeout, a bulkhead and a circuit breaker, calls to it fail quickly and the rest keeps working, and optional dependencies get a fallback.
  • "Why not retry everything?" Retries add load to a service that is already struggling, and retries at several layers multiply. Retry at one layer, with backoff, jitter and a budget, and only for operations that are safe to repeat.
  • "What is the difference between load shedding and backpressure?" Shedding rejects excess requests immediately, so the client sees an error. Backpressure makes the producer slow down, so the work is delayed instead of refused.
  • "How would you survive a region failure?" First ask whether the requirement exists, because multi-region is expensive. Active-passive recovers in minutes with a small data loss, and active-active gives local latency but needs conflict handling. Ask for the RPO and RTO first.
Your feed service calls an ads service. The ads service starts taking 10 seconds to respond. What happens? The feed calls ads with a 200 ms timeout and from its own small connection pool, so slow ads cannot use the threads that load the feed. If more than half of the ad calls fail within a 10-second window, a circuit breaker opens and the feed is served without ads until trial calls succeed again. The answer separates the critical feed from the optional ads and degrades the optional part.
