A seller lists a vintage camera at $50, ending Sunday at 20:00:00. In the last ten seconds, fifty people bid at once. At 20:00:00 exactly one must have won, every watcher must have seen the same price, and a bid 40 milliseconds late must not count.

It looks like CRUD but hides three hard problems: many people writing one record at once, showing it live, and an exact deadline. Think eBay's timed auctions. The steps follow A Framework for Any Design.

Clarify the problem

Design an online auction site. I'm assuming the highest bid wins at a fixed end time, and each bid must beat the current one by a minimum increment. Yes. Do bids in the final seconds count, or does a late bid extend the auction? They count, up to the end time. No extensions. How many auctions, and how busy does the hottest get? About 1.5 million new auctions a day, each running 7 days, about 10 bids each on average. A hot one can have 50,000 people watching and hundreds of bids in its last ten seconds. Then two bids can never both win, an accepted bid is never lost, one clock enforces the end time, and watchers see a new high within a second. Asking about late bids matters most: a hard or soft close changes the hardest part of the design.
  • Functional: create an auction (item, starting price, increment, end time); bid; see the highest bid live; close at the end time and tell winner and seller; see bid history.
  • Non-functional: strong consistency per auction (bids strictly ordered); accepted bids durable; an exact rule rejects late bids; new highs reach watchers within 1 second; the site stays up while a hot auction ends.
  • Out of scope: payment, shipping, search, fraud, buy-it-now, reserve prices.

Estimate the scale

A day has 86,400 seconds.

  • Live auctions: 1.5 million a day × 7 days ≈ 10 million open at any time.
  • Bids: 15 million a day ÷ 86,400 ≈ 170 a second; endings cluster in the evening, so about 1,700 at a 10x peak.
  • Page reads: 100 views per bid is about 17,000 reads a second: caches and replicas.
  • Storage: bids at 100 B: 1.5 GB a day, about 550 GB a year. Auctions at 2 KB: about 1.1 TB a year. Photos go in blob storage.
  • The hot auction: 500 bids in its last 10 seconds is 50 bids a second, all on one row.

Write the calls to create, bid on and watch an auction. What does a bid return when too low or too late?

A bid is a POST with a client id, answered at once: accepted, outbid (with the new minimum) or ended. Watching is a one-way stream, so server-sent events are enough.

Define the API

  201 { "status": "accepted", "seq": 37 }
  200 the same body again        a retry with the same bid_id
  409 { "status": "outbid", "min_next_cents": 12500 }
  410 { "status": "ended" }

GET  /auctions/{id}/live        text/event-stream
  event: high   data: { "seq": 37, "high_cents": 12000, "min_next_cents": 12500 }
  event: ended  data: { "winner": "ca***", "final_cents": 13000 }

GET  /auctions/{id}/bids?before_seq=37&limit=20     history, newest first

The decision worth arguing: the bid answers synchronously. A bidder in the last ten seconds must know now whether to bid again, and the path is one conditional write, so a direct answer is cheap.

bid_id is the bid's idempotency key. server_time lets the countdown run on the server's clock.

Sketch auctions and bids. Where does the current high live, and how do you keep every bid?

The auction row holds the high, the next minimum and a bid counter. Each accepted bid is appended to a bids table in the same transaction, numbered by that counter.

Model the data

auctions
  auction_id       BIGINT PRIMARY KEY
  seller_id        BIGINT
  title            VARCHAR(200)
  increment_cents  BIGINT
  end_at           TIMESTAMP
  status           VARCHAR(8)       -- open | closed
  high_cents       BIGINT NULL
  high_bidder_id   BIGINT NULL
  min_next_cents   BIGINT           -- starts at the starting price
  bid_count        INT              -- also the last bid's seq
  INDEX (status, end_at)            -- for the closer

bids
  auction_id   BIGINT
  seq          INT                  -- 1, 2, 3 ... per auction
  bid_id       VARCHAR(40)          -- from the client
  bidder_id    BIGINT
  amount_cents BIGINT
  placed_at    TIMESTAMP
  PRIMARY KEY (auction_id, seq)
  UNIQUE (auction_id, bid_id)

Every write touches one auction: a conditional update plus a bid insert. So use a relational database partitioned by auction_id, bids beside their auction, and each bid is a single-partition transaction. Keep every bid: "your bid was #37, at 19:59:58.100, for $120" settles disputes. Rejected attempts go to a separate log for fraud checks.

Where are bids checked and written, how does a new high reach 50,000 browsers, and what closes an auction?

An auction service runs the conditional write and publishes each new high to a topic per auction; live servers hold the streams and subscribe. A closer worker closes auctions past their end and triggers notifications.

High-level design

Deep dives

Concurrent bids

Two bids arrive together; each reads "high is $110" and writes. Every bid must be judged against the true current high.

WITH won AS (
  UPDATE auctions
     SET high_cents = 12000, high_bidder_id = :ana,
         min_next_cents = 12000 + increment_cents,
         bid_count = bid_count + 1
   WHERE auction_id = 812 AND status = 'open'
     AND end_at > now() AND 12000 >= min_next_cents
  RETURNING bid_count                        -- 37
)
INSERT INTO bids (auction_id, seq, bid_id, bidder_id, amount_cents, placed_at)
SELECT 812, bid_count, 'b-1', :ana, 12000, now() FROM won;
-- 1 row inserted: accepted as #37
-- 0 rows: read the auction to answer "outbid" or "ended"

The row lock is the serialisation point: lock order is seq order. It is the conditional update from ticket booking, which explains the isolation details. In PostgreSQL, now() is when the bid's transaction started, so a bid that arrived before the end but waited for the lock still counts. The service looks up bid_id first to answer retries; the unique key catches two racing copies. At 5,000 bids a second on one item, move to one owner per auction and name the failover cost.

Checking $120 against a cached or pushed price, then writing, reopens the race. The cache is for display; the check belongs in the same atomic write, against the row.

Showing the highest bid live

Watchers only receive, so use server-sent events: one-way, plain HTTP, automatic reconnect. Fan-out works as in the stock trading app: a topic per auction, one subscription per live server. Two details matter:

  • Every update carries seq; the browser keeps the highest. Seq 37 and 38 can arrive in either order, as can a snapshot and a delayed message. Without the rule the screen could drop back to $120 in the final second.
  • Send the latest state, at most every 250 ms. Each message is the whole high, so skipping some is safe: 200,000 messages a second instead of 2.5 million.

Closing exactly at the end time

A timer that closes the auction at 20:00:00 is tempting, but timers fire late. If the close stops bidding, a slow closer lets late bids in.

So enforce the deadline in the bid's write: end_at > now(), judged by the one database clock that owns the row, so drifting app-server clocks cannot disagree. The closer only does bookkeeping and can run seconds late.

Every second, the closer reads the (status, end_at) index and runs SET status = 'closed' WHERE auction_id = 812 AND status = 'open' AND end_at <= now(). The last condition matters with a soft close, where a bid may have moved the end. Only the closer that changes 1 row emits "ended", so none notify twice (see the job scheduler). 10% of a day's auctions ending in one hour is 150,000 ÷ 3,600 ≈ 42 closes a second: easy.

A soft close fits the same update: add end_at = GREATEST(end_at, now() + interval '2 minutes') to the SET. Either way, arrival time decides: a bid sent at 19:59:59.900 that arrives at 20:00:00.100 is late.

Scaling hot auctions

One auction cannot be split, and need not be: 50 writes a second against a ceiling of 500. Its real load is 50,000 viewers. Serve the page from a CDN and the price from live servers' memory, so the database sees bids, not viewers.

Bottlenecks and failures

At 10x (17,000 bids a second at peak), add partitions; 170,000 page reads a second is for caches and the CDN. A single item at 500 bids a second reaches the row's ceiling: that is when one owner per auction earns its complexity.

A bid arrives 40 ms after the end time. What happens? The close job runs at 20:00:00 and marks the auction closed, so the bid is rejected. Only if the job ran exactly on time. Two seconds late, and the bid may win. A bid arrives 40 ms after the end time. What happens? Its own write rejects it: the update requires end_at > now(), by the database clock that owns the auction. The closer only records the winner and notifies, so it could run seconds late with the same result. Isn't that unfair to someone on a slow connection? Yes; with a hard close, arrival decides. That's why I asked about soft close, which fits the same update.

Follow-up questions

How would you support automatic bidding up to a maximum?

Store each bidder's secret maximum. The visible price becomes the second-highest maximum plus one increment, capped at the highest; ties go to the earlier bid. That reads several values, so lock the row, compute in code and write, in one short transaction.

How do you stop a seller bidding up their own item?

Reject the seller's own account in the write. Shill bids from other accounts need offline analysis of the bid history.

Can a bidder retract a bid?

Mark it retracted and recompute the high in one transaction on the auction row. Allow it only well before the end, or it becomes a way to probe others' limits.

How do you show "you've been outbid" to someone who left the page?

Publish an "outbid" event for the previous high bidder; the notification system sends a push or email, rate-limited so a bidding war does not send fifty.

How would you run this in several regions?

Each auction has one home region for its bids; others pay a round trip. Multi-region writes would need consensus on every bid, which is slower.
