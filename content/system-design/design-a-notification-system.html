Your bank texts you a login code; a shop emails a receipt. Behind each, a product service said "tell user 42 about this", and a shared notification service decided how, when and through which provider it went.

The hard parts are off the happy path: a provider times out and you do not know if the text went out, a campaign sits in front of a login code, a retry sends an alert three times. The steps follow A Framework for Any Design.

Clarify the problem

Design a notification system. A shared service other teams call, sending push, SMS and email through third-party providers? Alerts only, or campaigns too? Yes, and both. Campaigns can target 50 million users. Volumes per day? And how fast must a login code arrive? About 500 million push, 100 million emails and 5 million texts a day, across 100 million users. Login codes within seconds, even during a campaign. Then priority is a first-class requirement. I'll aim for at-least-once with deduplication, because a lost login code is worse than a duplicate. The candidate found the conflict early: bulk campaigns and urgent codes share the same providers.
  • Functional: send a templated notification by push, SMS or email; campaigns to large segments; per-category channel preferences; a status check.
  • Non-functional: high-priority messages (login codes, security alerts) reach the provider within 5 seconds, even during a campaign; nothing accepted is silently dropped; duplicates are rare; intake is 99.99% available, while sending may lag.
  • Out of scope: the in-app inbox, campaign audience tools, A/B tests of message text.

Estimate the scale

  • Average rates: 500 million push ÷ 86,400 s ≈ 5,800 a second; 100 million emails ≈ 1,160 a second; 5 million texts ≈ 58 a second. About 7,000 a second in total.
  • Campaign peak: 50 million users in 30 minutes needs 50,000,000 ÷ 1,800 s ≈ 28,000 sends a second on one channel, four times the daily average.
  • Preferences and devices: 100 million users × 200 bytes = 20 GB of preferences; 2 devices each at 200 bytes per token = 40 GB. Both fit in a cache, which matters because every send reads them.
  • Provider limits: assume our SMS account allows 500 texts a second. That is a hard ceiling, not a target.

Write the endpoint a service uses to send one notification. What does it return, and how does a caller retry safely after a timeout?

A POST with the user, template, parameters, priority and an idempotency key. It returns 202 Accepted with a notification id; sending happens later, and a status endpoint reports on it. A retry with the same key returns the same id instead of sending twice.

Define the API

POST /v1/notifications
  Idempotency-Key: order-881-shipped
  body: { "user_id": 42, "template": "order_shipped", "params": { "order": "881" },
          "category": "order_updates", "priority": "high" | "normal" | "bulk",
          "channels": ["push", "email"]?, "expires_in": "24h"? }
  202 Accepted   { "notification_id": "n_501" }
  400 Bad Request         unknown template or missing parameter
  404 Not Found           unknown user
  409 Conflict            same Idempotency-Key with a different body
  429 Too Many Requests   this caller is over its quota

GET  /v1/notifications/n_501
  200 { "push": "sent", "email": "retrying", "sms": "skipped: user opted out" }

PUT  /v1/users/42/preferences   { "order_updates": ["push", "email"], "marketing": [] }
POST /v1/campaigns              { "segment": "...", "template": "...", "send_at": "..." }   202
POST /webhooks/{provider}       delivery receipts and bounces from providers

The decision worth arguing is 202, not 200. Providers can be slow or down for minutes, and the order service or login flow should never wait on them. The cost: the caller cannot see failures in the response, so it gets a status endpoint. The Idempotency-Key makes the caller's retries safe, as in Idempotency and Retries.

What records do you need, which are read on every send, and which kind of store suits each?

A notification log (one row per request, plus a status per channel), written heavily and read by id; and small per-user records (preferences, device tokens, contacts) read on every send and cached. Different access patterns, so different stores.

Model the data

notifications                     -- about 500 bytes, kept 90 days
  notification_id   CHAR(26)      PRIMARY KEY
  idempotency_key   VARCHAR(100)  UNIQUE (per caller), expires after 24 h
  user_id           BIGINT
  template, params, category, priority, created_at, expires_at

deliveries                        -- one row per (notification, channel, device)
  notification_id, channel, target    -- target: device token, phone or email
  status            -- queued | sent | delivered | failed | skipped
  attempts, provider, provider_msg_id, last_error, updated_at

preferences   PRIMARY KEY (user_id)   -- category -> allowed channels, quiet hours, time zone
devices       PRIMARY KEY (user_id, device_token)   -- platform, last_seen

The log takes thousands of writes a second, is read by id and expires after 90 days: a key-value or wide-column store with a TTL fits (such as DynamoDB or Cassandra). Preferences and devices are small, rarely change and are read on every send: a relational database with a read-through cache in front. The idempotency key needs an atomic "insert if absent", which both offer.

Sketch the path from a calling service to a phone, an inbox and a handset. Where do you check preferences, and where do queues go?

A thin API that validates, deduplicates, logs and returns 202; a router that applies preferences, rate limits and templates; then a queue and sender pool per channel, each talking to its provider. Channels fail and scale independently.

High-level design

Split the work where speed changes. The API must answer in milliseconds, so it only checks, records and enqueues. Providers are slow and unreliable, so each channel gets its own queue and senders; a slow email provider never holds up a push.

Deep dives

The pipeline: queues per channel and per priority

Push is fast and cheap, email providers can be slow, SMS is capped at 500 a second. In a shared queue the slowest channel sets everyone's pace. The 30-minute estimate shows priority needs the same treatment.

High and normal priority share the fast queue; bulk gets its own. Reserve the fast queue a share of senders and of each provider's rate limit, say 20%, and let bulk use the rest at a set pace below the provider ceiling. Retries go to a separate delay queue, so a failing message never blocks the head of the main queue.

Retries and duplicates

Every queue here delivers at least once (see Message Queues and Streams). A sender can crash after the provider accepts a message but before marking it done, so the user gets two texts. Exactly once is impossible: the provider call and your status write share no transaction. You can make duplicates rare:

  • Before sending, skip the job if its deliveries row already says sent. This closes most of the window, not all.
  • Send a stable id (n_501:email). Some providers drop repeats; push platforms collapse notifications that share a collapse key.
  • Retry only errors that can succeed later: timeouts, 5xx and 429. For an invalid device token or a hard bounce, remove the token or suppress the address.
  • Back off exponentially with jitter (1 s, 2 s, 4 s, capped at 10 minutes) until the deadline, then dead-letter.

Intake has the same gap: if the API crashes between writing the log and enqueuing, the caller's retry finds the key and stops. A sweeper re-enqueues anything still queued after a minute; routers skip ids already routed.

The deadline is a product decision per category. A login code is useless after 5 minutes, and a duplicate beats a loss, so retry hard. For marketing, a duplicate costs money, so retry less.

Preferences and rate limits

Check preferences in the router, as late as possible: a campaign that starts at 09:00 reaches some users at 09:29, and one who opted out at 09:15 must be skipped. Security alerts cannot be turned off. Quiet hours use the user's time zone: a normal message due at night waits until morning; a high-priority one goes through.

  • Per user, against spam: at most 3 marketing pushes a day, counted in the cache under a key like 42:marketing:2026-11-14.
  • Per caller, so a buggy service in a loop cannot flood users: a quota per API key, answered with 429.
  • Per provider, to stay under 500 texts a second: a token bucket shared by all SMS senders. See Rate Limiting.

When a provider fails

Providers fail by errors, slowness and silent loss. Slowness is worse than errors: senders wait and the queue grows. Use short timeouts and a circuit breaker per provider: if half the calls in 30 seconds fail, stop calling it for a while.

Silent loss is hardest: "accepted", then nothing arrives. Alert when a provider's delivery-receipt rate drops well below normal. For login codes, add a "resend code" button.

Bottlenecks and failures

At 10x, campaigns need about 280,000 sends a second and the log holds about 270 TB. Routers and senders are stateless and scale out. The first wall is provider limits: spread load across accounts and stretch campaigns over longer windows. Next is the preference cache: replicate it and keep a few seconds of copies in each router.

LevelWhat the answer does
JuniorAn API that calls providers directly, plus a preferences database. Adds a queue when asked about slow providers.
MidReturns 202, uses a queue per channel, checks preferences, retries with backoff, mentions idempotency keys.
SeniorFinds the campaign-versus-login-code conflict from the numbers and fixes it with priority queues and reserved capacity; makes duplicates rare, not impossible; sets deadlines per category; plans for provider slowness and silent loss.
The SMS provider times out on a login code. What do you do? I can't know if it was sent, so I retry: a duplicate code beats a missing one. If the circuit breaker is open, the retry goes to our second provider, which may mean two texts. The code expires in 5 minutes; that is the deadline. And for a marketing text? A duplicate costs money and annoys people, so I'd retry only the same provider with its message id, and accept losing a few. The same failure gets two answers, each tied to what the message is for. That is the judgement being tested.

Follow-up questions

How do you send a campaign to 50 million users?

A campaign job reads the segment in pages and feeds the bulk queues at a set pace, 28,000 a second for 30 minutes. It records progress so it can resume after a crash.

How do you handle device tokens that stop working?

Platform push services report invalid tokens. Delete them at once; dead tokens waste capacity and can count against you.

A user gets the same alert from three services. How do you stop it?

The router skips or merges an alert whose group key went to that user in the last 10 minutes. Better, give each event one owning service.

How do you send at 9 a.m. in each user's time zone?

Store scheduled notifications in buckets by send minute; a scheduler enqueues the current bucket. Time zones spread the load.

How do you know the system is healthy?

Track oldest-job age per queue, delivery rate per provider and dead-letter counts. Alert when high-priority queue age passes a few seconds; see Observability.
