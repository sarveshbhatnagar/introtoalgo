A swipe-based dating app shows one profile at a time. The user swipes right to say they are interested or left to pass, and when two people have swiped right on each other, both are told that they have matched. Interviewers ask for it because every swipe is a write, two people can swipe on each other at almost the same moment, and a user must never be shown the same profile twice.

The steps below follow A Framework for Any Design. Try each "Your turn" box before reading the answer.

Clarify the problem

Design the core of a swipe-based dating app. I understand it as profiles with preferences, a stack of nearby people who fit them, a swipe on each one, and a match when both swipe right. Is chat in scope? No, you can stop at the match. Assume 20 million daily users who each make about 100 swipes a day. Does the second person to swipe have to see the match immediately? Yes, the product is built around that moment. The first person gets a push notification. Then a match must never be missed or announced twice, it must appear within 200 ms, and no profile may be shown twice. A stack that is a few minutes old is acceptable. Naming the "never missed, never duplicated" requirement early shows the interviewer where you will spend your time.

Functional requirements

  • A user has a profile with photos and preferences: an age range, the genders they want to see, and a maximum distance.
  • The app serves a stack of candidates who fit my preferences and whose preferences I fit.
  • Two right swipes create a match, and a user can list their matches.

Non-functional requirements

  • A swipe, including the match answer, completes in under 200 ms.
  • Each pair of mutual right swipes produces exactly one match, and no profile is shown to the same user twice.
  • Right swipes must be durable. Losing a left swipe is acceptable, because the worst outcome is that someone is shown again.

Out of scope

Chat (see Design a Chat App), payments, photo moderation and the ranking model are out of scope.

Estimate the scale

Swipe rate

20 million users making 100 swipes each is 2 billion swipes a day. Dividing by about 86,400 seconds gives roughly 23,000 swipes a second on average, and an evening peak of about 3 times the average gives about 70,000 a second. Every swipe is a write. If 30% of swipes are right swipes, the peak is about 21,000 right swipes a second, and only those can create a match.

Storage and memory

  • Swipe history at about 50 bytes per swipe is 2 × 109 × 50 B = 100 GB a day, or about 36.5 TB a year.
  • Profiles for 100 million accounts at 2 KB each take 200 GB.
  • A cached stack holds 200 candidate ids of 8 bytes each, which is 1.6 KB per user, so 20 million daily users need 32 GB.

Write the endpoints for loading a stack and for swiping. How does the second swiper learn about the match immediately, and what happens if the phone retries a swipe?

A GET /stack call returns the next profiles, and POST /swipes returns whether the swipe produced a match in the same response. Swipes are identified by the pair (swiper, target), so a retry returns the same result and changes nothing.

Define the API

PUT  /me/profile          name, photos, bio, age range, genders wanted, max distance
PUT  /me/location         { "lat": 51.51, "lng": -0.12 }   sent when the app opens

GET  /stack?count=20
  200 { "profiles": [ { "user_id": "u_91", "name": "Ben", "age": 31,
                        "distance_km": 4, "photos": [...] }, ... ] }

POST /swipes
  body: { "target_id": "u_91", "direction": "right" }
  200 { "matched": true, "match_id": "u_12:u_91" }
  200 { "matched": false }
  404 Not Found     target deleted their account

GET  /matches?cursor=...

The API decision worth arguing is what the stack response leaves out. It could flag candidates who have already liked you, but then anyone inspecting the app's traffic could list everyone who liked them. The server keeps that to itself and checks it at swipe time.

The swipe call is idempotent for each (swiper, target) pair, so a retry returns the same answer and creates no second match (see idempotency and retries).

Sketch the records for profiles, swipe history and likes. Which key lets you answer "do these two people like each other?" with one atomic step?

Swipe history is keyed by swiper, which answers "who has this user already seen?". Likes are keyed by the pair of users, with the smaller id first and one flag for each direction. Both likes then live in a single row, and one atomic update can check them together.

Model the data

profiles                       -- relational, 200 GB
  user_id PK, name, birth_date, gender, bio, photo_urls,
  age_min, age_max, genders_wanted, max_distance_km,
  lat, lng, last_active_at

swipes                         -- wide-column, partition key swiper_id
  swiper_id, target_id, direction, created_at
  PRIMARY KEY ((swiper_id), target_id)    -- 2 billion rows a day

pair_likes                     -- sharded relational, key = the pair
  low_id, high_id              -- the two user ids, smaller first
  low_likes_high  BOOLEAN
  high_likes_low  BOOLEAN
  matched_at      TIMESTAMP NULL
  PRIMARY KEY (low_id, high_id)

The swipe history is append-only and read by swiper, which suits a wide-column store such as Cassandra. The pair row needs an atomic read-modify-write on a single key, so it lives in sharded relational tables or in a key-value store with conditional updates. It grows by up to 600 million rows a day (30% of 2 billion swipes), which is about 9 TB a year at 40 bytes a row, so the table is sharded by a hash of the pair. Profiles are relational, and their change stream updates the cached profile cards and a search index with a geo field.

Sketch how the system serves a stack, how it refills the stack, and how it records a swipe that may produce a match.

A stack service reads precomputed stacks from a cache. A stack builder queries the geo index and drops profiles the user has already seen. A swipe service appends to the swipe history and updates the pair row.

High-level design

Deep dives

Storing 70,000 swipes a second

Each swipe is a small append, and the only read is "all swipes by this user", which rebuilds a seen filter. A single relational primary cannot absorb 70,000 writes a second.

One option is to shard a relational database by swiper id, but that means rebalancing many shards for data that is never updated or joined. The other is a log-structured store such as a wide-column database (see indexing), which appends each write to memory and a commit log and flushes to disk in large sequential batches.

I choose the wide-column store, partitioned by swiper_id and clustered by target_id, so a repeated swipe overwrites one cell and a user's history is one partition of about 36,500 swipes a year, under 2 MB. Left swipes are 70% of the volume and only feed the seen filter, so one replica's acknowledgement is enough for them. Right swipes use a quorum write so none is lost.

Detecting a match exactly once

Ana and Ben may swipe right 3 ms apart on different servers, and the system must announce exactly one match.

Option 1: write my swipe, then read theirs

Each server writes "Ana likes Ben" under Ana's key, then reads whether Ben's key says he likes Ana. On an eventually consistent store both reads can run before either write has reached the replica they read, so neither server sees the other's like and the match is never created. With quorum reads and writes (R + W greater than N, no sloppy quorums) at least one request sees the other's like, but both can, so both would announce the match unless creation is idempotent.

Option 2: one row for the pair with an atomic update

Both directions are stored in one row keyed by the pair, and each swipe is an atomic update that sets its own flag. The database runs updates on one row one after the other, so the second update always sees the first one's flag and sets matched_at in the same statement. The cost is a second write for every right swipe.

Option 3: a stream partitioned by pair

Each right swipe is published to a stream partitioned by the pair key, and one consumer per partition processes both likes in order, with no locks. The weakness is that this is asynchronous, so the second swiper learns about the match later, by push, which breaks the 200 ms requirement.

The pair row is the right choice because the match must appear in the swipe response. The statement below is what Ben's server runs when he swipes right on Ana (Ana is user 12 and Ben is user 91). Ana's statement is the mirror image.

INSERT INTO pair_likes (low_id, high_id, low_likes_high, high_likes_low)
     VALUES (12, 91, false, true)
ON CONFLICT (low_id, high_id) DO UPDATE
   SET high_likes_low = true,
       matched_at = CASE WHEN pair_likes.low_likes_high
                         AND pair_likes.matched_at IS NULL
                         THEN now() ELSE pair_likes.matched_at END
RETURNING matched_at;    -- not null: tell Ben "It's a match"

Only the second swipe can see both flags, and detecting and storing the match are one write. If they were two steps, a crash between them would lose the match, because no later swipe rechecks those likes. A retry finds matched_at already set and returns the same answer, and the pair key doubles as the match id, so a redelivered event cannot create a second match.

Building the stack

A good candidate is nearby, fits my filters, has me inside theirs, is unseen and is recently active. The query could run when the user opens the app, which gives fresh data but makes the user wait for a geo query and a seen check on every open. The alternative is to precompute the stack in the background and cache it, so that opening the app is a cache read. I choose the second, because the requirements allow a stack a few minutes old.

The builder runs one query against the search index, with a geo filter built from cells and neighbouring cells as in Design Ride Sharing, plus filters on age, gender, the other person's preferences, and activity in the last 30 days. It drops profiles I have seen, ranks the rest, and caches 200 ids. The stack service serves 20 at a time and requests a refill when fewer than 50 remain, so a fast swiper never waits.

The cost of precomputing is staleness. A stacked profile may have been deleted since, so the stack service checks each batch of 20 against deletions before returning it.

Never showing a profile twice

The builder must remove everyone I have already swiped on from about 1,000 candidates.

Option 1: read the swipe history

The builder looks up each candidate in the user's swipe history. The answer is exact and nothing extra is stored, but every refill needs a batched read of up to 1,000 keys.

Option 2: keep an exact set in the cache

The cache holds every id the user has swiped on, so each lookup is one in-memory operation. At 10,000 swipes of 8 bytes each, that is 80 KB per user and 1.6 TB for 20 million users, which is a lot of cache memory for this one purpose.

Option 3: keep a Bloom filter in the cache

A Bloom filter (see Design a Web Crawler) answers either "definitely not seen" or "probably seen", so it never lets a repeat through. At a 1% false-positive rate it needs 12 KB per user, 240 GB in total. The cost is that about 1 in 100 unseen profiles is wrongly treated as seen and never shown, and a filter cannot remove items.

I choose the Bloom filter because a profile must never be shown twice, and it can only err in the safe direction. In a small town 1% of 1,000 candidates is 10 people who are never shown, so users with a small candidate pool should use the exact set instead. When a user outgrows the size the filter was built for, rebuild a larger one from the history, because an overfull filter's false-positive rate rises quickly.

Bottlenecks and failures

What breaks first at 10 times the load

At 10 times the load there are 700,000 swipes a second. The swipe history scales by adding nodes, because each user's partition is independent. The pair store adds shards for 210,000 right swipes a second, and a popular profile's likes are spread over many pair rows, so no row is hot.

Two people swipe right on each other in the same millisecond. What happens? Both likes go to one row keyed by the pair, and updates to that row run one after the other. Only the second request sees both flags, so it sets matched_at in the same statement and tells its user. That gives exactly one match, stored before anyone hears of it. Why not just read the other person's swipe? Replica reads can both miss the other's swipe, and strongly consistent reads can both see it and announce twice. The pair row gives exactly one match, at the price of one extra write for each right swipe.

Follow-up questions

How would you add a "see who liked you" feature?

The data is the set of pair rows where their flag is set and mine is not. Querying that needs an index by user, so I would keep a per-user "liked by" list fed from the pair rows' change stream. The server returns it only to entitled users and never puts it in the stack.

A user travels to another city. What changes?

The location update moves the user's document in the geo index and discards their cached stack, so the next refill is built for the new place. The seen filter is kept.

A user unmatches. Can they appear again?

No. The swipe stays in the history and the seen filter, so neither person is shown to the other again. The pair row keeps both flags and gains an unmatched_at time, so a retried swipe cannot recreate the match.

How would you shard the geo index?

Shard it by region and cap the maximum distance at about 100 km, so a query stays in one region. Big cities get more replicas, and a profile near a border is stored in both regions.
