A key-value store does two things: put(key, value) and get(key). On one machine that is a hash map with a log. Over thirty machines that fail, you must decide where each key lives, how many copies to keep, what a read returns while copies disagree, and how they heal.

It tests whether you are precise about guarantees; "eventually consistent" is not an answer. It follows A Framework for Any Design and leans on Consistent Hashing and Replication.

Clarify the problem

The design swings on one answer, so ask it early: during a failure, refuse writes, or accept them and sort out conflicts later?

Design a distributed key-value store. How big are keys and values, do we need more than get, put and delete, and how much data and traffic? Keys up to 256 bytes, values up to 1 MB but usually around 10 KB. Just get, put and delete. About 2 billion keys; at peak, 150,000 reads and 50,000 writes a second. If a node or link fails, should we reject writes, or accept them and resolve conflicts later? Think of a shopping cart. Accept them; a lost "add to cart" costs money. Some callers want stronger reads, though. Then I'll favour availability, make consistency tunable per request, and never lose an acknowledged write. One region, three zones. Asking in product terms gets a clear answer that justifies every later choice.
  • Functional: get, put and delete by key; the caller chooses how many replicas must answer.
  • Non-functional: writes accepted with some replicas down; p99 under 10 ms in the region; at the default level, an acknowledged write survives any one node failure; grows without downtime.
  • Out of scope: range scans, secondary indexes, multi-key transactions, multiple regions.

Estimate the scale

Write the three operations. What does get return when replicas disagree, and what must the caller send back on put?

get can return several values (siblings) plus an opaque context of their versions, which the next put sends back.

Define the API

get(key, read = "quorum")
  -> { values: [v1, ...], context }   one value normally; several after a conflict
  -> NOT_FOUND
  -> UNAVAILABLE                      fewer than R replicas answered in time

put(key, value, context?, write = "quorum")
  -> OK                               W replicas have it in their commit logs
  -> UNAVAILABLE                      fewer than W confirmed in time (it may
                                      still be stored on some replicas)
  -> TOO_LARGE                        key over 256 B or value over 1 MB

delete(key, context?, write = "quorum")   writes a tombstone

read / write levels: "one" | "quorum" | "all"   (R or W out of N = 3)

The decision worth arguing is the context. Without it, the newest timestamp wins and one of two concurrent writes silently vanishes. With it, the store can tell "this replaces what you read" from "these happened in parallel" and hand both back to merge. It adds work for callers, so make it optional: no context means last-write-wins.

What does a record hold besides key and value? What must each node know about the cluster?

A version vector, timestamp and tombstone flag. Each node also holds the ring and, via gossip, who is alive.

Model the data

record   (on disk, sorted by key)
  key              up to 256 B
  value            up to 1 MB, about 10 KB on average
  version          version vector, e.g. {B: 3, C: 1}, about 16 B per entry
  timestamp        8 B, used only for last-write-wins and tombstone expiry
  tombstone        1 bit: this key was deleted

cluster metadata (same on every node, a few MB)
  ring             node -> its virtual-node positions on the hash ring
  membership       node -> zone, status (up / suspected / leaving), heartbeat

Every operation is a single-key lookup or overwrite, and each node takes 5,000 replica writes a second to random keys. An LSM tree turns them into sequential appends (see Indexing), at the cost of reads that may check several files. With rare writes, a B-tree would win.

Sketch a put: who receives it, how it finds the key's owners, when it says "done", and what happens if an owner is down.

No leader. The receiving node hashes the key, walks the ring to the next 3 distinct nodes, writes to all 3 and replies after 2 confirm. If an owner is down, a stand-in keeps the write as a hint and passes it on later.

High-level design

Any node can coordinate any request, since every node knows the ring (about 100 virtual nodes per server). A key's preference list is the first 3 distinct servers clockwise from its hash, in 3 zones; skip points of servers already picked, or one zone outage could take every copy.

Deep dives

Partitioning with consistent hashing

Consistent Hashing covers virtual nodes. What they buy a replicated store is parallel rebuilds. A dead node's 2 TB is spread in small ranges over the other 29. If each streams its share at 100 MB/s, the rebuild takes 2 × 1012 ÷ (29 × 108) ≈ 690 s, about 11 minutes. From one peer it would take 5.6 hours.

Replication and tunable quorums

Each key has N = 3 replicas; a write waits for W of them, a read for R. Replication shows why R + W > N makes read and write sets overlap. Pick values per use case:

Setting (N = 3)What you getWhat it costs
W = 2, R = 2Reads normally see the latest acknowledged write; survives one replica down.Waits for the second-fastest replica. The default.
W = 1, R = 1Fastest; writes succeed with two replicas down.A read can miss a write that just succeeded. Fine for caches and sessions.
W = 3, R = 1Fast reads that see every acknowledged write.Any one replica down blocks all writes to its keys.

R + W > N guarantees overlap, not linearizability: concurrent writes both succeed, a failed write can still appear on one replica, and two reads during a write can see new then old. A sloppy quorum breaks even the overlap: if stand-ins like E met W, the real owners can miss the write until the hint arrives. See CAP and Consistency.

Resolving conflicts

A store that takes writes during failures lets two clients update one key unaware of each other.

A version vector detects concurrency but does not resolve it. Someone still merges, and a plain union has a flaw: an item removed on one device returns from the other.

Detecting failures and repairing data

No central monitor decides who is dead. Each node gossips its heartbeat counter to a few random peers every second; if one stalls for, say, 10 seconds, peers mark that node suspected: slow and dead look alike.

A suspected node gets hinted handoff and no data moves: streaming 2 TB for a node that reboots in a minute does harm. Its ranges rebuild only once an operator, or automation with a long timeout, declares it gone. Three mechanisms repair data:

  • Hinted handoff covers short outages. A node down 10 minutes misses 5,000 writes a second × 600 s = 3 million writes, about 30 GB, held by stand-ins.
  • Read repair fixes stale copies a read notices.
  • Anti-entropy catches the rest. Two replicas compare a Merkle tree (hashes over sub-ranges) and descend only into branches that differ. With 200 million keys per node and 215 leaves, one wrong key costs a walk down 15 levels and a sync of one leaf of about 6,000 keys, not 200 million.

The storage engine, in outline

Writes go to the commit log and a sorted in-memory table, later written out as immutable sorted files that compaction merges. A read checks memory, then files newest first, skipping any whose Bloom filter says "definitely not here".

Deletes are the trap. A delete writes a tombstone, which compaction may drop only after a grace period, typically days. If a replica missed the delete and the tombstone is purged before repair reaches it, anti-entropy copies the old value back: the deleted key returns. The grace period must outlast the longest outage you repair from.

Bottlenecks and failures

At 10x (600 TB replicated, 2 million operations a second), you need about 300 nodes. Consistent hashing handles growth, but hot keys do not spread (a popular key still lives on 3 nodes), and compaction debt, writes outrunning merging, makes reads check more files: watch files per read and throttle writes early.

R + W > N only makes read and write sets overlap. Linearizable reads need a leader per range chosen by consensus, at the cost of availability during failover.

What a strong answer sounds like

LevelWhat the answer does
JuniorShards by hash, adds replicas, says "eventually consistent". Needs prompting on disagreeing replicas.
MidVirtual nodes, R + W > N, read repair and hinted handoff.
SeniorTies choices to the availability requirement, says what quorums do not guarantee, prices last-write-wins and version vectors, separates temporary from permanent failure, knows why tombstones need a grace period.
With N = 3, W = 2, R = 2, is this strongly consistent? Not linearizable. Every read overlaps every acknowledged write, so normally it sees the latest. But concurrent writes both succeed as siblings, a failed write can still show up, and with a sloppy quorum a read can miss a write until the hint arrives. So when would you not use this design? For an account balance or a uniqueness check. Those need one leader per range with consensus; writes pause a few seconds during failover, the right trade for them. A weak answer says "yes". The strong one says what overlap gives, how it falls short, and when to choose another design.

Follow-up questions

How would you run it in two regions?

Keep N replicas per region, acknowledge after a local quorum, and replicate across regions asynchronously. Version vectors catch cross-region conflicts; a region failure loses the last unreplicated writes.

How do you support range scans?

Hashing scatters neighbouring keys. Partition by key range instead: it keeps order, but hot or large ranges must be split. One layout cannot do both.

How do you add expiry (TTL)?

Store an expiry time with the record; reads treat expired records as missing. The expired record must then act as a tombstone for the grace period, or an older copy without the expiry comes back through repair.

How does a new node join without downtime?

It takes about 100 points on the ring. Current owners stream it each range it now owns while new writes also go to it. It serves reads once streaming ends; then the old owners drop their copies.

One key gets 100,000 reads a second. What now?

With R = 2, that is 200,000 replica reads on 3 nodes, about 67,000 each: over 4 times a node's normal 15,000. Cache it for a second in the coordinators, or read with R = 1 if slight staleness is fine.
