You finish a match and the screen says "You are now #48,213 this week, up 2,904 places", with the players just above and below you. Another tab shows the world top 10, updating as you watch.

The first answer, ORDER BY score DESC, works for a thousand players and fails for fifty million: a rank means counting everyone above you. It tests whether you know a structure that counts in O(log n), keep an in-memory board durable, and can shard one global order. The steps follow A Framework for Any Design; try each "Your turn" box before you read on.

Clarify the problem

Design a leaderboard for an online game. Is a score the best single match, or points summed over matches? And which boards: all-time, weekly, daily? Best match score. All three boards. How many players, and how often do scores change? 50 million players on the all-time board, 10 million play each day, about 10 matches each. Scores come from our game servers, not phones. A lost score is worse than a slow one, so ranking can live in memory but scores must be durable. How do ties break? Whoever reached the score first. "Best" versus "sum" changes how updates combine; the tie rule changes the data. Asking both shows you know where the details hide.
  • Functional: record a score; keep each player's best per board; show the top 10, and a player's rank with the 5 above and below.
  • Non-functional: new scores ranked within about a second; reads under 50 ms; no accepted score lost; earlier score wins ties; boards readable when a node fails.
  • Out of scope: anti-cheat, friends-only boards (a follow-up), rewards for top players.

Estimate the scale

  • Score writes: 10 million × 10 = 100 million matches a day ÷ 86,400 ≈ 1,200 a second, about 5,800 at a 5x evening peak. Each updates three boards: 3 × 5,800 = 17,400 board writes a second.
  • Reads: assume 3 views per match: 300 million a day, about 3,500 a second, 17,000 at peak.

Who submits a score, and how does a client read the top 10 and "my rank"? What if a score arrives twice?

The game server submits a score with a match id, so a retry is ignored. The phone reads top and around me per board.

The decision worth arguing is who may write a score. If phones post scores, anyone with a proxy can claim 99,999. The game server that ran the match submits it, with a match_id that makes retries safe.

What is the durable record, and what answers "rank of player 42" in milliseconds? Same store?

Two stores: a durable database row per player per board, and an in-memory sorted set per board that ranks in O(log n) and is rebuilt from the rows.

Model the data

-- source of truth: a database, partitioned by player_id
best_scores
  board_id     VARCHAR(24)    -- "all_time", "weekly:2026-W46", "daily:2026-11-14"
  player_id    BIGINT
  score        INT
  reached_at   TIMESTAMP      -- for ties: earlier wins
  updated_at   TIMESTAMP      -- indexed, for replays after a failover
  PRIMARY KEY (board_id, player_id)

matches_applied               -- each match counted once
  PRIMARY KEY (player_id, match_id)   -- same partition as the player's rows,
                                      -- so one local transaction covers both

-- ranking: one in-memory sorted set per board
weekly:2026-W46   member = player_id, sort key = score with tie-break (see deep dive)

A score update writes one player's row: any database with a conditional update ("set 4200 if higher") works, partitioned by player. A rank is a query over everyone: SELECT COUNT(*) WHERE score > 4200 walks every higher index entry, up to 50 million. An in-memory sorted set, as in Redis, takes about log2(50 million) ≈ 26 steps, so rankings live there: a fast, rebuildable view of the database.

Sketch the write path from a finished match and the read path for "my rank". Which store is written first?

Game server, score service, database (deduplicated by match id), then sorted sets. Reads hit only the sorted sets. Database first means a crash can only leave the sorted set behind, which a replay fixes.

High-level design

Deep dives

The sorted-set structure

A sorted set is two structures kept in step: a hash map from player to score, and an index sorted by score (a skip list or a balanced tree). The trick: every index link stores how many entries it jumps over. To find a rank, walk from the top and add up the jumps, never visiting the entries you skip.

A skip list is a sorted linked list with express lanes: level 0 links every entry; each level above links a random half of the one below.

Updating a score is remove plus insert, each O(log n), fixing spans on the way. A balanced tree storing subtree sizes costs the same; skip lists are simply easier to make fast in memory.

Sharding a sorted set

Say it first: 5 GB and 51,000 operations a second fit on one primary with read replicas. Shard at 10x or with hundreds of boards.

  • Shard by player id (hash). Writes spread evenly. Top 10: take each of, say, 8 shards' top 10 and keep the best 10 of those 80; exact, because every global top-10 player is in their shard's top 10. Rank: ask every shard "how many scores beat 4,200?" (O(log n) each) and add. Neighbours: merge each shard's 5 entries just above and below 4,200 and keep the nearest 5 each side.
  • Shard by score range. Rank is the count of all higher shards plus your rank inside yours. But the top shard is hottest, ranges need rebalancing as scores grow, and players crossing a boundary move shards.

Pick hashing by player. Its cost: 8 parallel calls per rank lookup, as slow as the slowest. The cached top 10 is merged once a second.

Durability of an in-memory board

An in-memory store's own persistence (a log flushed every second, snapshots, asynchronous replicas) can each lose the last moment of writes. Better: stop needing the board to be durable, and repair it from the database:

  • After a failover, replay rows with updated_at in the last few minutes. "Set if higher" is idempotent and order-free, so overlapping replays are safe.
  • After losing everything, rebuild from the database: at an assumed 500,000 inserts a second, 50 million entries take 100 seconds. Serve the cached top 10 meanwhile.
  • If boards were sums, increments are not idempotent. Apply each match once in the database (matches_applied) and write the new total into the set, never "add 300".

Writing scores only to the sorted set means a failover can silently drop the last second of bests, and nobody can tell which.

Daily and weekly boards, and ties

Each period is its own sorted set, keyed by period (weekly:2026-W46), so a new period starts empty. When it ends, copy its top results to the database and let the set expire. Two details:

  • Late scores: use the match's ended_at, not arrival time, and keep the previous period open a few minutes before declaring final results.
  • Whose clock: pick one, usually UTC. Per-region boards with local midnights are just more keys.

For ties, put "earlier wins" in the sort key. Pack one number: the score in the high bits and (220 − 1 − seconds into the week) in the low bits, so earlier means bigger. A week's 604,800 seconds fit in 20 bits (220 = 1,048,576), as do scores up to a million. Example: score 4,200 reached 190,800 seconds in gives 4,200 × 1,048,576 + (1,048,575 − 190,800) = 4,404,876,975. Forty bits, safely below the 53 bits a 64-bit float holds exactly; some sorted sets store scores as floats. All-time needs about 30 bits for 34 years of seconds: 50 in all.

If equal scores should share a rank ("joint 12th"), compute rank as "players with a strictly higher score, plus 1": a count by score range, not a position.

Bottlenecks and failures

At 10x (58,000 matches a second at peak, about 514,000 sorted-set operations a second), shard by player into, say, 8 sets per board. The database takes 58,000 conditional updates a second, partitioned by player. Most matches do not beat the player's best, so the sorted sets see fewer writes.

What a strong answer sounds like

LevelWhat the answer does
JuniorUses a table with ORDER BY; adds a cache when asked about load.
MidExplains why counting rows is slow, uses a sorted set with O(log n) rank, adds weekly boards as separate keys.
SeniorKeeps the board rebuildable from the database, sizes it before sharding, merges shard top 10s correctly, makes updates idempotent, packs ties into the sort key.
How do you show a player their rank? From an in-memory sorted set. Its index stores how many entries each link skips, so rank is a sum along about 26 levels, not a count of 48,000 rows. At 5 GB one primary holds it, and it rebuilds from the database in about 100 seconds. And at 500 million players? Shard by player. Top 10 is an exact merge of each shard's top 10; rank is a parallel count of higher scores per shard. If that is too slow, exact rank at the top and score-bucket counts for "about #2 million" below.

Follow-up questions

How would you build a friends-only leaderboard?

Not a sorted set per player. Fetch the few hundred friends' scores in one batch and sort on read, in microseconds.

The top 10 must update live on screen. How?

Recompute it once a second and push it over server-sent events, or let viewers poll the cached copy.

How do you stop cheating?

Only game servers write scores, after validating the match. Scores far above a player's history stay hidden until reviewed.

Why not a heap for the top 10?

A heap gives the top k cheaply, but not anyone's rank, and updating an arbitrary player needs extra bookkeeping. The sorted set answers all three questions.

What if a score must be removed after a ban?

Delete the row and remove the member from each sorted set. Everyone below moves up automatically, because ranks are computed, not stored.
