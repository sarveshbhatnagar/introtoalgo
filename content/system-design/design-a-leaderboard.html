A leaderboard records the best score of each player in a game and shows the top players, together with a player's own rank and the players just above and below them. The system receives a stream of score updates and must answer rank queries immediately after each update.

The difficulty is the rank. The obvious query, ORDER BY score DESC, works for a thousand players, but with fifty million players, finding a rank means counting everyone with a higher score. Interviewers ask it to see whether you know a structure that ranks in O(log n), can keep an in-memory ranking durable, and can split one global order across machines. The steps follow A Framework for Any Design.

Clarify the problem

Design a leaderboard for an online game. Is a player's score the best single match, or the total of all their matches? And which boards do we need: all-time, weekly, daily? The best single match score. We need all three boards. How many players are there, and how often do scores change? There are 50 million players on the all-time board. About 10 million play each day, and each plays about 10 matches. I will assume that scores are submitted by our game servers and not by the players' phones. A lost score is worse than a late one, so the ranking can live in memory but the scores must be durable. How should ties be broken? The player who reached the score first ranks higher. Whether a score is a best or a sum changes how updates combine, and the tie rule changes the data you store.
  • Functional: record a score and keep each player's best score on each board; show the top 10; show a player's rank together with the 5 players above and the 5 below.
  • Non-functional: a new score appears in the rankings within about a second; reads take under 50 ms; no accepted score is lost; the player who reached a score first wins a tie; the boards stay readable when one node fails.
  • Out of scope: cheat detection and rewards for top players.

Estimate the scale

  • Score writes: 10 million players × 10 matches is 100 million matches a day. Dividing by 86,400 seconds gives about 1,200 matches a second, and a 5x peak gives about 5,800. Each match updates three boards, so the peak is 3 × 5,800 = 17,400 board writes a second.
  • Reads: assume 3 views per match, which is 300 million a day, about 3,500 a second and about 17,000 at peak. The top 10 comes from a 1-second cache, and each rank read needs 2 sorted-set operations.
  • Operations at peak: 17,400 board writes plus 17,000 × 2 = 34,000 read operations is 51,400 sorted-set operations a second. If one node performs about 100,000 such operations a second (state this assumption), one primary is about half busy, and read replicas add headroom.

Who submits a score, and how does a client read the top 10 and its own rank? What should happen if the same score arrives twice?

The game server submits each score together with a match id, so a retried request is ignored. The app reads the top entries and "around me" for each board.

The API decision to argue about is who may write a score. If phones post scores, anyone with a proxy can claim 99,999 points. The game server that ran the match submits the score with a match_id, so a retry cannot count a match twice.

What is the durable record, and what answers "what is the rank of player 42" in milliseconds? Can one store do both jobs?

Two stores are used. A database holds one durable row per player per board, and an in-memory sorted set per board answers rank queries in O(log n). The sorted sets can be rebuilt from the database rows.

Model the data

-- source of truth: a database, partitioned by player_id
best_scores
  board_id     VARCHAR(24)    -- "all_time", "weekly:2026-W46" or "daily:2026-11-14"
  player_id    BIGINT
  score        INT
  reached_at   TIMESTAMP      -- used to break ties, the earlier time wins
  updated_at   TIMESTAMP      -- indexed, used to replay recent changes after a failover
  PRIMARY KEY (board_id, player_id)

matches_applied               -- records each match so that it is counted once
  PRIMARY KEY (player_id, match_id)   -- stored in the same partition as the player's rows,
                                      -- so one local transaction covers both tables

-- ranking: one in-memory sorted set per board
weekly:2026-W46   member = player_id, sort key = score combined with a tie-break (see deep dives)

A score update changes one player's row, which any database can do with a conditional update such as "set the score to 4,200 if it is higher". Finding a rank is a different kind of query: SELECT COUNT(*) WHERE score > 4200 has to walk every higher entry in the score index, which can be up to 50 million entries. An in-memory sorted set, such as the one in Redis, finds a rank in about log2(50 million), or roughly 26, steps. The sorted sets therefore hold the rankings as a fast view of the database that can be rebuilt from it.

Sketch the write path for a finished match and the read path for "my rank". Which store is written first?

The path is game server, score service, database (deduplicated by match id), then the sorted sets. Reads use only the sorted sets. The database is written first, so a crash can only leave the sorted set behind, and a replay repairs that.

High-level design

Deep dives

How to compute a rank

There are three ways to answer "what is my rank?".

A database query. The database stores one row per player with an index on score, and the rank is COUNT(*) of the rows with a higher score, plus one. A rank near the bottom is not cheap, because the database has to walk every higher index entry, which for rank 30,000,000 means 30 million entries for a single request. This is correct and acceptable for tens of thousands of players.

An in-memory sorted set. A sorted set keeps two structures in step: a hash map from player to score, and an index ordered by score, built as a skip list or a balanced tree. Every link in the index stores how many entries it jumps over. To find a rank, the lookup walks down from the top of the index and adds up those counts, so it never visits the entries it skips. Rank, top N and a range around a player take O(log n). The cost is that the sorted set lives in memory, so it needs a durable source to rebuild from, and a single set is limited to the throughput of one node.

Score-bucket counts. Instead of ordering players, you count how many players have each score value and keep the counts in a Fenwick tree. A player's rank is the sum of the counts of all higher scores, which takes O(log of the score range). It cannot tell you who the neighbours are. It suits very large boards where an approximate rank is acceptable below the top.

Why a sorted set finds a rank in O(log n)

A skip list is a sorted linked list with express lanes. Level 0 links every entry, and each higher level links a random half of the entries on the level below. Every link also records its span, the number of entries it jumps over. To find a rank, the lookup starts at the top level and moves forward while the next entry scores higher than the target, adding the span of each link it follows, and drops a level when the next entry would pass the target. Take players A 980, B 950, C 900, D 870, E 820 and F 760, where level 1 links the head, B, D and F with a span of 2 each. The rank of C is found by following the level 1 link to B, which adds 2, then dropping to level 0, where the next entry is C itself. Two players are above C, so its rank is 3, and A was never visited. With 50 million players there are about 26 levels and a couple of links per level, so a rank takes roughly 50 steps instead of a count over tens of millions of entries.

Updating a score removes the old entry and inserts the new one, each in O(log n). A balanced tree that stores subtree sizes costs the same.

Sharding the sorted set

Say first that sharding is probably not needed: the boards take 5 GB and the peak load is about 51,000 operations a second, which one primary with read replicas can handle. Sharding becomes necessary at roughly 10x this load.

Shard by player id. A hash of the player id picks the shard, so writes spread evenly. Queries then have to combine results from all shards. For the top 10 with, say, 8 shards, you take each shard's top 10 and keep the best 10 of those 80 entries, which is exact because every player in the global top 10 is also in the top 10 of their own shard. For a rank, you ask every shard how many scores are higher than 4,200 (O(log n) on each) and add the answers. For the neighbours, you take each shard's 5 entries on each side of the score and keep the nearest 5 on each side. The cost is that every rank lookup makes 8 parallel calls and is as slow as the slowest.

Shard by score range. Each shard owns a band of scores. A rank is then the number of players in all higher shards (a small stored counter) plus the player's rank inside their own shard, so a lookup touches only one shard. The problems are that the shard with the top scores is the hottest, the bands need rebalancing as scores grow, and a player who crosses a boundary has to move shards.

Choose hashing by player. Even load matters more than saving parallel calls, and the cached top 10 is merged once a second.

Keeping the in-memory board durable

The persistence features of an in-memory store (a log flushed every second, snapshots, asynchronous replicas) can each lose the most recent writes. A better design makes the database the only source of truth and treats the sorted set as a copy that can be repaired:

  • After a failover, replay the rows whose updated_at falls in the last few minutes. Setting a score only if it is higher gives the same result when applied again and in any order, so overlapping replays are safe.
  • After losing every copy, rebuild the board from the database. At an assumed 500,000 inserts a second, 50 million entries take 100 seconds.

Daily and weekly boards

Each period gets its own sorted set, named after the period, such as weekly:2026-W46, so a new period starts with an empty set and needs no cleanup job. When a period ends, copy its final top results to the database and let the set expire. Late scores are assigned by the match's ended_at time and not by when they arrive, the previous period stays open for a few minutes before its results are final, and the boundaries use one agreed clock, usually UTC.

Breaking ties

To make the earlier player win a tie, put the time into the sort key. Pack one number with the score in the high bits and (220 − 1 − seconds into the week) in the low bits, so that an earlier time gives a bigger number. A week has 604,800 seconds, which fits in 20 bits (220 = 1,048,576), and so do scores up to a million. For example, score 4,200 reached 190,800 seconds into the week gives 4,200 × 1,048,576 + (1,048,575 − 190,800) = 4,404,876,975. This number has 40 bits, below the 53 bits that a 64-bit float stores exactly, which matters because some sorted sets store scores as floats. The all-time board needs about 30 bits for 34 years of seconds, so 50 bits in total.

If players with equal scores should share a rank, such as "joint 12th", compute the rank as the number of players with a strictly higher score plus one. That is a count over a score range and not a position in the order.

Bottlenecks and failures

At 10x the load there are about 58,000 matches a second at peak and about 514,000 sorted-set operations a second, which is too much for one primary, so you shard each board by player into, say, 8 sorted sets. The database takes 58,000 conditional updates a second, which works because it is partitioned by player.

What a strong answer sounds like

A weak answer stops at a table with ORDER BY. A strong answer explains why counting rows is too slow, uses a sorted set, keeps the board rebuildable from the database, makes updates safe to repeat, and shards by player with a correct merge of the top 10.

How do you show a player their rank? I keep the board in an in-memory sorted set. Each link in its index stores how many entries it skips, so the rank is a sum along about 26 levels and not a count of 48,000 rows. The board is 5 GB, so one primary holds it. What changes at 500 million players? I would shard by player. The top 10 is an exact merge of each shard's top 10, and a rank is the sum of a parallel count of higher scores on every shard. If that is too slow, I would keep exact ranks for the top entries and use score-bucket counts to give an approximate rank such as "about #2 million" below them.

Follow-up questions

How would you build a friends-only leaderboard?

A sorted set per player would be far too much data to keep up to date. Instead, fetch the scores of the player's few hundred friends in one batch and sort them on request.

The top 10 must update live on screen. How?

Recompute the top 10 once a second and push it to connected clients over server-sent events or a WebSocket.

Why not use a heap for the top 10?

A heap returns the top k entries cheaply, but it cannot tell you the rank of an arbitrary player, and changing the score of an arbitrary player needs extra bookkeeping to locate the entry. The sorted set answers all of these with one structure.

What if a score must be removed after a ban?

Delete the player's row in the database and remove the member from each sorted set. Every player below moves up automatically, because ranks are computed and not stored.
