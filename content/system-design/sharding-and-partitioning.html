A chat app stores 20 billion messages of about 400 bytes: 20 × 109 × 400 B = 8 TB. At peak it writes 30,000 a second. Replicas do not help: each holds all 8 TB and applies all 30,000 writes.

Sharding gives each machine a slice: with 8 shards, each holds about 1 TB and takes 30,000 ÷ 8 ≈ 3,750 writes a second.

The idea

A shard (or partition) is a subset of the rows on its own machine. A shard key, such as chat_id, decides which shard each row lives on. A query with the shard key goes to one shard; one without must ask them all.

Each shard is usually a small leader-follower group: sharding splits the work, replication protects each piece.

The cost: cross-shard joins and transactions become hard, every query must consider the shard key, and moving data is a project. That pain is permanent, so shard only when one machine cannot cope.

Three ways to map keys to shards

A common mistake is plain hash(key) mod 8. Going from 8 to 9 shards, a key stays put only if its hash gives the same remainder for 8 and 9: 8 values in every 72. So 64 ÷ 72 ≈ 89% of the data moves. Two fixes: consistent hashing, or many fixed partitions: hash keys into 1,024 partitions once and give each shard 128. A new shard takes whole partitions from the others, and only about 1 ÷ 9 ≈ 11% of the data moves.

Choosing the shard key

The checklist (applied to a booking system in data modeling):

  • The hottest queries include it. "Latest 50 messages in chat 8813" names the chat, so chat_id puts the whole query on one shard.
  • Things that change together share it. A transaction inside one shard is ordinary; across shards it is not.
  • Many distinct values, spread evenly. country has a few hundred values and a handful of giants: a few huge shards.

Hot keys

A good key still has outliers. A 50,000-member group chat may take 2,000 messages a second during an event, all on one shard. If that is a real requirement, split the key: write to a random one of chat:8813#0 to chat:8813#9, 200 a second each, and have reads gather the 10 and merge by time. Only for known hot keys: every read now costs 10 lookups.

Cross-shard queries

A query without the shard key goes to every shard and merges the answers (scatter-gather), so it is as slow as the slowest shard. If each is slow 1% of the time, a query to all 8 is slow 1 − 0.998 ≈ 7.7% of the time; with 100 shards, 1 − 0.99100 ≈ 63%. Keep them rare, or serve them from a copy sharded by their field, or a search index.

Adding a shard without downtime

8 shards, 1,024 partitions. A ninth shard joins and takes about 14 partitions from each of the 8, one at a time.

Numbers worth remembering

  • Plan for both limits: data per machine (often about 1 TB or less, so moves and rebuilds are quick) and writes per machine (roughly thousands a second for a relational primary).
  • Far more partitions than machines (hundreds to thousands), so growth moves whole partitions.
  • Scatter-gather tail: 1 − 0.99n of queries hit a slow shard.

In the interview

Bring up sharding when your estimate says one machine cannot cope. Name the shard key, the query it serves, the query it hurts, and how you handle hot keys and growth.

8 TB and 30,000 writes a second. How do you store messages? Shard by chat_id, hashed into 1,024 partitions over 8 shards. Loading a chat, the hottest query, hits one shard. A user's inbox would fan out, so it gets its own table sharded by user_id, updated with each message. One chat goes viral. Now what? Its partition runs hot. If one chat really takes thousands of messages a second, I'd split its key into 10 sub-keys for writes and merge on read, only for chats we flag as huge. The key is justified by a query, the cost is named, and the hot-key fix stays where needed.

Follow-ups to expect:

  • "How do you keep usernames unique across shards?" Shard the usernames table by username, so the check is one shard.

Common mistakes

Every new row has the latest time, so every write lands on the last shard while the others idle. Hash the key, or lead with something spread out (chat_id, then time).
