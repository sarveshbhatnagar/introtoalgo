A photo app saves each upload in a database column. Users add 2 million photos a day at about 3 MB each: 2 × 106 × 3 MB = 6 TB a day, about 2.2 PB a year. Every replica copies every byte, the nightly backup no longer finishes overnight, and each 3 MB upload ties up an app server while it streams through.

The database is good at small rows that change and get queried. Photos are large, written once and read whole. They belong somewhere else.

The idea

An object store (such as Amazon S3 or any of its look-alikes) keeps blobs of bytes under keys like photos/7f3a9c/original.jpg. You PUT an object, GET it, or DELETE it, over HTTP. There are no folders, only key prefixes, and an object is replaced whole, never edited in place.

In exchange it is cheap per gigabyte, scales to petabytes without you thinking about disks, and is built to be extremely durable. The costs: the first byte takes tens of milliseconds, small partial updates are impossible, and listing millions of keys is slow. So the rule is simple: metadata in the database, bytes in the object store. The database row says who owns the photo, its size, its status and its object key. The object store holds the bytes.

Objects, files and blocks

The metadata row is small and ordinary:

id          BIGINT PRIMARY KEY
owner_id    BIGINT
object_key  TEXT        -- "photos/7f3a9c/original.jpg", generated, never the user's filename
size_bytes  BIGINT
status      TEXT        -- pending | ready | deleted
created_at  TIMESTAMP

Uploading without touching the bytes

App servers should not relay uploads: 6 TB a day through them is about 6 × 1012 ÷ 86,400 ≈ 70 MB/s on average, all of it wasted work. Instead the server hands the client a pre-signed URL: a link to one object key, signed with the server's credentials, that allows one action for a short time. The client sends the bytes straight to the store.

Multipart upload for big files

A 2 GB video over a 20 Mbps connection takes 2 × 109 × 8 bits ÷ 2 × 107 bits/s = 800 seconds, about 13 minutes. One upload that fails at 90% throws away 12 minutes of work. Multipart upload splits the file into parts, here 2 GB ÷ 100 MB = 20 parts. Each part is a separate request, can go in parallel, and is retried on its own; a failure costs at most one part, 100 MB at 20 Mbps = 40 seconds. A final "complete" call tells the store to stitch the parts into one object. Set a lifecycle rule to clean up uploads that were started and never completed, or their parts sit there costing money.

Durability: copies or erasure coding

Object stores survive disk and rack failures in one of two ways. Replication stores 3 full copies on different machines: 3x the raw storage, simple, and fast to read and rebuild. Erasure coding splits an object into, say, 10 data fragments, computes 4 parity fragments, and spreads all 14 across different disks. Any 10 of the 14 rebuild the object, so it survives 4 lost fragments while using only 14 ÷ 10 = 1.4x the space. The price: rebuilding one lost fragment reads 10 others, and small objects pay overhead. Stores often replicate hot or small objects and erasure-code large, colder ones.

Numbers worth remembering

  • Object store first-byte latency: tens of milliseconds, much more than a database row read. Put a CDN in front of anything popular.
  • Replication: 3x raw space. Erasure coding with 10 + 4 fragments: 1.4x, survives 4 losses.
  • Upload time = size in bits ÷ link speed. 1 GB at 10 Mbps is 8 × 109 ÷ 107 = 800 seconds.

In the interview

Bring in blob storage as soon as the product has images, video, documents or any file bigger than a few hundred kilobytes. Say where the bytes go, where the metadata goes, and that uploads bypass your servers.

How do users upload photos? The client asks our API for an upload URL. The API writes a pending metadata row and returns a pre-signed URL for one key, valid 15 minutes. The client uploads straight to the object store, so 70 MB/s of photos never touch our servers. An upload event triggers thumbnailing and marks the row ready. What if the upload succeeds but the event is lost? The row stays pending. A sweeper checks pending rows older than a few minutes: if the object exists, it finishes processing; if not, it deletes the row. The object store and the database can disagree briefly, and the status column is how we notice. It keeps bytes off the app path and has a plan for the two stores disagreeing.

Follow-ups you should expect:

  • "How do you serve private photos?" Do not make the bucket public. Hand out short-lived pre-signed GET URLs, or signed CDN URLs, after checking permissions.
  • "How do you delete?" Mark the row deleted so it disappears at once, then delete the object and purge the CDN asynchronously.
  • "Can you avoid storing the same file twice?" Use a hash of the content as the key and count references, at the cost of more complex deletes.

Common mistakes

Every byte then crosses your servers twice, and slow mobile uploads hold connections for minutes. Use pre-signed URLs so clients talk to the store directly.
