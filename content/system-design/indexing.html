A shop's orders table has 50 million rows of about 200 bytes each. The account page runs "orders for customer 42 since 1 March". With no index, the database reads every row to find the 3 that match: 50 × 106 × 200 B = 10 GB. At 500 MB/s that is 10 GB ÷ 0.5 GB/s = 20 seconds, for one page view.

Add an index on (customer_id, created_at) and the same query reads a handful of pages and returns in a few milliseconds.

The idea

An index is a second copy of a few columns, kept sorted, with a pointer from each entry back to its row. Like the index at the back of a book: look the word up in a sorted list and jump to the page.

Sorted order is the whole trick: the database jumps to the first matching entry and reads forward. The cost is that every write must also update every index, and indexes take disk and memory.

Two ways to keep an index sorted

B-tree: update in place

A B-tree stores sorted keys in fixed-size pages, a few kilobytes each. Each page holds a few hundred keys, so the tree is very wide and very shallow (the balanced trees lesson shows why it stays balanced). With 500 keys per page, two levels cover 500 × 500 = 250,000 entries and three cover 125 million, so 50 million orders need 3 levels. The top two levels are only about 200 pages (1 root plus 50 million ÷ 500 ÷ 500 = 200) and stay in memory, so a lookup costs about one disk read for the leaf and one for the row.

A write changes the right leaf page where it sits, splitting it if full: a random disk write for each index touched.

LSM-tree: append, merge later

A log-structured merge tree never edits in place. Writes go to a sorted table in memory (plus an append-only log, so a crash loses nothing). When the memory table fills, it is written out as a new sorted file. A background job merges files together, dropping overwritten and deleted values; this is called compaction.

Writes are fast because they are sequential. Reads pay instead: a key could be in memory or in any of several files, checked newest first. A small per-file Bloom filter answers "definitely not here", so most files are skipped.

Composite indexes: column order matters

An index on (customer_id, created_at) sorts by customer first, and by date only within each customer. Like a phone book sorted by last name then first name: easy to find every "Garcia", useless for finding every "Maria". Step through two queries against the same index.

The rule: put columns tested with equals first, then the one column used for a range or sort. An index on (a, b, c) serves queries on a, on a, b, and on a, b, c, but not on b alone. Columns after a range condition help little, because inside the range they are no longer sorted.

Covering indexes

After finding 3 entries, the database still fetches 3 rows to read total: one random read each. If the index is (customer_id, created_at, total), the answer is in the index itself and the table is never touched. That is a covering index. It matters most on hot queries that return many rows: for a 200-row page it saves 200 reads. The cost is a bigger index.

What an index costs

Every index is maintained on every write. A table with a primary key and 3 secondary indexes does 4 B-tree updates per insert. At 2,000 inserts a second, that is 2,000 × 4 = 8,000 page changes a second instead of 2,000. Indexes also need memory: an index whose upper levels do not fit in RAM turns each lookup into several disk reads.

So index for the queries you actually run, and drop indexes nothing uses.

Numbers worth remembering

  • A lookup in a B-tree index: 3 or 4 levels for up to hundreds of millions of rows, usually 1 or 2 disk reads because the top levels are cached.
  • A random read: about 0.1 ms on an SSD, about 10 ms on a spinning disk. A sequential scan: hundreds of MB a second.

In the interview

Bring up indexes right after the access patterns. For each hot query, name the index that serves it, with column order. When writes are heavy, say how many indexes you will pay for.

Users see their orders, newest first, 20 per page. How does that stay fast? That query filters by customer and sorts by date, so I'd index (customer_id, created_at DESC). The database jumps to the customer and reads 20 entries in order: no sort, no scan. If the page only shows date and total, I'd add total to make it covering. Support also searches orders by status. Add an index on status? Alone, no. There are maybe five statuses, so "status = shipped" matches a huge share of rows, and the index barely narrows anything. If support filters by status within a date range, I'd index (status, created_at), or run those queries on a replica. Each index is tied to a named query, with column order and cost argued.

Follow-ups you should expect:

  • "How do you add an index to a 500 GB live table?" Use the database's online index build, which avoids blocking writes but takes hours and extra I/O. Run it off-peak.
  • "How do secondary indexes work when the data is sharded?" A local index per shard means a query by that column asks every shard. A global index is partitioned by the indexed value, so reads hit one place but each write updates another shard, usually asynchronously. See sharding.

Common mistakes

An index on (created_at, customer_id) does not help "orders for customer 42" much: the customer's rows are scattered across every date. Equality columns go first.

WHERE LOWER(email) = 'a@b.com' cannot use an index on email, because the index is sorted by the raw value. Store the normalised value, or index the expression itself if your database supports it.
