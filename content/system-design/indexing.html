An orders table has 50 million rows of about 200 bytes. The account page runs "orders for customer 42 since 1 March". With no index, the database reads every row to find the 3 that match: 50 × 106 × 200 B = 10 GB. At 500 MB/s that is 10 GB ÷ 0.5 GB/s = 20 seconds per page view. An index on (customer_id, created_at) cuts it to a few milliseconds.

The idea

An index is a sorted copy of a few columns, each entry pointing to its row. Like a book's index: find the word, jump to the page.

Sorted order is the trick: jump to the first match and read forward. The cost: every write updates every index, and indexes take disk and memory.

Two ways to keep an index sorted

B-tree: update in place

A B-tree stores sorted keys in pages of a few kilobytes, a few hundred keys each, so the tree is wide and shallow (see balanced trees). With 500 keys per page, two levels cover 500 × 500 = 250,000 entries and three cover 125 million, so 50 million orders need 3 levels. The top two levels are about 200 pages (1 root plus 50 million ÷ 500 ÷ 500 = 200) and stay in memory, so a lookup costs one disk read for the leaf and one for the row.

A write updates the leaf page in place, splitting it if full: a random disk write per index.

LSM-tree: append, merge later

A log-structured merge tree never edits in place. Writes go to a sorted table in memory (plus an append-only log for crashes), flushed as a new sorted file when full. Background compaction merges files and drops overwritten and deleted values.

Sequential writes are fast. Reads pay: a key could be in memory or any of several files, checked newest first. A per-file Bloom filter answers "definitely not here", so most files are skipped.

Composite indexes: column order matters

An index on (customer_id, created_at) sorts by customer, and by date only within each customer. Like a phone book sorted by last name then first name: easy to find every "Garcia", useless for every "Maria".

The rule: equals columns first, then one range or sort column; getting this backwards is the classic mistake. An index on (a, b, c) serves a, a, b and a, b, c, but not b alone. Columns after a range help little, as they are no longer sorted inside it.

Covering indexes

After finding 3 entries, the database still fetches 3 rows to read total, one random read each. With (customer_id, created_at, total), the answer is in the index and the table is never touched: a covering index. On a hot 200-row page it saves 200 reads, for a bigger index.

What an index costs

A table with a primary key and 3 secondary indexes does 4 B-tree updates per insert: at 2,000 inserts a second, 2,000 × 4 = 8,000 page changes a second. If an index's upper levels do not fit in RAM, each lookup becomes several disk reads. Index the queries you run; drop indexes nothing uses.

Numbers worth remembering

  • B-tree lookup: 3 or 4 levels for hundreds of millions of rows, usually 1 or 2 disk reads with the top cached.
  • Random read: about 0.1 ms on SSD, 10 ms on spinning disk. Sequential scan: hundreds of MB a second.

In the interview

Bring up indexes right after the access patterns: name the index for each hot query, with column order. When writes are heavy, say how many indexes you will pay for.

Users see their orders, newest first, 20 per page. How does that stay fast? It filters by customer and sorts by date, so (customer_id, created_at DESC). The database jumps to the customer and reads 20 entries in order: no sort, no scan. If the page shows only date and total, adding total makes it covering. Support also searches orders by status. Add an index on status? Alone, no. With maybe five statuses, "status = shipped" matches a huge share of rows; the index barely narrows anything. If support filters by status within a date range, I'd index (status, created_at), or run those queries on a replica. Each index serves a named query, with column order and cost argued.

Follow-ups to expect:

  • "How do you index a 500 GB live table?" An online build: no blocked writes, but hours of extra I/O. Run it off-peak.
  • "How do secondary indexes work when data is sharded?" With a local index per shard, a query by that column asks every shard. A global index is partitioned by the indexed value: reads hit one shard, but each write updates another, usually asynchronously. See sharding.

Common mistakes

WHERE LOWER(email) = 'a@b.com' cannot use an index on email, which is sorted by the raw value. Store the normalised value, or index the expression if your database supports it.
