A shop has 20 million products. Search runs WHERE title LIKE '%red shoes%'. A pattern starting with % cannot use an ordinary index, so every search reads every title and description: 20 × 106 × 1 KB = 20 GB per query, or 10 TB a second at 500 searches a second. It also misses "Red Shoe" and "shoes, red", and cannot rank matches. An inverted index fixes all three.

The idea

An inverted index maps each word to the documents containing it, like a cookbook index mapping "garlic" to pages 12, 40 and 97. A query combines its words' lists, so the work depends on how many documents match, not how many exist.

The cost: a second copy, always a little behind. The database stays the source of truth; the index can be rebuilt from it.

From text to tokens

An analyser splits text into words, lowercases them, drops punctuation, and reduces each to a stem ("shoes" to "shoe", "running" to "run"). Queries must use the same analyser, or "shoes" finds nothing in a stemmed index.

Each token's postings are the sorted ids of documents containing it: red → [1, 3, 4], shoe → [1, 3], run → [1, 2], and one-document lists for the rest.

That merge is the two-pointer pattern, O(a + b) for lists of length a and b. The token dictionary is kept sorted or in a trie, which also answers prefix queries like "sho".

Ranking, in outline

Matching finds candidates; ranking orders them. The classic text score, BM25 (a refinement of TF-IDF), rewards:

  • the word appearing often in the document, with diminishing returns;
  • the word being rare overall ("shoe" is in 2 of 4 documents, "red" in 3 of 4, so "shoe" says more);
  • a short document, where the match counts for more.

Shops add business signals: title matches beat description matches; popularity, stock and freshness lift results.

Keeping the index in step

Numbers worth remembering

  • Delay until searchable with change data capture: a second to a few seconds.
  • Index size: postings × a few bytes each, compressed (more with word positions for phrase search).
  • Below a few million documents with simple matching, the database's built-in full-text index is often enough.

In the interview

Add a search index for free-text search, typo tolerance, ranking, or filtering on many fields at once. Say what is indexed, how it syncs, and what is still read from the database.

Users need to search products by text. Can't the database do it? For 20 million products with ranking and typo tolerance, I'd add a search index fed by change data capture: a second or two behind, and rebuildable. Search returns ids; price and stock come from the database, so a stale index never shows a wrong price. How do you shard the index? By document: each shard holds a slice of products, and a query merges every shard's top results. Sharding by term lets a query hit fewer shards, but one product update would touch many, so document sharding is usual. It names the source of truth, the sync, the lag, and the recovery path.

Follow-ups:

  • "How do you handle typos?" Fuzzy matching within a small edit distance, or character n-grams. Both grow the index and the candidate list.
  • "How do you do autocomplete?" A small separate prefix index of popular queries.
  • "How do you change the analyser?" Build a new index beside the old, replay into it, then switch reads in one step.

Common mistakes

A crash between the writes leaves them different, with nothing to repair it. Feed the index from the database's committed changes. Read prices, stock and permissions from the database, never the index.
