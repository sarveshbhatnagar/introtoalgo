A shop has 20 million products. Search runs WHERE title LIKE '%red shoes%'. A pattern that starts with % cannot use an ordinary index, so every search reads every title and description: 20 × 106 × 1 KB = 20 GB per query. At 500 searches a second, that is 10 TB read a second. It also misses "Red Shoe" and "shoes, red", and it cannot say which match is best.

Search engines solve all three with one structure built ahead of time: the inverted index.

The idea

A normal index maps a row to its contents. An inverted index maps each word to the list of documents that contain it, the way the index of a cookbook maps "garlic" to pages 12, 40 and 97. A query looks up each of its words and combines the lists. The work depends on how many documents match, not on how many exist.

The cost: the index is a second copy of your data, built by a separate system, and it is always a little behind the database. The database stays the source of truth; the index is a derived copy you can throw away and rebuild.

From text to tokens

Before indexing, each text goes through an analyser: split into words, lowercase, drop punctuation, and reduce words to a stem so "shoes" and "shoe" match ("running" becomes "run"). The query goes through the same analyser. If the index stems and the query does not, "shoes" finds nothing.

1Red Running Shoesred, run, shoe
2Blue running shortsblue, run, short

4Red rain jacketred, rain, jacket

The inverted index lists, for each token, the sorted ids of the documents that contain it (its postings): red → [1, 3, 4], shoe → [1, 3], run → [1, 2], and one-document lists for the rest. Step through the query "Red shoes".

That merge is the two-pointer pattern: O(a + b) for lists of length a and b. The token dictionary itself is kept sorted or in a structure like a trie, which also answers prefix queries such as "sho" for autocomplete.

Ranking, in outline

Matching finds candidates; ranking orders them. The classic text score, BM25 (a refinement of TF-IDF), rewards three things: the query word appears often in the document (with diminishing returns), the word is rare across all documents (here "shoe" is in 2 of 4 documents and "red" in 3 of 4, so "shoe" says more), and the document is short, so the match is a bigger part of it. On top of that, products add business signals: a match in the title beats one in the description, and popularity, stock and freshness lift results. In an interview, naming those layers is enough.

Keeping the index in step

Numbers worth remembering

  • Index-to-searchable delay with change data capture: usually about a second or a few seconds.
  • Index size: number of postings × a few bytes each once compressed (more if you store word positions for phrase search).
  • Below a few million documents and simple matching, the database's built-in full-text index is often enough. Say so before adding a cluster.

In the interview

Add a search index when the requirements include free-text search, typo tolerance, relevance ranking, or filtering on many fields at once. Say three things: what is indexed, how it stays in sync, and what is still read from the database.

Users need to search products by text. Can't the database do it? For 20 million products with ranking and typo tolerance, I'd add a search index. The database stays the source of truth; the index is fed by change data capture, so it's a second or two behind and can be rebuilt from scratch. Search returns ids, and I read price and stock from the database so a stale index never shows a wrong price. How do you shard the index? By document: each shard indexes a slice of products, and a query asks every shard for its top results and merges them. Sharding by term would let a query hit fewer shards, but a single product update would touch many shards, so document sharding is the usual choice. It names the source of truth, the sync mechanism, the lag, and the recovery path.

Follow-ups you should expect:

  • "How do you handle typos?" Fuzzy matching within a small edit distance, or indexing character n-grams, at the cost of a bigger index and more candidates to rank.
  • "How do you do autocomplete?" A separate, small prefix index of popular queries; see Design Typeahead Search.
  • "How do you change the analyser?" Build a new index alongside the old one, replay into it, then switch reads over in one step.

Common mistakes

Writing the database and then the index from the app looks simple, but a crash between the two leaves them different with nothing to repair it. Feed the index from the database's committed changes.

The index lags and can be rebuilt; it is not where prices, stock or permissions are decided. Read those from the database after search returns ids.
