Dozens of services publish events: orders placed, payments taken. Dozens more read them at their own pace, and some reread last Tuesday's events after a bug fix. You build the broker in the middle, a Kafka: a cluster that accepts a hundred thousand messages a second, keeps them for a week, and never loses an acknowledged message when a broker dies.

Using a queue is covered in Message Queues and Streams. This lesson builds the log itself: files on disk, replicas, offsets, and the exact meaning of "acknowledged". The steps follow A Framework for Any Design.

Clarify the problem

Design a distributed message queue. A job queue, where each message goes to one worker and is deleted, or a log that several groups read and replay? A log. Do consumers need order across all events, or per key, like per order ID? And what scale and retention? Per key is enough. 100,000 messages a second on average, three times that at peak, about 1 KB each, kept for seven days. Each message is read by about three groups. Then my priorities: no acknowledged message is lost when a broker dies, order holds per key, and consumers can rewind. "Queue or log?" changes the whole storage design, and "order per what?" decides the partitioning.
  • Functional: produce to a topic, with an optional key; consume in groups, where each group gets every message and members share the work; commit and rewind positions; delete after retention, or keep only the latest value per key.
  • Non-functional: the priorities above; produce p99 under about 10 ms; 300,000 messages a second at peak; consumers hours behind do not slow producers.
  • Out of scope: delayed and priority messages, per-message acknowledgement, replication between regions.

Estimate the scale

  • Ingest: 100,000 × 1 KB = 100 MB/s on average, 300 MB/s at peak.
  • Per day: 100 MB/s × 86,400 s ≈ 8.6 TB.
  • Reads: three groups: 300 MB/s out on average, 900 MB/s at peak, plus replica traffic.

At peak each of 20 brokers writes 300 MB/s × 3 ÷ 20 = 45 MB/s and serves 900 MB/s ÷ 20 = 45 MB/s of reads. Comfortable for sequential I/O.

Write the calls for producing, consuming and saving a position. How does a consumer say where to read from, and what does a producer hear from the wrong broker?

Produce returns the batch's offset. Fetch takes a partition and an offset, so the consumer owns its position; commit saves it for the group. An error tells clients to refresh metadata when leadership moves.

The decision worth arguing is pull versus push. Consumers pull from their own offset at their own pace, so a slow consumer slows no one, reads batch well, and rewinding is asking for an older offset. To avoid busy polling, fetch waits up to max_wait_ms before answering empty.

How does a broker store a partition so appends and reads from any offset are fast and deleting old data is cheap? What must the cluster agree on?

A directory of segment files named by first offset, each with a sparse index. Appends go to the newest; retention deletes whole old ones. The cluster agrees on each partition's replicas, leader, and in-sync set.

There is no database: the broker's files are the store, accessed only by "append" and "read forward from offset X". Consumer positions are messages in a compacted internal topic. The critical metadata lives in a controller replicated with consensus.

Sketch one partition with three replicas. Who does the producer talk to, how do the copies get the data, and who picks the leader?

Producers and consumers talk to the partition's leader; followers fetch from it like consumers. A controller quorum records leaders and in-sync replicas and replaces a dead leader.

High-level design

Each partition has a leader and two followers on different brokers; each broker leads about a third of its partitions.

Deep dives

The log on disk

A random 1 KB write on a spinning disk costs a 10 ms seek: 100 KB a second. Appending, it streams about 200 MB/s, 2,000 times more; SSDs narrow the gap. So the broker only appends: no updates in place, no per-message index.

  • Batching. Producers group messages for a few milliseconds, say 16 KB: about 6,250 requests a second instead of 100,000, each compressed as a unit.
  • The page cache. The broker writes to the OS file cache without forcing each write to disk. Consumers that keep up read from memory.
  • Zero copy. Stored bytes equal sent bytes, so the kernel sends a file range straight to the socket.

Segments and the index. Segments are about 1 GB. To serve "read from offset 4,712,345", the broker picks the segment by name, then uses a sparse index with one entry per 4 KB: about 250,000 entries, 2 MB, in memory. Binary search finds the nearest entry in about 18 steps, then the broker scans forward under 4 KB.

Retention and compaction. Retention deletes a closed segment once its newest record is 7 days old: a file delete, not a rewrite. Where only the latest value per key matters (a user's address, consumer offsets), compaction rewrites old segments keeping the last record per key. A tombstone (empty value) deletes a key and is itself removed after a grace period, so slow readers still see the delete.

Replication and what "acknowledged" means

The leader tracks which followers are caught up, within say 10 seconds: the in-sync replicas (ISR). The high watermark is the highest offset every ISR member has; consumers see only records below it. The producer picks how long to wait with acks:

Be exact. With 3 replicas, acks=all and a minimum ISR of 2, an acknowledged record is in the log of at least 2 brokers: in their page cache, not necessarily on disk. Durability comes from copies failing independently, so use different racks or zones. Without the minimum, the ISR could shrink to the leader alone, and acks=all would quietly mean acks=1.

The controller. A quorum of 3 nodes keeps the metadata in a consensus log, spots dead brokers, picks leaders from the ISR, and records ISR changes. Each new leader gets a higher leader epoch, and brokers reject requests with an older one. This fences a zombie leader: cut off from the controller, it cannot shrink the ISR, so it cannot acknowledge an acks=all write alone. With acks=1 it can, and those writes are cut off when it rejoins.

If every ISR member dies, either wait for one to return (unavailable, no loss) or let an out-of-sync replica lead (available, acknowledged records lost). Wait, by default.

Ordering and producing without duplicates

Order is per partition, chosen by hashing the key. Retries can break it: batch 42 fails, 43 succeeds, then 42 lands after 43. And a retry after a lost acknowledgement writes a duplicate.

The idempotent producer fixes both. Each producer has an id and numbers its batches per partition. The broker remembers the last few sequence numbers per producer: a repeat gets the original offset, and a gap (43 before 42) is rejected so the producer resends in order. A restarted producer gets a new id, so its resends slip through unless it keeps a stable id. See Idempotency and Retries.

Consumer groups, offsets and delivery

When a member joins, leaves or misses heartbeats, the group coordinator rebalances. Each assignment has a generation, and commits from an old one are rejected, so a consumer that paused for a minute cannot overwrite its successor's position. Prefer a cooperative rebalance, which pauses only the partitions changing owner, not all 32.

Commit after processing for at-least-once: with commits every 5 seconds, a dead consumer's last 5 × 2,500 = 12,500 messages are processed again. For exactly-once within the log, a consumer that writes to another topic commits its output and offsets in one transaction, and readers of committed data never see a half-done result. That promise ends at the log: an email or external database write still needs idempotent processing.

A timer auto-commit can commit offset 5,001 while message 5,000 is still in progress. If the consumer then dies, 5,000 is skipped forever. Commit only finished work.

Bottlenecks and failures

At 10x (1 GB/s in, 1.8 PB a week) disks run out first: 1.8 PB ÷ 12 TB = 150 brokers, about 200 with headroom. Move segments older than a day to cheaper object storage; the same tiering keeps data for a year. Hot keys stay hot partitions. A consumer replaying last week evicts recent data from the page cache, so cap replay bandwidth per client.

With acks=all, can an acknowledged message be lost? With a minimum ISR of 2, only if both copies fail before either flushes, so replicas go in separate zones. Two settings lose it anyway: letting an out-of-sync replica lead, or a minimum of 1. Why not fsync every message? It caps each disk at its sync rate and adds milliseconds to every write. Independent copies buy more safety per millisecond. The guarantee, its preconditions, and the two settings that quietly break it.

Follow-up questions

Why not use a database table as the queue?

Every consume becomes an update or delete, and consumers fight over the same rows. A log only appends, and each group's position is one number per partition.

How do you add partitions to a busy topic?

It changes hash(key) mod n, so a key's new events land in a different partition from its old ones and order breaks. Size for future load, or migrate to a new topic.

How do you support many small topics?

Each partition costs files, index memory and metadata. Share partitions across tenants with a key prefix, or cap partitions per broker.
