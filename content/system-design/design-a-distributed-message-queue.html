A distributed message queue is a cluster of servers (brokers) that accepts messages from many producers, stores them durably, and lets many consumers read them later at their own pace. Kafka is the best-known example, and this lesson designs that kind of system: a log that several consumer groups read independently and can replay.

The question is hard because the broker must combine three things that pull against each other: very high throughput, an acknowledgement that really means the message will not be lost when a machine dies, and ordering that survives retries and failovers. The steps follow A Framework for Any Design, and how applications use a queue is covered in Message Queues and Streams.

Clarify the problem

Design a distributed message queue. Should it be a job queue, where each message goes to one worker and is deleted once handled, or a log that several consumer groups read and can replay? A log. Do consumers need ordering across all events, or only per key, for example per order ID? And what are the message rate and the retention? Order per key is enough. Assume 100,000 messages a second on average and three times that at peak, about 1 KB each, kept for seven days. Each message is read by about three consumer groups. Then my priorities are these: an acknowledged message is never lost when a broker dies, order holds per key, and consumers can rewind to an older position. Queue or log changes the whole storage design, and the order needed decides the partitioning.

Functional requirements. Producers publish messages to a topic, with an optional key. Consumers read in groups: every group receives every message, and the members of a group share the work. Consumers can save their position and rewind it.

Non-functional requirements. No acknowledged message is lost when one broker fails. Messages with the same key are read in the order they were written. Producing has a p99 latency under about 10 ms.

Out of scope. Delayed messages and cross-region replication.

Estimate the scale

The ingest rate is 100,000 messages a second × 1 KB = 100 MB/s on average and 300 MB/s at peak. With three consumer groups, the cluster sends out 300 MB/s on average and 900 MB/s at peak.

With 20 brokers, each one writes about 300 MB/s × 3 ÷ 20 = 45 MB/s at peak and serves about 900 MB/s ÷ 20 = 45 MB/s of reads, which is comfortable for sequential disk access.

Write the calls for producing, consuming and saving a position. What does a producer hear when it contacts the wrong broker?

Produce returns the offset of the batch. Fetch takes a partition and an offset, so the consumer owns its position, and commit saves that position for the group. When leadership moves, the broker returns an error that tells clients to refresh their metadata.

The API decision worth arguing is pull versus push. In this design consumers pull from their own offset at their own pace. A slow consumer then slows nobody else, the broker can return large batches efficiently, and rewinding is just a fetch with an older offset. With push, the broker would have to track how fast each consumer can accept data. To avoid wasted requests on an empty partition, a fetch waits on the broker for up to max_wait_ms before it returns an empty response.

How does a broker store a partition so that appends and reads from any offset are fast, and deleting old data is cheap? What must the cluster agree on?

A partition is a directory of segment files named by their first offset, each with a sparse index. Appends go to the newest segment, and retention deletes whole old segments. The cluster must agree on each partition's replicas, its leader and its set of in-sync replicas.

There is no database: the brokers' own files are the store, accessed only by appending and by reading forward from an offset. Consumer positions are stored as messages in a compacted internal topic. The metadata that must never be wrong, such as who leads each partition, is held by a controller that is replicated with consensus.

Sketch one partition with three replicas. Who does the producer talk to, how do the other copies get the data, and who chooses the leader?

Producers and consumers talk to the leader of the partition, and the followers fetch from the leader in the same way consumers do. A controller quorum records the leaders and the in-sync replicas and replaces a leader that dies.

High-level design

Each topic is split into partitions. Each partition has one leader and two followers on different brokers, and leaders are spread evenly across brokers.

Deep dives

How the log is stored on disk

The broker has to write 100 MB/s of small messages. A random 1 KB write on a spinning disk costs a seek of about 10 ms, so it manages about 100 writes and 100 KB a second. Appending to the end of a file streams at about 200 MB/s, roughly 2,000 times faster. For this reason the broker only appends, and it never updates a record in place or keeps a per-message index.

Three techniques make the append-only design fast.

  • Batching: producers send messages in batches of about 16 KB, so the broker handles about 6,250 requests a second instead of 100,000.
  • The page cache: the broker writes into the operating system's file cache, so consumers that keep up read recent data from memory.
  • Zero copy: the stored bytes are the bytes sent to consumers, so the kernel sends a file range to the socket directly.

A partition is split into segments of about 1 GB. To serve a fetch for offset 4,712,345, the broker picks the segment from the file names, then uses a sparse index with one entry per 4 KB of data, about 250,000 entries or 2 MB, which fits in memory. A binary search finds the nearest entry in about 18 steps, and the broker scans forward less than 4 KB from there.

There are two ways to remove old data. With time-based retention, the broker deletes a closed segment once its newest record is older than seven days. This is a cheap file delete. With compaction, for topics where only the latest value for each key matters (such as the consumer offsets), a background job rewrites old segments and keeps the last record for each key.

Replication and what an acknowledgement means

Each partition is copied to three brokers so that one machine failing loses nothing. The leader tracks which followers are caught up, for example within the last 10 seconds; these and the leader are the in-sync replicas (ISR). The high watermark is the highest offset that every member of the ISR has stored, and consumers can only read below it. This means a consumer never reads a record that could vanish if the leader failed. The producer chooses how long to wait through the acks setting, and there are three options.

With acks=0 the producer does not wait, so a crash loses messages unnoticed. With acks=1 the producer waits for the leader alone, about 1 to 2 ms, so a message acknowledged just before the leader fails can be lost. With acks=all the leader acknowledges only after every ISR member has the batch, which costs the latency of the slowest in-sync follower.

The choice is acks=all with a minimum ISR of 2, because acknowledged messages must not be lost. Without the minimum, the ISR could shrink to the leader alone, and acks=all would quietly behave like acks=1. With it, the broker returns NOT_ENOUGH_REPLICAS instead of accepting a write held by one machine.

An acknowledged record is in the log of at least two brokers, but possibly only in their page cache and not yet on disk. The safety comes from the copies failing independently, so the replicas belong in different racks or zones.

The controller is a quorum of three nodes that stores the cluster metadata in a consensus log. It detects dead brokers, chooses new leaders from the ISR and records every change of the ISR. Each new leader gets a higher leader epoch, and brokers reject requests that carry an older epoch. This fences a zombie leader, a broker that was replaced but does not know it yet. The followers have moved on, so the zombie cannot collect acks=all acknowledgements, although with acks=1 it can still acknowledge writes that are later discarded.

If every member of the ISR dies, there are two options. The cluster can wait for one of them to come back, which keeps the topic unavailable but loses nothing. Or it can let an out-of-sync replica become leader, which restores availability but loses acknowledged records that replica never received. Waiting is safer.

Ordering and producing without duplicates

Order is guaranteed only within a partition, and the partition is chosen by hashing the key, so all messages with one key stay in order. Retries can break this: if batch 42 fails after batch 43 was already sent, batch 42 lands after 43. A retry after a lost acknowledgement can also write a batch twice.

The idempotent producer solves both problems. Every producer has an id and numbers its batches for each partition. The broker remembers the last few sequence numbers for each producer. If it sees a sequence number it already has, it returns the original offset without writing again. If it sees a gap, such as 43 arriving before 42, it rejects the batch, and the producer resends in order. See Idempotency and Retries.

Consumer groups, offsets and delivery guarantees

Within a group, each partition is read by exactly one member, so a topic has at most as many busy consumers as partitions. When a member joins, leaves or stops sending heartbeats, the group coordinator rebalances the assignment. Every assignment has a generation number, and the broker rejects commits that carry an old generation. A consumer that paused for a minute and was replaced therefore cannot overwrite its successor's position. A cooperative rebalance pauses only the partitions that change owner.

The time at which a consumer commits its offset decides the delivery guarantee. Committing after processing gives at-least-once delivery. If the consumer dies, it restarts from the last commit, and with commits every 5 seconds and a consumer handling 2,500 messages a second, up to 5 × 2,500 = 12,500 messages are processed again. So processing must be idempotent.

Exactly-once is possible inside the log. A consumer that reads from one topic and writes to another can commit its output messages and its input offsets in a single transaction, and readers configured to see only committed data never observe a half-finished result. The promise ends at the edge of the log: sending an email or writing to an external database is not covered, and those side effects still need idempotent handling.

Bottlenecks and failures

At 10 times the load, which is 1 GB/s of input and 1.8 PB of disk for a week, disk runs out first. 1.8 PB ÷ 12 TB is 150 brokers, or about 200 with headroom. Segments older than a day can move to cheaper object storage. A hot key still maps to a single partition, which can then become much busier than the rest. A consumer that replays last week's data pushes recent data out of the page cache, so replay bandwidth per client should be capped.

With acks=all, can an acknowledged message still be lost? With a minimum ISR of 2, it is lost only if both brokers holding it fail before either flushes it to disk, which is why the replicas go in separate zones. Two settings lose it anyway: allowing an out-of-sync replica to become leader, and setting the minimum ISR to 1. Why not call fsync on every message? It limits each disk to its sync rate and adds milliseconds to every write, and copies on independent machines give more safety for less latency. It states the guarantee, its conditions and the settings that break it.

Follow-up questions

Why not use a database table as the queue?

Every consume becomes an update or a delete, and consumers compete for the same rows. A log only appends, and several groups can read and replay the same data.

How do you add partitions to a busy topic?

Adding partitions changes the result of hash(key) mod n, so new messages for a key go to a different partition from its older messages, and the order for that key breaks. Choose the partition count for next year's load at the start, or migrate to a new topic.

What happens to a consumer group that is far behind?

Producers are not affected, because each group reads at its own offset. The group reads older segments from disk instead of the page cache, which is slower. If its lag exceeds the retention period, the data it needs is deleted and it gets OFFSET_OUT_OF_RANGE, so it must restart from the earliest or latest available offset.
