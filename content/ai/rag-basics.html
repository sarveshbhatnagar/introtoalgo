Retrieval-augmented generation, or RAG, is a technique where the system searches your own documents for passages related to a question, adds those passages to the prompt, and asks the model to answer from them. It lets a model answer questions about material it was never trained on, such as your help pages, handbook or meeting notes, and it lets you cite where each answer came from.

Without retrieval, the model answers from its training data and produces a confident, generic answer that may not match your documents. Sending the whole collection in every prompt is usually impossible, because a real document collection is far larger than the context window.

How RAG works

A RAG system does three things for every question. It retrieves the passages most related to the question, it augments the prompt by adding those passages and telling the model to answer from them, and it generates the answer, ideally with a citation for each claim. The model itself is unchanged. RAG is a form of context engineering in which the material in the prompt is selected automatically for each question.

The search usually matches meaning rather than exact words, using embeddings, because people rarely phrase a question in the words of the document. Someone asks "when do I get my money back?" and the answer sits under a heading called "Refund processing times".

Indexing is slow, so it happens ahead of time. Each document is cut into passages called chunks (the next lesson covers how), each chunk is turned into a vector, and the vectors are stored. When a question arrives, the system only has to embed the question and compare it with the stored vectors.

Retrieval by hand

The example below uses a bookshop help centre with five chunks. To keep the arithmetic readable, each embedding has only three numbers, which you can think of as "about money", "about shipping" and "about accounts". Real embeddings have hundreds or thousands of numbers, but the calculation is the same.

The question "When will I get my money back?" embeds to [5, 1, 0], which has a length of √26 ≈ 5.10. Each chunk is scored with cosine similarity (explained in Embeddings) and the two highest scores are kept.

function topK(queryVec, chunks, k) {
  return chunks

    .sort((a, b) => b.score - a.score)

import math

def dot(a, b):
    return sum(x * y for x, y in zip(a, b))

def cosine(a, b):
    return dot(a, b) / math.sqrt(dot(a, a) * dot(b, b))

def top_k(query_vec, chunks, k):
    scored = [{**c, "score": cosine(query_vec, c["vec"])} for c in chunks]
    scored.sort(key=lambda c: c["score"], reverse=True)
    return scored[:k]

def build_prompt(question, passages):
    sources = "\n".join(f"[{i + 1}] {p['text']}" for i, p in enumerate(passages))
    return (
        "Answer using only the sources below. Cite them like [1].\n"
        'If they do not contain the answer, say "I don\'t know."\n\n'
        f"{sources}\n\nQuestion: {question}"
    )

    {"text": "Reset your password from the sign-in page.", "vec": [0, 0, 5]},

The instruction to say "I don't know" is important. When retrieval finds nothing useful and that instruction is missing, the model falls back on its training data and gives an answer that sounds just as grounded as a correct one.

Choosing how to search

Retrieval does not have to use embeddings. There are three common choices, and each fails in its own way.

Embedding search

Embedding search compares the meaning of the question with the meaning of each chunk. It handles paraphrases well, so "money back" finds "refund". It is weaker on exact identifiers. A product code, an error number or a person's name has little meaning for an embedding model, so the chunk that contains that exact string may not rank near the top.

Keyword search

Keyword search scores chunks by how many of the question's words they contain, weighting rare words more heavily than common ones. It finds exact strings reliably and needs no embedding model. It fails when the question and the document use different words for the same thing, because "money back" shares no words with "refund".

Hybrid search

Hybrid search runs both methods and merges the two ranked lists. It is the usual choice when the documents contain a mix of ordinary prose and exact identifiers, such as a support knowledge base that mentions error codes. The two rankings use scores on different scales, so they are usually merged by rank rather than by score. A common rule is reciprocal rank fusion, which gives each chunk a value of 1 divided by (a constant plus its rank) in each list and adds the values. The cost is a second index to maintain.

Choosing how many passages to retrieve

The number of passages, called k, is a trade-off. If k is too small, the passage that holds the answer may rank just below the cutoff and never reach the model. If k is too large, the prompt fills with loosely related text, which costs tokens and gives the model more chances to latch onto the wrong passage. In the trace above, the gift card chunk scored 0.88, close behind the returns chunk at 0.92, and k = 2 left it out.

A fixed k always returns something, even for a question the documents do not cover. Adding a minimum score fixes this: passages below the threshold are dropped, and if none remain, the system can reply that it found nothing instead of passing weak matches to the model. The right threshold depends on the embedding model, so find it by testing questions whose answers you know.

Improving the retrieved passages

When the right passage exists but does not reach the prompt, three changes are the usual fixes.

Reranking retrieves a generous number of candidates, such as 30, and then reorders them with a slower model that reads the question and each candidate together. Embedding search compares two vectors that were computed separately, so it is fast but approximate; a reranker sees both texts at once and is more accurate. You then keep only the top few for the prompt.

Query rewriting is needed when the user's message is not a good search query by itself. In a conversation, "and what about for gift cards?" has no meaning without the earlier turns, so the system first asks the model to rewrite it as a standalone question, such as "What is the refund policy for gift cards?", and searches with that.

Metadata filtering restricts the search to chunks whose stored attributes match, such as the product, the document version or the language. It is also how access control works: the filter must remove the chunks the current user is not allowed to read before they are retrieved, because anything that reaches the prompt can appear in the answer.

When RAG is the right tool

Use RAG when the material is too large to send whole, changes often, or is private. Updating the documents updates the answers, with no retraining.

Skip RAG when the material is small. If the whole handbook fits comfortably in the prompt, send all of it, which removes the possibility of a retrieval miss.

Do not use fine-tuning as a substitute for facts that change. Fine-tuning is good for teaching a style or a format, but it is a poor place to store facts you will need to correct next month, and a fine-tuned model cannot point to a source.

Pitfalls

If the passage that holds the answer never reached the prompt, no change to the wording will help. Log which passages were retrieved for each question, and test retrieval on its own with questions whose correct passage you already know.

Vectors produced by two different embedding models cannot be compared, in the same way that coordinates from two different maps cannot be compared. If you switch models, re-embed every chunk, and make sure questions are embedded with the same model as the chunks.

Retrieved text can be out of date, wrong, or written to steer the model, as in prompt injection. Keep stale documents out of the index, and tell the model in the prompt that the passages are reference material and not instructions.

If a document is edited or deleted but its old chunks stay in the index, the system keeps answering from the old text. Re-index changed documents, and remove the chunks of deleted ones.

If the prompt does not require citations, a wrong answer and a right one look identical to the reader. Ask for a citation per claim, and check that each cited passage supports the claim.

What this changes in practice

When a RAG answer is wrong, look at the retrieved passages before you change the prompt. If the right passage is missing, the problem is in indexing or search. If it is present and the answer is still wrong, the problem is in the prompt or the model. Keeping these two cases apart saves a lot of wasted prompt editing.

Build a small test set of real questions, each with the passage that should answer it, and measure how often that passage appears in the top k. Rerun the test whenever you change the chunk size, the embedding model or k. Record what each change does to the result, in the same way you would for the evals of a prompt.

A staff assistant was asked "How many days of parental leave do we get?" It answered "Most companies offer 12 weeks." The retrieved passages were: [1] "Annual leave: 25 days per year, plus public holidays." [2] "Sick leave must be reported to your manager before 10am." Find the two separate failures and say what you would change.

The first failure is in retrieval. Neither passage is about parental leave. Either the policy is not in the index, or it was chunked or embedded badly so that a generic match on "leave" ranked above it. Check that the policy is in the store, then search for it directly to see where it ranks.

The second failure is in generation. The model should have said that the passages did not answer the question, but it used general knowledge instead. Add an instruction such as "If the sources do not answer the question, reply: I couldn't find this in the staff handbook." Requiring citations also helps, because an answer with no source stands out.

Fixing only the prompt makes the assistant honest but unhelpful. Fixing only retrieval leaves it free to invent an answer the next time a question is not covered. Both need fixing.
