You call a support line about a delivery. The agent has never spoken to you; all they know is the notes on their screen: your order, the last agent's comments, the refund rules. If the last agent wrote "customer called, sorted", you start from zero.

A language model is in that position on every request. It has broad knowledge from training, but about you and this task it knows only what is on its screen right now. That screen is the context.

Two kinds of knowing

  • Training: language, world facts, how code usually looks. Broad, but frozen at some date, and nothing private: not your files, your company's rules or yesterday's news.
  • Context: the text sent on this call. Narrow, but current and specific, and you control it.

A generic, outdated or wrong answer usually means the needed fact was missing from the context, so the model filled the gap from training. That is the pattern behind hallucinations and the generic answers in Prompting Basics.

About your situation, a model knows only what is in its context on this call. Deciding what goes in, and what stays out, is the main skill of working with it.

What goes into the context

Your message is only one piece of what the model reads.

  • Instructions: the app's role, rules and tone (System Prompts).
  • Tool descriptions, if the model can search, run code or call services (Tools and MCP).
  • Retrieved documents looked up for your question (RAG).
  • Saved notes from earlier sessions (memory).
  • The conversation so far.
  • Your new message, plus anything pasted or attached.

To the model it is all one long text, read top to bottom, with markers saying who wrote what. This module is about choosing those pieces well.

Watch a chat being resent

The model keeps nothing between calls. A chat feels continuous because the app resends the whole conversation every time.

Same model, same question, different context, different answer. The model did not "forget" Lena. It never remembered her; it only ever read her.

The same thing in code

The app's side of that tracer. The history list is the only memory, and it lives in the app.

// The app keeps the conversation. The model keeps nothing.
function buildRequest(system, history, newMessage) {
  return [
    { role: "system", content: system },
    ...history,
    { role: "user", content: newMessage },
  ];
}

const system = "You take orders for a small bakery.";
const history = [];

const first = buildRequest(system, history, "I'm Lena. 12 rolls for Friday.");
history.push(first.at(-1), { role: "assistant", content: "Noted: 12 rolls, Friday." });

const second = buildRequest(system, history, "Can I make it 20?");
console.log(second.length); // 4: system, two saved turns, new message

const freshChat = buildRequest(system, [], "Can I make it 20?");
console.log(freshChat.length); // 2: nothing says what "it" is

# The app keeps the conversation. The model keeps nothing.
def build_request(system, history, new_message):
    return (
        [{"role": "system", "content": system}]
        + history
        + [{"role": "user", "content": new_message}]
    )

system = "You take orders for a small bakery."
history = []

first = build_request(system, history, "I'm Lena. 12 rolls for Friday.")
history += [first[-1], {"role": "assistant", "content": "Noted: 12 rolls, Friday."}]

second = build_request(system, history, "Can I make it 20?")
print(len(second))  # 4: system, two saved turns, new message

fresh_chat = build_request(system, [], "Can I make it 20?")
print(len(fresh_chat))  # 2: nothing says what "it" is

Real apps send the list through an API, but the shape is the same: a list of messages, rebuilt and resent on every call.

Context beats cleverness

The wording barely changes between these two. The information does.

Is my flight affected by the strike? I don't have information about your specific flight. Strikes can affect airlines, airports or air traffic control. I'd recommend checking your airline's website or app for updates on your booking. Is my flight affected by the strike? Answer from the notice below only. My flight: leaves Thursday 07:40 from Terminal 2. Ground staff at Terminal 2 will strike from 06:00 to 10:00 on Thursday. Flights in that window may be delayed by up to 3 hours. Terminal 1 is not affected. Yes, probably. Your flight leaves at 07:40 from Terminal 2, which falls inside the 06:00 to 10:00 strike window. The notice says flights in that window may be delayed by up to 3 hours.

The first reply is an honest model with nothing to work with.

Common mistakes

A new chat starts with empty history. Unless a memory feature loads notes into the context, nothing from yesterday is there. Paste in what matters.

The model does not see your screen, open files, today's date or the email you are replying to, unless the app adds them. When an answer seems oddly unaware, check whether that fact was in the text.

If an outdated price list sits next to the new one, the model may use either. Remove wrong information as carefully as you add right information.

Try it yourself

Someone asks an assistant: "Should I accept this meeting invite?" List what the model would need in its context to answer usefully, and where each piece could come from (the user, a calendar, a document, earlier conversation).

One reasonable list:

  • The invite: sender, topic, time, length. Pasted by the user, or from a calendar tool.
  • The user's calendar that day, to spot a clash. From a calendar tool.
  • The user's priorities: "I'm protecting mornings for focus work this month." From the user or saved notes.
  • Who the sender is to them: manager, vendor, stranger. From the user or a contacts lookup.
  • Whether they are needed: the agenda, and whether a colleague is going. From the invite or the user.

Without these, the only answer is generic meeting advice. The question is usually the smallest part of a good context.
