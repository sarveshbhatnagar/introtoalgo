You ask an agent to compare how three open-source web frameworks handle security updates: how fast they ship fixes, how they announce them, and how long old versions get patches. It reads Framework A's documentation, then B's, then C's. By the time it writes the report, its history holds dozens of pages. The report says Framework A supports old versions for two years. That was Framework C.

Nothing was wrong with any single step. The task was simply too long for one loop to hold clearly. There are two tools for this problem: make the agent plan, and split the work across several agents that each see less.

Plan first, then act

An agent running the agent loop picks one step at a time. On a long task that leads to drift: it follows an interesting lead, forgets a part of the request, and runs out of steps with one framework still unread.

The fix is cheap. Before any tool call, ask the model for a short plan, keep that plan in the history as a checklist, and have the agent tick items off and rewrite the plan when it learns something new.

Before using any tool, write a numbered plan of at most 6 steps. After each step, restate the plan with finished steps marked [done]. If a result changes what you need to do, rewrite the remaining steps and say why. Compare how Framework A, B and C handle security updates: time to ship a fix, how fixes are announced, and how long old versions are supported. Cite a page for each claim. Plan: 1. Find Framework A's security policy page and note the three facts. 2. Same for Framework B. 3. Same for Framework C. 4. For any fact a policy page does not state, check release notes for the last 3 security fixes. 5. Build a table: framework × three facts, with a source per cell. 6. Write a short comparison under the table. Starting step 1.

A plan helps in three ways. The checklist stops parts of the task from being forgotten. A person can read it and correct the approach before any work is done. And progress becomes visible: "step 4 of 6" means something.

The plan is a guess, not a contract. Step 4 exists because the agent expects some pages to be incomplete. If Framework B turns out to have no security page at all, the right move is to rewrite the remaining steps, not to follow the old ones.

Several agents, each with a fresh context

Planning keeps the agent on track, but it does not shrink the history. All three frameworks' pages still pile up in one context. The second tool is to split the work.

In the most common design, an orchestrator agent breaks the task into parts and hands each part to a worker agent. Each worker starts with an empty history and only its own part. It does the reading, and sends back a short summary. The orchestrator never sees the raw pages, only the summaries.

The numbers are illustrative, and the single-agent total assumes the task (100 tokens) plus 12,000 tokens of pages per framework. The shape is what matters: workers keep the orchestrator's context small and focused, and the work can run in parallel. Each worker is just the loop from the previous lesson, given its own goal.

// runWorker(brief) runs one agent loop and returns its final answer.
function orchestrate(goal, parts, runWorker) {
  const summaries = parts.map((part) =>
    runWorker(`Overall goal: ${goal}\nYour part: ${part}\n` +
      "Reply with at most 5 bullet points, each with a source link."));
  return summaries; // in a real app, run the workers in parallel
}

const fakeWorker = (brief) => `summary of: ${brief.split("\n")[1]}`;
console.log(orchestrate("Compare security updates",
  ["Framework A", "Framework B", "Framework C"], fakeWorker));
// [ 'summary of: Your part: Framework A', ... ]

# run_worker(brief) runs one agent loop and returns its final answer.
def orchestrate(goal, parts, run_worker):
    summaries = [
        run_worker(f"Overall goal: {goal}\nYour part: {part}\n"
                   "Reply with at most 5 bullet points, each with a source link.")
        for part in parts
    ]
    return summaries  # in a real app, run the workers in parallel

fake_worker = lambda brief: f"summary of: {brief.splitlines()[1]}"
print(orchestrate("Compare security updates",
                  ["Framework A", "Framework B", "Framework C"], fake_worker))
# ['summary of: Your part: Framework A', ...]

Look at what the brief contains. The worker knows nothing except what is in that string, so the brief has to carry the goal, the boundaries of the part, and the shape of the reply. A vague brief, like "Research Framework B", gets back a vague essay.

When one agent is better

Multi-agent systems are popular to draw and often worse in practice. They cost more in total, as the tracer showed. Every handoff loses context the orchestrator had and did not write down. And when the final answer is wrong, there are more places to look.

Split work only when the parts are truly independent: researching separate topics, checking separate files, trying separate approaches and keeping the best. Keep one agent when the parts depend on each other. Two workers writing different halves of the same program will each make reasonable choices about names, data formats and error handling, and the choices will not match.

Split a task across agents only when the parts can be done without talking to each other. Otherwise, one agent with a plan is simpler, cheaper and easier to debug.

Research assistants that answer broad questions often use workers to read many sources in parallel. Coding agents more often stay single, because edits to one codebase depend on each other, and use a plan to stay organized.

Try it yourself

The orchestrator in the framework comparison sends this brief to a worker. The worker comes back with a long history of the project and no dates. Rewrite the brief so the summary is usable in the final table.

 Research Framework B. Overall goal: a table comparing how three web frameworks handle security updates. You are covering Framework B only. Find these three facts: 1. Typical time from a reported vulnerability to a released fix. 2. Where fixes are announced (mailing list, blog, advisory database...). 3. How long older major versions receive security fixes. Use the project's own security policy and release notes first. If a fact is not stated anywhere, write "not stated" rather than estimating. Reply with exactly three bullet points, one per fact, each ending with the source URL. No background on the project.

Why it works: the worker knows how its output will be used (a table cell), exactly which three facts to find, where to look, what to do when a fact is missing, and the shape of the reply. That is the same brief you would give a human contractor who cannot ask you questions.

Common mistakes

If worker B needs a decision worker A makes, they will each guess, and the guesses will clash. Either do those parts in one agent, or make the decision first and put it in both briefs.

A plan written before any tool ran is based on assumptions. When a result contradicts one, update the plan. Tell the agent in its instructions that rewriting the plan is expected, or it may stick to the original out of obedience.

The orchestrator cannot check what a worker read. Ask workers to cite a source for each claim, so a person, or a checking step, can follow it back.
