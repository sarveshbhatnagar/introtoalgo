You ask a friend whether it will rain this afternoon. They do not know, so they check the weather app on their phone. Without the phone, they could only look at the sky and guess.

A model has no phone. Everything it knows comes from training or from its context, which is prepared before the call. Tools let the model ask for fresh information, or for an action, in the middle of answering.

How a tool call works

The model cannot run anything; it only writes text. Tool calling is a protocol between the model and the app around it:

  1. Describe. The app puts each tool's name, purpose and inputs in the context.
  2. Request. If a tool would help, the model writes a structured request instead of an answer: "call getWeather with city = Bristol".
  3. Run. The app checks the request and runs the real code: an API call, a database query, a file read.
  4. Return. The app adds the result to the context and calls the model again.
  5. Answer. The model reads the result and writes its reply, or requests another tool.

The app is in charge: it chooses which tools exist, whether a request is allowed, and what goes back into the context. That is where safety checks live.

The loop can go around many times: search, read a page, search again, then answer. A model running that loop with real freedom is an agent, covered in The Agent Loop.

What the app writes

A tool description is a small block of structured data. Field names differ between providers, but all carry a name, a plain-words description, and typed inputs.

{
  "name": "getWeather",
  "description": "Get the hourly forecast for a city for today. Use for questions about rain, temperature or wind today. Not for past weather or forecasts beyond today.",
  "parameters": {
    "type": "object",
    "properties": {
      "city": { "type": "string", "description": "City name, e.g. \"Bristol\"" }
    },
    "required": ["city"]
  }
}

The description is for the model, which reads it to decide when to use the tool and what to pass. Write it like instructions to a colleague, including when not to use it.

On the app's side, running a request is a lookup and a function call. Here it is with a fake weather function:

const tools = {
  getWeather: ({ city }) => ({ city, rainChance: 0.8, at: "15:00" }), // fake data
};

function runToolCall(call) {
  const tool = tools[call.name];
  if (!tool) return { error: `Unknown tool: ${call.name}` };
  if (typeof call.arguments?.city !== "string") return { error: "city must be a string" };
  return tool(call.arguments);
}

// The model wrote this instead of an answer:
const call = { name: "getWeather", arguments: { city: "Bristol" } };
console.log(runToolCall(call)); // { city: 'Bristol', rainChance: 0.8, at: '15:00' }
console.log(runToolCall({ name: "bookFlight", arguments: {} })); // { error: 'Unknown tool: bookFlight' }

tools = {
    "getWeather": lambda args: {"city": args["city"], "rain_chance": 0.8, "at": "15:00"},  # fake data
}

def run_tool_call(call):
    tool = tools.get(call["name"])
    if tool is None:
        return {"error": f"Unknown tool: {call['name']}"}
    if not isinstance(call.get("arguments", {}).get("city"), str):
        return {"error": "city must be a string"}
    return tool(call["arguments"])

# The model wrote this instead of an answer:
call = {"name": "getWeather", "arguments": {"city": "Bristol"}}
print(run_tool_call(call))  # {'city': 'Bristol', 'rain_chance': 0.8, 'at': '15:00'}
print(run_tool_call({"name": "bookFlight", "arguments": {}}))  # {'error': 'Unknown tool: bookFlight'}

The checks matter. The request is generated text, so it can name a missing tool or pass a bad input. The app validates first and sends any error back into the context so the model can retry.

MCP: one plug for every tool

Without a standard, every app writes its own connector to every service. With 3 apps and 3 services, that is 3 × 3 = 9 connectors, and each new app or service adds a whole row or column.

The Model Context Protocol (MCP) is an open standard that removes that multiplication. A service is wrapped once as an MCP server. Any app that speaks MCP can connect to it, ask what it offers, and pass that on to its model: 3 + 3 pieces of work instead of 9.

An MCP server can offer three kinds of things:

  • Tools: actions the model can request, like "create a ticket" or "search the repository".
  • Resources: data the app can read and put into the context, like a file or a database record.
  • Prompts: ready-made templates for common tasks, which a user can pick.

MCP does not change the tool loop. It standardizes how the app discovers and calls tools. The model still only writes requests, and the app still decides what runs.

Tools turn "the model does not know" into "the model can ask". But every tool description and result is context, competing for the same space and attention as everything else.

Common mistakes

Each tool's description is usually sent on every call. Fifty tools cost tokens before the user types anything, and similar tools make the model pick the wrong one. Connect only what this task needs.

A search that returns 200 full results fills the window in one step. Return the top few matches, only the fields that matter, and a way to ask for more.

A web page or email returned by a tool can contain text written to steer the model: prompt injection. Treat tool results as data, and have a human confirm anything that sends, deletes, buys or publishes. Only connect MCP servers you trust; their descriptions reach the model too.

Try it yourself

A team's assistant calls this tool for general knowledge questions and passes whole sentences as the query. Rewrite the description so the model knows when to use it and what to pass.

 name: search description: Searches stuff. parameters: q (string)

One better version:

{
  "name": "searchTeamWiki",
  "description": "Search the team's internal wiki (runbooks, onboarding guides, design docs). Use when the question is about our own systems, processes or decisions. Do not use for general programming or world knowledge. Returns up to 5 page titles with a short excerpt each.",
  "parameters": {
    "type": "object",
    "properties": {
      "query": { "type": "string", "description": "2 to 6 keywords, e.g. \"deploy rollback runbook\". Not a full sentence." }
    },
    "required": ["query"]
  }
}

Why it works: the name says what is searched. The description says when to use it, when not to, and what comes back. The parameter description shows the format with an example.
