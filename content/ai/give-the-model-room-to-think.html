A language model produces its reply one token at a time, and the only place it can keep intermediate results is the text it has already written. If you ask for working before the answer, the model can use each step it writes as input for the next one, and multi-step problems such as arithmetic, comparing options and checking rules become much more reliable. If you force the answer to come first, the model has to produce it with no working on the page.

The practical consequence is that the order and length of the reply are part of the prompt. A prompt that says "reply with the answer only" on a problem with several steps removes the one thing that helps the model get it right.

Why written working changes the answer

For every token, the model runs a fixed amount of computation over the prompt and everything it has written so far. That amount does not grow because the question is harder. A problem that needs five dependent steps therefore cannot be solved in the single token that carries a one-word answer, unless the model has memorised the result.

When the reply starts with working, each step is written down and becomes part of the text that later tokens read. The final answer then only has to pick out a result that is already on the page. This is the same reason you get a better result from a calculation done on paper than from one done in your head.

Ways to give the model room to think

Asking for step-by-step reasoning

The simplest form is a sentence in the prompt, such as "Work through this step by step, then give the final answer." It needs no format and works in any chat. It is the right choice for a one-off question where you will read the whole reply yourself.

Its weakness is that the working and the answer arrive mixed together. A program that reads the reply has to guess where the answer is, and a person has to scan a long reply for it. Free-form working also varies in length and style between runs.

Separating the working from the answer

When another system will use the result, ask for the working and the answer in separate marked sections. The example below shows what goes wrong without room to think, and then the same task with the sections.

Our team needs a meeting slot. Ana can't do mornings. Ben is out Tuesday and Wednesday. Chloe only works Monday to Wednesday. Slots: Mon 10:00, Tue 14:00, Wed 15:00, Thu 11:00. Which slot works for everyone? One word. Wednesday

Wednesday is wrong because Ben is out that day. Checking every person against every slot takes several steps, and the prompt left no room for them.

Our team needs a meeting slot. Ana can't do mornings. Ben is out Tuesday and Wednesday. Chloe only works Monday to Wednesday. Slots: Mon 10:00, Tue 14:00, Wed 15:00, Thu 11:00. Check each slot against each constraint inside tags. Then give the slot that works for everyone inside tags, or "none" if no slot works. Mon 10:00: morning, so Ana can't. Out. Tue 14:00: Ben is out Tuesday. Out. Wed 15:00: Ben is out Wednesday. Out. Thu 11:00: morning for Ana, and Chloe doesn't work Thursday. Out. none

The correct answer is "none". The one-word prompt made that answer unlikely, because it implied that some slot must work. The second prompt allows for it explicitly, which is the habit from Be Clear and Specific of saying what the model should do when the task has no answer. Because the answer is inside tags, a program can ignore the working and read only the result.

function extractAnswer(reply) {
  const match = reply.match(/([\s\S]*?)<\/answer>/);
  return match ? match[1].trim() : null; // null: the tag was missing
}

const reply = "Mon 10:00 ... Out.\nnone";
console.log(extractAnswer(reply)); // "none"

import re

def extract_answer(reply):
    match = re.search(r"(.*?)", reply, re.DOTALL)
    return match.group(1).strip() if match else None  # None: the tag was missing

reply = "Mon 10:00 ... Out.\nnone"
print(extract_answer(reply))  # none

The code returns nothing when the tag is missing, and your program has to handle that case. Models follow a requested format most of the time but not always, and a reply that was cut off before the closing tag will not match.

Telling the model what the working should contain

"Think step by step" leaves the model to choose its own steps, and it may skip the one that matters. If you know what a good solution has to check, say so. In the meeting example the prompt asked for each slot to be checked against each constraint, and in the try-it exercise below the prompt asks for weekly commuting hours before any comparison. Naming the steps works best when the task has a known method, and it also makes the working easier to review, because you can see whether each requested step was done.

The risk is that you prescribe the wrong method. If the steps you list are not the right ones for the problem, the model will follow them anyway, so keep the instructions to checks you are sure are needed.

Built-in thinking settings

Some models and tools have a setting that makes the model write working before its reply, and that working may or may not be shown to you. With it turned on, adding "think step by step" to the prompt usually adds little, because the model is already doing it. A structured request for the working can still help when you want to review the steps yourself or extract only the answer, since the built-in working may be hidden or summarised, and it does not give you a section that a program can parse.

Splitting a large task into several prompts

One reply can only hold so much working before it becomes hard to follow or drifts. For a large job, such as reviewing a long document against twenty rules, run one prompt for each part and pass each result into the next prompt. This gives every part its own room to think, and it lets you check the intermediate results.

When to skip it

Written working helps when the answer depends on several steps: arithmetic, comparing options, checking a list of rules, debugging, and planning. It adds little to a lookup, a translation of a short phrase or a short creative task, and it costs extra tokens and waiting time on every call. For a high-volume task that does not need reasoning, asking for working is a cost with no benefit.

Pitfalls when asking for working

A prompt such as "Give the answer, then explain your reasoning" produces a justification instead of reasoning, because the answer is written before any working exists and the explanation is then made consistent with it. Reverse the order so that the working comes first and the answer comes last.

Written steps make errors easier to find, but they can be wrong, and they do not always describe how the model actually reached its answer. Check the numbers and rules that the result depends on yourself, as described in Verifying AI Output.

Instructions such as "be brief" or "one word only" on a multi-step problem take away the working without anyone noticing. If you want a short result, ask for a short final answer and still allow the working before it, for example inside tags that your program discards.

If your code assumes that every reply has an answer tag, one malformed reply will break the pipeline or pass an empty value downstream. Return an explicit failure when the tag is missing, and retry or flag the item.

What this changes in practice

When a task has more than one step, write the prompt so that the working comes first and the answer last, and say where each part goes. Tag the answer whenever a program reads the result. Look at the working when the answer matters, because a wrong step is the quickest way to find out why a result is wrong. For simple lookups, leave the working out and keep the reply short.

This prompt gets a one-word pick that often ignores the commute. Rewrite it so that the model compares the offers on what matters before it chooses, and so that the choice is easy to find.

 Which job offer should I take? Just tell me A, B or C. A: $62k, 70-minute commute each way. B: $58k, fully remote. C: $60k, 20-minute commute, 4-day week. Help me pick a job offer. I care most about time with my family, then pay. A: $62k, 70-minute commute each way, 5 days a week. B: $58k, fully remote. C: $60k, 20-minute commute each way, 4-day week. Inside tags: work out the weekly hours spent commuting for each, then compare the offers on free time first and pay second. Then give your pick inside tags as one letter, followed by one sentence explaining why.

This version works because the model writes the numbers before it decides: A is about 11.7 hours of commuting a week, C is about 2.7, and B has none. Your stated priorities tell it how to weigh them, and the tag makes the choice easy to find.
