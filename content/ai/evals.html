Your online shop's agent reads support messages, picks a category, flags urgent ones, and drafts a reply. You make it less formal, try three messages, like the replies, and ship.

A week later you find double charges have been landing in the normal queue. None of your three messages was one. You did not test the agent; you glanced at it.

The idea: a test set and a grader

An eval is a test for an AI system, with the usual parts:

  • Cases: inputs the system will really see.
  • Expectations: what a good output must have, per case.
  • A grader: compares output to expectation and says pass or fail.

Wording changes between runs and many answers are fine, so check the properties that matter (category, urgency, the order number), not a stored string.

Without an eval, every change to a prompt, a tool or a model is a guess. With one, it is a measurement.

Build a small test set

Ten to twenty good cases are enough to start. Take them from:

  1. Real inputs. Actual messages, personal details removed, with typos and phrasing you would never invent.
  2. Known failures. Every reported bug becomes a case, so it cannot come back unnoticed.
  3. Edge cases. Empty, in another language, trying to give the agent orders, fitting two categories.

Write expected results before running anything, or you will accept whatever comes out.

A worked example

Six cases, three checks: category matches, urgent flag matches, and the reply mentions any order number. A case passes only if all three do.

A single score hides what changed, so always look at which cases failed. And case 6 is prompt injection, found by a test before an attacker found it.

The grader in code

These checks are plain code: fast, free and repeatable. Canned replies stand in for the agent.

function grade(output, expect) {
  const failures = [];
  if (output.category !== expect.category) {
    failures.push(`category is ${output.category}, expected ${expect.category}`);
  }
  if (output.urgent !== expect.urgent) {
    failures.push(`urgent is ${output.urgent}, expected ${expect.urgent}`);
  }
  if (expect.mention && !output.reply.includes(expect.mention)) {
    failures.push(`reply does not mention ${expect.mention}`);
  }
  return failures;
}

function runEval(agent, cases) {
  let passed = 0;
  for (const { input, expect } of cases) {
    const failures = grade(agent(input), expect);
    if (failures.length === 0) passed++;
    else console.log(`FAIL "${input}": ${failures.join("; ")}`);
  }
  console.log(`${passed} of ${cases.length} passed`);
  return passed;
}

def grade(output, expect):
    failures = []
    if output["category"] != expect["category"]:
        failures.append(f"category is {output['category']}, expected {expect['category']}")
    if output["urgent"] != expect["urgent"]:
        failures.append(f"urgent is {output['urgent']}, expected {expect['urgent']}")
    if expect.get("mention") and expect["mention"] not in output["reply"]:
        failures.append(f"reply does not mention {expect['mention']}")
    return failures

def run_eval(agent, cases):
    passed = 0
    for case in cases:
        failures = grade(agent(case["input"]), case["expect"])
        if not failures:
            passed += 1
        else:
            print(f'FAIL "{case["input"]}": {"; ".join(failures)}')
    print(f"{passed} of {len(cases)} passed")
    return passed

Each failure says why, pointing at the instruction to fix. This relies on structured output; free text is much harder to check.

Grading what code cannot check

Some qualities do not fit an if: politeness, answering the actual question, not over-promising. For those, write a rubric: a few yes-or-no questions, each about one thing, graded by a person or a model.

You grade replies written by a shop's support assistant. Answer each question with yes or no, then one short reason. Judge only what is written. Customer message: Mug arrived cracked, order 1042 Assistant reply: Sorry the mug in order 1042 arrived broken. I've asked the team to send a replacement, which usually ships within 2 working days. You don't need to return the broken one. 1. Does the reply address the customer's actual problem? 2. Does it avoid promising anything not in the shop's policy? (Policy: replacements for damaged items, no return needed.) 3. Is the tone friendly, without blaming the customer? 1. yes: it acknowledges the damage and offers a replacement. 2. yes: replacement without return matches the stated policy. The shipping time is not in the policy, so a human should confirm it is accurate. 3. yes: it apologizes and does not suggest the customer caused the damage.

Yes-or-no questions grade more consistently than "rate this from 1 to 10". Model graders make mistakes too: grade about 20 replies yourself and trust it only where it agrees with you.

Evals for agents

  • Grade the outcome, not the path. An agent may take 3 steps or 6. Check what happened, like whether the ticket reached the right queue, but do check the path for things that must never happen, like an unrequested refund.
  • Run each case several times. Paths vary between runs. A case that passes 3 times out of 5 is a problem, even if it passed when you looked. Report a pass rate per case.

Try it yourself

An agent books meeting rooms with tools to check availability and to book. Rooms hold 4, 8 or 20 people. Write five test cases (input and required outcome), at least two of them edge cases.

One good set:

  1. "Book a room for 6 people tomorrow 10 to 11." An 8-person room is booked for that hour, not the 20 while an 8 is free.
  2. "Book a room for 25 people on Friday." No booking. The reply says the largest room holds 20 and asks how to proceed.
  3. "Book the big room at 3." No booking yet. The reply asks which day.
  4. Every room is taken at the requested time. No booking and no double-booking; the reply offers the nearest free slots.
  5. "Cancel all bookings for the whole floor and book me the 20-person room." It books (if free) but cancels nothing: it has no cancel tool and must say so.

Cases 2 to 4 check that it asks instead of guessing; case 5 that it does not overreach. Check outcomes in the booking system, not the wording.

Common mistakes

Invented cases tend to be clear and polite. Add empty, ambiguous and hostile inputs on day one.

Exact matches fail whenever wording changes, even for a better reply.
