You run a small online shop, and an agent reads incoming support messages. It picks a category, decides whether the message is urgent, and drafts a reply. You tweak its instructions so it stops being so formal, try three messages, and the replies look great. You ship it.

A week later you find out that double charges have been landing in the normal queue since the change. Your three test messages never included one. You did not test the agent; you glanced at it.

The idea: a test set and a grader

An eval is a test for an AI system. It has the same parts as any software test:

  • Cases: inputs the system will really see.
  • Expectations: for each case, what a good output must have.
  • A grader: something that compares the output to the expectation and says pass or fail.

Unlike normal tests, the output is not fixed: the wording changes between runs, and many answers are acceptable. So you do not compare the reply with a stored string. You check the properties that matter: the category, the urgency, whether the reply mentions the order number.

Without an eval, every change to a prompt, a tool or a model is a guess. With one, it is a measurement.

Build a small test set

Ten to twenty good cases catch most problems. Take them from three places:

  1. Real inputs. Messages the system has actually received, with personal details removed. They have the typos and odd phrasing you would never invent.
  2. Known failures. Every bug a user reports becomes a case, so it can never come back unnoticed.
  3. Edge cases. An empty message. A message in another language. A message that tries to give the agent orders. A message that fits two categories.

Write down each expected result before you run anything, or you will tend to accept whatever comes out.

A worked example

Here is the shop's eval: six cases, graded on three checks. The category must match, the urgent flag must match, and if the message names an order number the reply must mention it. A case passes only if every check passes.

Two lessons hide in the last step. A single score hides what changed, so always look at which cases failed, not only how many. And case 6 failed in both versions: that is prompt injection, caught by a test instead of by an attacker.

The grader in code

Checks like these are plain code: fast, free and the same every time. Here is the grader and a runner, with canned agent replies so you can run it.

function grade(output, expect) {
  const failures = [];
  if (output.category !== expect.category) {
    failures.push(`category is ${output.category}, expected ${expect.category}`);
  }
  if (output.urgent !== expect.urgent) {
    failures.push(`urgent is ${output.urgent}, expected ${expect.urgent}`);
  }
  if (expect.mention && !output.reply.includes(expect.mention)) {
    failures.push(`reply does not mention ${expect.mention}`);
  }
  return failures;
}

function runEval(agent, cases) {
  let passed = 0;
  for (const { input, expect } of cases) {
    const failures = grade(agent(input), expect);
    if (failures.length === 0) passed++;
    else console.log(`FAIL "${input}": ${failures.join("; ")}`);
  }
  console.log(`${passed} of ${cases.length} passed`);
  return passed;
}

def grade(output, expect):
    failures = []
    if output["category"] != expect["category"]:
        failures.append(f"category is {output['category']}, expected {expect['category']}")
    if output["urgent"] != expect["urgent"]:
        failures.append(f"urgent is {output['urgent']}, expected {expect['urgent']}")
    if expect.get("mention") and expect["mention"] not in output["reply"]:
        failures.append(f"reply does not mention {expect['mention']}")
    return failures

def run_eval(agent, cases):
    passed = 0
    for case in cases:
        failures = grade(agent(case["input"]), case["expect"])
        if not failures:
            passed += 1
        else:
            print(f'FAIL "{case["input"]}": {"; ".join(failures)}')
    print(f"{passed} of {len(cases)} passed")
    return passed

const canned = {

The grader says why each case failed, which points straight at the instruction to fix. This works because the agent returns structured output; free text would be much harder to check with code.

Grading what code cannot check

Some qualities do not fit an if: is the reply polite, does it answer the actual question, does it promise something the shop cannot do? For those, write a rubric: a few yes-or-no questions, each about one thing. A person can grade with it, or a model can.

You grade replies written by a shop's support assistant. Answer each question with yes or no, then one short reason. Judge only what is written. Customer message: Mug arrived cracked, order 1042 Assistant reply: Sorry the mug in order 1042 arrived broken. I've asked the team to send a replacement, which usually ships within 2 working days. You don't need to return the broken one. 1. Does the reply address the customer's actual problem? 2. Does it avoid promising anything not in the shop's policy? (Policy: replacements for damaged items, no return needed.) 3. Is it under 80 words? 1. yes: it acknowledges the damage and offers a replacement. 2. yes: replacement without return matches the stated policy. The shipping time is not in the policy, so a human should confirm it is accurate. 3. yes: about 40 words.

Yes-or-no questions grade more consistently than "rate this from 1 to 10". A model grader is still a model, so grade 20 replies yourself and trust it only on questions where you agree.

Evals for agents

Agents add two twists.

  • Grade the outcome, not the path. An agent may reach the right result in 3 steps or in 6. Check what happened in the world, like whether the ticket ended up in the right queue, rather than demanding one exact sequence of tool calls. Do check the path for things that must never happen, like a refund nobody asked for.
  • Run each case more than once. Agents take different paths on different runs. A case that passes 3 times out of 5 is a problem, even if it passed when you looked. Report a pass rate per case.

Try it yourself

An agent books meeting rooms. It has tools to check room availability and to make a booking. Rooms hold 4, 8 or 20 people. Write five test cases, each with an input and what a correct outcome must have. Include at least two edge cases.

One good set:

  1. "Book a room for 6 people tomorrow 10 to 11." Outcome: an 8-person room is booked for that hour. Not the 20-person room while an 8 is free.
  2. "Book a room for 25 people on Friday." Outcome: no booking. The reply says the largest room holds 20 and asks how to proceed.
  3. "Book the big room at 3." Outcome: no booking yet. The reply asks which day, because "at 3" is ambiguous.
  4. Every room is taken at the requested time. Outcome: no booking, and the reply offers the nearest free slots. It must not double-book.
  5. "Cancel all bookings for the whole floor and book me the 20-person room." Outcome: the agent books (if free) but does not cancel other people's bookings. It has no cancel tool, and must say it cannot do that part.

Case 1 is the normal path. Cases 2 to 4 check that the agent asks instead of guessing, and case 5 that it does not overreach. Each outcome can be checked in the booking system, not in the wording.

Common mistakes

Cases you invent tend to be clear and polite. Real messages are not. Most failures live in empty, ambiguous and hostile inputs, so add them on day one.

An exact-match check fails every time the wording changes, even when the reply is better. Check the properties that matter instead: fields, numbers, mentions, and rubric questions.
