A meeting room has one whiteboard. By noon it is full of notes, so the next person wipes the oldest corner. Nobody checks whether that corner held the one decision everybody agreed on at 9 a.m.

A model's context has the same problem. The app resends the whole conversation on every call (What Is Context), but the model can only read so much text at once. That limit is the context window.

A fixed budget, counted in tokens

The window is a maximum number of tokens per call. Three things trip people up:

  • Everything counts. Instructions, tool descriptions, documents, every earlier message and the new one share one budget. Users see only their own messages, so they underestimate how full it is.
  • The reply counts too. The answer is written into the same window. If the input fills it, the reply gets cut off.
  • The size depends on the model, and has grown over time. Check your model's documentation rather than a number you remember.

What happens when it fills up

When a conversation outgrows the window, the app has three common choices:

  1. Refuse with an error and ask you to start over or shorten your input. Honest, but annoying.
  2. Drop the oldest messages. Keep the instructions and newest turns, and quietly leave out the rest. Simple and widely used.
  3. Summarize old turns. Better, but a summary can lose details. Memory covers this.

The second is dangerous because it is silent. Take a cooking chat with a toy window of 120 tokens, 20 reserved for the reply, so the input may use 100.

The most important fact was said first, so "oldest first out" dropped it first.

The trimming in code

// history is oldest first. Each item has a token count.
function fitToWindow(system, history, newMessage, budget) {
  let used = system.tokens + newMessage.tokens;
  const kept = [];
  for (let i = history.length - 1; i >= 0; i--) { // newest first
    if (used + history[i].tokens > budget) break;
    kept.push(history[i]);
    used += history[i].tokens;
  }
  kept.reverse(); // back to oldest first
  return { request: [system, ...kept, newMessage], used };
}

const history = [15, 10, 10, 35, 10, 25].map((tokens, i) => ({ id: i, tokens }));
const result = fitToWindow({ tokens: 20 }, history, { tokens: 10 }, 100);
console.log(result.used, result.request.length); // 100 5

# history is oldest first. Each item has a token count.
def fit_to_window(system, history, new_message, budget):
    used = system["tokens"] + new_message["tokens"]
    kept = []
    for msg in reversed(history):  # newest first
        if used + msg["tokens"] > budget:
            break
        kept.append(msg)
        used += msg["tokens"]
    kept.reverse()  # back to oldest first
    return {"request": [system, *kept, new_message], "used": used}

history = [{"id": i, "tokens": t} for i, t in enumerate([15, 10, 10, 35, 10, 25])]
result = fit_to_window({"tokens": 20}, history, {"tokens": 10}, 100)
print(result["used"], len(result["request"]))  # 100 5

The loop uses break, not "skip and keep looking". Skipping a big message but keeping an older small one would leave a hole, and the model would read replies to questions it never saw.

Fitting is not the same as reading well

A bigger window means more fits, not that the model uses all of it equally well. As context grows:

  • Cost and speed suffer. The whole context is read on every call, so longer usually means pricier and slower, turn after turn.
  • The middle gets less attention. Models use information near the start and end more reliably. A key line on page 40 of 80 is easier to miss than the same line at the top.
  • Noise distracts. Asked about one product with ten similar product sheets in context, a model can mix up details between them.

The window is a ceiling, not a target. Fill it with what the task needs, not with everything that fits.

Common mistakes

Fill the input to the limit and the reply stops mid-sentence or the call fails. Always reserve space for output, more for long answers like code or reports.

Trimming removes the oldest turns first. Long-lived facts like allergies, names and hard rules belong in the instructions or a pinned note sent every call, not only in message 1.

The token-to-word ratio varies. Code, numbers, IDs and less common languages use more tokens per word. Use the tokenizer or the API's token count when numbers matter.

Try it yourself

A toy model has a 2,000-token window. Your app sends instructions (300 tokens), 4 tool descriptions (400 in total), a document (1,100) and the conversation including the new message (200). You reserve 500 for the reply. Does it fit? If not, by how much is it over, and what would you cut first?

300 + 400 + 1,100 + 200 + 500 = 2,500. That is 500 tokens over.

Options, roughly in order:

  • Trim the document, the biggest item. If the question is about one section, send that. Cutting it to 600 tokens fixes the budget alone: 300 + 400 + 600 + 200 + 500 = 2,000.
  • Drop tools this task cannot use. Two irrelevant tools save about 200 tokens and remove options the model could misuse.
  • Do not cut the reply reserve. That just moves the failure to a truncated answer.
