A warehouse manager asks an assistant which of two warehouses has more blue mugs. The assistant has one tool, stockLevel, and needs to call it twice, once per warehouse, then compare. On its first try it writes the warehouse name with a capital letter and gets an error back.

Whether this ends with the right answer, a crash, or a loop that never stops depends on about twenty lines of ordinary code around the model. That code is the agent loop, and this lesson writes it.

The idea: four moves, repeated

What Is an Agent showed the loop as pseudocode. Written properly, every pass does four things:

  1. Ask. Send the whole history to the model and get one reply.
  2. Check. If the reply is a final answer, stop and return it.
  3. Act. Otherwise the reply is a tool request. Run it. If it fails, turn the failure into an error message instead of crashing.
  4. Record. Add the reply and the result to the history, so the next call can see them.

Around those four moves sits one more rule: a hard limit on the number of passes. A model can keep asking for tools forever, so the code, not the model, must have the last word on when to stop.

The model decides what to do next. The loop decides whether it is allowed to keep going.

One run, step by step

Here is the blue-mug question running through the loop. North has 140 mugs and south has 95. The model's replies are realistic but scripted, so you can follow exactly what the code does with each one.

The loop in code

The model argument is any function that takes the history and returns either { type: "answer", text } or { type: "tool", tool, input }. In a real app it wraps a call to a model API and converts the reply into one of those two shapes. Here it is a stand-in, so the code runs without one.

function runAgent(model, tools, goal, maxSteps = 10) {
  const history = [{ role: "user", text: goal }];
  for (let step = 1; step <= maxSteps; step++) {
    const reply = model(history);
    history.push(reply);
    if (reply.type === "answer") {
      return { answer: reply.text, steps: step, stopped: "answered" };
    }
    let result;
    try {
      const tool = tools[reply.tool];
      if (!tool) throw new Error(`No tool named ${reply.tool}`);
      result = tool(reply.input);
    } catch (err) {
      result = { error: err.message }; // the model reads errors too
    }
    history.push({ role: "tool", result });
  }
  return { answer: null, steps: maxSteps, stopped: "step limit" };
}

def run_agent(model, tools, goal, max_steps=10):
    history = [{"role": "user", "text": goal}]
    for step in range(1, max_steps + 1):
        reply = model(history)
        history.append(reply)
        if reply["type"] == "answer":
            return {"answer": reply["text"], "steps": step, "stopped": "answered"}
        try:
            tool = tools.get(reply["tool"])
            if tool is None:
                raise ValueError(f"No tool named {reply['tool']}")
            result = tool(**reply["input"])
        except Exception as err:
            result = {"error": str(err)}  # the model reads errors too
        history.append({"role": "tool", "result": result})
    return {"answer": None, "steps": max_steps, "stopped": "step limit"}

Swap fakeModel for a real model call and tools for real ones, and the loop itself does not change. Real frameworks add streaming, logging and several tool calls per reply, but this is the core of all of them.

Good reasons to stop

An answer is the stop you want. The others are safety nets, and the loop should return which one fired, so the caller never mistakes a cut-off run for a finished one.

  • Step limit. The one shown above. Pick it from real runs: if a task normally takes 5 steps, a limit of 15 leaves room without allowing endless wandering.
  • Budget or time. Stop when total tokens or seconds pass a limit, for the same reason.
  • Repeats. If the model asks for the exact same tool with the exact same input it already tried, it is probably stuck. Keep a set of past requests, and on a repeat either stop or add a note to the history: "You already tried this. Try something different or answer with what you have."
  • A person says stop. Long runs should be cancellable.

What each step costs

The number of model calls grows in a straight line with the number of steps. The amount of text the model reads does not. Every call re-reads the whole history, and the history gets longer every step.

Say each step adds about 500 tokens. Call 1 reads 500, call 2 reads 1,000, call 20 reads 10,000. Over 20 calls that is 500 × (1 + 2 + … + 20) = 500 × 210 = 105,000 tokens read, for a history that ends only 10,000 tokens long.

That is why long runs get slow and expensive faster than you expect, and why short tool results matter so much. Many systems cut the cost by caching the unchanged start of the history, or by summarizing old steps, at the risk of losing details covered in Context Rot.

Try it yourself

This loop works in the demo and fails in production. Find at least three problems and say how to fix each.

 def run_agent(model, tools, goal): history = [goal] while True: reply = model(history) if reply["type"] == "answer": return reply["text"] result = tools[reply["tool"]](**reply["input"]) history.append(result)
  1. No step limit. while True runs until the model chooses to answer, which may be never. Use a for loop up to max_steps and return a clear "stopped: step limit".
  2. Tool failures crash the run. An exception inside a tool, or a misspelled tool name (a KeyError on tools[...]), ends the whole program. Catch errors and put the message into the history so the model can correct itself.
  3. The model's own request is never recorded. Only the result goes into the history. On the next call the model sees an answer to a question it cannot see itself asking. Append the reply, then the result.
  4. The caller cannot tell how it ended. Returning only text hides whether the run answered or was cut off. Return the reason too.

Each of these is invisible on a happy demo run, which is why they reach production.

Common mistakes

Most runs end with an answer. Some do not: the model keeps searching, or keeps retrying a broken tool. Without a hard limit in code, one bad run can make hundreds of calls before anyone notices.

Catching an exception and silently skipping the step leaves the model thinking the call never happened, so it asks again. Put the error text into the history, as the loop above does.

If the step limit fires, the last thing in the history might be a half-finished plan. Check the stop reason before showing anything as an answer, and say plainly when the agent did not finish.
