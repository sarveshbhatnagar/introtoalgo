A warehouse manager asks which of two warehouses has more blue mugs. The assistant must call its one tool, stockLevel, once per warehouse and compare. On its first try it capitalizes the warehouse name and gets an error.

Whether this ends with the right answer, a crash, or a loop that never stops depends on about twenty lines of ordinary code around the model: the agent loop.

The idea: four moves, repeated

What Is an Agent showed the loop as pseudocode. Every pass does four things:

  1. Ask. Send the whole history to the model and get one reply.
  2. Check. If the reply is a final answer, stop and return it.
  3. Act. Otherwise run the requested tool. If it fails, turn the failure into an error message instead of crashing.
  4. Record. Add the reply and the result to the history for the next call.

One more rule: a hard limit on passes. A model can keep asking for tools forever, so the code has the last word on stopping.

The model decides what to do next. The loop decides whether it is allowed to keep going.

One run, step by step

North has 140 mugs and south has 95. The model's replies are scripted so you can follow what the code does with each.

The loop in code

model is any function that takes the history and returns { type: "answer", text } or { type: "tool", tool, input }. In a real app it wraps a model API call; here it is a stand-in.

function runAgent(model, tools, goal, maxSteps = 10) {
  const history = [{ role: "user", text: goal }];
  for (let step = 1; step <= maxSteps; step++) {
    const reply = model(history);
    history.push(reply);
    if (reply.type === "answer") {
      return { answer: reply.text, steps: step, stopped: "answered" };
    }
    let result;
    try {
      const tool = tools[reply.tool];
      if (!tool) throw new Error(`No tool named ${reply.tool}`);
      result = tool(reply.input);
    } catch (err) {
      result = { error: err.message }; // the model reads errors too
    }
    history.push({ role: "tool", result });
  }
  return { answer: null, steps: maxSteps, stopped: "step limit" };
}

def run_agent(model, tools, goal, max_steps=10):
    history = [{"role": "user", "text": goal}]
    for step in range(1, max_steps + 1):
        reply = model(history)
        history.append(reply)
        if reply["type"] == "answer":
            return {"answer": reply["text"], "steps": step, "stopped": "answered"}
        try:
            tool = tools.get(reply["tool"])
            if tool is None:
                raise ValueError(f"No tool named {reply['tool']}")
            result = tool(**reply["input"])
        except Exception as err:
            result = {"error": str(err)}  # the model reads errors too
        history.append({"role": "tool", "result": result})
    return {"answer": None, "steps": max_steps, "stopped": "step limit"}

Swap in a real model and real tools and the loop does not change. Frameworks add streaming, logging and several tool calls per reply, but the core is this loop.

Good reasons to stop

An answer is the stop you want. The others are safety nets, and the loop should return which one fired, so the caller never mistakes a cut-off run for a finished one.

  • Step limit. Pick it from real runs: if a task normally takes 5 steps, a limit of 15 leaves room without endless wandering.
  • Budget or time. Stop when total tokens or seconds pass a limit.
  • Repeats. The exact same tool and input again means it is probably stuck. Keep a set of past requests; on a repeat, stop or add a note: "You already tried this. Try something different or answer with what you have."
  • A person says stop. Long runs should be cancellable.

What each step costs

Model calls grow linearly with steps. Text read does not, because every call re-reads the whole, growing history.

If each step adds about 500 tokens, call 1 reads about 500, call 2 about 1,000, and call 20 about 10,000. Over 20 calls that is 500 × (1 + 2 + … + 20) = 500 × 210 = 105,000 tokens read, for a history only about 10,000 tokens long.

So long runs get expensive fast, and short tool results matter. Systems cut the cost by caching the unchanged start of the history, or by summarizing old steps, which can drop a detail needed later. Long histories also hurt quality: see Context Rot.

Try it yourself

This loop works in the demo and fails in production. Find at least three problems and say how to fix each.

 def run_agent(model, tools, goal): history = [goal] while True: reply = model(history) if reply["type"] == "answer": return reply["text"] result = tools[reply["tool"]](**reply["input"]) history.append(result)
  1. No step limit. while True runs until the model answers, maybe never. Loop up to max_steps and return "stopped: step limit".
  2. Tool failures crash the run. A tool exception or a misspelled tool name (a KeyError on tools[...]) ends the program. Catch errors and put the message into the history.
  3. The model's request is never recorded. The model sees results to requests it cannot see itself making. Append the reply, then the result.
  4. The caller cannot tell how it ended. Return the stop reason too.

None of these shows on a happy demo run, which is why they reach production.

Common mistakes

Some runs never answer: the model keeps searching or retrying a broken tool. Without a hard limit in code, one bad run can make hundreds of calls before anyone notices.

Silently skipping a failed step leaves the model thinking the call never happened, so it asks again. Put the error text into the history.

When the step limit fires, the history may end in a half-finished plan. Check the stop reason before showing an answer, and say plainly when the agent did not finish.
