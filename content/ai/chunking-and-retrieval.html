You cut a cookbook into index cards of exactly 100 words each. One card ends with "Bake at". The next starts "180°C for 25 minutes, then let it cool." Later you search for "how long does the lemon cake bake?", but the card with the answer never mentions lemon cake, so it does not come up.

Bad cuts are among the most common causes of bad RAG answers: the right piece either does not exist or does not look like what it contains.

The size trade-off

Each chunk becomes one vector that must stand for the whole chunk.

  • Too big, and it covers several topics. Its vector averages them and matches none strongly. It also wastes context on text the question did not need.
  • Too small, and it loses its subject. "Bake for 25 minutes" is useless without "lemon cake", and two-sentence answers get split.

A paragraph or short section, a few hundred tokens, is a common starting size for prose. The better rule: a chunk should make sense on its own to someone with no other context.

A good chunk is a self-contained unit of meaning that carries its own subject. Cut along the document's structure, and attach its title and section path, embedded with the text.

Three ways to cut

  1. Fixed size with overlap. Take a window of N words and move it forward by fewer than N, so neighbours share a few words. Works on any text, and a sentence cut at one edge appears whole in the next chunk.
  2. Follow the structure. Split on headings, then paragraphs; fall back to fixed size only for long sections. An FAQ gives one chunk per question, code one per function. Tables stay whole.
  3. Add the context back. Prefix each chunk with its source: "Lemon cake > Baking: …". Store metadata too: title, section, date, product, version. The prefix helps the vector match; metadata lets you filter.

The first method on a 15-word recipe sentence, with windows of 6 and overlap 2:

function chunkWords(text, size, overlap) {
  const words = text.split(/\s+/);
  const step = size - overlap; // must be at least 1
  const chunks = [];
  for (let start = 0; start < words.length; start += step) {
    chunks.push(words.slice(start, start + size).join(" "));
    if (start + size >= words.length) break;
  }
  return chunks;
}

chunkWords("Bake the lemon cake at 180°C for 25 minutes then let it cool before icing", 6, 2);
// 4 chunks, the second is "at 180°C for 25 minutes then"

def chunk_words(text, size, overlap):
    words = text.split()
    step = size - overlap  # must be at least 1
    chunks = []
    for start in range(0, len(words), step):
        chunks.append(" ".join(words[start:start + size]))
        if start + size >= len(words):
            break
    return chunks

chunk_words("Bake the lemon cake at 180°C for 25 minutes then let it cool before icing", 6, 2)
# 4 chunks, the second is "at 180°C for 25 minutes then"

Chunking is one O(n) pass for n words. Overlap costs storage: about n ÷ (size − overlap) chunks, so overlap 2 on size 6 makes about 1.5 times as many as no overlap. Real systems count tokens, not words, and use much larger windows.

Retrieving well

Plain "top k by cosine similarity" is a fine start. Each addition below fixes a common failure.

  • Metadata filters. Asked about the kettle, search only kettle chunks. Filters are exact and cheap, and stop similar text about another product from winning.
  • A minimum score, so retrieval can say "nothing found" (see the mistake below).
  • Hybrid search. Embeddings are weak at exact strings like error codes, part numbers and names. Add a keyword search and merge the results.
  • Reranking. Cheaply retrieve 20 or 50 candidates, then have a slower, more careful model score each against the question and keep the best few.
  • Query rewriting. In a chat, "and for the blue one?" means nothing alone. Rewrite it into a full question before searching.

The first two in code, reusing cosine from RAG Basics. Toy dimensions: cleaning, indicator lights, filling.

const dot = (a, b) => a.reduce((s, x, i) => s + x * b[i], 0);
const cosine = (a, b) => dot(a, b) / Math.sqrt(dot(a, a) * dot(b, b));

function retrieve(queryVec, chunks, { product, k, minScore }) {
  return chunks
    .filter((c) => c.product === product)
    .map((c) => ({ text: c.text, score: cosine(queryVec, c.vec) }))
    .filter((c) => c.score >= minScore)
    .sort((a, b) => b.score - a.score)
    .slice(0, k);
}

const manual = [
  { product: "kettle", text: "Kettle > Care: descale monthly with vinegar.", vec: [5, 0, 1] },
  { product: "kettle", text: "Kettle > Lights: red means boiling.", vec: [1, 4, 0] },
  { product: "toaster", text: "Toaster > Care: empty the crumb tray weekly.", vec: [4, 1, 1] },
  { product: "kettle", text: "Kettle > Filling: never fill above MAX.", vec: [1, 1, 4] },
];
// "How do I clean the kettle?" embeds to [5, 1, 0]
retrieve([5, 1, 0], manual, { product: "kettle", k: 2, minScore: 0.5 });
// [{ text: "Kettle > Care: ...", score: 0.96 }]

import math

def dot(a, b):
    return sum(x * y for x, y in zip(a, b))

def cosine(a, b):
    return dot(a, b) / math.sqrt(dot(a, a) * dot(b, b))

def retrieve(query_vec, chunks, product, k, min_score):
    scored = [
        {"text": c["text"], "score": cosine(query_vec, c["vec"])}
        for c in chunks if c["product"] == product
    ]
    scored = [c for c in scored if c["score"] >= min_score]
    scored.sort(key=lambda c: c["score"], reverse=True)
    return scored[:k]

manual = [
    {"product": "kettle", "text": "Kettle > Care: descale monthly with vinegar.", "vec": [5, 0, 1]},
    {"product": "kettle", "text": "Kettle > Lights: red means boiling.", "vec": [1, 4, 0]},
    {"product": "toaster", "text": "Toaster > Care: empty the crumb tray weekly.", "vec": [4, 1, 1]},
    {"product": "kettle", "text": "Kettle > Filling: never fill above MAX.", "vec": [1, 1, 4]},
]
# "How do I clean the kettle?" embeds to [5, 1, 0]
retrieve([5, 1, 0], manual, "kettle", k=2, min_score=0.5)
# [{'text': 'Kettle > Care: ...', 'score': 0.96}]

Without the filter, the toaster's care chunk would win with 0.97, because cleaning is cleaning. Of the kettle chunks, care scores 0.96, lights 0.43 and filling 0.28. The threshold removes the last two, so you get one chunk though k is 2, instead of padding with noise.

Measure it

You cannot tune chunking by reading a few answers. Write 20 to 50 real questions, note which chunk holds each answer, then run retrieval alone and count how often the right chunk lands in the top k. Rerun after every change to size, overlap or filters. A rising number beats a feeling. Evals builds this into a habit.

Common mistakes

Prose, FAQs, code, tables and slides have different natural units. Splitting a table every 200 tokens separates rows from their headers. Split by structure first; fixed size is the fallback.

When nothing is relevant, top k still returns k chunks, and the model treats them as relevant. Use a threshold and let "nothing found" reach the model.

Try it yourself

You are indexing a gym's 40-question FAQ. Each entry is a bold question and a one-to-three-paragraph answer. Some answers say things like "Yes, as above, but only at weekends." How would you chunk it, what would you store with each chunk, and how would you handle answers like that?
  • One chunk per question and answer, question included. Users phrase questions like the FAQ does, so the question is often the best thing to match.
  • No fixed-size splitting unless an answer is very long. The structure already gives self-contained units.
  • Prefix and metadata: "Gym FAQ > Memberships > Can I bring a guest?", plus section, gym location if there are several, and last-updated date.
  • "As above" answers: rewrite them to stand alone when indexing ("Yes, guests are allowed, but only at weekends."), or attach the referenced answer. A retrieved "as above" is meaningless.
