A customer asks a support agent where order 1O42 is, typing a capital O instead of a zero. The agent calls getOrder("1O42") and gets Error: invalid input. It retries twice with the same ID, then tells the customer the order system is down.

The tool said something was wrong but not what, so the model had nothing to fix. Change that one error message and the same model usually gets it right on the second try.

The model only sees the text

As Tools and MCP showed, the app describes each tool, the model writes a request, and the app runs it and returns the result. To the model, a tool is three pieces of text:

  1. The description: the name, what it does, when to use it.
  2. The inputs: what it takes, and in what form.
  3. The output: the result, or the error.

If that text is unclear, the model guesses. Designing a tool is mostly writing it for a reader who is smart, literal and in a hurry.

The tool in code

Version B checks the input before looking anything up, and every failure returns a sentence the model can act on. The data is fake.

const orders = { "1042": { status: "shipped", items: 3 } };

function getOrder(orderId) {
  if (!/^\d{4}$/.test(orderId)) {
    const guess = orderId.replace(/[oO]/g, "0");
    const hint = /^\d{4}$/.test(guess) ? ` Did you mean "${guess}"?` : "";
    return { error: `"${orderId}" is not an order ID. IDs are 4 digits.${hint}` };
  }
  const order = orders[orderId];
  if (!order) {
    return { error: `No order "${orderId}". Use findOrders(email) to list a customer's orders.` };
  }
  return { orderId, ...order };
}

console.log(getOrder("1O42")); // error, suggests "1042"
console.log(getOrder("1042")); // { orderId: '1042', status: 'shipped', items: 3 }

import re

orders = {"1042": {"status": "shipped", "items": 3}}

def get_order(order_id):
    if not re.fullmatch(r"\d{4}", order_id):
        guess = re.sub(r"[oO]", "0", order_id)
        hint = f' Did you mean "{guess}"?' if re.fullmatch(r"\d{4}", guess) else ""
        return {"error": f'"{order_id}" is not an order ID. IDs are 4 digits.{hint}'}
    order = orders.get(order_id)
    if order is None:
        return {"error": f'No order "{order_id}". Use find_orders(email) to list a customer\'s orders.'}
    return {"order_id": order_id, **order}

print(get_order("1O42"))  # error, suggests "1042"
print(get_order("1042"))  # {'order_id': '1042', 'status': 'shipped', 'items': 3}

The "not found" error names the tool that can find the right ID. Errors are a cheap place to teach the agent how your tools fit together.

Short results, with a way to get more

Every result stays in the context for the rest of the run. Returning 300 orders in full can eat a large share of it in one step and bury the line that matters. Return the few useful items and fields, and say what was left out:

function limitResults(items, max = 5) {
  if (items.length <= max) return { results: items };
  return {
    results: items.slice(0, max),
    note: `Showing ${max} of ${items.length}. Add a status or date range to narrow it.`,
  };
}

console.log(limitResults([1, 2, 3, 4, 5, 6, 7, 8]).note);
// Showing 5 of 8. Add a status or date range to narrow it.

def limit_results(items, max_items=5):
    if len(items) <= max_items:
        return {"results": items}
    return {
        "results": items[:max_items],
        "note": f"Showing {max_items} of {len(items)}. Add a status or date range to narrow it.",
    }

print(limit_results([1, 2, 3, 4, 5, 6, 7, 8])["note"])
# Showing 5 of 8. Add a status or date range to narrow it.

Without the note, the model may assume those five orders are all there are.

Size the tools like the task

  • Too small: getCustomerField(id, field) needs one call per field. Name, email and plan take three calls, three chances to go wrong and three times the waiting.
  • Too big: runSql(query) can do anything. The model must write correct SQL against a schema it cannot see, and a bad query can change or delete data.
  • About right: findOrders(email, status) matches a step a person would take, returns what that step needs, and can do nothing else.

Then make inputs hard to get wrong:

  • Use fixed values (status: "packing", "shipped" or "returned") instead of free text.
  • Put units in names: timeoutSeconds, not timeout.
  • Ask for IDs from earlier results rather than names the model might misspell.

Read tools and write tools

A read tool like getOrder is safe to call twice; a write tool like refundOrder is not. If a refund times out, the model cannot tell whether it worked, retries, and refunds twice.

Make write tools idempotent: doing it twice has the same effect as once. The tool can check whether the action already happened ("order 1042 was already refunded on 3 March"), or accept a request ID and ignore repeats. Which write tools an agent gets, and which need a person's approval, is covered in Guardrails.

Payment APIs have long accepted a request ID (an idempotency key) with each charge, because networks drop replies and clients retry. Agents retry too.

Try it yourself

An agent misuses this ticket tool: it invents actions, puts the whole conversation into data, and loops on ERR_22. Redesign it: which tools, what inputs, and what one error message should say.

 name: doTicket description: Does ticket stuff. inputs: action (string), data (string) errors: ERR_22 (bad action), ERR_31 (bad data)

Split it into tools that each match one step:

createTicket(title, priority)
  priority: one of "low", "normal", "urgent"
  title: one line, under 80 characters
  Returns: { ticketId: "T-5521" }

closeTicket(ticketId, reason)
  reason: one of "fixed", "duplicate", "won't fix"
  Safe to repeat: closing a closed ticket returns
  "T-5521 is already closed (fixed)."

Example error:
  "T-552 is not a ticket ID. IDs look like T-5521.
   Use findTickets(text) to search by title."

Why it works:

  • Each tool does one thing, so its name says when to use it. No free-text action to invent.
  • Fixed values for priority and reason rule out whole classes of bad input.
  • The error says what went wrong, what a right ID looks like, and which tool helps.
  • Closing twice is harmless, so a retry after a timeout does no damage.

Common mistakes

ERR_22 or a stack trace is noise to the model, so it repeats itself. Return what went wrong and what to do instead, in one or two plain sentences.

A raw API response with 60 fields and nested metadata wastes context and buries the useful part. Return only the fields a person would look at.

If calling a tool twice sends two emails or two refunds, the agent will eventually do it. Check for an earlier identical action, or use a request ID.
