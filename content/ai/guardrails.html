A developer asks a coding agent to clear the project's temporary folder. The instructions say, in capitals, "BE CAREFUL. ONLY DELETE FILES IN tmp/." The agent builds the path from two pieces, one is empty, and the delete runs on the project folder itself. A week of uncommitted work is gone.

The instruction was clear, but an instruction is a request, and the delete tool accepted any path. A guardrail is a delete tool that refuses any path outside tmp/, no matter who asks.

The idea: limits the model cannot talk its way past

A model can misread, be tricked by a tool result, or follow plausible but wrong reasoning. Better instructions cannot make that chance zero.

So put limits in code, outside the model, where they hold whatever it writes. Four layers, from the outside in:

  1. Permissions. Which tools exist, and what their credentials can reach.
  2. Tool limits. Which paths, amounts and recipients each tool accepts.
  3. Human approval. Which actions wait for a person's yes.
  4. Untrusted input. How far text from tool results may steer later actions.

A guardrail is a check in code that runs before an action, whatever the model says. In the prompt only, it is a suggestion.

Permissions: give the least that works

The safest tool is one the agent does not have. An agent answering order questions needs to read orders, not delete customers. Leave that tool off and make its database account read-only, and even an attack that fully fools the model has nothing to call.

Same for credentials: if the agent's API key can do what your admin account can, every bug is an admin bug. Give it its own scoped key, which also marks its actions in the logs.

Tool limits: check the arguments

Tool Use showed tools that reject bad input. Guardrails use the same place to reject dangerous input:

  • A file tool accepts only paths inside tmp/, after resolving .. and links.
  • A refund tool accepts amounts up to the order's value.
  • An email tool sends only to addresses on the customer's record.
  • A code-running tool runs in a sandbox with no network and no access to your files.

Add rate limits too, say 10 refunds an hour. It will not stop one bad action, but it stops a confused agent repeating it a hundred times.

Human approval for risky actions

Sort every tool by what happens if it is used wrongly:

RiskExamplesDefault
Read onlylook up an order, search docsrun automatically
Small or easy to undoa refund under 50, a draft replyrun, and log it
Costly, external or permanentlarge refunds, sending email, deleting, publishingask a person first
Not needed for this jobdelete a customerno tool at all

A policy gate applies that sorting to every tool request before anything runs:

The gate in code

The gate replaces the direct tool run in the agent loop. askHuman shows a person the request and returns yes or no.

const policy = {
  getOrder: { risk: "read" },
  refundOrder: { risk: "money", autoLimit: 50 },
  sendEmail: { risk: "external" },
};

function checkAction(call) {
  const rule = policy[call.tool];
  if (!rule) return { decision: "block", reason: `${call.tool} is not on the allowed list` };
  if (rule.risk === "read") return { decision: "allow" };
  if (rule.risk === "money" && call.input.amount <= rule.autoLimit) {
    return { decision: "allow" };
  }
  return { decision: "ask" };
}

function guardedRun(call, runTool, askHuman) {
  const { decision, reason } = checkAction(call);
  if (decision === "block") return { error: `Blocked: ${reason}.` };
  if (decision === "ask" && !askHuman(call)) {
    return { error: "A person declined this action. Do not retry it." };
  }
  return runTool(call);
}

policy = {
    "get_order": {"risk": "read"},
    "refund_order": {"risk": "money", "auto_limit": 50},
    "send_email": {"risk": "external"},
}

def check_action(call):
    rule = policy.get(call["tool"])
    if rule is None:
        return {"decision": "block", "reason": f"{call['tool']} is not on the allowed list"}
    if rule["risk"] == "read":
        return {"decision": "allow"}
    if rule["risk"] == "money" and call["input"]["amount"] <= rule["auto_limit"]:
        return {"decision": "allow"}
    return {"decision": "ask"}

def guarded_run(call, run_tool, ask_human):
    check = check_action(call)
    if check["decision"] == "block":
        return {"error": f"Blocked: {check['reason']}."}
    if check["decision"] == "ask" and not ask_human(call):
        return {"error": "A person declined this action. Do not retry it."}
    return run_tool(call)

Two details matter. The policy lists what is allowed, so an unknown tool is blocked until someone decides. And a block or refusal returns as an error the model can read, so it tells the user instead of retrying.

Text from tools is untrusted

The tracer's sendEmail came from text in a customer message, not the user (see Prompt Injection). Once an agent reads text you do not control, such as web pages, emails or documents, treat its next actions as possibly steered by that text's author.

So tighten the gate after untrusted reads: no sending messages or touching private data without approval. The gate keeps apart the dangerous trio of untrusted text, private data and a way to send data out.

Try it yourself

An assistant manages a person's calendar and email with these tools. For each, choose run automatically, run and log, ask first, or remove, with one reason.

 readCalendar createEvent (only on the user's own calendar) sendEmail deleteEmail readWebPage forwardAllEmail (set up automatic forwarding to any address)
  • readCalendar: run automatically. Reading changes nothing.
  • createEvent: run and log. Own calendar only, easy to undo.
  • sendEmail: ask first. It reaches others and cannot be unsent. Show the recipients and full text.
  • deleteEmail: ask first, or make it reversible by moving mail to a trash folder that empties after 30 days.
  • readWebPage: run automatically, then treat the session as untrusted and require approval for any send.
  • forwardAllEmail: remove. No everyday task needs it, and it is what an attacker wants: a silent, permanent copy of everything.

Decide by what a wrong call would cost, not by how often the tool is useful.

Common mistakes

"Never delete files outside tmp/" in the instructions makes mistakes rarer, not impossible, and an injected instruction can argue against it. Enforce the rule in the tool.

A person approving every lookup stops reading by the tenth and approves the dangerous one too. Ask only for risky actions, show exact details (recipient, amount, file list), and default to "no".

Allowing sendEmail without checking the recipient allows email to anyone. Most real limits are on arguments.
