A prompt has worked for weeks. Then someone forwards a bad reply. You add a line, "Be careful with this kind of request", try the bad case again, and it looks fine. A week later, three different cases that used to work are broken, and nobody knows which edit did it.

That is debugging by feel. Prompts deserve the same habits as code: reproduce the problem, test against a fixed set of cases, change one thing at a time, and check you did not break anything else.

The loop

  1. Collect cases. Gather 5 to 20 real inputs: the ones that failed, plus a spread of ones that already work. Write down the right answer for each.
  2. Run them all and record which pass.
  3. Read the failures next to the prompt, and guess why. Name one cause.
  4. Change one thing that targets that cause.
  5. Rerun every case, not just the one you were fixing. Keep the change only if the total got better and no important case broke.

Step 5 is the one people skip. A prompt is a single piece of text that affects every input, so a fix for one case can quietly change many others.

Never judge a prompt change on one example. Keep a small set of test cases with known answers and rerun all of them after every change.

Finding the cause

Most prompt bugs come from a short list of causes. Match the symptom first.

SymptomLikely causeTry
Generic or off-target answerMissing contextSay who it is for and why (Prompting Basics)
Different readings of one wordUndefined termDefine it, with a reason (Be Clear and Specific)
Right content, wrong formatFormat described, not shownAdd an example or template (Show Examples)
Wrong answer to a multi-step problemNo room for workingWorking before answer (Give the Model Room to Think)
Ignores one rule, sometimesRules that conflict, or the rule is buriedSay which rule wins; move it up
Confident made-up detailsFacts not provided, no fallbackProvide the facts; say what to write when unsure

A useful trick when you cannot see the cause: ask the model. Add "Before the label, explain in one sentence which words in the ticket decided it." The explanation is not a reliable account of how the model really reached its label, but it often shows which part of your prompt or input it latched onto.

A tiny test runner

Once you have more than a few cases, run them with code. The runner below takes your cases and any function that returns a label. In real use that function sends the prompt and the ticket to a model; here a stand-in returns fixed answers so you can run it as is.

function runTests(cases, getLabel) {
  const failures = [];
  for (const c of cases) {
    const got = getLabel(c.ticket);
    if (got !== c.expected) failures.push(`${c.ticket}: expected ${c.expected}, got ${got}`);
  }
  console.log(`passed ${cases.length - failures.length} / ${cases.length}`);
  for (const f of failures) console.log("  " + f);
}

const cases = [
  { ticket: "Calm: no one can pay", expected: "urgent" },
  { ticket: "FURIOUS about typo", expected: "low" },
  { ticket: "Reports page slow", expected: "normal" },
];
// Stand-in for a real model call, behaving like prompt v1:
const v1 = { "Calm: no one can pay": "normal", "FURIOUS about typo": "urgent", "Reports page slow": "normal" };
runTests(cases, (ticket) => v1[ticket]); // passed 1 / 3

def run_tests(cases, get_label):
    failures = []
    for c in cases:
        got = get_label(c["ticket"])
        if got != c["expected"]:
            failures.append(f'{c["ticket"]}: expected {c["expected"]}, got {got}')
    print(f"passed {len(cases) - len(failures)} / {len(cases)}")
    for f in failures:
        print("  " + f)

cases = [
    {"ticket": "Calm: no one can pay", "expected": "urgent"},
    {"ticket": "FURIOUS about typo", "expected": "low"},
    {"ticket": "Reports page slow", "expected": "normal"},
]
# Stand-in for a real model call, behaving like prompt v1:
v1 = {"Calm: no one can pay": "normal", "FURIOUS about typo": "urgent", "Reports page slow": "normal"}
run_tests(cases, lambda ticket: v1[ticket])  # passed 1 / 3

Model replies vary from run to run, as Sampling and Temperature explains. So run each case a few times. A case that passes 2 times out of 3 is a real problem, even though a single run might have hidden it. Growing this runner into a proper test suite is the subject of Evals.

 Translate the following app text into Spanish. Bloom keeps your notes in sync across devices.

Cause: the prompt never says that some words are names, so "Bloom" looks like an ordinary English word to translate.

Translate the app text below into Spanish for users in Spain. Use the informal "tú". Do not translate names of products, features or buttons. Keep these exactly as written: Bloom, Sync Hub, Quick Note. Users search for them in our help pages by their English names, so a translated name sends them nowhere. Reply with the translation only. Bloom keeps your notes in sync across devices.

Why it works: it fixes the cause (names were not marked as names) with a general rule plus a list, and the reason lets the model treat other feature names the same way. After the change, rerun your other translation test cases too, to check the new rule did not stop ordinary words from being translated.

Common mistakes

If you add an example, reword the task and move a rule in one edit, and the results improve, you do not know which change helped. Worse, one of them may have hurt, masked by the others.

A rule per failing input ("if it mentions payroll…") makes the prompt longer and more fragile without making it better at new inputs. Ask what the failures have in common, and fix that.

Before concluding that a model "can't do this", reread the prompt as a stranger would. Many failures come from something missing or ambiguous in the prompt. Swapping models is a fair test only after the prompt is clear.
