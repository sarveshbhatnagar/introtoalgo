A prompt has worked for weeks. Then someone forwards a bad reply. You add "Be careful with this kind of request", retry the bad case, and it looks fine. A week later, three cases that used to work are broken, and nobody knows which edit did it.

That is debugging by feel. Debug prompts like code instead.

The loop

  1. Collect cases. Gather 5 to 20 real inputs: the failures plus a spread that already work. Write down the right answer for each.
  2. Run them all and record which pass.
  3. Read the failures next to the prompt and name one likely cause.
  4. Change one thing that targets that cause.
  5. Rerun every case. Keep the change only if the total improved and no important case broke.

Step 5 is the one people skip. One prompt affects every input, so a fix for one case can quietly break others. Never judge a change on one example.

A debugging session

A support team's prompt labels tickets urgent, normal or low. They collected six tickets with the right label for each, then tried three prompt versions.

The fix was not "If the ticket mentions payroll, label it urgent." That passes the test but fails the next ticket, which will mention invoices. Fix the cause, not the case.

Finding the cause

Most prompt bugs come from a short list of causes.

SymptomLikely causeTry
Generic or off-target answerMissing contextSay who it is for and why (Prompting Basics)
Different readings of one wordUndefined termDefine it, with a reason (Be Clear and Specific)
Right content, wrong formatFormat described, not shownAdd an example or template (Show Examples)
Wrong answer to a multi-step problemNo room for workingWorking before answer (Give the Model Room to Think)
Ignores one rule, sometimesRules that conflict, or the rule is buriedSay which rule wins; move it up
Confident made-up detailsFacts not provided, no fallbackProvide the facts; say what to write when unsure

Can't see the cause? Ask: "Before the label, explain in one sentence which words in the ticket decided it." That is not a reliable account of how the model decided, but it often shows what it latched onto.

A tiny test runner

Past a few cases, run them with code. In real use getLabel sends the prompt and ticket to a model; here a stand-in returns fixed answers.

function runTests(cases, getLabel) {
  const failures = [];
  for (const c of cases) {
    const got = getLabel(c.ticket);
    if (got !== c.expected) failures.push(`${c.ticket}: expected ${c.expected}, got ${got}`);
  }
  console.log(`passed ${cases.length - failures.length} / ${cases.length}`);
  for (const f of failures) console.log("  " + f);
}

const cases = [
  { ticket: "Calm: no one can pay", expected: "urgent" },
  { ticket: "FURIOUS about typo", expected: "low" },
  { ticket: "Reports page slow", expected: "normal" },
];
// Stand-in for a real model call, behaving like prompt v1:
const v1 = { "Calm: no one can pay": "normal", "FURIOUS about typo": "urgent", "Reports page slow": "normal" };
runTests(cases, (ticket) => v1[ticket]); // passed 1 / 3

def run_tests(cases, get_label):
    failures = []
    for c in cases:
        got = get_label(c["ticket"])
        if got != c["expected"]:
            failures.append(f'{c["ticket"]}: expected {c["expected"]}, got {got}')
    print(f"passed {len(cases) - len(failures)} / {len(cases)}")
    for f in failures:
        print("  " + f)

cases = [
    {"ticket": "Calm: no one can pay", "expected": "urgent"},
    {"ticket": "FURIOUS about typo", "expected": "low"},
    {"ticket": "Reports page slow", "expected": "normal"},
]
# Stand-in for a real model call, behaving like prompt v1:
v1 = {"Calm: no one can pay": "normal", "FURIOUS about typo": "urgent", "Reports page slow": "normal"}
run_tests(cases, lambda ticket: v1[ticket])  # passed 1 / 3

Replies vary from run to run (Sampling and Temperature), so run each case a few times. A case that passes 2 times out of 3 is a real problem. Evals grows this runner into a proper test suite.

Try it yourself

This prompt translates app text for a Spanish release of a product called Bloom. Some replies translate the name as "Florecer", which confused testers. Name the likely cause in one sentence, then rewrite the prompt to fix the cause, not just this word.

 Translate the following app text into Spanish. Bloom keeps your notes in sync across devices.

Cause: the prompt never says that some words are names, so "Bloom" looks like an ordinary English word to translate.

Translate the app text below into Spanish for users in Spain. Use the informal "tú". Do not translate names of products, features or buttons. Keep these exactly as written: Bloom, Sync Hub, Quick Note. Users search for them in our help pages by their English names, so a translated name sends them nowhere. Reply with the translation only. Bloom keeps your notes in sync across devices.

Why it works: a general rule plus a list fixes the cause, and the reason lets the model treat other feature names the same way. Then rerun your other translation cases to check ordinary words still get translated.

Common mistakes

Add an example, reword the task and move a rule in one edit, and you cannot tell which change helped, or which one hurt.

A rule per failing input ("if it mentions payroll…") makes the prompt longer and more fragile, not better. Fix what the failures share.

Before deciding a model "can't do this", reread the prompt as a stranger would. Swapping models is a fair test only once the prompt is clear.
