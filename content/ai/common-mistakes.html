No single step was reckless. Each was a small shortcut that felt reasonable, and the shortcuts stacked.

Four mistakes worth a closer look

The regenerate loop

Regenerating feels like progress, but with the same prompt you are drawing again from the same spread of likely answers (see Sampling and Temperature). After two tries, stop and say what is wrong.

This draft is too generic. Three changes: 1. Lead with the one number my manager cares about: revenue for the quarter compared with last quarter. I'll give you both figures below. 2. Cut the "market overview" section. My manager knows the market. 3. Each section should end with what we are doing next, in one sentence. Revenue Q2: 412,000. Revenue Q3: 470,000.

Still check the result: (470,000 − 412,000) ÷ 412,000 is 14.1%. Anything else is wrong.

Using AI where a plain tool is better

Adding a column, sorting a list, matching lines, converting dates: a spreadsheet, script or search box does these exactly; a model does them approximately. Have the assistant write the formula or script, then let the tool do the work.

Set and forget

An automation that worked in testing can drift: inputs change, the provider updates the model, new kinds of request appear. Review a sample of real outputs every week, and rerun your test set when anything changes.

All-or-nothing trust

Some people trust everything after a few good answers; others give up after one bad one. Trust should depend on the task: an assistant can be reliable at rewording email and unreliable at quoting case law. Learn where it is strong by checking, and adjust how much you check.

When a result disappoints, reread your request. If a capable stranger could not have done better with the same words, fix the request, not the tool.

For anything others will rely on, such as figures, legal text or production code, say what was AI-assisted and what you checked. It tells reviewers where to look, and is often a rule at work or school.

Correcting Sam's growth figure is not enough. Fix the habit behind it, or it happens again next quarter.

Try it yourself

List every mistake in this story and the habit that would prevent it.

 Jo needed to update a pricing function before a release. She pasted the whole repository's config folder (including the .env file) into a chat and asked "fix the discount bug". The assistant changed 14 files. The tests failed, so she asked it to "make the tests pass", and it edited two test files. Everything was green, so she merged it at 5:55pm on a Friday.
  1. Pasted the .env file. It usually holds secrets. Paste only the code involved, secrets replaced, and rotate any real key that went in.
  2. "Fix the discount bug" with no detail. Write a brief: what is wrong, an example input and expected output, which files to change.
  3. Accepted a 14-file change. Too much to review. Ask for the smallest fix and read the diff.
  4. "Make the tests pass". This invites the model to change the tests, which are the contract.
  5. Green meant done. Changed tests passing proves little. Check what changed in the test files first.
  6. Merged with no time to watch it. AI-assisted changes need the same care as any other: merge when someone can notice and fix problems.
