A customer searches a clothing shop for "warm jacket". The shop's "insulated winter coat" is exactly right, but keyword search misses it because the phrases share no words. It returns a "jacket potato" recipe card instead.

The fix is to compare meanings, not letters. For that, a computer needs meaning as numbers. That is an embedding.

Meaning as a position

An embedding is a list of numbers (a vector) representing a piece of content, chosen so that similar meanings get similar lists. Think of each as a point in space: "insulated winter coat" and "warm jacket" land near each other, "linen shirt" elsewhere, and "jacket potato" far away.

Real embeddings have hundreds or thousands of numbers per item. You cannot picture that, but the arithmetic is the same as in two or three dimensions.

Where the numbers come from

Embeddings come out of a neural network trained on a task that forces similar things to look similar inside it. Two common tasks:

  • Predict the context. Guess a word from the words around it. Words used in similar sentences, like "coat" and "jacket", need similar hidden values to make similar guesses.
  • Match pairs. Show pairs that belong together, like a question and its answer, or a search and the product clicked. Matching pairs should get close vectors, random pairs distant ones.

After training, one of the network's layers is the embedding: feed in any text and read off the numbers.

Measuring closeness

The standard similarity measure is cosine similarity. It compares direction, ignoring length: 1 for the same way, 0 at right angles (unrelated), −1 for opposite. It needs two ingredients:

  • The dot product: multiply matching positions and add. For [4, 1, 1] and [5, 2, 2] it is 4×5 + 1×2 + 1×2 = 24.
  • The length of a vector: Pythagoras in more dimensions. For [4, 1, 1] it is √(16 + 1 + 1) = √18 ≈ 4.24.

cosine(a, b) = dot(a, b) / (length(a) × length(b))

Dividing by the lengths makes it about direction only, so a long and a short document on the same thing still score as similar.

Trace a search

Give each item a hand-made 3-number embedding: how warm, how dressy, how waterproof. The query "warm jacket" becomes [4, 1, 1]. Real dimensions do not have tidy names, but the search works the same way.

function dot(a, b) {
  let total = 0;
  for (let i = 0; i < a.length; i++) total += a[i] * b[i];
  return total;
}

// Cosine similarity: 1 means same direction, 0 means unrelated.
function cosine(a, b) {
  return dot(a, b) / (Math.sqrt(dot(a, a)) * Math.sqrt(dot(b, b)));
}

// Item names with their scores, most similar first.
function search(query, items) {
  return Object.entries(items)
    .map(([name, vec]) => [name, cosine(query, vec)])
    .sort((x, y) => y[1] - x[1]);
}

search([4, 1, 1], {
  "insulated winter coat": [5, 2, 2],
  "wool overcoat": [4, 4, 0],
  "rain shell": [1, 1, 5],
  "linen shirt": [0, 3, 0],
}); // coat 0.985, overcoat 0.833, shell 0.454, shirt 0.236

import math

def dot(a, b):
    return sum(x * y for x, y in zip(a, b))

def cosine(a, b):
    """Cosine similarity: 1 means same direction, 0 means unrelated."""
    return dot(a, b) / (math.sqrt(dot(a, a)) * math.sqrt(dot(b, b)))

def search(query, items):
    """Item names with their scores, most similar first."""
    scored = [(name, cosine(query, vec)) for name, vec in items.items()]
    return sorted(scored, key=lambda pair: pair[1], reverse=True)

search([4, 1, 1], {
    "insulated winter coat": [5, 2, 2],
    "wool overcoat": [4, 4, 0],
    "rain shell": [1, 1, 5],
    "linen shirt": [0, 3, 0],
})  # coat 0.985, overcoat 0.833, shell 0.454, shirt 0.236

An embedding turns meaning into a position, so "find similar things" becomes "find nearby points", which is just arithmetic.

What embeddings are used for

  • Search by meaning. Embed every document once; at query time, embed the query and return the nearest documents.
  • Recommendations. "You might also like" becomes "items near this one".
  • Duplicates. Near-identical tickets or listings sit almost on top of each other.
  • Feeding language models. Language models turn every token into an embedding first. Retrieval systems use embedding search to find passages for a model to read before answering (RAG Basics).

Common mistakes

Each model builds its own space; position 17 in one means nothing in another. If you switch models, re-embed everything.

"Refunds are accepted within 30 days" and "Refunds are not accepted" share a topic, so their embeddings are close. Similarity finds related text, not agreeing or true text. Read what you retrieve.

The raw dot product grows with vector length, so long or repetitive items can outscore better matches. Use cosine, or scale every vector to length 1 first, after which the dot product equals the cosine.

Try it yourself

A query is [1, 2], document A is [2, 4] and document B is [3, 1]. Compute the query's dot product and cosine with each. Which is the better match, and why do the measures disagree on how strong it is?
  • A: dot = 1×2 + 2×4 = 10. Lengths are √5 and √20, so cosine = 10 / √100 = 10 / 10 = 1.0.
  • B: dot = 1×3 + 2×1 = 5. Lengths are √5 and √10, so cosine = 5 / √50 ≈ 0.71.

A points in exactly the query's direction, just twice as far, so cosine gives a perfect 1.0. The dot product also ranks A first, but its values (10 and 5) depend on length, so they cannot show that A's direction is a perfect match. Cosine's scale is fixed from −1 to 1, whatever the lengths.
