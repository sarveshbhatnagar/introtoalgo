A team builds a feature that sorts incoming support tickets into five categories. They pick the most capable model their provider offers, because it is "the best". It works well, until the first monthly bill arrives and users complain that the form hangs for five seconds after Send.

A smaller model labels fifty old tickets almost as well, in about a second, at a fraction of the cost. Meanwhile the team next door used a small, fast model to review contracts and kept missing unusual clauses. Both chose a model before they knew what the task needed.

There is no best model, only a best fit

Bigger models follow long instructions better, handle subtle cases and reason through harder problems, but are slower and cost more per token. Smaller models are fast, cheap and often good enough for narrow, well-defined tasks.

FactorWhat it meansMatters most when
QualityHow often the output is right for your taskMistakes are costly or hard to spot
SpeedHow long until the reply starts and finishesA person is waiting, as in chat or autocomplete

Some models also offer a mode where they "think" longer before answering (see Give the Model Room to Think). That trades more time and tokens for better answers on hard problems. On easy tasks it often adds cost and nothing else.

Cost multiplies. Five times more per request barely matters at ten requests a day. On 30,000 tickets a month, the same factor of five turns a rounding error into a budget line someone will ask about.

First decide what "good enough" means for your task, in numbers. Then choose the cheapest, fastest model that meets it on your own examples.

Let your own tests decide

Public rankings measure models on someone else's tasks. The reliable way to choose is a small test set of your own real examples with known right answers: run each candidate on it and compare. Fifty labelled examples is a reasonable start for a simple task (see Evals).

The ticket team's bar: at least 90% labelled correctly, and a reply in at most 2 seconds.

// Results from running each candidate on your own 50 test tickets.
const candidates = [
  { name: "large", accuracy: 0.96, seconds: 4.8, cost: 20 },
  { name: "small", accuracy: 0.84, seconds: 0.6, cost: 1 },
  { name: "medium", accuracy: 0.92, seconds: 1.4, cost: 4 },
];

function chooseModel(candidates, minAccuracy, maxSeconds) {
  const byCost = [...candidates].sort((a, b) => a.cost - b.cost);
  for (const model of byCost) {
    if (model.accuracy >= minAccuracy && model.seconds <= maxSeconds) {
      return model.name; // cheapest one that clears every bar
    }
  }
  return null; // nothing is good enough: rethink the task or the bar
}

chooseModel(candidates, 0.9, 2); // "medium"

# Results from running each candidate on your own 50 test tickets.
candidates = [
    {"name": "large", "accuracy": 0.96, "seconds": 4.8, "cost": 20},
    {"name": "small", "accuracy": 0.84, "seconds": 0.6, "cost": 1},
    {"name": "medium", "accuracy": 0.92, "seconds": 1.4, "cost": 4},
]

def choose_model(candidates, min_accuracy, max_seconds):
    for model in sorted(candidates, key=lambda m: m["cost"]):
        if model["accuracy"] >= min_accuracy and model["seconds"] <= max_seconds:
            return model["name"]  # cheapest one that clears every bar
    return None  # nothing is good enough: rethink the task or the bar

choose_model(candidates, 0.9, 2)  # "medium"

The names are placeholders, and cost is in relative units: "small" costs 1 per ticket, "large" 20.

If nothing passes, do not just lower the bar. Make the task easier: clearer instructions, a few examples in the prompt, or one hard request split into two simple ones. A better prompt often moves a cheaper model over the line.

If you are not sure a task is possible, try the most capable model first. If even it fails, the problem is the task or the prompt. Once it works, try cheaper models on the same tests.

Mixing models

You need not use one model for everything. With routing, a small model handles the easy, high-volume cases and passes anything it is unsure of to a bigger one. Or a capable model plans and a cheaper one does the simple steps. Each split adds moving parts, so split only when cost or speed demands it.

Providers update and retire models. Keep your test set and rerun it whenever a model changes. Teams with tests can swap models in an afternoon; teams without are left guessing whether things got worse.

Try it yourself

For each feature, say which two factors matter most, what kind of model you would try first, and why.

  1. Suggested replies that appear while a user types in a chat app.
  2. A nightly job that summarises 2,000 long legal documents for a law firm's archive.
  3. A tool at a hospital that drafts discharge notes from patient records.
  1. Speed and cost. The user is waiting, and it runs every few keystrokes for every user. A slightly worse suggestion costs little: the user ignores it. Try a small, fast model first.
  2. Context size and quality. Documents are long, nobody is waiting, and errors in a legal archive are costly. Try a capable model that can take a whole document at once, or a cheaper one with a good chunking plan (see Chunking and Retrieval), and compare on a sample with known good summaries.
  3. Privacy and quality. Patient data may have to stay inside the hospital's systems, which can rule out hosted options before any testing. Quality matters a great deal, and every draft needs a clinician's review. Start from what the hospital may use, then test within that.

"Which model is smartest" was never the first question. The task decided the factors, and the factors narrowed the choice.

Common mistakes

Public rankings say little about your task. Test on fifty of your own examples before you commit, and again before you switch.

Three good replies prove almost nothing. Models differ on the harder cases, which only a real test set shows.

The best model is useless if your data may not go there. Check where it runs and what happens to inputs before testing it. Privacy and Security lists the questions to ask.
