You are going away for a week and a neighbour will feed your cat. You could hand them a shoebox with every vet bill, the cat food receipts and the manual for the automatic feeder you stopped using last year. Everything they need is in there somewhere. Or you could write one page: how much food and when, the pill on Tuesdays, the vet's number, and "she hides under the bed when the doorbell rings, that's normal."

The one-page note works better, even though it contains less. Building the context for a model is the same job.

From wording to the whole screen

Prompting is about how you phrase a request. Context engineering is about everything the model reads on a call: which information goes in, in what form, in what order, and what stays out. In a chat you do it by hand when you paste in the right paragraph. In an app, code does it on every request.

You already have the two facts that make this matter. The model only knows what is in its context, and the window is limited and works best when it is focused. So the question on every call is: what is the smallest set of information that lets the model do this task well?

Good context is relevant, current, consistent and clearly labelled. Adding text has a cost; every piece should earn its place.

Four moves

Most ways to improve context come down to four moves.

  1. Select. Include only what this task needs. Leave out the shipping rates when the question is about returns.
  2. Compress. Send the relevant section instead of the whole manual. Replace a long thread with a short summary of what was decided. Strip boilerplate like headers, footers and legal text that repeats on every page.
  3. Order and label. Put instructions where they cannot be missed. Wrap each piece of material in a clear label saying what it is and where it came from. For long material, restate the question after it, so it is near the end where the model reads it last.
  4. Isolate. Split a big job into smaller calls, each with its own focused context. A call that summarizes ten reports one by one, then a call that compares the ten summaries, often beats one call with all ten reports at once.

Just as important is what to keep out: outdated versions of a document, two sources that disagree, material that is only loosely related, secrets the model does not need, and text from untrusted sources that might contain instructions (see Prompt Injection).

Packing a context, step by step

A customer asks a shop's assistant: "Can I return headphones I've already opened?" The app has six candidate pieces of context. Each has a relevance score (in a real system this comes from retrieval, from fixed rules, or from a quick check by another model) and a size in tokens. The budget for this material is 250 tokens.

The method: throw out anything stale first, then take the most relevant pieces that still fit, and skip anything below a minimum relevance of 0.3.

Unlike trimming chat history, skipping a piece and carrying on is fine here: the pieces are independent.

function selectContext(pieces, budget, minScore = 0.3) {
  const candidates = pieces
    .filter((p) => !p.stale)
    .sort((a, b) => b.score - a.score);
  const chosen = [];
  let used = 0;
  for (const p of candidates) {
    if (p.score < minScore) continue;           // not relevant enough
    if (used + p.tokens > budget) continue;     // does not fit
    chosen.push(p.name);
    used += p.tokens;
  }
  return { chosen, used };
}

selectContext([
  { name: "policy", score: 0.9, tokens: 120 },
  { name: "product", score: 0.6, tokens: 80 },
  { name: "order", score: 0.8, tokens: 40 },
  { name: "FAQ", score: 0.4, tokens: 300 },
  { name: "old policy", score: 0.7, tokens: 120, stale: true },
  { name: "shipping", score: 0.2, tokens: 60 },
], 250); // { chosen: ["policy", "order", "product"], used: 240 }

def select_context(pieces, budget, min_score=0.3):
    candidates = sorted(
        (p for p in pieces if not p.get("stale")),
        key=lambda p: p["score"],
        reverse=True,
    )
    chosen, used = [], 0
    for p in candidates:
        if p["score"] < min_score:          # not relevant enough
            continue
        if used + p["tokens"] > budget:     # does not fit
            continue
        chosen.append(p["name"])
        used += p["tokens"]
    return chosen, used

select_context([
    {"name": "policy", "score": 0.9, "tokens": 120},
    {"name": "product", "score": 0.6, "tokens": 80},
    {"name": "order", "score": 0.8, "tokens": 40},
    {"name": "FAQ", "score": 0.4, "tokens": 300},
    {"name": "old policy", "score": 0.7, "tokens": 120, "stale": True},
    {"name": "shipping", "score": 0.2, "tokens": 60},
], 250)  # (['policy', 'order', 'product'], 240)

Sorting dominates the cost: O(n log n) for n pieces, tiny next to the model call. The hard part is getting good scores and honest "stale" flags.

What the model receives

Here is the difference between dumping material and engineering it, on the same question.

Can I return headphones I've already opened? [full FAQ page] [returns policy 2019] [returns policy current] [shipping rates] [product page] [order record] Yes, you can return opened items within 30 days of delivery as long as they are in their original packaging. Please note that some items may be subject to a restocking fee. You answer returns questions for an electronics shop. Use only the material provided. If it does not answer the question, say so and offer to connect the customer with staff. Unopened items: 30 days. Opened items: 14 days, except in-ear headphones, which cannot be returned once the seal is broken, for hygiene reasons. Faulty items are always covered by the warranty. Bought 6 days ago: Model T2 headphones. Model T2: over-ear wireless headphones. Customer question: Can I return headphones I've already opened? Yes. Your T2 headphones are over-ear, so the in-ear exception does not apply. Opened items can be returned within 14 days, and you bought them 6 days ago, so you have 8 days left.

The first reply mixed the two policies and missed the in-ear rule. In the second, every fact it needed was there, labelled, and nothing contradicted it.

Common mistakes

Extra material costs tokens, slows the call, and gives the model more ways to latch onto the wrong detail. Include what the task needs; if you are unsure, test with and without.

Two versions of a policy, an old and a new price list, a draft and a final spec. The model has no reliable way to know which wins. Remove the stale one, or label clearly which is current and say so in the instructions.

An instruction in the middle of a long pasted document can read as part of the document. Put instructions first, material in labelled blocks, and repeat the actual question at the end.

Try it yourself

You ask a coding assistant to fix a failing test for a shopping-cart total. You could give it any of these: the whole repository (about 2,000 files), the failing test file, the function being tested, the test's error output, the team's style guide, last week's chat about a different feature, and the project README. Which do you include, which do you leave out, and why?

Include:

  • The error output. It says what actually went wrong, often the single most useful piece.
  • The failing test. It defines what "correct" means.
  • The function under test, plus anything it calls that might be involved, such as a discount helper.

Maybe: the relevant part of the style guide, if the fix will be reviewed against it. A few lines, not the whole document.

Leave out: the whole repository (mostly irrelevant, and it buries the three files that matter), last week's chat (a different feature, and it may describe code that has since changed), and the README (general, rarely needed for a local fix).

Coding tools that search the repository themselves do this same selection automatically, which is why pointing them at the error and the files first helps.
