A neighbour will feed your cat for a week. You could hand them a shoebox of vet bills, food receipts and the manual for a feeder you stopped using last year. Or one page: how much food and when, the pill on Tuesdays, the vet's number, and "she hides under the bed when the doorbell rings, that's normal." The page works better, though it contains less. Building a model's context is the same job.

From wording to the whole screen

Prompting is how you phrase a request. Context engineering covers everything the model reads: what goes in, in what form and order, and what stays out. In an app, code does it on every request.

The model only knows its context, and the window is limited and works best focused. So on every call, ask: what is the smallest set of information that lets the model do this task well?

Good context is relevant, current, consistent and clearly labelled. Every piece should earn its place.

Four moves

  1. Select. Include only what this task needs. Leave out shipping rates when the question is about returns.
  2. Compress. Send the relevant section, not the manual. Summarize long threads into decisions. Strip repeated headers, footers and legal text.
  3. Order and label. Put instructions where they cannot be missed. Label each piece with what it is and its source. After long material, restate the question.
  4. Isolate. Split a big job into focused calls: summarize each report alone, then compare the summaries.

Equally, keep out outdated versions, sources that disagree, loosely related material, unneeded secrets, and untrusted text that might contain instructions (Prompt Injection).

Packing a context, step by step

A customer asks a shop's assistant: "Can I return headphones I've already opened?" The app has six candidate pieces, each with a size in tokens and a relevance score (from retrieval, fixed rules, or a quick check by another model). The budget is 250 tokens.

The method: drop anything stale, then take the most relevant pieces that fit, skipping anything below 0.3 relevance.

Unlike trimming chat history, skipping a piece and carrying on is fine here: the pieces are independent.

function selectContext(pieces, budget, minScore = 0.3) {
  const candidates = pieces
    .filter((p) => !p.stale)
    .sort((a, b) => b.score - a.score);
  const chosen = [];
  let used = 0;
  for (const p of candidates) {
    if (p.score < minScore) continue;           // not relevant enough
    if (used + p.tokens > budget) continue;     // does not fit
    chosen.push(p.name);
    used += p.tokens;
  }
  return { chosen, used };
}

selectContext([
  { name: "policy", score: 0.9, tokens: 120 },
  { name: "product", score: 0.6, tokens: 80 },
  { name: "order", score: 0.8, tokens: 40 },
  { name: "FAQ", score: 0.4, tokens: 300 },
  { name: "old policy", score: 0.7, tokens: 120, stale: true },
  { name: "shipping", score: 0.2, tokens: 60 },
], 250); // { chosen: ["policy", "order", "product"], used: 240 }

def select_context(pieces, budget, min_score=0.3):
    candidates = sorted(
        (p for p in pieces if not p.get("stale")),
        key=lambda p: p["score"],
        reverse=True,
    )
    chosen, used = [], 0
    for p in candidates:
        if p["score"] < min_score:          # not relevant enough
            continue
        if used + p["tokens"] > budget:     # does not fit
            continue
        chosen.append(p["name"])
        used += p["tokens"]
    return chosen, used

select_context([
    {"name": "policy", "score": 0.9, "tokens": 120},
    {"name": "product", "score": 0.6, "tokens": 80},
    {"name": "order", "score": 0.8, "tokens": 40},
    {"name": "FAQ", "score": 0.4, "tokens": 300},
    {"name": "old policy", "score": 0.7, "tokens": 120, "stale": True},
    {"name": "shipping", "score": 0.2, "tokens": 60},
], 250)  # (['policy', 'order', 'product'], 240)

Sorting costs O(n log n) for n pieces, tiny next to the model call. The hard part is good scores and honest "stale" flags.

What the model receives

Can I return headphones I've already opened? [full FAQ page] [returns policy 2019] [returns policy current] [shipping rates] [product page] [order record] Yes, you can return opened items within 30 days of delivery as long as they are in their original packaging. Please note that some items may be subject to a restocking fee. You answer returns questions for an electronics shop. Use only the material provided. If it does not answer the question, say so and offer to connect the customer with staff. Unopened items: 30 days. Opened items: 14 days, except in-ear headphones, which cannot be returned once the seal is broken, for hygiene reasons. Faulty items are always covered by the warranty. Bought 6 days ago: Model T2 headphones. Model T2: over-ear wireless headphones. Customer question: Can I return headphones I've already opened? Yes. Your T2 headphones are over-ear, so the in-ear exception does not apply. Opened items can be returned within 14 days, and you bought them 6 days ago, so you have 8 days left.

The first reply mixed the two policies and missed the in-ear rule. The second had every needed fact, labelled, with nothing contradicting it.

Common mistakes

Extra material costs tokens, slows the call, and offers more wrong details to latch onto. If unsure, test with and without.

Two policy versions, old and new price lists, draft and final specs: the model cannot reliably tell which wins. Remove the stale one, or label which is current.

An instruction in the middle of a pasted document can read as part of it. Put instructions first, material in labelled blocks, and repeat the question at the end.

Try it yourself

A coding assistant must fix a failing test for a shopping-cart total. You could give it: the whole repository (about 2,000 files), the failing test file, the function being tested, the test's error output, the team's style guide, last week's chat about a different feature, and the README. What do you include or leave out, and why?

Include:

  • The error output: what actually went wrong, often the most useful piece.
  • The failing test: it defines "correct".
  • The function under test, plus anything involved that it calls, such as a discount helper.

Maybe: a few relevant lines of the style guide, if the fix will be reviewed against it.

Leave out: the whole repository (it buries the three files that matter), last week's chat (a different feature, possibly outdated code), and the README (rarely needed for a local fix).

Coding tools that search the repository make this selection themselves, so pointing them at the error and files first helps.
