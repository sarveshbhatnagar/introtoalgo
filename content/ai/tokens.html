Ask an AI assistant how many times "r" appears in a long, unusual word, and it may get it wrong while explaining in perfect English. The model is not careless about letters. It mostly never sees them.

In What Is an LLM, a model predicts the next piece of text again and again. Those pieces are tokens, not letters. They explain why limits and prices are counted in tokens, why some languages cost more, and why counting letters is hard for a system that writes so well.

Text becomes a list of numbers

A model works only with numbers. A tokenizer cuts the text into pieces from a fixed list, the vocabulary, and replaces each piece with its position in that list. The model sees only these token IDs.

Common short words like "tired" are one token. A long or rare word is split into chunks. The space usually belongs to the token after it (shown as ␣), so " tired" and "tired" have different IDs.

Single letters would make every sentence dozens of tokens long. Whole words would need a vocabulary of every word, name, typo and number ever written. Pieces in between keep frequent text short, and anything can still be spelled from smaller pieces.

Where the pieces come from

A common method, byte-pair encoding, learns the vocabulary from a sample of text:

  1. Start with every word split into single characters.
  2. Count every pair of neighbouring pieces across all the text.
  3. Glue the most frequent pair into one new piece, and add it to the vocabulary.
  4. Repeat until the vocabulary is as big as you want.

Here it is on six words: tea, tea, team, teams, steam, seat.

Real tokenizers run this on billions of words, usually on raw bytes rather than letters so any script works, and stop after tens of thousands of merges or more. New text is tokenized by applying the learned merges in the same order.

The code

function learnMerges(words, numMerges) {
  let pieces = words.map((w) => w.split("")); // start from single letters
  const merges = [];
  for (let m = 0; m < numMerges; m++) {
    const counts = new Map(); // count every pair of neighbouring pieces
    for (const word of pieces) {
      for (let i = 0; i + 1 < word.length; i++) {
        const pair = word[i] + "|" + word[i + 1];
        counts.set(pair, (counts.get(pair) || 0) + 1);
      }
    }
    let best = null; // most frequent pair; the first one seen wins a tie
    for (const [pair, c] of counts) if (best === null || c > counts.get(best)) best = pair;
    if (best === null) break; // every word is already one piece
    const [a, b] = best.split("|");
    merges.push(a + b);
    pieces = pieces.map((word) => {
      const out = [];
      for (let i = 0; i < word.length; i++) {
        if (word[i] === a && word[i + 1] === b) { out.push(a + b); i++; }
        else out.push(word[i]);
      }
      return out;
    });
  }
  return { merges, pieces };
}

learnMerges(["tea", "tea", "team", "teams", "steam", "seat"], 3).merges;
// ["ea", "tea", "team"]

def learn_merges(words, num_merges):
    pieces = [list(w) for w in words]  # start from single letters
    merges = []
    for _ in range(num_merges):
        counts = {}  # count every pair of neighbouring pieces
        for word in pieces:
            for a, b in zip(word, word[1:]):
                counts[(a, b)] = counts.get((a, b), 0) + 1
        if not counts:
            break  # every word is already one piece
        best = max(counts, key=counts.get)  # the first one seen wins a tie
        merges.append(best[0] + best[1])
        new_pieces = []
        for word in pieces:
            out, i = [], 0
            while i < len(word):
                if i + 1 < len(word) and (word[i], word[i + 1]) == best:
                    out.append(word[i] + word[i + 1])
                    i += 2
                else:
                    out.append(word[i])
                    i += 1
            new_pieces.append(out)
        pieces = new_pieces
    return merges, pieces

learn_merges(["tea", "tea", "team", "teams", "steam", "seat"], 3)[0]
# ['ea', 'tea', 'team']

Each merge scans all the text once, so k merges over n characters is O(k · n) here. Production tokenizers use smarter bookkeeping for the same kind of vocabulary.

Why tokens matter to you

  • Limits and prices are in tokens. How much a model can read at once, and what a request costs, are counted in tokens. English prose takes somewhat more tokens than words; the exact ratio depends on the tokenizer.
  • Not all text is equal. Text common in the tokenizer's sample, like English and popular programming languages, packs into few tokens. Rarer languages, unusual names, long numbers and IDs break into many small pieces, so the same message can cost several times more in one language than another.
  • Letters are hidden. The model receives the ID for "␣tired", not t-i-r-e-d. It can often spell, having seen many spellings, but counting or reversing letters asks it to recover something it was never directly shown. Numbers suffer too: "2847" might be one token, "284" + "7", or four digits. When chunks do not match place value, the model cannot line up units with units, which is part of why long arithmetic is unreliable without a calculator.

A model reads and writes tokens: chunks of text mapped to numbers. Anything that depends on individual characters is harder for it than its fluent text suggests.

Common mistakes

A limit that fits 50 pages of English prose may fit far fewer of code, tables, another language or numbers. When it matters, count tokens with your model's tokenizer.

"How many letters", "reverse this string", "check every digit": the model may get these wrong while sounding certain. Ask it to write the characters out one by one first, or better, to write code that counts.

Different models use different vocabularies, so the same text gets different splits and counts. Never reuse one model's count for another.
