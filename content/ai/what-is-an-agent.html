Last night's backup failed, and you ask an AI assistant why. A plain chat model can only guess: "Backups often fail because of full disks, expired credentials or network problems." True, and no help.

A colleague with server access would read the log, see the disk is full, then check what fills it. Each step depends on what the last one showed, so nobody could script them in advance.

An agent is a model set up to work like that colleague: look, decide, act, look again, until the job is done.

The idea: a model with tools, in a loop

In Tools and MCP, a model asks the app to run a tool and reads the result. An agent puts the model in charge of the next step. Four parts:

  • A goal. What you want, ideally with a finish line: "Find out why the backup failed. Do not delete anything."
  • Tools. Actions it can request: read a log, check disk usage, list a folder.
  • A loop. The app calls the model, runs the tool it asks for, adds the result to the context, and repeats.
  • A stop. The model gives a final answer, or the app's limits end it (too many steps, too much time).

An agent is a model calling tools in a loop, choosing each next step from the last result. In ordinary software you write the steps; here the model picks them at run time.

The app did nothing clever: it ran the loop and the tools and kept the history. The judgement ("disk full, so check the disk") came from the model. The Agent Loop turns this pseudocode into real code.

Who decides the next step

"Agent" gets used for almost anything with AI. A more useful sort is by who decides the next step.

  • Single call. One prompt, one answer. "Rewrite this paragraph more simply."
  • Workflow. Several model calls in an order your code fixes. "Summarize each support ticket, classify it, draft a reply." The model never chooses what comes next.
  • Agent. The model chooses the next step and when to stop, within your goal, tools and limits.

Workflows are underrated: every path is known in advance, so they are cheaper, faster and easier to test.

When not to use an agent

Freedom has a price. Each step is another model call, so agents are slower and cost more, and they can take a different path each run, so they are harder to test.

Errors also compound. If each step is right 95% of the time and one wrong step spoils the run, a ten-step run is fully right only about 60% of the time: 0.9510 ≈ 0.60. Agents sometimes fix a bad result, so reality can be better, but more steps still means more chances to go wrong.

Use the simplest thing that works:

  1. If one good prompt does it, use a single call.
  2. If you can write the steps down in advance, write a workflow.
  3. Use an agent only when the steps depend on what you find, and a wrong turn can be noticed and undone. Debugging and research fit; a weekly report does not.

Coding assistants that edit and run tests until they pass are agents, as are research tools that search, read and search again. A person checks the final work.

Try it yourself

Pick the simplest approach for each task: single call, workflow or agent. Give one line of reasoning each.

  1. Translate a product description into Spanish.
  2. Every morning, tag new customer reviews by topic and post a count per topic to the team chat.
  3. Find out why the checkout page got slower this week, using logs, code changes and metrics.
  4. Turn a meeting transcript into a list of action items with owners.
  1. Single call. One input, one output, no lookups.
  2. Workflow. Same steps every day: fetch, tag, count, post. Code runs them; the model only tags.
  3. Agent. The answer could be in logs, a code change or metrics. Each finding decides where to look next.
  4. Single call. It looks big, but the transcript fits in one prompt and needs no tools.

An agent earns its cost only when the path is unknown until you start walking it.

Common mistakes

If you can draw the steps as a flowchart in advance, write them as code. A model rediscovering them every run is slower, costlier, and sometimes skips one.

"Improve our test coverage" never ends. "Add tests for parseDate until every branch is covered, then stop" does. Without a done condition, the agent stops too early or runs until a limit cuts it off.

An agent's last message says what it thinks it did, and can claim a test passes that it never ran. Check the real outcome: the file, the test result, the database record. Evals make that checking systematic.
