Last night's backup failed, and you ask an AI assistant why. A plain chat model can only guess: "Backups often fail because of full disks, expired credentials or network problems." All true, and no help to you.

Now picture a colleague with access to the server. They open the backup log and see "no space left on device". So they check how full the disk is. It is 98% full, so they look at what is taking the space, and find an old snapshot folder nobody uses. Each step depended on what the previous step showed. Nobody could have written those steps down in advance.

An agent is a model set up to work like that colleague: it looks, decides what to do next, does it, and looks again, until the job is done.

The idea: a model with tools, in a loop

You already know from Tools and MCP that a model can ask the app to run a tool and read the result. An agent is that same mechanism with the model in charge of the next step. It has four parts:

  • A goal. What you want, and ideally how to tell when it is done: "Find out why the backup failed. Do not delete anything."
  • Tools. The actions it can request: read a log, check disk usage, list a folder.
  • A loop. The app calls the model, runs whatever tool it asks for, adds the result to the context, and calls the model again.
  • A stop. The loop ends when the model gives a final answer, or when the app's limits say so (too many steps, too much time).

The important word is decides. In ordinary software, you write the sequence of steps. In an agent, the model picks each step at run time, based on what it has seen so far.

An agent is a model calling tools in a loop, choosing each next step from the results of the last one. Everything else in this module is about making that loop useful and safe.

Who decides the next step

"Agent" gets used for almost anything with AI in it. A more useful way to sort systems is to ask one question: who decides the next step?

  • Single call. One prompt, one answer. "Rewrite this paragraph more simply."
  • Workflow. Several model calls, but your code fixes the order. "Summarize each support ticket, then classify it, then draft a reply." The model does each step; it never chooses what comes next.
  • Agent. The model chooses the next step and when to stop. You set the goal, the tools and the limits.

Workflows are underrated. They are cheaper, faster, easier to test and easier to debug, because you know every path in advance. Most useful AI features are single calls or workflows.

When not to use an agent

Freedom has a price. Each extra step is another model call, so agents are slower and cost more. They can take a different path on each run, which makes them harder to test. And errors compound: if each step is right 95% of the time, a ten-step run is fully right only about 60% of the time (0.9510 ≈ 0.60).

So use the simplest thing that works:

  1. If one good prompt does it, use a single call.
  2. If you can write the steps down in advance, write a workflow.
  3. Reach for an agent only when the steps depend on what you find along the way, and when a wrong turn can be noticed and undone.

Debugging, research across many sources, and working through an unfamiliar codebase fit that last description. Sending the same weekly report does not.

Coding assistants that read files, run tests and edit code until the tests pass are agents. So are research tools that search, read and search again. Both have the same shape: the next step depends on the last result, and a person checks the final work.

Try it yourself

For each task, pick the simplest approach that would work: single call, workflow or agent. Write one line of reasoning for each.

  1. Translate a product description into Spanish.
  2. Every morning, take new customer reviews, tag each one by topic, and post a count per topic to the team chat.
  3. Find out why the checkout page got slower this week, using logs, recent code changes and metrics.
  4. Turn a meeting transcript into a list of action items with owners.
  1. Single call. One input, one output, no lookups.
  2. Workflow. The steps are the same every day: fetch, tag each review, count, post. Code can run them in order and the model only does the tagging.
  3. Agent. You cannot know in advance whether the answer is in the logs, a code change or a database. Each finding decides where to look next.
  4. Single call. It looks like a big job, but the whole transcript fits in one prompt and no tools are needed. Adding an agent would only add cost and ways to fail.

The pattern: an agent earns its cost only when the path is unknown until you start walking it.

Common mistakes

If you can draw the steps as a flowchart before running anything, write them as code. Letting a model rediscover the same five steps on every run is slower, costs more and sometimes skips one.

"Improve our test coverage" never ends by itself. "Add tests for parseDate until every branch is covered, then stop" does. Without a clear done condition, the agent either stops too early or keeps going until a limit cuts it off.

An agent's last message says what it thinks it did. It can claim a test passes when it never ran it. Check the real outcome: the file, the test result, the record in the database. Evals make that checking systematic.
