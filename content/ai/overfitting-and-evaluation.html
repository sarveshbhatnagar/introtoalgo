A student memorizes last year's exam. On those same questions they score 100%. On the real exam, with new questions on the same topics, they fail. They learned the answers, not the subject.

Models do the same, and it is one of the most common ways machine learning goes wrong. A model that aces its training examples can be useless on the next one. You need to catch that before your users do.

Memorizing versus learning

In What Is Machine Learning, the rule "late if at least 6 km" got 6 of 7 deliveries right. The odd one was a 10 km trip that arrived on time.

A fussier rule, "late if 6 to 9 km, or 11 km and over", gets all 7 right. It is also nonsense: 10 km is on time but 9 km and 11 km are late, all because of one lucky day. It fits the training data better and will predict new deliveries worse.

This is overfitting: learning the noise along with the pattern. The opposite, underfitting, is a model too simple to capture the pattern, like predicting "on time" for every delivery.

Test on data the model has never seen

Before training, split your labelled examples into separate piles:

  • Training set (often around 70 to 80%). The model learns from these.
  • Validation set. For comparing settings: which features, how flexible a model, which learning rate.
  • Test set. Locked away until the end. Score the final model on it once; that is your honest estimate of real-world performance.

Why three piles? Each time you check a score and change something, you fit a little to that data. Keep the best of twenty settings, and its score is flattering. The test set played no part in any choice.

When data is scarce, use cross-validation: split the training data into, say, 5 parts, train 5 times holding out a different part each time, and average the 5 scores.

A score only means something on data the model did not learn from and you did not tune on.

Accuracy can lie

The obvious number is accuracy: the share of predictions that were right. It hides a trap.

A fraud detector checks 10 card payments, 3 of them fraud. A lazy model that always says "fine" scores 70% while catching zero fraud. Real fraud is far rarer than 3 in 10, so the lazy model can score 99.9%.

To see what a classifier really does, sort every prediction into four boxes, a confusion matrix:

  • True positive: fraud, flagged.
  • False negative: fraud, not flagged. A miss.
  • False positive: fine, but flagged. A false alarm.
  • True negative: fine, not flagged.

Precision and recall

  • Precision: when the model flags, how often is it right? True positives ÷ everything flagged. Low precision means many false alarms.
  • Recall: of all the real cases, how many were caught? True positives ÷ all real positives. Low recall means many misses.

They pull against each other. Raising the threshold (from Regression and Classification) usually raises precision and lowers recall. Which matters more depends on the cost of each mistake: a cancer screening wants high recall; a system that blocks accounts automatically wants high precision.

// actual and predicted are lists of 1 (fraud) and 0 (fine).
function evaluate(actual, predicted) {
  let tp = 0, fp = 0, fn = 0, tn = 0;
  for (let i = 0; i < actual.length; i++) {
    if (predicted[i] === 1 && actual[i] === 1) tp++;
    else if (predicted[i] === 1) fp++; // flagged a fine payment
    else if (actual[i] === 1) fn++;    // missed a fraud
    else tn++;
  }
  return {
    accuracy: (tp + tn) / actual.length,
    precision: tp + fp ? tp / (tp + fp) : 0, // of the flags, how many were right
    recall: tp + fn ? tp / (tp + fn) : 0,    // of the frauds, how many we caught
  };
}

evaluate([1, 0, 0, 1, 0, 0, 0, 1, 0, 0],
         [1, 0, 1, 0, 0, 0, 0, 1, 0, 0]);
// { accuracy: 0.8, precision: 0.666..., recall: 0.666... }

def evaluate(actual, predicted):
    """actual and predicted are lists of 1 (fraud) and 0 (fine)."""
    tp = fp = fn = tn = 0
    for a, p in zip(actual, predicted):
        if p == 1 and a == 1:
            tp += 1
        elif p == 1:
            fp += 1   # flagged a fine payment
        elif a == 1:
            fn += 1   # missed a fraud
        else:
            tn += 1
    return {
        "accuracy": (tp + tn) / len(actual),
        "precision": tp / (tp + fp) if tp + fp else 0,
        "recall": tp / (tp + fn) if tp + fn else 0,
    }

evaluate([1, 0, 0, 1, 0, 0, 0, 1, 0, 0],
         [1, 0, 1, 0, 0, 0, 0, 1, 0, 0])
# {'accuracy': 0.8, 'precision': 0.666..., 'recall': 0.666...}

For regression, report the average error on the test set: the mean squared error from How Models Learn, or the average absolute error, which is easier to explain ("off by 40 a month on average").

Common mistakes

A model predicting patient readmission scores 98%. One feature is "follow-up visits booked", which is only filled in after the readmission. The model is reading the answer. For every feature, ask: would I know this at prediction time?

When predicting next week's sales, a random split lets the model train on later weeks and peek at the future. Train on the past and test on the most recent period.

Checking the test score after every change turns the test set into a second validation set, and the final number is too optimistic. Use the validation set for decisions and the test set once.

Try it yourself

A team reports on a model that predicts whether a customer will cancel next month. List what makes you doubt the result, and what you would ask for instead.

 "We trained on all 50,000 customers from the last three years and measured 96% accuracy on the same data. Only 4% of customers cancel in a typical month. Our strongest feature is 'days since the customer last logged in', measured on the day we pulled the data."
  • Scored on training data. Ask for a score on a held-out test set, ideally the most recent months, since this predicts the future.
  • Accuracy with rare positives. With 4% cancelling, predicting "stays" for everyone scores 96%, exactly the number reported. Ask for precision and recall on cancellations.
  • Possible leakage. "Days since last login", measured today, is huge for customers who already cancelled. Measure each feature as of the date the prediction would have been made.

Any one of these can make a useless model look good.
