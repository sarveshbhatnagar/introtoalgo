A login bug has you stuck, so you paste the config file and the last fifty lines of the server log into an AI assistant. It spots the problem in seconds. You did not notice that the log held a customer's email address and the config held the production database password.

That password now sits on a server you do not run, kept as long as the service keeps things, visible to whoever can open your account.

Pasted text leaves your hands

A prompt to a hosted assistant travels to the provider's servers. Depending on the provider, your plan and your settings, it can be kept in your chat history, kept in logs for abuse monitoring or debugging, and in some setups used to improve future models.

Find out, once, for each tool you use:

  • Is this tool approved for this kind of data? Your employer may allow a tool for code and forbid it for customer data.
  • Is my data used for training, and can I turn it off? Personal and business plans often differ.
  • How long are conversations kept, and does deleting a chat delete it everywhere?
  • Who else can see my history? Shared workspaces, admins and shared devices count.

Treat every prompt as something you send to someone else. If you would not email it to an outside contractor, do not paste it as it is.

What to keep out

  • Secrets: passwords, API keys, access tokens, private keys, connection strings.
  • Other people's personal data: names with contact details, health, financial or student records. They did not agree to share it, and laws in many places say you need a reason to.
  • Confidential work: unreleased plans, contract terms, code your employer has not cleared for the tool.

The model rarely needs the real value: to debug a login, it needs to know a password is set, not what it is. Placeholders like [EMAIL] or [SECRET] get you the same help.

Redact before you paste

For logs and config files, a small script is faster and more reliable than your eyes.

// Rules run in order. Each replaces one known shape of sensitive text.
const RULES = [
  [/[\w.+-]+@[\w-]+\.[\w.]+/g, "[EMAIL]"],
  [/\b(\w*(?:password|secret|token|key))\s*[=:]\s*\S+/gi, "$1=[SECRET]"],
  [/\b[A-Za-z0-9_-]{32,}\b/g, "[TOKEN]"],
];

function redact(text) {
  for (const [pattern, replacement] of RULES) {
    text = text.replace(pattern, replacement);
  }
  return text;
}

import re

# Rules run in order. Each replaces one known shape of sensitive text.
RULES = [
    (r"[\w.+-]+@[\w-]+\.[\w.]+", "[EMAIL]"),
    (r"(?i)\b(\w*(?:password|secret|token|key))\s*[=:]\s*\S+", r"\1=[SECRET]"),
    (r"\b[A-Za-z0-9_-]{32,}\b", "[TOKEN]"),
]

def redact(text):
    for pattern, replacement in RULES:
        text = re.sub(pattern, replacement, text)
    return text

The safest data is data you never sent. The error and the ten lines around it usually beat the whole file, and give the model less to be distracted by.

Security risks that come back out

AI output often ends up running on your machine, so what comes out matters too.

  • Insecure fixes. Asked to "make the error go away", a model may suggest turning off certificate checks, opening permissions wide, or gluing strings into a database query. Each works, and each opens a hole. When a fix disables a safety check, find out why the check failed instead.
  • Packages that do not exist. Models sometimes suggest plausible names that were never published, and an attacker can publish a harmful package under such a name. Check that anything new is the real, maintained project.
  • Commands you have not read. Read before you run, especially anything that deletes, changes permissions, or downloads and runs a script.
  • Assistants with access. An assistant that can read your files or act on your accounts can be steered by text hidden in what it reads. Give it only the access the task needs (see Prompt Injection).

Try it yourself

You want help replying to this customer email. Rewrite what you would paste so the assistant can still help, but nothing personal or secret leaves your hands.

 Help me reply to this. From: Daniel Okafor , account 448-2291-07. "Hi, I was charged twice on 3 March for my yearly plan, card ending 4417. My temporary password you sent me (Rx7!pq2) also doesn't work. Please fix both." Help me write a reply to a customer. Friendly, under 120 words. Their email says: they were charged twice on 3 March for a yearly plan, and the temporary password we sent them does not work. They want both fixed. What I can tell them: the duplicate charge will be refunded within 5 working days, and I'm sending a new password reset link separately. Address them as [NAME].

Why it works: the assistant needs the situation, not the identity. The name, email, account number and card digits are personal data that add nothing. The temporary password is a live secret: send it nowhere, and reset it. Saying what you may promise makes the reply accurate.

Common mistakes

A pasted password or key may already be in logs or backups. Change the password or revoke the key: that is the only fix that works.

Test keys often have more access than you think, and test databases often hold copies of real data. Use placeholders for every secret.

A dashboard screenshot can show customer names in the sidebar; a document can carry comments and earlier versions. Look at the whole thing before you upload it.
