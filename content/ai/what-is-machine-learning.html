You run a small delivery service, and customers keep asking whether their parcel will be late. You could write rules: late if over some distance, unless it is a weekday morning, unless the driver is new. Every week a case breaks your rules, and every fix makes them harder to read.

You already have something better: a spreadsheet of past deliveries, each with its distance and whether it arrived late. Machine learning lets the program work out the rule from that.

Rules versus examples

The rule it finds is a model: a function that takes the facts about one case and returns a guess. You then use it on new cases. It is "learned" because some numbers inside it were chosen from the examples, not typed in by you.

Watch a rule being learned

Start with the simplest model: "a delivery is late if its distance is at least t km". It has one parameter, t. Below are seven past deliveries; note the 10 km one that arrived on time anyway. Real data has cases like that.

Training: try each distance as the cut-off, count the mistakes, and keep the cut-off with the fewest.

A new 7 km order comes in. The model says late, because 7 is at least 6. That is a prediction: an answer for a case not in the training data.

The model still gets the 10 km delivery wrong, and that is fine. A model that matches every example has often memorized noise, the trap covered in Overfitting and Evaluation.

The code

function learnThreshold(distances, late) {
  let bestT = null;
  let fewest = Infinity;
  for (const t of distances) {         // try each distance as the cut-off
    let mistakes = 0;
    for (let i = 0; i < distances.length; i++) {
      const guess = distances[i] >= t; // the rule: late if at least t km
      if (guess !== late[i]) mistakes++;
    }
    if (mistakes < fewest) {
      fewest = mistakes;
      bestT = t;
    }
  }
  return { threshold: bestT, mistakes: fewest };
}

const distances = [2, 3, 5, 6, 8, 10, 12];
const late = [false, false, false, true, true, false, true];
learnThreshold(distances, late); // { threshold: 6, mistakes: 1 }

def learn_threshold(distances, late):
    best_t = None
    fewest = float("inf")
    for t in distances:                # try each distance as the cut-off
        mistakes = 0
        for d, was_late in zip(distances, late):
            guess = d >= t             # the rule: late if at least t km
            if guess != was_late:
                mistakes += 1
        if mistakes < fewest:
            fewest = mistakes
            best_t = t
    return best_t, fewest

distances = [2, 3, 5, 6, 8, 10, 12]
late = [False, False, False, True, True, False, True]
learn_threshold(distances, late)  # (6, 1)

Trying every option works with one parameter and seven examples. Real models have thousands to billions of parameters, too many combinations to try. They need a smarter search.

Machine learning is choosing a model's numbers so it makes few mistakes on examples with known answers, then using it on similar new cases.

Three kinds of learning

  • Supervised learning. Every example has a label, like our late column. Spam filters and price estimates work this way. Most of this module is about it.
  • Unsupervised learning. No labels. The program finds structure itself, such as groups of customers who shop alike.
  • Reinforcement learning. The program acts, gets a reward or penalty, and adjusts. Used in game playing and robot control.

When machine learning is the wrong tool

Machine learning gives you a rule that is usually right. That is a bad trade when:

  • The rule is known. Sales tax, sorting, checking a password. Write the code.
  • You have few examples, or none with answers. The model can only learn what the data shows.
  • Every answer must be exact and explainable. "Usually right" is not good enough for a bank balance.

Our model only sees distance. If lateness is really caused by rain, no amount of data will teach it that. Check that your features could explain the answer.

If every example came from quiet summer weeks, the cut-off will be wrong in December.

"The model says late" means "deliveries like this were usually late". Show it as an estimate, and keep a way to correct it.

Try it yourself

For each task, would you write the rule by hand or learn it from examples? Give a one-line reason.

 1. Work out the shipping cost from a published price table. 2. Flag product reviews that are probably fake. 3. Estimate how long a support ticket will take to resolve. 4. Check that a date entered in a form is a real date.
  1. Write it by hand. The rule is exact. Learning it would only add mistakes.
  2. Learn it. Fake reviews have subtle signs nobody can list, and moderators can label examples.
  3. Learn it. Past tickets with real resolution times are good examples, and a rough estimate is still useful.
  4. Write it by hand. Whether 31 April exists is a fact, not a pattern.

The test: is the rule hard to write down, do you have examples with answers, and can you live with occasional mistakes? You need yes to all three.
