By five o'clock, a day-long planning workshop's whiteboard holds three timelines, a budget rejected at lunch, and crossed-out ideas nobody erased. A newcomer cannot tell which plan is current, and even the people who were there start quoting the rejected budget.

Long AI sessions go the same way. A hundred messages in, the assistant forgets an early rule, brings back a fix you rejected, and mixes old code with new. The context has rotted.

Why long sessions degrade

Every message, attempt and tool result stays in the context and is reread on each call. As it grows:

  • Dead ends stay. An abandoned approach is still there in full, looking as authoritative as the right one, unless you clearly said it failed.
  • Old versions pile up. With three drafts of a function in the context, a request to change "the function" may hit the wrong one or blend them.
  • Early instructions fade. A rule from message 3 is buried under everything since. Models use long contexts less reliably than short ones (see The Context Window), and near the limit the app may trim the rule away.
  • Mistakes become examples. Earlier wrong replies are part of the text the model continues, so it tends to repeat them.

A long session's context is mostly history, much of it no longer true. Quality drops as the share of current material shrinks.

Signs your session has rotted

  • It forgets or breaks a rule you set early on.
  • It brings back an approach or bug you rejected.
  • It edits an old version instead of the latest.
  • You write more corrections than requests.
  • Replies get longer, vaguer and more hedged.

Two or more together: change the context, do not argue.

What to do about it

  1. Start fresh with a handoff. Ask for a short summary, correct it, and paste it into a new chat. Include the goal, current state, decisions and rules, what failed and why, and the next step.
  2. Keep a notes file. For multi-day work, keep the handoff in a file such as NOTES.md. Load it each session and update it at milestones; some coding tools load it automatically. It is memory you control.
  3. Edit instead of piling on. If your message caused a bad reply, edit it and regenerate, so the bad reply leaves the context.
  4. Split the work. One task per session. The logging tangent deserves its own chat.
  5. Restate what matters. When a late request depends on an early rule, repeat the rule. It costs one sentence.
# Date bug fix: notes

Goal: dates entered as DD/MM must not be read as MM/DD.
Rules: keep the public API unchanged. All tests must pass.

Current state: parser fixed in parseDate() (attempt B). Tests pass.
Tried and failed:
- Rewriting the parser (attempt A): changed the public API.

Next: add tests for 29 Feb and for two-digit years.

Some apps do part of this for you, called compaction: near the limit, older turns are replaced by a summary and old tool results may be cleared. It helps, but the summary decides what matters.

Common mistakes

Each correction adds noise, and each wrong reply is another example to copy. After two or three failed corrections, start fresh with a handoff.

If the summary lists only what works, the fresh session will retry rejected approaches. Keep one line per dead end, with the reason.

Model-written summaries can be confidently wrong about what was decided. Read and fix the handoff before using it.

Try it yourself

After 60 messages planning a team offsite, replies are getting muddled. Here is what happened, in no order. Write a handoff for a fresh session in under 120 words.

  • Porto was considered, then dropped because flights were too expensive. Lisbon was chosen.
  • Dates: 12 to 14 May. Budget: 400 per person, 9 people.
  • Three people are vegetarian.
  • Hotel 1 was over budget. Hotel 2 had no meeting room. Hotel 3 has not replied yet.
  • A long side discussion about team T-shirts went nowhere.
  • Next: chase Hotel 3, then draft a day-by-day agenda.
