Backtracking is a way to generate every answer to a problem that is built from a series of choices, such as all subsets of a list, all orderings of a list, or all valid placements on a board. It uses one shared partial answer, extends it with a choice, recurses to make the remaining choices, and then removes the choice so the next option can be tried. You reach for it when a problem asks for all solutions, or for any solution that satisfies rules that can be checked while the answer is still being built.

The alternative is to build every complete candidate and check it afterwards. Backtracking drops a partial answer as soon as it breaks a rule, along with every answer that would have grown from it.

How backtracking works

The search keeps one list called path, which holds the choices made so far. At each decision point, a recursive function goes through the options that are still allowed and does three things for each one:

  1. Choose the option by adding it to the path.
  2. Explore by calling the function recursively to make the remaining decisions.
  3. Un-choose by removing the option from the path, which restores the path to what it was before step 1 so that the next option starts from the same state.

The call stack remembers where each decision point was, as in Recursion. Un-choosing is what lets all branches of the search share a single path instead of each branch copying it.

Every backtracking solution is this loop. Problems differ in what counts as an option, when to record an answer, and which options to skip.

The simplest example is listing every sandwich you can make from three extras: cheese (C), egg (E) and tomato (T), including the plain sandwich with none. To avoid listing "egg then cheese" after "cheese then egg", each call only offers the extras that come after the last one chosen. The calls then form a tree in which every sandwich is one node.

Listing all subsets

The trace below follows the search from the first call. The path holds the sandwich being built, and the recorded list holds a copy of every sandwich found so far. Every call records the path as it stands, because every partial sandwich is itself a valid sandwich.

function subsets(items) {
  const result = [];
  const path = [];
  function explore(start) {
    result.push([...path]); // record a copy, not path itself
    for (let i = start; i < items.length; i++) {
      path.push(items[i]);  // choose
      explore(i + 1);       // explore
      path.pop();           // un-choose
    }
  }
  explore(0);
  return result;
}

subsets(["C", "E", "T"]);
// [[], ["C"], ["C","E"], ["C","E","T"], ["C","T"], ["E"], ["E","T"], ["T"]]

# [[], ['C'], ['C', 'E'], ['C', 'E', 'T'], ['C', 'T'], ['E'], ['E', 'T'], ['T']]

Cost of backtracking

Backtracking visits every node of its call tree, and the number of nodes grows very fast: 2²⁰ is about a million, and 12! is about 479 million. It is practical for small inputs, or when pruning removes most of the tree.

Variants

Permutations

When the order of the choices matters, the same template applies with two changes. The options at each step are all items that are not yet in the path, which is tracked with a used array instead of a start index. The path is recorded only when it contains every item, instead of at every call.

function permutations(items) {
  const result = [];
  const path = [];
  const used = new Array(items.length).fill(false);
  function explore() {
    if (path.length === items.length) {
      result.push([...path]);
      return;
    }
    for (let i = 0; i < items.length; i++) {
      if (used[i]) continue;
      used[i] = true;     // choose
      path.push(items[i]);
      explore();          // explore
      path.pop();         // un-choose
      used[i] = false;
    }
  }
  explore();
  return result;
}

permutations(["Ana", "Ben", "Cy"]).length; // 6

def permutations(items):
    result = []
    path = []
    used = [False] * len(items)

    def explore():
        if len(path) == len(items):
            result.append(path[:])
            return
        for i in range(len(items)):
            if used[i]:
                continue
            used[i] = True          # choose
            path.append(items[i])
            explore()               # explore
            path.pop()              # un-choose
            used[i] = False

    explore()
    return result

len(permutations(["Ana", "Ben", "Cy"]))  # 6

Choosing updates both used and path, so un-choosing has to undo both. The number of results is 3 × 2 × 1 = 6, because each position has one fewer item left to choose from.

Constraint problems with pruning

In the n queens problem, you place n queens on an n × n board so that no two share a row, column or diagonal. Each call places the queen for one row and tries each column in turn.

The new ingredient is pruning: before choosing a column, the code checks whether the square is attacked and skips it if so. A partial board that has gone wrong is abandoned immediately, and so is every board that would have been built from it.

To check a square in O(1) time, the code keeps three sets: the columns in use, the values of row - col in use, and the values of row + col in use. All squares on one down-right diagonal share the same row - col, and all squares on one down-left diagonal share the same row + col.

function solveQueens(n) {
  const cols = new Set(), down = new Set(), up = new Set();
  const placed = []; // placed[row] = column of that row's queen
  const solutions = [];
  function explore(row) {
    if (row === n) { solutions.push([...placed]); return; }
    for (let col = 0; col < n; col++) {
      // prune: column or diagonal already taken
      if (cols.has(col) || down.has(row - col) || up.has(row + col)) continue;
      // choose
      cols.add(col); down.add(row - col); up.add(row + col);
      placed.push(col);
      explore(row + 1); // explore
      // un-choose
      cols.delete(col); down.delete(row - col); up.delete(row + col);
      placed.pop();
    }
  }
  explore(0);
  return solutions;
}

solveQueens(4); // [[1, 3, 0, 2], [2, 0, 3, 1]]

def solve_queens(n):
    cols, down, up = set(), set(), set()
    placed = []  # placed[row] = column of that row's queen
    solutions = []

    def explore(row):
        if row == n:
            solutions.append(placed[:])
            return
        for col in range(n):
            if col in cols or row - col in down or row + col in up:
                continue  # prune
            cols.add(col)  # choose
            down.add(row - col)
            up.add(row + col)
            placed.append(col)
            explore(row + 1)  # explore
            cols.remove(col)  # un-choose
            down.remove(row - col)
            up.remove(row + col)
            placed.pop()

    explore(0)
    return solutions

solve_queens(4)  # [[1, 3, 0, 2], [2, 0, 3, 1]]

Combinations that add up to a target

A common interview version is: given positive numbers, find every combination that adds up to a target, where each number may be used any number of times. The path holds the numbers chosen so far, and the function also carries the amount still needed. When that amount is 0, the path is a solution. A number larger than the remaining amount is pruned, because every number is positive and adding it can only overshoot.

The only change from the subsets template is that the recursive call passes i instead of i + 1, which allows the same number to be chosen again. Passing i + 1 would be the version where each number can be used once.

function combinationSum(numbers, target) {
  const result = [];
  const path = [];
  function explore(start, remaining) {
    if (remaining === 0) {
      result.push([...path]);
      return;
    }
    for (let i = start; i < numbers.length; i++) {
      if (numbers[i] > remaining) continue; // prune
      path.push(numbers[i]);                // choose
      explore(i, remaining - numbers[i]);   // explore; i allows reuse
      path.pop();                           // un-choose
    }
  }
  explore(0, target);
  return result;
}

combinationSum([2, 3, 6, 7], 7); // [[2, 2, 3], [7]]

def combination_sum(numbers, target):

    path = []

    def explore(start, remaining):
        if remaining == 0:
            result.append(path[:])
            return
        for i in range(start, len(numbers)):
            if numbers[i] > remaining:
                continue  # prune
            path.append(numbers[i])                  # choose
            explore(i, remaining - numbers[i])       # explore; i allows reuse
            path.pop()                               # un-choose

    explore(0, target)
    return result

combination_sum([2, 3, 6, 7], 7)  # [[2, 2, 3], [7]]

Input with duplicate values

If the input contains repeated values, such as [1, 2, 2], the subsets template records the subset [1, 2] twice, once for each 2. The fix has two parts. First sort the input, so equal values are next to each other. Then, inside the loop, skip a value that equals the one before it unless it is the first option at this decision point: if i > start and items[i] == items[i - 1]: continue. The i > start condition keeps [2, 2] valid, because a repeat is only skipped when an identical value was just tried at the same position.

When backtracking does not apply

Backtracking enumerates answers, so it is the wrong tool when the question asks only for a count or an optimum and the same smaller problem appears again and again. Counting the ways to make change for an amount, or finding the longest increasing subsequence, would take exponential time with backtracking and polynomial time with dynamic programming. If a simple rule shows that a locally best choice is always safe, a greedy algorithm avoids the search entirely.

Pitfalls

Writing result.push(path) stores a reference to the single shared list. By the end of the search the un-chooses have emptied it, so the result is a list of empty lists, one for each answer. Store a copy instead: [...path] in JavaScript or path[:] in Python.

If choosing changes more than one thing, such as used[i] and path, or the three queen sets, un-choosing has to reverse all of them. If one is left behind, a removed queen still blocks its column, and valid solutions are silently missing from the result.

Building every complete candidate and testing it afterwards is plain brute force, and it makes the n queens search visit all 256 boards for n = 4 and far more for larger n. Test each option before choosing it, so a bad partial answer is dropped immediately.

In the interview

The signals are in the wording of the problem. Phrases such as "return all", "list every", "generate all", or "find all combinations" point to backtracking, because the output itself is exponentially large and there is nothing faster than producing it. Problems that ask whether a valid arrangement exists, such as solving a Sudoku, placing queens, or finding a word in a grid of letters, also fit, because you build the arrangement step by step and abandon it as soon as it breaks a rule. If the problem asks only for the number of ways or the best value, check whether dynamic programming fits first.

When you start, say out loud what the path holds, what the options are at each step, when a path is complete, and what lets you prune. Interviewers usually follow with these questions:

  • "What is the time complexity?" It is the number of nodes in the call tree times the work per node. For subsets it is O(n · 2ⁿ), because there are 2ⁿ results and each takes O(n) to copy. For permutations it is O(n · n!).
  • "Why do you copy the path when you record it?" The path is one list that is changed for the rest of the search. A stored reference would show whatever the path contains at the end, which is empty. A copy keeps the contents at the moment of recording.
  • "How do you avoid duplicate results?" For subsets and combinations, pass a start index so each call only looks at later items, which stops the same set appearing in a different order. If the input has repeated values, sort it and skip a value equal to the previous one at the same position.
