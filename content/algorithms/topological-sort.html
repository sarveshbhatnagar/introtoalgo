You are making pizza at home with friends. The toppings cannot go on until the dough, the sauce and the grated cheese are ready. The pizza cannot bake until the toppings are on and the oven is hot. You cannot eat until it has baked. Four people want a job right now. Which jobs can start, and what is a full order that never makes anyone wait on something unfinished?

Each rule is a one-way link: "dough must come before toppings". That makes this a directed graph, as in Graph Basics, with an arrow from each task to the task that needs it. An order of all the tasks where every arrow points forward is called a topological order. Finding one is a topological sort.

There is usually more than one valid order. Dough, sauce, cheese, oven, toppings, bake, eat works. So does oven, cheese, sauce, dough, toppings, bake, eat. What never works is a cycle: if toppings needed bake and bake needed toppings, neither could ever start. A topological order exists exactly when the directed graph has no cycle. Such a graph is called a DAG (directed acyclic graph).

The idea: start with what nothing blocks

For each task, count the arrows coming into it. That count is its in-degree: the number of tasks it is still waiting on. A task with in-degree 0 is ready right now.

  1. Put every ready task (in-degree 0) in a queue.
  2. Take a task from the queue and add it to the order.
  3. It is done, so remove its outgoing arrows: subtract 1 from the in-degree of each task after it. Any task that drops to 0 has just become ready. Add it to the queue.
  4. Repeat until the queue is empty.

This is Kahn's algorithm. It looks a lot like BFS, but a task joins the queue only when its last blocker is done, not the first time anything points at it.

A task is ready when everything pointing into it is done. Keep a count of unfinished blockers per task, and release a task the moment its count reaches 0.

The code

Notice the last line. If the graph has a cycle, the tasks on it never reach in-degree 0, so they never enter the queue. The order comes out shorter than the task list, and that is how you detect the cycle.

// rules: list of [before, after] pairs.
function taskOrder(tasks, rules) {
  const next = {};
  const inDegree = {};
  for (const t of tasks) { next[t] = []; inDegree[t] = 0; }
  for (const [before, after] of rules) {
    next[before].push(after);
    inDegree[after]++;
  }
  const queue = tasks.filter((t) => inDegree[t] === 0);
  const order = [];
  let head = 0;
  while (head < queue.length) {
    const task = queue[head++];
    order.push(task);
    for (const after of next[task]) {
      inDegree[after]--;
      if (inDegree[after] === 0) queue.push(after); // last blocker gone
    }
  }
  return order.length === tasks.length ? order : null; // null: cycle
}

taskOrder(
  ["dough", "sauce", "cheese", "oven", "toppings", "bake", "eat"],
  [["dough", "toppings"], ["sauce", "toppings"], ["cheese", "toppings"],
   ["toppings", "bake"], ["oven", "bake"], ["bake", "eat"]]
); // ["dough", "sauce", "cheese", "oven", "toppings", "bake", "eat"]

from collections import deque

# rules: list of (before, after) pairs.
def task_order(tasks, rules):
    nxt = {t: [] for t in tasks}
    in_degree = {t: 0 for t in tasks}
    for before, after in rules:
        nxt[before].append(after)
        in_degree[after] += 1
    queue = deque(t for t in tasks if in_degree[t] == 0)
    order = []
    while queue:
        task = queue.popleft()
        order.append(task)
        for after in nxt[task]:
            in_degree[after] -= 1
            if in_degree[after] == 0:
                queue.append(after)  # last blocker gone
    return order if len(order) == len(tasks) else None  # None: cycle

task_order(
    ["dough", "sauce", "cheese", "oven", "toppings", "bake", "eat"],
    [("dough", "toppings"), ("sauce", "toppings"), ("cheese", "toppings"),
     ("toppings", "bake"), ("oven", "bake"), ("bake", "eat")],
)  # ['dough', 'sauce', 'cheese', 'oven', 'toppings', 'bake', 'eat']

The DFS version

Depth-First Search gives a second way. A DFS call on a task does not return until it has finished every task reachable from it, which is every task that must come after it. So when a task finishes, everything that depends on it has already finished. Write tasks down in the order they finish, then reverse the list.

Cycle detection needs one extra state. A task is either unvisited, on the current path (its call has started but not returned), or finished. If DFS reaches a task that is on the current path, it has followed arrows in a circle, and there is no valid order.

function taskOrderDfs(tasks, rules) {
  const next = {};
  for (const t of tasks) next[t] = [];
  for (const [before, after] of rules) next[before].push(after);
  const state = {}; // undefined: unvisited, 1: on the path, 2: finished
  const finished = [];
  function visit(task) {
    if (state[task] === 2) return true;
    if (state[task] === 1) return false; // back on our own path: cycle
    state[task] = 1;
    for (const after of next[task]) {
      if (!visit(after)) return false;
    }
    state[task] = 2;
    finished.push(task); // everything after it is already finished
    return true;
  }
  for (const t of tasks) {
    if (!visit(t)) return null;
  }
  return finished.reverse();
}
// pizza tasks → ["oven", "cheese", "sauce", "dough", "toppings", "bake", "eat"]

def task_order_dfs(tasks, rules):
    nxt = {t: [] for t in tasks}
    for before, after in rules:
        nxt[before].append(after)
    state = {}  # missing: unvisited, 1: on the path, 2: finished
    finished = []

    def visit(task):
        if state.get(task) == 2:
            return True
        if state.get(task) == 1:
            return False  # back on our own path: cycle
        state[task] = 1
        for after in nxt[task]:
            if not visit(after):
                return False
        state[task] = 2
        finished.append(task)  # everything after it is already finished
        return True

    for t in tasks:
        if not visit(t):
            return None
    return finished[::-1]
# pizza tasks → ['oven', 'cheese', 'sauce', 'dough', 'toppings', 'bake', 'eat']

On the pizza tasks, DFS starts at dough and runs dough, toppings, bake, eat. Eat finishes first, then bake, toppings and dough. Sauce, cheese and oven each finish straight away. Reversed, that gives a different order from Kahn's, and an equally valid one. Both versions are O(V + E). Kahn's needs no recursion, so it is the safer choice on large inputs; the DFS version is handy when you are already writing a DFS.

Common mistakes

"Toppings depends on dough" means the arrow goes from dough to toppings: the thing that must happen first points at the thing that waits. Get it backwards and the algorithm still runs, but the order comes out backwards: eat first, dough last. Write the rule as a [before, after] pair and check it against one example by hand.

With a cycle, Kahn's algorithm does not crash or loop forever. It quietly returns a partial order with the stuck tasks missing. If you return that order without comparing its length to the number of tasks, your program claims a schedule that leaves work out.

Most graphs have many valid orders. Which one you get depends on the order of the task list and the neighbour lists. If a problem asks for a specific one, such as "the alphabetically smallest", you need a rule for which ready task to take first, for example a priority queue instead of a plain queue.

Build tools compile files after the files they import. Package managers install libraries after the libraries they need, and report an error when two packages need each other. Spreadsheets recalculate a cell only after the cells its formula reads. All of these are topological sorts.
