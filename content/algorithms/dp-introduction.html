A ticket machine gives change in coins worth 1, 4 and 5, with plenty of each. A customer is owed 8. Hand over as few coins as possible.

"Biggest coin first" gives 5, 1, 1, 1: four coins. But 4 + 4 is two. That is the trap from Greedy Algorithms: to be right, you have to consider every first coin.

Version 1: honest, slow recursion

The first coin is a 1, a 4 or a 5, and what remains is the same problem with a smaller amount. So the fewest coins for 8 is one coin plus the best of the answers for 7, 4 and 3. Each breaks down the same way, down to 0, which needs no coins.

// Fewest coins that add up to amount (Infinity if impossible).
function fewestCoins(amount, coins) {
  if (amount === 0) return 0;
  let best = Infinity;
  for (const coin of coins) {
    if (coin <= amount) {
      best = Math.min(best, 1 + fewestCoins(amount - coin, coins));
    }
  }
  return best;
}

fewestCoins(8, [1, 4, 5]); // 2

import math

# Fewest coins that add up to amount (math.inf if impossible).
def fewest_coins(amount, coins):
    if amount == 0:
        return 0
    best = math.inf
    for coin in coins:
        if coin <= amount:
            best = min(best, 1 + fewest_coins(amount - coin, coins))
    return best

fewest_coins(8, [1, 4, 5])  # 2

This is correct, but for 8 it makes 35 calls, and for 30 it makes 255,904. There are only 31 amounts from 0 to 30, so almost all that work is repeated.

It is the same waste as Fibonacci in Recursion. Two signs together call for dynamic programming:

  • The big answer is built from smaller answers. The best way to pay 8 is one coin plus the best way to pay what is left.
  • The smaller problems repeat. Different paths keep landing on the same amount.

Version 2: remember answers (memoisation)

Keep a map from amount to answer. Check it before working anything out; store the result after. Each amount is solved once, and every later visit is a lookup.

function fewestCoinsMemo(amount, coins, memo = new Map()) {
  if (amount === 0) return 0;
  if (memo.has(amount)) return memo.get(amount); // solved before
  let best = Infinity;
  for (const coin of coins) {
    if (coin <= amount) {
      best = Math.min(best, 1 + fewestCoinsMemo(amount - coin, coins, memo));
    }
  }
  memo.set(amount, best); // remember for next time
  return best;
}

def fewest_coins_memo(amount, coins, memo=None):
    if memo is None:
        memo = {}
    if amount == 0:
        return 0
    if amount in memo:  # solved before
        return memo[amount]
    best = math.inf
    for coin in coins:
        if coin <= amount:
            best = min(best, 1 + fewest_coins_memo(amount - coin, coins, memo))
    memo[amount] = best  # remember for next time
    return best

For 30, the calls drop from 255,904 to 84. The logic is unchanged; you just stopped throwing answers away.

Version 3: fill a table from the bottom

Every amount depends only on smaller amounts. So skip the recursion and work upward: 0, then 1, then 2. When you reach any amount, everything it needs is already in the table. This is tabulation.

function fewestCoinsTable(amount, coins) {
  const best = new Array(amount + 1).fill(Infinity);
  best[0] = 0;
  for (let a = 1; a <= amount; a++) {
    for (const coin of coins) {
      if (coin <= a) best[a] = Math.min(best[a], 1 + best[a - coin]);
    }
  }
  return best[amount]; // Infinity means "cannot be paid"
}

fewestCoinsTable(8, [1, 4, 5]); // 2

def fewest_coins_table(amount, coins):
    best = [math.inf] * (amount + 1)
    best[0] = 0
    for a in range(1, amount + 1):
        for coin in coins:
            if coin <= a:
                best[a] = min(best[a], 1 + best[a - coin])
    return best[amount]  # math.inf means "cannot be paid"

fewest_coins_table(8, [1, 4, 5])  # 2

Both do the same work. Memoisation is easier to write first: your recursion plus three lines. Tabulation cannot overflow the call stack on a large amount, and is usually a little faster.

The five-step recipe

Every dynamic programming solution in this module answers five questions. Write them in words before any code:

  1. State. What does one cell of the table mean? Here: best[a] is the fewest coins that add up to exactly a.
  2. Recurrence. How is a cell built from smaller cells? Here: best[a] = 1 + min(best[a − coin]) over every coin that fits.
  3. Base cases. Which cells do you know outright? Here: best[0] = 0.
  4. Order. Which fill order has each cell's inputs ready? Here: from 0 upward.
  5. Answer. Which cell holds the result? Here: best[amount].

Dynamic programming is recursion that never solves the same subproblem twice: remember answers as you recurse, or fill a table in an order where every answer you need is already there.

Step 1 is where the thinking happens. If you cannot say in one sentence what a cell means, the recurrence will not come.

For any DP, time = number of cells × work per cell.

Common mistakes

Start at 0 and min(best[a], …) keeps the 0, so every answer is 0. Start "fewest" problems at ∞ so any real option beats it. ∞ also marks amounts that cannot be paid: with coins 4 and 5, best[3] stays ∞.

const memo = new Map() inside the function body gives each call its own empty map, so nothing is reused. Pass the memo along, as above. In Python, never write memo={} as a default argument: that dictionary survives between separate calls, so answers for one coin set leak into the next.

Loop downward and best[8] reads best[7], best[4] and best[3] while they are still ∞, giving ∞ instead of 2. Point at one cell and check that every cell it reads is already computed.

Spreadsheets recalculate cells in an order where inputs are ready first, and build tools cache every step they have done. Both are "solve once, reuse".
