You want to know if anyone signed up twice on a guest list, and you write two versions of the check. With 100 names, both finish instantly. With a million names, one takes a few milliseconds. The other takes several minutes.

The difference is how the work grows when the list grows. Big-O notation lets you see that in the code, before you run it.

Count steps, not seconds

A stopwatch tells you about one machine, one input and one moment. Instead, count the basic steps: comparisons, additions, lookups. Then ask how that count changes as the input size, n, grows.

The slow duplicate check compares every name with every name after it. Watch the comparison counter.

The exact count is more detail than you need. What matters is the shape: double the names and the work roughly quadruples. Big-O captures that shape.

Keep only what grows fastest

To turn a step count into Big-O, drop constant factors and every term except the fastest-growing one.

Plug in a big number to see why. With n = 1,000,000, n²/2 − n/2 gives 500,000,000,000 minus 500,000: the second term barely matters. The "divide by 2" does not change the growth either: double n and the work still quadruples. So n(n − 1) / 2 becomes O(n²), read "order n squared".

  • 3n + 5 becomes O(n).
  • n² + 100n becomes O(n²).
  • 7 becomes O(1): the work does not depend on n at all.

Big-O describes how cost grows as input grows: the shape of the curve, not exact seconds.

A computer does very roughly a few hundred million simple steps per second. So a million names at O(n²) means minutes; at O(n), milliseconds.

Reading Big-O from code

You rarely need a formula. Three rules get you most of the way:

  1. Steps in a row add up, and the biggest wins. A loop over n, then another loop over n, is 2n, which is O(n).
  2. Nested loops multiply. A loop over n inside a loop over n is O(n²).
  3. Halving each time is O(log n). You can only halve n about log₂(n) times: 20 steps for a million items.

The fast duplicate check remembers every name in a set, so "have I seen this before?" is one step instead of a whole loop.

// O(n²) time: compare every pair
function hasDuplicateSlow(names) {
  for (let i = 0; i < names.length; i++) {
    for (let j = i + 1; j < names.length; j++) {
      if (names[i] === names[j]) return true;
    }
  }
  return false;
}

// O(n) time: remember what you have seen
function hasDuplicate(names) {
  const seen = new Set();
  for (const name of names) {
    if (seen.has(name)) return true; // O(1) on average
    seen.add(name);
  }
  return false;
}

# O(n²) time: compare every pair
def has_duplicate_slow(names):
    for i in range(len(names)):
        for j in range(i + 1, len(names)):
            if names[i] == names[j]:
                return True
    return False

# O(n) time: remember what you have seen
def has_duplicate(names):
    seen = set()
    for name in names:
        if name in seen:  # O(1) on average
            return True
        seen.add(name)
    return False

Memory counts too

Big-O works for memory too. The fast version stores up to n names: O(n) extra space. The slow version keeps two counters: O(1).

Spending memory to save time is the most common trade in algorithms. It is usually worth it, but not always on a tiny device or a huge dataset. Knowing both numbers lets you choose.

Worst case, unless someone says otherwise

If the duplicate is the first two names, even the slow version stops after one comparison. Big-O usually describes the worst case, because that is what brings your app down. The average case is named when meant, as with hash set lookups: O(1) on average.

list.includes(x) in JavaScript and x in some_list in Python scan the list from the start. Inside a loop, your "single loop" is really O(n²). So are indexOf, slicing, and building a string with + in a loop. A set or map makes the lookup O(1).

Only nested loops multiply. Two loops in a row are O(n) + O(n) = O(n). In patterns like two pointers, an inner while moves a pointer that never goes back, so the whole run is still O(n).

To check if a solution is fast enough, plug the largest input from the constraints into your Big-O. If n is 100,000 and you have O(n²), that is 10 billion steps: too slow. O(n log n) is about 1.7 million: fine.

A feature that compares every new comment against every old one works fine with 50 comments in testing. Months later there are 50,000 and the page times out. Nothing broke: the input grew, and the O(n²) was there from the start.
