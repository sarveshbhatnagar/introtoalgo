Heap sort sorts an array in place by first arranging it as a max-heap and then repeatedly moving the largest item to the end. It runs in O(n log n) time on every input and uses O(1) extra memory. You reach for it when you need both of those guarantees together, which merge sort (extra memory) and quicksort (bad worst case) cannot give.

It is a faster version of selection sort. Selection sort finds the largest remaining item by scanning all of them, which costs O(n) per item and O(n²) overall. A heap keeps the largest item at the front and restores that property in O(log n) steps after each removal.

What a heap needs to provide

A max-heap is a binary tree in which every parent is at least as large as its children, so the largest item is always at the root. The full treatment is in Heaps and Priority Queues. Heap sort uses three facts from it.

  • The tree is stored in a plain array, level by level. The children of index i are at 2i + 1 and 2i + 2, so no pointers are needed.
  • The root, a[0], is the largest item.
  • Sift down repairs a heap whose root is out of place. It swaps the item with its larger child, again and again, until the item is at least as large as both of its children. The tree has about log₂ n levels, so a sift down makes at most log₂ n swaps.

How heap sort works

The algorithm has two phases. In the first, it turns the whole array into a max-heap in place. In the second, it repeats the following until one item is left: swap the root, which is the largest item, with the last item of the heap; that position is now final, so the heap shrinks by one; then sift the new root down to repair the heap. The array is therefore split into a shrinking heap at the front and a growing sorted section at the back.

Phase 1: build the heap

Every item in the second half of the array is a leaf, and a leaf is already a heap of one item. So the build starts at the last parent, index n/2 − 1, and sifts down each item on the way back to index 0. When the loop reaches an item, both of its subtrees are already heaps, so sifting it down makes its whole subtree a heap.

Phase 2: move the maximum to the end

In the next trace, the faded nodes and marked cells are the sorted section, which is no longer part of the heap.

Code

function heapSort(a) {
  const n = a.length;
  // phase 1: build a max-heap, from the last parent up to the root
  for (let i = Math.floor(n / 2) - 1; i >= 0; i--) siftDown(a, i, n);
  // phase 2: move the max to the end, shrink the heap, repair it
  for (let end = n - 1; end > 0; end--) {
    [a[0], a[end]] = [a[end], a[0]];
    siftDown(a, 0, end); // the heap is now a[0..end-1]
  }
  return a;
}

function siftDown(a, i, size) {
  while (true) {
    let big = i;
    const left = 2 * i + 1, right = 2 * i + 2;
    if (left < size && a[left] > a[big]) big = left;
    if (right < size && a[right] > a[big]) big = right;
    if (big === i) return; // bigger than both children: done
    [a[i], a[big]] = [a[big], a[i]];
    i = big;
  }
}

heapSort([3, 8, 5, 1, 9, 2]); // [1, 2, 3, 5, 8, 9]

def heap_sort(a):
    n = len(a)
    # phase 1: build a max-heap, from the last parent up to the root
    for i in range(n // 2 - 1, -1, -1):
        sift_down(a, i, n)
    # phase 2: move the max to the end, shrink the heap, repair it
    for end in range(n - 1, 0, -1):
        a[0], a[end] = a[end], a[0]
        sift_down(a, 0, end)  # the heap is now a[0..end-1]
    return a

def sift_down(a, i, size):
    while True:
        big = i
        left, right = 2 * i + 1, 2 * i + 2
        if left < size and a[left] > a[big]:
            big = left
        if right < size and a[right] > a[big]:
            big = right
        if big == i:  # bigger than both children: done
            return
        a[i], a[big] = a[big], a[i]
        i = big

heap_sort([3, 8, 5, 1, 9, 2])  # [1, 2, 3, 5, 8, 9]

Time and space

Phase 2 performs n − 1 sift downs, and each one moves down at most log₂ n levels, so the sort is O(n log n) on every input. Unlike quicksort, there is no input that makes it slower.

Phase 1 is only O(n), even though it also performs n/2 sift downs. Half of the items are leaves and never move. A quarter of the items sit one level above the leaves and move at most one step, an eighth move at most two steps, and only the root can travel the full height. These counts add up to fewer than n swaps in total.

All of the work consists of swaps inside the array, so the extra space is O(1).

Variants and alternatives

Building the heap by inserting one item at a time

Instead of sifting down from the last parent, you can start with a heap of one item and insert the remaining items one by one, sifting each new item up. This also produces a valid heap, but it takes O(n log n) because the items near the bottom, which are the majority, may each travel the full height upward. The sort as a whole is still O(n log n), but the bottom-up build above is the standard choice because it is faster and reuses the sift down that phase 2 needs anyway.

Sorting in descending order

To sort in descending order, use a min-heap, in which every parent is at most as large as its children, and make the same two phases. The smallest item is then moved to the end of the array each round, which leaves the array in descending order. In code, only the two comparisons in the sift down change direction.

Heap sort compared with quicksort and merge sort

Quicksort is O(n²) in the worst case but is usually the fastest of the three, because it reads memory in order and so works well with the CPU cache. Heap sort jumps between indexes that are far apart, such as 1, 3 and 7, which makes it slower in practice even though its operation count is the same order. Merge sort is O(n log n) in every case and is stable, but it needs O(n) extra memory for arrays. Heap sort is the only one of the three that has the O(n log n) guarantee and O(1) extra space at the same time.

When heap sort is not the right tool

Heap sort is not stable: swapping the root with the last item can move an item past other items that are equal to it, so the original order of equal keys is lost. If you need to keep it, for example when sorting records by one field after sorting by another, use merge sort. Heap sort also needs random access by index, so it does not suit linked lists, and when you only need the k largest items, you should not sort at all. Keep a min-heap of size k and push each item through it, which costs O(n log k).

Pitfalls

After each swap, the sift down must treat only a[0..end-1] as the heap, so it takes end as its size. If you pass n, the sift down can compare against the sorted items at the back and pull a large one back into the heap, which breaks the result.

Looping from index 0 up to the last parent does not produce a heap, because sift down assumes that both subtrees of the item are already heaps. The loop has to run from the last parent n/2 − 1 down to 0, so that the subtrees are finished before their parent is processed.

The item must swap with the larger of its two children. If a 2 has the children 8 and 5 and you swap it with the 5, the 5 becomes the parent of the 8, and the heap property is broken. Also check that a child index is below the heap size before reading it, because the last parent may have only one child.

In the interview

Interviewers rarely ask you to write heap sort from scratch. When they do, the point is usually to check that you can implement a heap with array indexes. More often, the problem statement points to a heap, and the sorting step is a side issue. The signals are phrases such as "the k largest", "the k-th smallest", "the next largest item repeatedly" or "merge k sorted lists", and a requirement for O(n log n) time in the worst case with constant extra space. For the first group, use a heap of size k and do not sort at all. For the last one, heap sort is the answer.

These are the follow-up questions to expect.

  • "Why is building the heap O(n) and not O(n log n)?" Most items are near the bottom of the tree and can move only a few levels down. Half of the items are leaves and never move, a quarter move at most one level, and so on, so the total number of swaps is below n. The O(n log n) bound for phase 1 is correct but not tight.
  • "Is heap sort stable?" No. Swapping the root with the last item of the heap moves it over every item in between, including items equal to it, so equal keys can end up in a different order. To get a stable O(n log n) sort, use merge sort, and accept the extra memory.
  • "Why is quicksort usually faster if heap sort has a better worst case?" Quicksort scans memory in order, which suits the CPU cache, and it does fewer comparisons on average. Heap sort jumps between distant indexes and does two comparisons per level of each sift down. Real libraries combine them: introsort starts with quicksort and switches to heap sort if the recursion gets too deep, which keeps the worst case at O(n log n).
  • "When would you choose heap sort?" When memory is tight, so merge sort is out, and a bad worst case is not acceptable, so plain quicksort is out. That is a narrow case, and saying so is a good answer.
  • "How would you find the 10 largest of a million numbers?" Keep a min-heap of size 10. For each number, if it is larger than the heap's root, replace the root with it and sift down. This takes O(n log 10) time and O(10) memory, while sorting everything would take O(n log n).
  • "Can you do it without recursion?" Yes. The sift down in the code above is a loop, so the whole sort is iterative and uses no call stack.
