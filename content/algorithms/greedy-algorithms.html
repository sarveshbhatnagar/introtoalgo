A cashier owes you 63 cents in coins of 25, 10, 5 and 1. Every cashier does the same thing: hand over the biggest coin that still fits, and repeat. 25, 25, 10, 1, 1, 1. Six coins, and you cannot do it with fewer.

A greedy algorithm builds its answer one step at a time, takes whatever looks best right now, and never reconsiders. Backtracking tries every option; greedy tries one per step, so it is fast. The catch: "best right now" is not always best overall.

The idea: commit to one choice

One meeting room, six booking requests, each with a start and end hour. Accept as many as possible with no two overlapping. A booking that ends at 6 and one that starts at 6 are fine together.

You could try shortest first, earliest start, or earliest end. Only earliest end is always right: the booking that ends first leaves the room free for the longest time afterwards.

So: sort by end time, walk through, and keep a booking if it starts at or after the end of the last one you kept.

Bookings, traced

// bookings: [start, end] pairs. Back-to-back bookings are allowed.
function maxBookings(bookings) {
  const byEnd = [...bookings].sort((a, b) => a[1] - b[1]);
  let kept = 0;
  let lastEnd = -Infinity;
  for (const [start, end] of byEnd) {
    if (start >= lastEnd) { // fits after the last booking we kept
      kept++;
      lastEnd = end;
    }
  }
  return kept;
}

maxBookings([[2, 5], [6, 8], [1, 3], [1, 7], [4, 6], [7, 9]]); // 3

def max_bookings(bookings):
    by_end = sorted(bookings, key=lambda b: b[1])
    kept = 0
    last_end = float("-inf")
    for start, end in by_end:
        if start >= last_end:  # fits after the last booking we kept
            kept += 1
            last_end = end
    return kept

max_bookings([[2, 5], [6, 8], [1, 3], [1, 7], [4, 6], [7, 9]])  # 3

Why earliest end is safe

"It looks right" is not a proof: the other two rules look right too, and they are wrong. Prove a greedy choice with an exchange argument.

Let X be the booking that ends first. Take any best schedule and its first booking, Y. Y cannot end before X. Swap Y out and X in. X ends no later than Y, so it cannot clash with anything after Y. The schedule is still valid, with the same count.

So some best schedule starts with X, and taking X is never a mistake. The rest is the same problem on the bookings that start at or after X ends.

A greedy choice is safe when some best answer already makes it: swap it into any optimal answer and show the result is still valid and no worse.

The swap breaks for the other rules. Earliest start picks 1–10 out of 1–10, 2–3 and 4–5, and blocks both short meetings: 1 booking instead of 2. Shortest first picks 4–7 out of 1–5, 4–7 and 6–10, and it overlaps both others: 1 instead of 2.

When greedy fails

Now use coins worth 1, 3 and 4 to make 6. Greedy takes 4, leaving 2, which needs 1 + 1: three coins. But 3 + 3 is two.

The exchange argument fails. Swap one 3 in 3 + 3 for the greedy 4 and you get 7, too much. The first coin changes what is left to solve, and greedy never looks ahead.

With coins 25, 10, 5 and 1 the swap always works, so the cashier is safe. Same code; only the coin set decides whether it is correct.

// coins sorted from largest to smallest
function greedyChange(coins, amount) {
  let used = 0;
  for (const coin of coins) {
    while (amount >= coin) {
      amount -= coin;
      used++;
    }
  }
  return amount === 0 ? used : -1; // -1: greedy got stuck
}

greedyChange([25, 10, 5, 1], 63); // 6, the true minimum
greedyChange([4, 3, 1], 6);       // 3, but 3 + 3 needs only 2

# coins sorted from largest to smallest
def greedy_change(coins, amount):
    used = 0
    for coin in coins:
        while amount >= coin:
            amount -= coin
            used += 1
    return used if amount == 0 else -1  # -1: greedy got stuck

greedy_change([25, 10, 5, 1], 63)  # 6, the true minimum
greedy_change([4, 3, 1], 6)        # 3, but 3 + 3 needs only 2

For coins in general, use dynamic programming: it solves every smaller amount instead of betting on one coin.

How to tell

  1. Hunt for a counterexample. Try tiny inputs built to trap the rule: a long item that starts first, a big coin that leaves an awkward remainder. Most wrong rules die in a minute.
  2. Try the exchange argument. Swap the greedy choice into any best answer. If it stays valid and no worse, the rule is safe.
  3. Watch for choices that change the future. If a choice uses up a budget or reshapes what is left, like a coin changing the remaining amount, greedy is suspect. That smells like knapsack, a dynamic programming problem.

Unsure? Write a slow brute force with backtracking and compare it with greedy on a few thousand random small inputs. A mismatch is a counterexample.

Common mistakes

Most greedy solutions are "sort, then scan", and the proof lives in the sort key. Sorting bookings by start or length looks the same and passes simple tests, then fails on the cases above.

With coins 4, 3 and 1, the coin code is right for 1 to 5 and for 7, 8 and 9. It fails on 6. Samples rarely contain the trap.

Whether 3–6 and 6–8 clash depends on the problem. Here they do not, so the test is start >= lastEnd. If shared endpoints clash, use >. Test a back-to-back pair.

Greedy rules are everywhere because they are fast: schedulers that pick the job finishing soonest, compression that pairs the two rarest symbols first, and routers taking the closest unvisited node in Dijkstra's algorithm. Each has a proof that its choice is safe.
