A photographer wants a class lined up by height. She picks one child, Sam, and says: "Shorter than Sam, stand on his left. Taller, on his right." Neither side is sorted yet, but Sam stands exactly where he belongs in the final line.

Then she does the same with each group. Each round puts at least one more child in place, and the groups keep shrinking. That is quicksort.

The idea: partition around a pivot

  1. Pick a pivot, one item from the range.
  2. Partition: move smaller items before the pivot and the rest after it. The pivot lands in its final position.
  3. Recurse on the part before the pivot and the part after it.

Merge sort splits blindly and does its work when merging. Quicksort does its work while splitting, so there is nothing to combine: once both sides are sorted, the range is sorted. It also sorts in place.

Partitioning, traced

This version uses the last item as the pivot. Everything left of boundary b is smaller than the pivot, so b is where the next small item goes. Pointer j scans the range once.

The code

This is the traced partition with one addition: it first swaps a random item to the end, so the pivot is random. The next section explains why.

function quickSort(a, lo = 0, hi = a.length - 1) {
  if (lo >= hi) return a; // 0 or 1 items: sorted
  const p = partition(a, lo, hi);
  quickSort(a, lo, p - 1);  // the pivot at p is already final
  quickSort(a, p + 1, hi);
  return a;
}

function partition(a, lo, hi) {
  const r = lo + Math.floor(Math.random() * (hi - lo + 1));
  [a[r], a[hi]] = [a[hi], a[r]]; // random pivot, moved to the end
  const pivot = a[hi];
  let b = lo; // a[lo..b-1] holds items smaller than the pivot
  for (let j = lo; j < hi; j++) {
    if (a[j] < pivot) {
      [a[b], a[j]] = [a[j], a[b]];
      b++;
    }
  }
  [a[b], a[hi]] = [a[hi], a[b]]; // pivot into its final slot
  return b;
}

quickSort([7, 2, 9, 4, 1, 6]); // [1, 2, 4, 6, 7, 9]

import random

def quick_sort(a, lo=0, hi=None):
    if hi is None:
        hi = len(a) - 1
    if lo >= hi:  # 0 or 1 items: sorted
        return a
    p = partition(a, lo, hi)
    quick_sort(a, lo, p - 1)  # the pivot at p is already final
    quick_sort(a, p + 1, hi)
    return a

def partition(a, lo, hi):
    r = random.randint(lo, hi)
    a[r], a[hi] = a[hi], a[r]  # random pivot, moved to the end
    pivot = a[hi]
    b = lo  # a[lo..b-1] holds items smaller than the pivot
    for j in range(lo, hi):
        if a[j] < pivot:
            a[b], a[j] = a[j], a[b]
            b += 1
    a[b], a[hi] = a[hi], a[b]  # pivot into its final slot
    return b

quick_sort([7, 2, 9, 4, 1, 6])  # [1, 2, 4, 6, 7, 9]

Good pivots and bad pivots

Partitioning n items costs O(n), one scan. What matters is how evenly the pivot splits the range.

Pivots near the middle halve the range, as in merge sort: about log n levels of O(n) work, so O(n log n).

Now sort an already sorted array with the last item as pivot. The pivot is the biggest item, so one side gets everything else and each level removes one item. That is n + (n − 1) + … + 1 steps, O(n²), and the recursion goes n calls deep.

A random pivot fixes this: no input can force bad pivots, because the choice is fresh every run. On a large array the worst case is vanishingly unlikely, and the expected cost is O(n log n) for any input of distinct items. Many equal items are a separate problem, covered below.

Partitioning puts the pivot in its final place in one O(n) pass. Quicksort is fast when pivots split ranges roughly in half, and a random pivot makes that the expected case.

Quicksort is not stable. Partition swaps throw items over each other: in the trace, 7 went from slot 0 to 1, then 3, then 5. Nothing keeps equal keys in their original order.

Common mistakes

It falls apart on sorted or reversed data, which is common: log files, IDs, timestamps. Pick a random pivot, or the median of the first, middle and last items.

Recurse on [lo, p − 1] and [p + 1, hi]. With [lo, p], a largest-item pivot gives the call the same range again, and with a fixed last-item pivot it never stops.

If every item is the same, a[j] < pivot is never true, so everything lands on one side: O(n²) even with a random pivot. Use a three-way partition into smaller, equal and bigger, and recurse only on smaller and bigger.

For just the k-th smallest item, partition and recurse into the one side containing position k. This is quickselect, O(n) on average: the scans cost about n + n/2 + n/4 + …, under 2n.

C++'s std::sort is usually an introsort: quicksort, with insertion sort for tiny ranges and a switch to heap sort if recursion gets too deep. Quicksort's speed, with an O(n log n) guarantee.
