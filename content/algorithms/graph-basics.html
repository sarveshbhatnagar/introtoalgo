A small town has seven bus stops, A to G. A bus runs between some pairs of stops: A to B, A to C, B to D, and so on. Can you get from A to G at all? What is the trip with the fewest stops? If the road between D and F closes, is anyone cut off?

An array has a first and last item. A tree has one root, and every node has one parent. The bus map has neither: C connects to three stops, and you can ride A, B, D, C and back to A. You need a structure where anything can connect to anything: a graph.

The idea: dots and lines

A graph is a set of things, called nodes (or vertices), and connections between pairs of them, called edges. Everything else is vocabulary.

  • Neighbours: the nodes one edge away. C's neighbours are A, D and E.
  • Degree: how many edges touch a node. C has degree 3. G has degree 1.
  • Path: nodes where each consecutive pair is joined by an edge, like A, C, E, F, G. Its length is the number of edges: 4.
  • Cycle: a path that comes back to where it started without reusing an edge. A, B, D, C, A is one.
  • Connected: every node can reach every other, as on our map. Otherwise the graph splits into pieces called components. Close D–F and the map stays connected through E. Close F–G and G becomes a component on its own.

Graphs come in three flavours:

  • Undirected: an edge works both ways, like a two-way road or a friendship.
  • Directed: each edge has an arrow, like a one-way street, a "follows" link, or "task X before task Y".
  • Weighted: each edge carries a number, like minutes of travel or a price. Weights come later with Dijkstra's algorithm.

A tree is a connected graph with no cycles, so the ideas from Tree Traversals carry over. The new problem is cycles: in a graph you can walk back to a node you have seen, so every graph walk must remember where it has been.

Storing a graph: the adjacency list

Problems usually hand you an edge list: pairs like [["A","B"], ["A","C"], ...]. To find C's neighbours you would scan every edge.

Instead, build an adjacency list: a map from each node to its neighbours. Then "who is next to C?" is one lookup. In an undirected graph, each edge goes into both endpoints' lists.

// nodes: list of names. edges: list of [u, v] pairs, two-way.
function buildGraph(nodes, edges) {
  const graph = {};
  for (const node of nodes) graph[node] = [];
  for (const [u, v] of edges) {
    graph[u].push(v);
    graph[v].push(u); // leave this line out for a directed graph
  }
  return graph;
}

const graph = buildGraph(
  ["A", "B", "C", "D", "E", "F", "G"],
  [["A", "B"], ["A", "C"], ["B", "D"], ["C", "D"],
   ["C", "E"], ["D", "F"], ["E", "F"], ["F", "G"]]
);
graph["C"]; // ["A", "D", "E"]

# nodes: list of names. edges: list of (u, v) pairs, two-way.
def build_graph(nodes, edges):
    graph = {node: [] for node in nodes}
    for u, v in edges:
        graph[u].append(v)
        graph[v].append(u)  # leave this line out for a directed graph
    return graph

graph = build_graph(
    ["A", "B", "C", "D", "E", "F", "G"],
    [("A", "B"), ("A", "C"), ("B", "D"), ("C", "D"),
     ("C", "E"), ("D", "F"), ("E", "F"), ("F", "G")],
)
graph["C"]  # ['A', 'D', 'E']

The other classic layout is an adjacency matrix: a V × V true/false table, where V is the number of nodes, marked at row u, column v if there is an edge. It checks one edge in one step, but always takes V² cells, and listing a node's neighbours reads a whole row. Most real graphs are sparse (a bus stop has a few neighbours, not thousands), so the adjacency list is the default.

Grids are graphs too

A maze, a game board, a map of land and water, an image: all arrive as a 2D grid. Every cell is a node. Its neighbours are the cells up, down, left and right, if inside the grid and not a wall.

Skip the adjacency list for a grid. Compute neighbours on the spot: add four direction offsets to the row and column, and keep results that land inside the grid on an open cell.

const DIRS = [[-1, 0], [1, 0], [0, -1], [0, 1]]; // up, down, left, right

function gridNeighbours(grid, r, c) {
  const result = [];
  for (const [dr, dc] of DIRS) {
    const nr = r + dr;
    const nc = c + dc;
    const inside = nr >= 0 && nr < grid.length && nc >= 0 && nc < grid[0].length;
    if (inside && grid[nr][nc] !== "#") result.push([nr, nc]);
  }
  return result;
}

const grid = ["..#.", "....", "...#"];
gridNeighbours(grid, 1, 1); // [[0, 1], [2, 1], [1, 0], [1, 2]]
gridNeighbours(grid, 0, 3); // [[1, 3]]

DIRS = [(-1, 0), (1, 0), (0, -1), (0, 1)]  # up, down, left, right

def grid_neighbours(grid, r, c):
    result = []
    for dr, dc in DIRS:
        nr, nc = r + dr, c + dc
        inside = 0 <= nr < len(grid) and 0 <= nc < len(grid[0])
        if inside and grid[nr][nc] != "#":
            result.append((nr, nc))
    return result

grid = ["..#.", "....", "...#"]
grid_neighbours(grid, 1, 1)  # [(0, 1), (2, 1), (1, 0), (1, 2)]
grid_neighbours(grid, 0, 3)  # [(1, 3)]

An R × C grid has R × C nodes and at most 4 edges each, so it is sparse. Every graph algorithm in this module works on it unchanged: wherever the code says "for each neighbour", call gridNeighbours.

A graph problem rarely says "graph". When you see things plus connections between pairs (stops and roads, people and friendships, cells and their sides, tasks and "must come before"), draw dots and lines, then reach for a graph algorithm.

Common mistakes

In an undirected graph, every edge goes into both lists. With only graph[u].push(v), B reaches D but D cannot reach B, and a search from D silently misses half the map. "Roads connect" means two-way; "depends on" or "follows" means one-way.

If you create lists only while reading edges, a node with no edges gets none. Then graph[node] is undefined in JavaScript or a KeyError in Python, and the node is missing when you count components. Create an empty list for every node first.

Grid cells are grid[row][col]: row first, the y direction. Thinking in (x, y) leads to grid[x][y], which breaks on non-square grids. Use r and c, and check rows against grid.length, columns against grid[0].length.

Routing apps store roads as weighted directed graphs; package managers store "needs" links between libraries as directed graphs. Social networks, web links and a paint program's flood-fill bucket are graphs underneath.
