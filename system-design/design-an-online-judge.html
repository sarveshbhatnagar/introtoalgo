Design an Online Judge

Design a coding practice and contest site: sandboxing untrusted code, a submission queue with polling, a live leaderboard and the spike at contest start.

You write a solution and press Submit. Seconds later the site says "Accepted, 48 ms" or "Wrong Answer on test 12". In a weekly contest, tens of thousands do this at once while a live leaderboard reorders. Think LeetCode.

The core action is alarming: strangers send you programs and you run them. A good answer treats every submission as hostile, keeps slow judging off the request path, and plans for a spike whose start is known to the second. The steps follow A Framework for Any Design.

#Clarify the problem

  • Functional: view problems; submit code in several languages; run sample tests; get a verdict (accepted, wrong answer, time or memory limit, runtime or compile error); contests with a live leaderboard.
  • Non-functional: untrusted code fully isolated; deterministic verdicts; verdict in 10 s at p95, 30 s in contests; no accepted submission lost; leaderboard a few seconds stale at most; problem pages load instantly at contest start.
  • Out of scope: discussions, plagiarism detection, problem authoring tools, payments.

#Estimate the scale

A day has 86,400 seconds. A submission needs about 2 seconds of CPU: compiling plus about 50 hidden tests.

  • Normal day: 1 million ÷ 86,400 ≈ 12 submissions a second: 12 × 2 = 24 busy cores.
  • Contest: 50,000 people × 8 submissions or runs = 400,000 in 90 minutes (5,400 s): about 74 a second, with bursts of 3x: 220 a second.
  • Problem pages: 50,000 loads in the first 10 seconds is 5,000 a second, identical for everyone.
  • Storage: 1 million × 2 KB of code = 2 GB a day, about 730 GB a year. Test data: 3,000 problems × 10 MB = 30 GB, small enough to cache on every judge.

Estimate: Status polls while waiting

At the contest peak, each waiting browser polls once a second for its verdict. How many polls a second is that?

You know
  • 220 submissions a second
  • About 10 seconds from submit to verdict
  • One poll per second per waiting submission

Show the working
  1. Waiting at any moment (Little's law): 220 a second × 10 s = 2,200
  2. Each polls once a second: 2,200 polls a second

Estimate 2.2 thousand/s (anything from 700/s to 7 thousand/s is a good answer)

Only waiting submissions poll, not all 50,000 users.

Your turn: Define the API

Write endpoints for submitting, getting the verdict, and the leaderboard. Does submit wait for the verdict?

Compare with a model answer

No. Submit returns 202 Accepted with an id at once, and the client polls for the verdict. The leaderboard is a paged read plus "my rank".

GET  /v1/submissions/{id}                   poll; the server suggests Retry-After: 1
  200 { "status": "judging", "tests_done": 31, "tests_total": 50 }
  200 { "status": "done", "verdict": "accepted", "time_ms": 48, "memory_kb": 9216 }
 
GET  /v1/contests/{id}/standings?page=1     top 50 per page, cached for 5 s
GET  /v1/contests/{id}/standings/me         { "rank": 812, "solved": 2, "penalty": 3120 }

The decision worth arguing is polling against pushing the verdict. Polling is a plain read that works through any proxy and retries trivially, and it is only 2,200 reads a second at peak. Pushing (see Realtime Communication) saves those reads but needs 50,000 open connections and routing for each verdict. Start with polling; Retry-After lets the server slow clients under load.

Your turn: Model the data

Sketch records for problems, submissions and standings. What is the leaderboard's source of truth?

Compare with a model answer

Problems with versioned test files; one row per submission; per-user, per-problem contest results. Submissions are the source of truth; the leaderboard is derived and rebuildable.

#Model the data

Records (relational)
problems      (problem_id PK, slug, statement_html, time_limit_ms, memory_mb,
               tests_version INT)          -- tests live in object storage, by version
 
submissions   (submission_id PK, user_id, problem_id, contest_id NULL,
               language, code_key,         -- code in object storage, about 2 KB
               status,                     -- queued | judging | done
               verdict NULL, time_ms, memory_kb, tests_version,
               created_at, judged_at)
  INDEX (user_id, problem_id, created_at)
 
contest_results (contest_id, user_id, problem_id,      PK (contest_id, user_id, problem_id)
                 wrong_before_accept INT, accepted_at TIMESTAMP NULL)

Volumes are modest (12 rows a second, a few hundred in a contest), and scoring needs a small transaction: "record this accept only if it is the first". A relational database fits, partitioned by user if it outgrows one primary. Code and tests go in object storage. Recording tests_version makes a verdict repeatable: a rejudge uses new tests on purpose, not by accident.

Your turn: High-level design

Where does a submission wait, where does code run, and how does the verdict reach the user and the leaderboard?

Compare with a model answer

The API stores the submission and enqueues its id. Sandboxed judge workers run it against cached tests and write the verdict, which the client polls for. A contest accept updates an in-memory leaderboard.

#Deep dives

#Running untrusted code

Assume every submission is an attack. Each threat needs its own defence:

  • Infinite loops: a CPU-time limit per test, plus a wall-clock limit (say twice the CPU limit) for programs that sleep or block.
  • Eating memory, forking, huge output: caps of 256 MB, 64 processes and a few MB of output, enforced by kernel resource controls such as cgroups on Linux.
  • Reading the answers: a read-only system image, a small temp directory, and only the input on standard input. The judge compares outputs outside.
  • Sending data out: an empty network namespace.
  • Kernel exploits: a system-call filter and a non-root user.

Plain process with limitsStarts in milliseconds; simplest to build.Shares the file system and kernel with the judge. One missed rule exposes the machine.Never for code from strangers.

Run each submission in a fresh container inside a micro-VM (Firecracker is one example) from a warm pool, destroyed afterwards so nothing carries over to the next. Pin each sandbox to its own CPU core: two submissions sharing a core slow each other, and the same program could pass on Monday and time out on Tuesday.

Putting the expected output inside the sandbox

If the program can read the expected output, it prints it and passes every test. Feed only the input in; compare outside.

#The queue and getting results back

Keep slow, retryable judging out of the HTTP request. The API writes the row first, then enqueues its id. If the enqueue fails, a sweeper re-enqueues rows still queued after a minute, so nothing accepted is lost.

The queue (see Message Queues and Streams) delivers at least once. A worker holds a 15-second lease, renews it every 5 seconds, and acknowledges only after writing the verdict and score. If it dies, another worker rejudges within 15 seconds; a 60-second lease would break the 30-second target. Judging twice is harmless because the effects are idempotent: the verdict write requires the row not be done, and the leaderboard counts only the first accept per user and problem. That is exactly-once in effect, as in Design a Job Scheduler.

Use separate queues for contest, practice and "Run". Workers prefer the contest queue, so practice traffic never delays a contest verdict. Limit each user to one submission every 5 seconds: at 50,000 users that caps the worst case at 10,000 a second and stops scripts flooding the queue.

#The live leaderboard

Rank by problems solved (more is better), then penalty (less is better). Penalty sums, over solved problems, the seconds from start to accept plus 300 for each earlier wrong submission. Zoe solved A at 460 seconds after one wrong try: 460 + 300 = 760.

Make it one sortable number: score = solved × 10,000,000 − penalty. A penalty never reaches 10 million seconds (about 115 days), so more solved always wins. Keep scores in an in-memory sorted set such as Redis's: updates and "my rank" are O(log n), the top 50 is a range read, and 50,000 entries × 100 bytes is 5 MB.

Submissions finish out of order: a wrong answer sent at 400 s can be judged after the accept sent at 460 s. So the verdict transaction recomputes the user's contest_results row in submit order, not judge order. The worker then sets the score (not an increment), so a redelivered job writes the same value.

The load is reads. 3 of 4 problems solved on average is 150,000 accepts ÷ 5,400 s ≈ 28 writes a second; everyone refreshing every 30 seconds is 50,000 ÷ 30 ≈ 1,700 reads a second. Render each standings page every 5 seconds and serve it from a cache or CDN; only "my rank" hits the sorted set. If the set is lost, rebuild it from about 50,000 contest_results rows in seconds. The leaderboard case study covers much larger scale.

#The spike at contest start

This spike is on the calendar. Use that.

  • Pages: render problem pages ahead and publish them to the CDN at the start, so 5,000 loads a second never reach the API. Before the start the API returns 403, by the server's clock, not the browser's.
  • Judges: scale from 24 busy cores to about 600 fifteen minutes early, warm the sandbox pool, and copy test data to every worker.
  • Queue: it absorbs bursts. With 3,000 jobs queued and 300 finished a second, the newest waits about 10 seconds, inside the target. Watch queue age, not just length.
  • Sign-in: warm session caches so 50,000 logins at 10:00 do not all hit the user database.

#Bottlenecks and failures

At 10x (a 500,000-person contest), judging needs about 4,400 busy cores at peak, reserved for contest hours. The CDN and the 50 MB sorted set cope unchanged. The submissions database sees about 2,200 new rows a second plus as many verdict updates, so partition it by user.

#What a strong answer sounds like

LevelWhat the answer does
JuniorRuns code with a timeout, stores results, adds a queue when asked about load.
MidUses limited containers with no network, an async queue with polling, and a sorted set leaderboard.
SeniorLists attacks and defences, argues for a VM boundary, makes retries safe with leases and conditional writes, scales ahead of a known start, and caches standings because reads dominate.

#Follow-up questions

#A test case was wrong. How do you rejudge a contest?

Publish a new tests_version, enqueue affected submissions on a low-priority queue, and recompute contest_results and the leaderboard from the new verdicts.

#How do you support "interactive" problems?

A trusted interactor outside the sandbox talks to the submission over pipes and decides the verdict.

#How do you make time limits fair across languages?

Time reference solutions per language on the judge hardware and set per-language limits, or multiply a base limit by a per-language factor.

#How would you freeze the leaderboard for the last 15 minutes?

Keep updating the sorted set but serve a snapshot from the freeze; users still see their own verdicts. Unfreeze by publishing the live set.

#How would you push verdicts instead of polling?

Each API server holds its users' WebSockets; workers publish verdicts to a channel keyed by user, and the server holding that socket forwards it. Keep polling as the fallback.
