Mock Interview Practice

How to run a timed 45-minute mock system design interview alone or with a partner, review it, and which practice prompts to use.

A mock interview is a timed, spoken run through a system design question, done alone or with a partner, using the same time split as the real interview. It exists because reading case studies trains you to recognise a design, while an interview tests whether you can build and explain one out loud, on time, while someone interrupts you.

Without mocks, the first time you speak a design under a clock is the real interview, and people who have only read tend to run out of time before the hard part.

#How to run a mock interview

A mock has three phases: setup, the 45 minutes themselves, and a review afterwards. The 45 minutes follow the real interview's structure, so the timings below are the ones to hold yourself to.

#Setup

Pick a prompt you have not seen, and decide in advance whether you have a partner. With a partner, give them the prompt and a short facts sheet with the answers to the questions you are likely to ask, such as the number of users and whether data may be lost. Without one, record yourself and talk as if someone were listening.

#The 45 minutes

Every mock should include the same four things, because every real interview does: clarifying questions and a rough estimate in the first eleven minutes, a design that works from end to end by about minute 27, a deep dive on the part you choose as the hardest, and a closing statement of what is weakest. The API and data model are expected in most interviews, but you can keep them to a few lines each unless the interviewer asks for more. The deep dive is where most of the time and most of the marks are, so protect it: if you are still on the data model at minute 20, stop and move on.

#The review

The review is where the learning happens, and it is the step people skip. Replay the recording at normal speed and note the time at which each phase actually started, then tick the checklist at the end of this page. Pick one thing to change in the next mock. A partner should give one thing you did well and two things to fix, so that the feedback stays usable.

#Choosing the next prompt

A random prompt is the best default, because the real interview gives you a question you did not choose. If two reviews in a row flag the same weakness, such as never discussing failures, pick a prompt where that weakness matters and go in with the specific goal of fixing it.

#Practice prompts

Each prompt below has a model answer that lists the clarifying questions and the deep dives. Run the whole mock first and open the answer only afterwards.

Your turn: 1. A game leaderboard

A mobile game with 20 million daily players wants a global leaderboard and a "your rank" screen.

Compare with a model answer

Ask whether the board is global only or also among friends, whether it resets daily, weekly or never, how often scores change, and whether a player's rank must be exact or whether "top 45%" is enough.

The main deep dive is computing a rank quickly, which a sorted set does in O(log n). Twenty million entries at about 100 bytes each is roughly 2 GB, which fits on one in-memory node with a replica, so sharding is not the hard part. Also cover how the server rejects scores that are impossible, since the client cannot be trusted.

Your turn: 2. A parking garage system

A chain of 500 garages wants online reservations and entry gates that keep working when the network is down.

Compare with a model answer

First ask whether the interviewer wants the object-oriented class design or the distributed system. Then ask whether drivers reserve a specific spot or a type of spot such as compact or electric, and how long a spot is held for a late driver.

The deep dives are preventing double booking with a conditional decrement on the combination of garage, spot type and time slot, letting an offline gate check against a local copy of today's reservations that syncs later, and charging a driver only once even when the gate retries the payment.

Your turn: 3. A metrics dashboard

10,000 servers each send 200 metric values every 10 seconds. Engineers want charts for the last 30 days and alerts.

Compare with a model answer

Ask how fresh the charts must be, how long full-resolution data is kept, how many label combinations there are, and whether data can arrive late.

The ingest rate is 10,000 servers times 200 values divided by 10 seconds, which is 200,000 points per second, so buffer it through a stream. Store the points in a compressed time-series layout partitioned by metric and time. Build 1-minute and 1-hour rollups so that a 30-day chart reads 720 hourly points per series instead of 259,200 raw ones.

Your turn: 4. An online code judge

Users submit solutions to programming problems: 10,000 submissions an hour, and 10 times that during contests.

Compare with a model answer

Ask which languages are supported, what the time and memory limits per test are, and whether there is a contest scoreboard. Also say, without being asked, that the submitted code is untrusted.

Run each submission in a fresh sandbox with no network and with CPU and memory limits. Size the workers for contests: 100,000 submissions an hour is about 30 a second, and at 10 seconds per run that is about 300 runs in progress at once. Decide whether the result reaches the user by polling or by a push from the server.

Your turn: 5. A comment system

Readers comment under articles on a news site. Most articles get a few comments, and a breaking story gets thousands an hour.

Compare with a model answer

Ask how deeply replies nest, whether comments are shown newest first or top first, whether moderation happens before or after publishing, and whether new comments must appear live.

Store a parent id on each comment plus a path for sorting, and paginate with a cursor. Cache the first page of the breaking story for a few seconds. Make moderation asynchronous so that a comment can be hidden after it is published.

Your turn: 6. A link analytics service

Show owners of short links the clicks per hour, the top countries and the number of unique visitors. Peak traffic is 20,000 clicks a second.

Compare with a model answer

Ask whether the numbers must be fresh to the second or only to the hour, whether unique visitors must be exact or within 1%, how long raw clicks are kept, and whether bots count.

Aggregate the click stream into hourly counters per link, and keep the raw events so that you can reprocess them. Count unique visitors with an approximate sketch such as HyperLogLog, which gives under 1% error in about 12 KB per counter. Handle duplicate and late events. This extends the URL shortener.

Your turn: 7. An online auction

Timed auctions where most get a few bids, but the last minute of a popular auction gets hundreds of bids a second.

Compare with a model answer

Ask what the minimum bid increment is, whether a late bid extends the end time, what watchers see live, and when the winner is charged.

Order the bids for one auction with a conditional write that succeeds only if the new bid is higher than the current top, or give each auction a single owner. Push new top bids to watchers over persistent connections. Close the auction on the server's clock and never on the client's.

#Habits that make mock practice less useful

#Practising silently

Thinking through a design in your head skips the hardest skill, which is saying it clearly while the clock runs. Talk out loud for the whole session and record it, even when you are alone.

#Repeating one prompt until it is perfect

Doing the same question again and again trains a memorised answer that falls apart when the interviewer changes one requirement. After a first review, move to a new prompt and apply the lesson there.

#A partner who helps too much

A partner who answers every question with a hint or fills silences makes the mock easier than the real interview. Ask your partner to answer only from the facts sheet, to stay quiet while you work, and to interrupt only with the failure and scale questions described above.

#Skipping the review

A mock without a review repeats the same mistakes. Only the recording shows that you spent 18 minutes on the data model or never mentioned a failure.

#In the interview

The mock gives you a routine, and the routine matters more than any single design. Use the same opening on every prompt, so that something automatic comes out while you start thinking, and say what you are doing at each stage so the interviewer can follow.

Questions you may be asked about the process itself, and what a good answer sounds like:

  • "How would you start?" Restate the scope in one sentence, then ask a few questions about features before asking about scale. Say that you will get one path working end to end first and then go deep on the hardest part.
  • "What would you build first?" Name the smallest version that serves the main use case, for example the write and read path for a single record type. Explain that you would add the other features and the scaling work after it works.
  • "Which part of your design is weakest?" Pick a real one, such as a single database that is a bottleneck, and say what you would change.
  • "How would you know it works?" Describe the metrics you would watch, such as latency percentiles, error rate and queue depth, and the alerts that would fire first when it breaks.
  • "What if the traffic grows ten times?" Name which component hits its limit first, using your estimate, and what you would do about it, such as adding replicas, partitioning or a cache.
  • "What if this component fails?" Say what users see, what recovers automatically and what needs a person. Do this for each component on your diagram, starting with the data store.
Quick check

Two of your three mock reviews say you never raise failures until the interviewer asks. What should the next session be?

  1. Right. This fixes the named gap on material you have not memorised.
  2. Not quite. Reading builds recognition, not the spoken habit.
  3. Not quite. This trains one memorised answer instead of the habit.

You are practising alone. Your design gets awkward at minute 20, and you notice that a different answer to an earlier clarifying question would make it simpler. What should you do?

  1. Not quite. The real interviewer will not let you change it, so you would be practising something you cannot do.
  2. Right. Writing the assumptions down first is what keeps solo practice honest.
  3. Not quite. This avoids the awkward part, which is the part worth practising.
