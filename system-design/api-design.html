API Design

Design endpoints the way interviewers expect: REST resources, cursor pagination, idempotency keys, versioning, errors, and when RPC or events fit.

A diner taps "Book" for 4 people at 19:30. The server books a table, but the phone loses signal before the reply arrives. The app times out and retries, and the server books a second table. If 0.5% of the reservation system's 1 million daily bookings lose their reply, that is 1,000,000 × 0.005 = 5,000 duplicates a day.

That is an API design bug. Settle the parts that are expensive to change: resources, paging, retries, errors, versions.

Optional in the interview

Write out the API only if the interviewer asks, an API choice shapes the design, or time permits. Otherwise name the main calls in a sentence and move on.

#Resources and methods

Each functional requirement becomes an endpoint. In REST, URLs name things (nouns) and HTTP methods say what you do to them. Spend at most 3 minutes here (see the framework).

Reservation API (version 1)
GET    /v1/restaurants/{id}/availability?date=2026-12-04&party_size=4
         200  { "slots": [ { "time": "19:00", "tables_free": 2 }, ... ] }
 
POST   /v1/reservations          Idempotency-Key: 6f1c...e2
         body { "restaurant_id": 42, "time": "...", "party_size": 4 }
         201  { "id": "r-5521", "status": "confirmed" }
         409  slot_taken     422  invalid_party_size     429  rate_limited
 
GET    /v1/reservations/{id}                  200 | 404
DELETE /v1/reservations/{id}                  204 | 404
GET    /v1/users/me/reservations?limit=20&cursor=...
         200  { "items": [ ... ], "next_cursor": "eyJ0IjoiMjAyNi0..." }

The client asks for a time and party size; the server picks a free table. So a blind retry books a second table instead of failing.

Methods differ on retries. GET changes nothing. PUT and DELETE are idempotent: twice leaves the same state as once. POST creates something new each time, so repeating it is dangerous.

#Idempotency keys

The fix: the client generates a unique key per user action (a random UUID when the diner taps "Book") and sends it with every retry of that action. The server stores each key with its response, and answers a repeat with the stored response instead of booking again.

Details interviewers check:

  • A repeat arriving while the first still runs must not run in parallel. The key row is claimed first, so the second waits or gets a "still in progress" error.
  • The same key with a different body is a client bug: reject it with 422.
  • Keep keys longer than any client retries (24 hours is typical).

The network can still deliver a request twice; the key makes the effect happen once (see idempotency and retries).

#Pagination

A diner's reservation history grows, so return it in pages of 20.

  • Offset: ?offset=20&limit=20 means "sort, skip 20, take 20". An item added while the diner pages shifts everything, so items repeat. And the database still reads every skipped row.
  • Cursor: the response includes next_cursor, an opaque token holding the last item's sort key, such as (created_at, id). The next query asks for items after it, which an index answers directly; inserts elsewhere shift nothing.
Two ways to page a list
OptionGood atBad atPick it when
Offset and limitSimple. Lets a user jump to page 37.Items repeat or vanish when the list changes. Deep pages get slower.Small, stable lists, or an admin table that needs page numbers.

#Errors and versioning

The status code gives the category, the body the detail: {"error": {"code": "slot_taken", "message": "Table 7 was just booked", "retryable": false}}. The app reacts to code (show other times) and retryable. 4xx means the client must change something; 5xx and 429 may succeed later, with backoff.

Adding a field is safe; clients ignore what they do not know. Removing, renaming or redefining one breaks apps that live on phones for years. For a public API, put a major version in the path (/v1/), and run old and new side by side until the old one's traffic fades.

#In the interview

Write 3 to 5 endpoints with error cases, then argue the decision that matters most. Phrases that show judgment:

  • "Booking is a POST that clients retry on bad networks, so it takes an idempotency key."
  • "History changes while you scroll, so I'll page it with a cursor."
  • "Public clients get REST; booking emits an event for the email service, so it never waits for an email."

Expected follow-ups:

  • "Who generates the key?" The client, once per action, before the first attempt. A server-made key cannot recognize a retry.
  • "How do you rate limit this API?" Per user or API key, returning 429 with Retry-After (see rate limiting).
  • "Would you use GraphQL?" Only if many screens need different shapes of the same data.

#Common mistakes

Verbs in URLs

POST /createReservation and GET /getUserReservations hide the resources. Use POST /reservations and GET /users/me/reservations: the method is the verb.

Storing the key outside the transaction

Key in a cache, booking in the database: a crash between them books with no key, and the retry books again. Use one transaction.

Quick check

A list is paged with offset, 20 per page. A diner reads page 1, a new item is added at the top, then they load page 2. What do they see?

  1. Not quite. Offsets count from the top, and the top just moved.
  2. Right. Everything shifted down by one, so position 21 holds the old 20th item.
  3. Not quite. Nothing fails; the result is silently wrong.

Which request is safe for a client to retry with no extra mechanism?

  1. Not quite. Each POST creates a new reservation.
  2. Right. Deleting twice leaves the same state as once. The second call may return 404, but nothing new happens.
  3. Not quite. Repeating it could charge twice. It needs an idempotency key even more.

A list is sorted by an indexed column. With offset=100000&limit=20, about how many rows does the database read?

  1. Not quite. That is what a cursor query reads. Offset still reads the rows it skips.
  2. Right. 100,000 skipped plus 20 returned: 100,020 rows.
  3. Not quite. Walking the index, it stops after offset + limit rows.
