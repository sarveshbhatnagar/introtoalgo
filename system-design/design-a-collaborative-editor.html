Design a Collaborative Editor

Let many people edit one document at once: merging edits with OT or CRDTs, one server per document, an operation log with snapshots, and cursors.

Three people have one document open. Ana fixes a typo while Ben adds a sentence above it and Chen watches both cursors move. Each types into their own copy with no delay, and a moment later every copy matches. Nobody presses Save; no edit is lost.

The boxes are simple; the core problem is not: two edits made at once on the same text must merge into one result on every screen, whatever order they arrive in. The steps follow A Framework for Any Design; try each "Your turn" box before you read on.

#Clarify the problem

  • Functional: type instantly; see others' changes and cursors live; work offline; browse history.
  • Non-functional: copies converge; remote edits within 200 ms in one region; no acknowledged edit lost; up to 100 editors per document; opens in under a second.
  • Out of scope: comments, search, sharing screens, rich-text layout.

#Estimate the scale

The client batches about 100 ms of typing into one operation, such as "insert the at position 4". Assume one operation every 2 seconds per open document, counting pauses.

Estimate: Operations per second at peak

How many operations per second reach the servers at peak?

You know
  • 2 million people have a document open at peak
  • Each sends one operation every 2 seconds on average

Show the working
  1. 2,000,000 ÷ 2 s = 1,000,000 operations a second

Estimate 1 million/s (anything from 300 thousand/s to 3 million/s is a good answer)

Each must be ordered against the others on the same document. That is the whole design.

  • Daily volume: open an hour a day, 3,600 ÷ 2 ≈ 2,000 operations per user; × 20 million users = 40 billion, averaging 40 × 109 ÷ 86,400 ≈ 460,000 a second, about half the peak.
  • Fan-out: 2 editors per document means 1 million open documents. Each operation is acked to its author and sent to one other: 2 million messages out a second.
  • Connections: 2 million WebSockets. At an assumed 50,000 per server (load test it), 40 servers.
  • Snapshots: 1 billion documents × 50 KB = 50 TB for the latest copies.
Estimate: Operation log per day

How much operation log is written per day?

You know
  • 40 billion operations a day
  • About 100 bytes per operation (position, text, author, revision, time)

Show the working
  1. 40 × 109 × 100 B = 4 × 1012 B = 4 TB a day
  2. Kept for 30 days: 120 TB, or 240 TB on a leader and its replica

Estimate 4 TB (anything from 1 TB to 15 TB is a good answer)

The log grows far faster than the documents, so fold it into snapshots.

Your turn: Define the API

Write the editing messages. What must an operation carry?

Compare with a model answer

HTTP loads the document at a revision; then a WebSocket. Each operation carries its base revision and a client sequence number. The server acks with the final revision.

#Define the API Optional

Optional in the interview. Sketch the API only if the interviewer asks, if an API choice shapes the design, or if time permits. Otherwise say "I'll skip the detailed API unless you want it" and go to the data model.

HTTP and WebSocket messages
GET /docs/{id}
  200 { "rev": 1042, "content": "...", "title": "Q3 plan" }
  403 Forbidden    no access     404 Not Found
 
WSS /docs/{id}/live?since=1042
  client -> server
    { "type": "op", "base_rev": 1042, "client": "c7", "seq": 17,
      "ops": [ { "insert": "the ", "at": 4 } ] }
    { "type": "cursor", "rev": 1043, "at": 88 }
  server -> client
    { "type": "ack", "seq": 17, "rev": 1043 }
    { "type": "op", "rev": 1044, "author": "ben", "ops": [...] }
    { "type": "cursors", "users": [ { "user": "ben", "rev": 1044, "at": 12 } ] }
    { "type": "reload" }   since is older than the kept log; fetch a snapshot

The decision worth arguing: each client keeps at most one operation in flight. Until seq 17 is acked, new typing is buffered. The server only adjusts it against what was committed since its base_rev. (client, seq) makes resends harmless: the server drops any seq it already applied.

Your turn: Model the data

What do you store so a document opens fast, replays for history, and catches up after a reconnect?

Compare with a model answer

An append-only operation log keyed by document and revision; periodic full-text snapshots; a metadata record per document. Presence is not stored.

#Model the data

Records
documents                         -- metadata, relational
  doc_id        BIGINT PRIMARY KEY
  owner_id      BIGINT
  title         VARCHAR(200)
  snapshot_rev  BIGINT            -- newest snapshot
  updated_at    TIMESTAMP
 
doc_ops                           -- about 100 B a row
  doc_id        BIGINT
  rev           BIGINT            -- 1, 2, 3 ... per document, no gaps
  author_id     BIGINT
  client_id     VARCHAR(16)
  client_seq    INT
  op            BYTES             -- the transformed operation
  created_at    TIMESTAMP
  PRIMARY KEY (doc_id, rev)
 
snapshots  -- blob store, key "docs/{doc_id}/{rev}", about 50 KB

Every access (append the next revision, read operations after 1000, fetch the newest snapshot) stays inside one document, so partition by doc_id.

Put doc_ops in a store with one leader per shard and a unique primary key, such as a sharded relational database. "Insert revision 1043" then fails cheaply if 1043 exists, which stops two servers writing the same revision. At 1 million inserts a second and an assumed 20,000 per shard: 50 shards, each with a synchronous replica so an acked operation survives losing the leader. Write-once snapshots go to blob storage.

Your turn: High-level design

Sketch the boxes. Where do WebSockets end, and which server orders document 42's operations?

Compare with a model answer

Gateways hold the sockets and forward to the document's one owning server, chosen by consistent hashing. It orders, transforms, logs and broadcasts. A compactor writes snapshots.

#High-level design

The cheapest place to order a document's operations is one process's memory. So each open document has one owner: a document server holding its text, recent operations and editors.

#Deep dives

#Merging concurrent edits: OT or CRDT

The document is dog. Ana inserts s at 3; at the same moment Ben inserts my at 0. Applied as sent, Ana gets my dogs, but Ben applies "insert s at 3" to my dog and gets my sdog. The copies have diverged.

Operational transformation (OT) fixes the position before applying. For two inserts: if the other landed before yours, shift yours right by its length; at the same position, the one committed first goes left. Deletes need matching rules (overlapping deletes shrink each other), which is where implementations get subtle.

The central server keeps OT manageable: with one order, the transform only has to make A then B-transformed equal B then A-transformed. Peer-to-peer OT must meet a much harder second condition, which several published algorithms were later shown to break.

A CRDT (conflict-free replicated data type) avoids positions. Every character gets a permanent unique id, such as (ben, 1), and an insert says "after the character with id X": Ana's s goes after the id of g. Ids never shift, so operations apply in any order, repeats change nothing, and every copy ends at my dogs; ties are ordered by id. A deleted character stays as a hidden tombstone, since a later insert may point at it.

#One server per document

The gateways hash the document id onto a consistent-hash ring of document servers. Membership lives in a small strongly consistent store that gateways cache and watch. Adding a 41st server moves about 1/41 of documents (1,000,000 ÷ 41 ≈ 24,000), where hash mod N would remap almost all.

A server paused by garbage collection may wake still believing it owns a document.

  • A lease makes this rare: an owner stops serving when its lease lapses, before reassignment.
  • The log as a fence makes it harmless: each revision is written once, so two servers cannot both commit 1045. The loser checks the ring and steps down.

Consensus and leader election explains why a lease alone is not enough.

#Storing operations and compacting them

The compactor writes a snapshot every 1,000 operations, so opening reads one 50 KB snapshot and at most 999 operations, about 150 KB. Keep operations 30 days (120 TB). Keep the newest snapshot plus one per editing session, not all of them (40 million a day, 2 TB). A snapshot is a cache of the log: a bad one is rebuilt from the previous snapshot and the operations.

#Cursors, reconnects and offline work

Cursors are not operations. They live in the owner's memory, never logged. A cursor carries its revision, so when Ben inserts 3 characters before Ana's cursor, the same transform shifts it right by 3. Cursors hurt big documents: 100 editors sending 10 a second to 99 others is 100 × 10 × 99 = 99,000 messages a second. Instead the owner sends each client one combined update every 500 ms: 100 × 2 = 200 a second.

Reconnecting reuses the edit path: send since=1044, transform unacked operations against what arrives, and resend them with their original (client, seq).

Offline editing is a long reconnect: the edits go as one operation with the old base_rev. If that revision is older than the 30-day log, the server answers reload; the client fetches a snapshot and does a three-way merge, or saves a copy.

Sending the whole document on every save

"Upload the full text; last write wins" loses every concurrent edit but one and sends 50 KB per batch instead of 100 bytes. Send operations and merge them.

#Bottlenecks and failures

At 10x (10 million operations a second), add gateways and document servers; the log grows to about 500 shards. The real limit is one document's owner. At 100 editors, 100 × 0.5 = 50 operations a second to 99 others is about 5,000 messages a second: easy. 10,000 readers need a read-only stream through a separate fan-out tier.

Acknowledging before the operation is logged

If the owner acks then dies before logging, the client drops the operation and the new owner never sees it. Log on two machines, then ack.

#Follow-up questions

#How does undo work with several editors?

Undo only your own edits: keep each operation's inverse, transform it against everything since, and send it as a new operation.

#How do you add formatting such as bold?

Add range operations, such as "bold from 10 to 18". The transform shifts the range ends when text changes before or inside them.

#Someone loses access while editing. What happens?

The metadata service tells the owner, which drops that user's socket and rejects their pending operations. Every operation passes the owner, so that is enough.

#How would you run this in several regions?

Each document's owner lives in one region. Distant editors type with zero delay but see others' edits a cross-region round trip later. If two regions must accept writes for one document, use a CRDT.

#How do you show last Tuesday's version?

Take the nearest earlier snapshot and, within 30 days, apply operations up to that moment. Older versions are limited to kept snapshots.
