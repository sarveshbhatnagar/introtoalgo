Transactions and Isolation

ACID in plain words, the race conditions isolation levels stop, locking choices, and how sagas and the outbox pattern replace distributed transactions.

A concert has one ticket left. Two fans press "buy" in the same 10 ms. Both requests read remaining = 1, both charge a card, both write remaining = 0. Two people paid for one seat, and the database never reported an error.

Each request was correct on its own; the bug is in how they overlapped. Isolation levels decide which overlaps the database allows.

#The idea

A transaction groups several reads and writes so the database treats them as one unit. ACID names its four promises:

  • Atomic: all of the writes happen, or none do. A crash halfway leaves nothing behind.
  • Consistent: your rules hold before and after. Mostly your job; constraints such as UNIQUE and CHECK (stock >= 0) help.
  • Isolated: concurrent transactions do not see each other's half-done work. How strictly is set by the isolation level; the default is rarely the strictest.
  • Durable: once committed, the data survives a crash, because it is in a log on disk (and often on replicas).

Stricter isolation means more waiting or more retries. Choose the weakest level that stops the races your data can have.

Read committed is a common default. Snapshot isolation gives each transaction a frozen view as of its start; some databases also abort a transaction whose row changed underneath it, others let the later write win. Names differ between products, so check what yours does. Serializable means the result equals some one-at-a-time order, at the cost of more aborts to retry.

For write skew, make the transactions collide on purpose: lock the team row (SELECT … FOR UPDATE on teams) before counting admins, or run that one transaction as serializable.

#Across services: 2PC and sagas

An order touches the orders database, payments and inventory. No single transaction spans them.

Two-phase commit (2PC) adds a coordinator. Phase 1: it asks every participant to prepare (do the work, hold the locks, promise to commit). Phase 2: if all voted yes, it tells them to commit; otherwise to abort. It is atomic, but if the coordinator dies after "prepare", participants hold their locks until it returns. It costs two round trips per transaction, and every participant must support it.

A saga gives up atomicity across services. It runs a chain of local transactions, each publishing an event that triggers the next. If a step fails, compensating actions undo earlier steps: refund the card, release the seat. Others can see the middle states ("paid, not yet reserved"), so design for them.

Each step must update its database and publish an event. As two separate writes, a crash between them loses one. The outbox pattern fixes this: write the event into an outbox table in the same local transaction, and let a relay publish rows from the outbox afterwards.

The usual default across services is a saga with outboxes and idempotent consumers. Reach for 2PC only when the participants are a few databases that support it, in one data center, and a visible in-between state is unacceptable.

#Numbers worth remembering

  • A short transaction on one database: about 1 to 10 ms. Locks held that long are cheap; locks held across a network call or a user's think time are not.
  • 2PC adds at least two round trips per transaction, plus a durable log write at each step.
Estimate: Is optimistic locking a good fit?

On average, how many other committed updates land on the same row between one transaction's read and its write?

You know
  • One hot row is updated 200 times a second
  • Each transaction takes 10 ms between its read and its write

Show the working
  1. 10 ms = 0.01 s
  2. 200 × 0.01 = 2 other updates in each transaction's window

Estimate 2 (anything from 0.7 to 6 is a good answer)

With about 2 rivals in every window, most attempts fail their version check and retry. Use an atomic update or a lock for this row.

#In the interview

Bring this up whenever two users can change the same thing (stock, seats, balances) or one action spans services. Name the race, then the fix: "Two buyers can read the same stock, so I decrement with a conditional update and treat zero rows as sold out."

Follow-ups you should expect:

  • "What if the compensation fails?" Retry it; it must be idempotent. After several failures, alert a human.
  • "Why not publish the event, then write the database?" A crash between the two leaves an event for an order that does not exist. The outbox makes them one write.

#Common mistakes

Read in the app, write back the result

Reading a counter, adding one in code and writing it back is the lost update. Do the arithmetic in the database, or check a version.

Assuming the default level is serializable

Many databases default to read committed. Write skew and lost updates pass through it without an error.

Quick check

Each of two reviewers checks that the article has another reviewer, then unassigns themselves. Both commit under snapshot isolation. Which anomaly is this?

  1. Not quite. Both read committed data. Nothing was rolled back.
  2. Not quite. They wrote different rows, so neither overwrote the other.
  3. Right. Each read the same set, then wrote a different row, breaking a rule over the set. Snapshot isolation allows it.

A seat counter is decremented 500 times a second during a sale. What is the best fix for lost updates?

  1. Not quite. With so many writers, most version checks fail and retry, adding load exactly when it hurts.
  2. Right. One atomic statement with no read-then-write gap; zero rows updated means sold out.
  3. Not quite. 2PC coordinates several databases. This is one row in one database.

A service writes an order row, then publishes an event in a separate call. What does the outbox pattern change?

  1. Not quite. The relay can still publish twice after a crash. Consumers must dedupe.
  2. Right. Both rows commit together, so an order can never exist without its event, or the reverse.
  3. Not quite. Delivery is at-least-once, so idempotent consumers are still required.
