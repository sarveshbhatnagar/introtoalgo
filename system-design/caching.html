Caching

Keep hot data in memory so most reads skip the database: where caches sit, how to keep them fresh, what to evict, and how to talk about it in an interview.

An online shop's product page reads one database row per view: 400 reads a second on a normal day. During a sale it is 4,000 a second at about 5 ms each, and the database times out, though nearly every read asks for one of the same few hundred products.

A cache remembers answers: the first request for product 42 goes to the database, and the next few thousand get a copy from memory in half a millisecond.

#The idea

A cache is a small, fast store of copies of data that is expensive to fetch or compute. Check it first. On a hit, return the copy. On a miss, read the source and keep a copy.

It works because traffic is lopsided: a few keys get most reads. At a 90% hit rate, the database sees 4,000 × 0.1 = 400 reads a second during the sale, a quiet day's load. Average latency drops too: 0.9 × 0.5 ms + 0.1 × (0.5 + 5) ms = 1 ms, against 5 ms.

The price: two copies that can disagree. Most of caching is deciding how much disagreement you can live with.

#Hit, miss and invalidation

The most common pattern is cache-aside: the application talks to both the cache and the database. Watch what a write must do to the cached copy.

#What to drop when memory is full

  • LRU (least recently used) drops the key untouched for longest. The usual default: recent use predicts the next.
  • LFU (least frequently used) keeps long-term favourites, but last week's hot key can squat in memory.
  • A TTL removes entries too old to trust, even with room to spare: a safety net for any invalidation you miss.

#The stampede

A popular key expires, and every request before the refill misses and runs the same query. If rebuilding the home page feed takes 200 ms at 4,000 requests a second, 4,000 × 0.2 = 800 identical queries hit the database. That cache stampede can take down the database the cache protects.

The fix: one request rebuilds the value while the rest wait or use the old one (a lock per key, or request coalescing in each server). Also refresh hot keys before they expire, and add random jitter to TTLs so keys written together do not expire together.

#Numbers worth remembering

  • Local memory read: about 100 ns. Round trip in a data center: about 0.5 ms, most of a networked cache read.
  • Indexed database read: about 1 to 10 ms, more under load.
  • One in-memory cache node: on the order of 100,000 simple reads a second.
  • Sizing: hot items × bytes each. 10 million products at 2 KB is 107 × 2 × 103 = 20 GB: a large node or small cluster.

From 90% to 95% hits halves the database load.

#In the interview

Bring up a cache when reads dominate (10 per write or more) and some keys are much hotter, or a result is expensive and often requested. Give the numbers and the staleness you accept. Caching every box by reflex is a red flag.

Expected follow-ups:

  • "How do you keep the cache consistent?" Delete on write, plus a TTL. Data that must never be stale is read from the database.
  • "What if one key is extremely hot?" Copy it into each app server's memory for a few seconds.
  • "Why delete instead of updating the cached value?" Two writers' updates can land in the wrong order and leave the older value. A delete cannot.

#Common mistakes

Updating the cache before the database

If the database write fails after the cache update, readers see a value that never existed. Write the database first, then delete the key.

Quick check

Reads hit a cache 80% of the time. Each cache read costs 1 ms and each database read 10 ms. What is the average read latency with cache-aside?

  1. Not quite. That is 0.8 × 1 + 0.2 × 10. A miss also pays for the failed cache lookup.
  2. Right. 0.8 × 1 + 0.2 × (1 + 10) = 0.8 + 2.2 = 3 ms.
  3. Not quite. That weights the database read by the hit rate, but hits never reach the database.

A popular key expires and 500 requests miss at once, each running the same 300 ms query. Which fix targets this?

  1. Not quite. The key expired; it was not evicted for lack of space.
  2. Right. That turns 500 identical queries into one.
  3. Not quite. Eviction only matters when memory is full.
