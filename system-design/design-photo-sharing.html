Design Photo Sharing

Design a photo app with follows and a feed: direct uploads, a resizing pipeline, CDN delivery, the metadata partition key and hot celebrity posts.

You take a photo, add a caption and tap Share. Seconds later your friends see it, sharp on a big phone and quick on a slow network. Think Instagram: upload photos, follow people, scroll a feed.

It mixes two kinds of data. Photos are huge, never change and are read millions of times: object storage behind a CDN. Metadata (posts, follows, likes) is tiny, changes constantly and must be partitioned well. Keep the two apart. The steps follow A Framework for Any Design; the feed itself is in Design a News Feed.

#Clarify the problem

  • Functional: upload a photo with a caption; follow and unfollow; home feed, newest first; profile grid; like and unlike.
  • Non-functional: no photo lost once "posted"; feed in under 200 ms; images show within about a second; posts reach followers within 10 seconds; reads stay available.
  • Out of scope: video, stories, messages, search, ads, ranking.

#Estimate the scale

A day has 86,400 seconds; peaks are 3 times the average.

  • Uploads: 50 million ÷ 86,400 ≈ 580 photos a second, about 1,700 at peak.
  • Feed loads: 10 opens per user per day is 2 billion ÷ 86,400 ≈ 23,000 a second.
  • Bytes per photo: 2 MB original plus a 30 KB thumbnail, 120 KB feed size and 250 KB full screen: 2.4 MB.
  • Ingest: 580 × 2 MB ≈ 1.2 GB/s.
  • Metadata: 500 B per post × 50 million = 25 GB a day, about 9 TB a year.

Originals are rarely read after processing, so move them to colder storage after a month.

Estimate: Image bandwidth to viewers

Each feed load shows about 10 photos at the 120 KB feed size. What is the average outgoing image bandwidth?

You know
  • 23,000 feed loads a second
  • 10 photos per load
  • 120 KB per photo

Show the working
  1. Per load: 10 × 120 KB = 1.2 MB
  2. 23,000 × 1.2 MB ≈ 28 GB/s, about 83 GB/s at peak

Estimate 28 GB/s (anything from 9 GB/s to 90 GB/s is a good answer)

A CDN's job. At 95% CDN hits the store still sends about 1.4 GB/s.

The feed JSON for those 10 posts is about 10 KB, so 99% of what a user downloads is pictures.

Your turn: Define the API

Write the endpoints for uploading and posting a photo, reading the feed, following and liking. Where do the image bytes travel?

The decision worth arguing: creating a post returns 202 and processing. The API never saw the bytes, so nothing is promised until a worker has checked them and made the sizes. Follow and like are PUT on me, so a retry is harmless.

Your turn: Model the data

Sketch the records for posts, follows and likes. Pick a partition key for each and say which reads it serves.

Compare with a model answer

Posts by author, sorted by a time-ordered id; follows stored in both directions; likes by the user who liked, with a separate count per post.

#Model the data

Metadata tables (wide-column store)
posts               PRIMARY KEY ((author_id), post_id)   -- post_id DESC
  author_id   BIGINT
  post_id     BIGINT      -- 64-bit, time-ordered
  photo_id    VARCHAR(16)
  caption     TEXT        -- up to 2,200 chars
  status      VARCHAR(10) -- processing | ready | failed | deleted
  width, height, image_version INT
 
followers           PRIMARY KEY ((followee_id, bucket), follower_id)
following           PRIMARY KEY ((follower_id), followee_id)
 
photos              PRIMARY KEY (photo_id)
  post_id     BIGINT NULL, processed BOOLEAN           -- see "upload"
 
likes               PRIMARY KEY ((user_id), post_id)     -- did I like it?
like_counts         PRIMARY KEY (post_id)
  count BIGINT,  last_offset BIGINT                     -- see "hot posts"

Every access is "one key, newest first", and nothing joins. That fits a wide-column store such as Cassandra: it partitions by key, keeps rows sorted inside a partition and takes a high write rate.

Post ids come from a time-ordered ID generator, so sorting by id is sorting by time and a cursor is "older than this id". Keep 3 replicas and use a quorum of 2 for reads and writes: since 2 + 2 > 3, every read sees the latest acknowledged write.

Your turn: High-level design

Sketch the boxes: where do bytes go on upload, what makes the three sizes, where are images served from, and when does a post reach followers?

Compare with a model answer

Bytes go to a photo store; its event wakes resize workers, which mark the post ready and trigger fan-out. A CDN serves images; the API serves metadata.

#High-level design

#Deep dives

#The media path: upload, resize, serve

Upload. Signed URLs are explained in Blob Storage. Don't trust bytes that skipped your code: the URL fixes the key, maximum size and content type, and the post stays processing until a worker has decoded the file. A file that does not decode is deleted and the post marked failed.

Ordering. The worker can finish before the post exists and find nothing to mark. So both sides write the photo's row with a compare-and-set: the post request sets post_id only if empty (this is also the 409), and the worker sets processed. Whichever lands second sees both, marks the post ready and starts fan-out, exactly once.

Resize. At 0.2 CPU-seconds per photo: 580 × 0.2 ≈ 120 cores on average, 1,700 × 0.2 ≈ 350 at peak. Autoscale on queue depth, which is what delays posts.

When to make the resized copies

Resize eagerly, but pick the size list with care: backfilling one year is 18 billion × 0.2 s = 3.6 billion CPU-seconds, about 4,000 cores for 10 days.

Serve. Each image URL holds the photo id, size and a version: /p7001/t.v1.jpg. A URL's content never changes, so the CDN may cache it for a year; re-processing writes v2 and nothing needs purging. A regional origin shield turns hundreds of edges missing on one new photo into one store request. Private accounts get short-lived signed CDN URLs (see CDNs).

#Metadata and the partition key

One key must serve a profile grid (one author, newest first) and a feed page (10 posts by different authors).

Partition key for posts

By post idLoad spreads evenly; a feed page is 10 direct lookups.A profile grid needs a second table kept in step.Profiles are rare.
By author, sorted by post id Usual defaultA profile is one partition read; feed entries carry the author, so a feed page is still 10 lookups.A famous author's partition gets heavy reads; feed entries are 16 bytes instead of 8.Profiles are a main screen, as here.

Partition by author. A heavy poster's partition is 10,000 posts × 500 B = 5 MB, which is small; hot reads are a caching problem. Follows are written twice, because "who follows Mia" (fan-out) and "whom does Leo follow" (pulling big accounts) need different partitions. A 50-million-follower list is 50 × 106 × 16 B = 800 MB, too big for one partition, so followers adds a bucket per 1 million followers: 50 partitions for the biggest account, 1 for everyone else.

#Hot celebrity posts

An account with 50 million followers posts. Four things heat up.

  • Fan-out. 50 million inserts at 200,000 a second take 250 seconds. Use the news feed hybrid: above 100,000 followers, followers pull at read time.
  • The post record. 20% of followers opening it within an hour is 10 million ÷ 3,600 ≈ 2,800 reads a second of one key. The post never changes, so cache it, plus a few-second copy in each API server.
  • The image. The CDN takes the reads; the origin shield stops the first burst of misses.
  • Likes. 5% liking in 10 minutes is 2.5 million ÷ 600 ≈ 4,200 likes a second on one post.

Likes need the most care. The likes table is partitioned by the user who liked, so writes spread out. The count is separate: each like also goes to a stream partitioned by post id, and the aggregator owning that partition sums a post's likes for one second, then writes count += n once. 4,200 updates a second become 1.

The stream delivers at least once, so after a crash events may replay. The aggregator stores the last applied offset in the count's row, in the same write, and skips anything at or below it; one aggregator owns all of a post's events, in order. A nightly recount from likes repairs other drift.

One counter row updated on every like

count = count + 1 on every like puts 4,200 writes a second on one row, all fighting for the same lock. Batch the increments and keep the per-user like records elsewhere.

#The feed: what photos change

Reuse the news feed design, with three changes:

  • Fan-out starts when the post is ready, not when it is created.
  • Feed entries hold (author, post) pairs to fit the partition key.
  • The app picks the image size for its screen and prefetches the next page's images. With 99% of bytes being images, that beats a faster feed query.

#Bottlenecks and failures

At 10x (500 million photos a day) the pain is bytes and money. Storage grows about 440 PB a year, so originals go to cold storage after 30 days, erasure-coded. Images average 280 GB/s, so the CDN is the main cost. Resize grows to 1,200 to 3,500 cores; metadata and feeds add partitions.

#Follow-up questions

#How would you support several photos in one post?

The post holds an ordered list of photo ids and is ready when all are processed. Ten photos are ten parallel jobs.

#A user deletes a photo. What has to happen?

Mark the post deleted so reads skip it, then delete the objects and purge the CDN in the background. On private accounts, short-lived signed URLs make copied links die sooner.

#The phone retries a post after a timeout. Do you get two posts?

No. The idempotency key returns the first post, and the 409 stops a photo joining two posts.

#How do you make images load fast on a slow network?

Put a blurred preview of a few hundred bytes in the post metadata so the feed paints at once, then load the size that fits the screen.

#How would you add content moderation?

A second consumer of the upload events scores each image. Flagged posts stay out of feeds until reviewed; posts already wait for "ready", so this slots in.
