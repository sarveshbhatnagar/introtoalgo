Design File Sync

Design a cloud file sync service: chunking and content hashes for dedup and delta sync, a consistent metadata journal, conflicts and device notifications.

You save a spreadsheet on your laptop, and by the time you pick up your phone the new version is there. Edit the same file in two places while offline, and nothing is silently lost: you get both versions and decide.

This question mixes two systems. One moves lots of bytes and must never send them twice. The other tracks small metadata records and must be strictly correct, because a wrong file list destroys someone's work. The steps follow A Framework for Any Design.

#Clarify the problem

  • Functional: upload, download, update, delete and move files; sync to a user's other devices; share folders; keep 30 days of versions; work offline.
  • Non-functional: no acknowledged change is ever lost; every device sees a folder's changes in one order (strong consistency per folder); online devices see changes within about 5 seconds; upload only what changed.
  • Out of scope: real-time co-editing, search inside files, previews.

#Estimate the scale

  • Stored data: 10 million users × 2 GB = 2 × 1016 B = 20 PB before dedup and redundancy.
  • Changes: 3 million active users × 20 saves = 60 million changes a day. 60 × 106 ÷ 86,400 ≈ 700 a second; a 3x working-hours peak is about 2,100 a second.
  • Upload bandwidth: at 1 MB per change, 60 million × 1 MB = 60 TB a day, about 700 MB/s.
  • Connected devices: 10 million users × 3 devices = 30 million. If 30% are online at once, 9 million wait to hear about changes.

Estimate: Bytes saved by delta sync

A user changes a few cells in a 200 MB file. With 4 MB chunks, how many bytes are uploaded?

You know
  • The file is 200 MB
  • The edit falls inside one 4 MB chunk
  • Unchanged chunks are already on the server

Show the working
  1. 200 MB ÷ 4 MB = 50 chunks
  2. Only 1 chunk's hash changed: 1 × 4 MB = 4 MB uploaded, 50 times less than 200 MB

Estimate 4 MB (anything from 2 MB to 20 MB is a good answer)

Your turn: Define the API

Write the calls to save a changed file without re-uploading what the server has, and how another device learns of the change.

Compare with a model answer

The client sends the chunk hashes; the server answers with the ones it is missing. The client uploads those, then commits, naming the version it started from. Other devices hold a long poll that says "this folder changed", then ask for changes since their last cursor.

#Define the API

Sync API
POST /v1/commit
  body { namespace_id, path, base_rev: 7, commit_id, size, chunks: [sha256, ...] }
  200 { rev: 8, journal_seq: 1042 }
  412 { missing: [sha256, ...] }        upload these first, then retry
  409 { current_rev: 8 }                 someone else changed it since rev 7
 
PUT  /v1/chunks/{sha256}     (raw bytes, at most 4 MB)
  201 stored     200 already had it     400 hash does not match bytes
GET  /v1/chunks/{sha256}     -> bytes
 
GET  /v1/changes?namespace_id=N&cursor=1041
  200 { entries: [ { path, rev, chunks, deleted } ], cursor: 1042, has_more }
GET  /v1/notify?cursors=N:1041,M:88       long poll, up to 60 s
  200 { changed: ["N"] }    or    204 nothing changed, poll again

The decision worth arguing is chunks before metadata. A commit succeeds only if every chunk it names is stored, so a file record never points at missing bytes. The cost is an extra round trip on a 412; metadata first would send other devices after bytes that have not arrived.

Both writes are safe to retry. A chunk named by its hash is stored once. The commit carries a client-made commit_id, so a retry after a lost reply gets back the applied commit, not a false 409 against its own edit.

Your turn: Model the data

Sketch the records for folders, files, versions and chunks. How does a device ask "what changed since I last looked"?

Compare with a model answer

A version is a list of chunk hashes. Each namespace (a shared folder or user root) has a numbered journal of changes. A device keeps a cursor, the last number it applied, and asks for entries after it.

#Model the data

Metadata tables (sharded by namespace_id)
namespaces:  namespace_id PK, owner_id, next_seq BIGINT
files:       (namespace_id, path) PK, file_id, latest_rev INT, deleted BOOL
revisions:   (file_id, rev) PK, size, chunk_hashes BLOB,   -- ordered list
             device_id, created_at                            -- kept 30 days
journal:     (namespace_id, seq) PK, file_id, rev, op         -- the change log
members:     (namespace_id, user_id) PK, role                 -- sharing
 
-- sharded by hash
chunks:      sha256 PK, blob_key, size, ref_count
-- chunk bytes live in object storage under their sha256

A commit checks the base revision, writes a new revision, bumps the file's latest revision and appends a journal entry, all or nothing. That needs a relational database, sharded by namespace, so every change to one folder lands on one shard in one order. Chunk bytes go to object storage keyed by hash; the chunk index is a key-value lookup sharded by hash.

Your turn: High-level design

Draw how a save on one device reaches another, with separate byte and metadata paths.

Compare with a model answer

Three services: block (chunks), metadata (commits and the journal), notification (long polls). Notifications only say where to look, so losing one loses no data.

#Deep dives

#Chunking and content hashing

Name every chunk by a cryptographic hash of its bytes, such as SHA-256. Same hash means same bytes, for every practical purpose, so each distinct chunk is stored once. That gives three wins: delta sync (upload only chunks whose hash changed), deduplication (a chunk shared by two files or versions is stored once), and safe retries (re-sending a chunk changes nothing).

How to cut a file into chunks
OptionGood atBad atPick it when
Whole fileSimplest; one hash per file.A one-byte change re-uploads the whole 200 MB file.Small files only, under one chunk anyway.
Fixed 4 MB chunks Usual defaultEasy to compute and explain. Edits in place change one chunk.Inserting bytes near the start shifts every later boundary, so every later chunk gets a new hash.Files edited in place, like disk images. A good first answer.
Content-defined chunksBoundaries follow the content, so an insertion changes only the chunks around it.Chunk sizes vary; needs a rolling hash and a minimum and maximum size.Documents with text inserted in the middle. The next step up.

Content-defined chunking computes a cheap rolling hash over a small sliding window, say 48 bytes, and cuts wherever the low 22 bits are all zero: on average once every 222 ≈ 4.2 million bytes, so chunks average about 4 MB. The cut depends only on nearby bytes, so an inserted paragraph moves only the boundaries near it.

Worth raising: deduplicating across users leaks information, since an instant upload reveals someone else has that exact file. I would start per user and say what cross-user dedup would save and cost.

#The metadata service and consistency

Bytes can be eventually consistent: a chunk exists or not, and never changes. File lists cannot. A device that applied "rename A to B" before "create A" would end up with the wrong folder. So each change gets the next journal sequence number in the same transaction that changes the file record, and devices apply entries in order.

The guarantee: within one namespace, every device sees the same changes in the same order, and never sees revision 8 without its chunks. Changes across namespaces are not ordered, and need not be, so normal saves never need cross-shard transactions. The cost: a huge shared folder lands on one shard, so give it a dedicated shard or split it.

On failover, promote only a replica with every committed transaction (a synchronous replica, or a consensus-based database). With an asynchronous one, a commit the phone already applied could vanish. See replication.

#Conflicts

Two devices edit the same file while one is offline. Something has to give.

What to do when two edits collide
OptionGood atBad atPick it when
Last writer winsNo user interaction; always one version.Silently throws away an edit.Never for user files.
Conflicted copy Usual defaultNothing is lost. The second version is saved as budget (Desktop's conflicted copy).xlsx.The user has to merge by hand.Any file type the server cannot parse. My default.
Automatic mergeNo duplicates when edits touch different parts.Only for formats you can parse; a wrong merge corrupts a file.Formats like plain text, with a tested merge.

The mechanism is optimistic concurrency: every commit names its base_rev, and the server accepts it only if that is still the latest. The loser gets 409 and uploads its version under a conflicted-copy name; both appear on every device. Deletes conflict too: if one device deletes a file another just edited, keep the edit.

#Notifying other devices

Polling every 5 seconds from 9 million online devices would be 9 million ÷ 5 = 1.8 million requests a second, nearly all "nothing new". Instead each device holds one long poll (or a WebSocket) listing its namespaces and cursors. The service answers when one of them changes, or after 60 seconds: 9 million ÷ 60 = 150,000 empty answers a second.

The notification says only "namespace N changed": a hint, not the truth. A lost one does no harm, because the next poll carries the device's cursors and the service answers at once if one is behind. So this path can be fast and best-effort while the journal stays strict. Realtime communication compares long polling and WebSockets.

Sending file contents in the notification

Pushing the data to every device makes delivery a correctness problem: a dropped message is a missed change, and an offline device has nothing to replay. Notify; let the device pull from its cursor.

#Bottlenecks and failures

At 10x (200 PB, about 21,000 commits a second at peak, 90 million online devices):

  • The chunk store just grows; object storage adds capacity.
  • The metadata database adds shards, and the hottest namespaces get their own.
  • The notification service adds connection servers.
  • Storage is the main bill: use erasure coding instead of three full copies, and expire versions past 30 days by decrementing chunk reference counts.

#What a strong answer sounds like

LevelWhat the answer does
JuniorUploads whole files to object storage, keeps a table of paths, and polls.
MidHashed chunks for delta sync, metadata separate from bytes, push notifications.
SeniorCommits only after chunks exist, keeps an ordered journal per namespace with device cursors, handles conflicts with base revisions and conflicted copies, treats notifications as hints, and knows why fixed chunks fail on insertions.

#Follow-up questions

#How do you restore a file to last week's version?

Commit a new revision with last week's chunk list. No bytes move; the chunks are still stored.

#How do you sync a folder with 100,000 files to a new device?

Start from a snapshot of the file list plus its cursor, then download chunks in parallel, smallest or newest files first.

#How do you handle a 50 GB file?

The same way: 50 GB ÷ 4 MB = 12,500 chunks, uploaded in parallel and resumable chunk by chunk. The revision holds 12,500 hashes, about 400 KB.

#How does sharing work?

A shared folder is its own namespace with a members table. Members' devices add it and its cursor to their long poll.

#Can you encrypt files so the server cannot read them?

Yes, by encrypting on the device. The cost: identical files from different users no longer match, so cross-user dedup is gone, and chunk names must be keyed hashes so they do not reveal content.
