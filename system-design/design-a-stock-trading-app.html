Design a Stock Trading App

Design a retail brokerage app: live prices for millions of screens, orders that stay correct with an outside exchange, and the daily spike at the open.

A price flickers on your phone. You tap Buy, 10 shares, limit $50.00, and seconds later the app says "Filled at $49.98". Your broker traded nothing itself: it checked your cash, wrote the order down, and sent it to an exchange it does not control, over a network that can drop the answer.

Two problems pull in opposite directions. Live prices are fan-out, where a second stale is fine. Orders are real money, where a lost or doubled message is a disaster. The question means the app (think Robinhood), not the exchange. The steps follow A Framework for Any Design.

#Clarify the problem

  • Functional: live quotes for the symbols on screen; place market and limit orders; cancel open orders; show each order's status as it changes.
  • Non-functional: quotes within about 1 second of the exchange; an accepted order is never lost or sent twice; status always ends up matching the exchange; the order path survives the open at about 20 times the average rate.
  • Out of scope: matching, options, crypto, charts, account opening, tax reports.

#Estimate the scale

Do prices and orders separately. These are scenario givens, not a real broker's figures.

  • Connections: 2 million ÷ 50,000 per push server = 40 servers. Run 80, half full, to absorb a dead server's clients.
  • Market data in: up to 200,000 quote updates a second across 10,000 symbols. Nobody reads a price changing 50 times a second, so send each symbol at most once a second: 10,000 updates.
  • Updates out: 10 symbols per screen is 20 million symbol updates a second, but one frame per client per second makes it 2 million frames, 25,000 per server.
  • Orders: a trading day is 6.5 hours = 23,400 seconds, so 5,000,000 ÷ 23,400 ≈ 214 a second on average.
  • Storage: 2 KB per order with history × 5 million = 10 GB a day; × 252 trading days ≈ 2.5 TB a year; about 18 TB over 7 years.

Estimate: Orders in the first minute

How many orders a second arrive in the first minute after the open?

You know
  • 5 million orders a day
  • The first minute carries 5% of the day's orders

Show the working
  1. 5% of 5,000,000 = 250,000 orders
  2. 250,000 ÷ 60 s ≈ 4,200 a second, about 20 times the 214 average

Estimate 4.2 thousand/s (anything from 1.5 thousand/s to 12 thousand/s is a good answer)

A relational database partitioned by account handles this, if you scale up before 9:30.

Prices are integer cents; floating-point dollars round badly.

The decision worth arguing is what POST and DELETE promise. The exchange decides later, so POST returns 201 once the order is durably recorded, DELETE returns 202, and the result arrives as an event. An app that shows "Cancelled" on the 202 will one day show a cancelled order that filled.

The app creates client_order_id once and reuses it on every retry: it is the order's idempotency key.

Orders, fills and buying power

                                    -- | filled | cancel_pending | cancelled | rejected
  filled_qty       INT
  reserved_cents   BIGINT           -- cash held back for this order
  updated_at       TIMESTAMP
  UNIQUE (account_id, client_order_id)
 
fills
  exec_id          VARCHAR(40) PRIMARY KEY   -- from the exchange
  order_id         BIGINT
  qty              INT
  price_cents      BIGINT
  executed_at      TIMESTAMP
 
accounts
  account_id       BIGINT PRIMARY KEY
  cash_cents       BIGINT
  reserved_cents   BIGINT           -- spendable = cash - reserved
 
positions
  account_id       BIGINT
  symbol           VARCHAR(8)
  qty              INT
  reserved_qty     INT              -- shares held back for open sells
  PRIMARY KEY (account_id, symbol)

Placing, updating, listing and filling orders are each a transaction within one account, so use a relational database partitioned by account_id. Quotes are not stored: the latest per symbol lives in the feed handler's memory.

Unique keys do the deduplication, so no code can race: a retried order hits UNIQUE (account_id, client_order_id), a repeated fill hits exec_id.

#Deep dives

#Fanning out live prices

The naive design sends all 200,000 ticks a second to every watcher. Three ideas shrink that:

  • Conflate at the source. Publish the latest quote per symbol once a second: 10,000 messages instead of 200,000. Each is the full quote, not a change, so the next one repairs a lost one.
  • Subscribe per server, not per client. A symbol on 1 million screens costs the pub/sub 80 messages a second, one per server; each server copies it to its 12,500 watchers.
  • Batch per client. One frame a second holds all its symbols.

On reconnect, the app resubscribes, gets snapshots, and calls GET /orders?status=open so no order status is missed. Real-time communication covers holding connections at this scale.

Using the displayed price to fill an order

The quote on screen is up to a second old; a market order fills at the exchange's price. Reserve cash with a margin (say 5% for market buys) and settle on the fill price.

#Keeping orders right with an outside exchange

Your database and the exchange cannot share a transaction, so for a moment only one knows about the order. You choose which.

Ordering the database write and the exchange call
OptionGood atBad atPick it when
Call the exchange, then writeNo record of orders that never left.Crash after the call and a live order exists with no row and no reserved cash.Never, for money.
Write first, then call Usual defaultEvery order the exchange can know has a row first. A crash leaves a pending row you resolve by asking.Some pending rows were never sent; a reconciler must settle them.The usual answer when the same service writes and sends.
Write with an outboxThe order and an outbox row commit together; a separate sender calls the exchange.One more moving part; the sender still checks status before any resend.Sending is a separate service that must survive the order service being down.

The rule: the row with the client order id is durable (committed on a synchronous replica too) before the exchange can hear about the order. Then:

  • Never resend blindly. A pending order may or may not have arrived. Protocols such as FIX carry your client order id on every message, so ask the exchange about it and send only if it has never heard of it. Ask only after the crashed server's session is closed, so its message cannot still be on the way. At-least-once sending plus this check gives the effect of once.
  • Apply reports idempotently, forward only. Fills are keyed by execution id; a late "accepted" after "filled" changes nothing.
  • Reconcile twice. Continuously, for stuck pending or cancel_pending orders; daily, against the clearing firm's trade report.

Cancels race with fills. Ana taps Cancel; the exchange fills her order 10 ms later, then answers the cancel with "too late". So the order sits in cancel_pending ("Cancelling…") until the exchange decides.

#Surviving the open

The spike comes at 9:30 every trading day. Reactive autoscaling is minutes too late. So:

  • Scale on a schedule. Push servers, order servers and database reach the open's level by 9:15.
  • Spread the reconnect storm. Clients add jitter; snapshots come from memory, never a database.
  • Drain the overnight queue at a set rate. Exchange connections have message limits. With 10 connections at 1,000 messages a second and 100,000 queued orders, live orders use 4,200 of the 10,000, so the queue drains in 100,000 ÷ 5,800 ≈ 17 seconds. Say "at or shortly after the open", or add connections.
  • Shed the right load. Charts and news give way first, never orders; cancels go first because they reduce risk.

#Bottlenecks and failures

At 10x, the price path grows linearly: 800 push servers, 8 GB/s; the pub/sub barely grows. Orders at 42,000 a second need more partitions and exchange connections, which take time to arrange.

#Follow-up questions

#How would you add stop orders?

A trigger service sends a market order when the stop price is crossed. It reads the full feed, not the conflated stream, or it can miss a brief cross; a conditional status update makes it fire once.

#How do you show the portfolio's value live?

The app multiplies shares by the quotes it already gets. The server sends positions on connect and after fills, instead of revaluing 2 million portfolios a second.

#How do you stop a user spending the same cash twice?

The reservation is a conditional update in the same transaction as the order insert: SET reserved_cents = reserved_cents + 50000 WHERE account_id = :a AND cash_cents - reserved_cents >= 50000. Two orders racing for the last $500 cannot both pass: the account row is updated one transaction at a time.

#An order fills 4 of 10 shares, then the user cancels. What happens?

The exchange cancels the other 6; the order ends cancelled with filled_qty 4 and the cash for 6 released. The cancel and a late fill can arrive in either order, so never let a report lower filled_qty.

#How would you add a second exchange?

The order service writes the chosen venue on the row before sending, with one connection pool per venue, so the reconciler knows which exchange to ask.
