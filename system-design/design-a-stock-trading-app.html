Design a Stock Trading App

How a stock trading app streams live prices to millions of screens, keeps orders correct with an outside exchange, and copes with the market open.

A retail trading app, meaning the broker's app and not the exchange, shows live prices for the stocks a user is watching and lets the user place, cancel and track orders. The broker does not match trades itself; it records the order and sends it to an exchange it does not control.

The design is hard because the two halves have opposite requirements. Live prices are a fan-out problem in which a price that is one second old is acceptable, but millions of screens need it. Orders involve real money, so an order must never be lost or executed twice, even though the call to the exchange can fail after the exchange has already acted on it. The steps below follow A Framework for Any Design.

#Clarify the problem

  • Functional requirements: users see live quotes for the symbols on their screen, place market and limit orders, cancel open orders, and see each order's status change as it happens.
  • Non-functional requirements: quotes arrive within about 1 second of the exchange, an accepted order is never lost and never sent twice, the order status always ends up matching the exchange, and the order path survives the open, when the order rate is about 20 times the daily average.
  • Out of scope: the matching engine, options, crypto, charts, account opening and tax reports.

#Estimate the scale

The price path and the order path are estimated separately. The figures are scenario assumptions, not those of a real broker.

  • Connections: if one push server holds 50,000 WebSocket connections, 2 million clients need 40 servers. Running 80 leaves each server half full, so it can absorb the clients of a dead one.
  • Market data coming in: the exchange feed delivers up to 200,000 quote updates a second across 10,000 symbols. Nobody can read a price that changes dozens of times a second, so each symbol is sent at most once a second, which is 10,000 updates.
  • Updates going out: a screen shows about 10 symbols, so 2 million screens need 20 million symbol updates a second. Sent as one frame per client per second, that is 2 million frames, or 25,000 per push server, and about 800 MB/s in total at 40 bytes per symbol.
  • Orders: a trading day is 6.5 hours, or 23,400 seconds, so 5 million orders a day is about 214 orders a second on average.
  • Storage: an order with its history takes about 2 KB, so 5 million orders add about 10 GB a day.

Quotes and order updates share one WebSocket. Placing an order returns "pending", with an app-generated id so that a retry cannot create a duplicate, and cancelling returns "cancel requested". The real results arrive later as events.

Prices are integer cents, because floating-point dollars cause rounding errors.

The API decision worth discussing is what POST and DELETE promise. Because the exchange decides later, POST returns 201 as soon as the order is durably recorded, DELETE returns 202 because the cancel has only been requested, and the result arrives as an event on the stream. An app that showed "Cancelled" on the 202 would eventually show a cancelled order that had already filled.

The app creates client_order_id once and reuses it on every retry. It is the order's idempotency key, which lets the server tell a retry from a new order.

Your turn: Model the data

Sketch the tables for orders and fills. Decide how a retried order and a repeated fill are each counted only once.

Compare with a model answer

A unique key on the account and the client order id rejects a retried order, and fills keyed by the exchange's execution id reject a repeated fill. The order and the cash reservation for it are committed in one transaction.

Placing an order, updating it, listing a user's orders and recording a fill are each a transaction that touches only one account. That access pattern fits a relational database partitioned by account_id, which gives real transactions without cross-partition coordination. Quotes are not stored; the feed handler keeps the latest one per symbol in memory.

Unique keys do the deduplication, so two servers cannot race past it. A retried order violates UNIQUE (account_id, client_order_id), and a repeated fill violates the primary key on exec_id.

Your turn: High-level design

Sketch how a price reaches 2 million screens, and how an order reaches the exchange and its status comes back to the user.

Compare with a model answer

A feed handler publishes each symbol's latest quote once a second to pub/sub, and push servers forward it over WebSockets. An order service records each order before calling the exchange and publishes status events back through pub/sub.

#High-level design

#Deep dives

#Fanning out live prices

Sending every tick to every watcher is far more than any system can sustain, so the design uses three techniques.

The first technique is conflation at the source: the feed handler publishes only the latest quote per symbol once a second, so pub/sub carries 10,000 messages a second instead of 200,000. Each message is a full quote, so the next one repairs a lost one.

The second technique is subscribing per server instead of per client. A symbol shown on 1 million screens costs the pub/sub system 80 messages a second, one for each push server, and each push server then copies the quote to its roughly 12,500 watchers.

The third technique is batching per client: each client receives one frame a second containing all of its symbols.

The remaining choice is how prices reach the app. Polling means each app asks over plain HTTP every second, which produces 2 million requests a second with full headers. Server-sent events keep one HTTP response open, but the stream is one-way, so every subscription change is a separate call that must reach the right server. A WebSocket is two-way, so subscriptions and order updates share one connection, at the cost of stateful servers that must be drained during deploys. This design uses WebSockets because subscriptions change constantly as the user scrolls.

After a reconnect the app subscribes again and calls GET /orders?status=open so that it does not miss a status change. Real-time communication covers holding this many connections.

A market order fills at the exchange's current price, not the price on the screen, which can be a second old. The system therefore reserves cash with a margin, for example 5% extra for a market buy, and settles on the fill price.

#Keeping orders correct with an outside exchange

The broker's database and the exchange cannot take part in one transaction, so there is always a moment when only one of them knows about the order. The design must decide which one knows first. There are three orderings.

Calling the exchange first and writing afterwards looks natural, but a crash between the two steps leaves a live order at the exchange with no row in the database and no cash reserved. The customer could own shares that the broker has no record of.

Writing first and then calling the exchange reverses the order. The service commits the order as pending, with the cash reserved, and only then sends it. A crash now leaves a pending row, and some of those rows were never sent, but no order can exist at the exchange without a record at the broker. The remaining work is to find out, for each stuck row, whether the exchange received it.

Writing with an outbox commits the order and a row in an outbox table in the same transaction, and a separate sender process reads the outbox and calls the exchange. It is the right choice when sending must continue while the order service is down, at the cost of another component.

The rule is that the row holding the client order id must be durable, which means committed on a synchronous replica as well, before the exchange can hear about the order. Three practices follow.

The first is never to resend a pending order blindly, since it may have reached the exchange. Exchange protocols such as FIX carry the client order id on every message, so the reconciler asks the exchange whether it knows that id and sends the order only if the answer is no. It asks only after the crashed server's session is closed, so the original message cannot still be in transit.

The second is to apply exchange reports idempotently and only forward: fills are keyed by execution id, and a late "accepted" after "filled" changes nothing. The third is to reconcile continuously for stuck pending or cancel_pending orders, and daily against the clearing firm's trade report.

Cancels race with fills. If Ana taps Cancel and the exchange fills her order 10 ms later, the exchange answers the cancel with "too late". The order therefore stays cancel_pending, shown as "Cancelling", until the exchange reports the final state.

#Surviving the market open

The spike comes at the same time every trading day, and autoscaling that reacts to load is too slow, so the system scales the push servers, order servers and database on a schedule so that they are ready by 9:15. Clients add jitter to their reconnect delay, and snapshots are served from memory.

#Bottlenecks and failures

At 10 times the load, the price path needs about 800 push servers and 8 GB/s of outgoing bandwidth, while the pub/sub system barely grows because it carries one message per symbol per server. The order path would reach 42,000 orders a second, which needs more database partitions and more exchange connections, and those take time to arrange. #Follow-up questions

#How would you add stop orders?

A trigger service sends a market order when the stop price is crossed. It reads the full feed rather than the conflated stream, because a brief cross within one second could be missed, and a conditional status update from "waiting" to "triggered" makes the order fire only once.

#How do you stop a user from spending the same cash twice?

The reservation is a conditional update in the same transaction as the order insert: SET reserved_cents = reserved_cents + 50000 WHERE account_id = :a AND cash_cents - reserved_cents >= 50000. If two orders compete for the last $500, only one update matches the condition, because the database processes updates to the same account row one transaction at a time. The other order is rejected with "insufficient buying power".

#An order fills 4 of 10 shares and then the user cancels. What happens?

The exchange cancels the remaining 6 shares, so the order ends as cancelled with filled_qty of 4, and the cash reserved for the 6 unfilled shares is released. A late fill and the cancel confirmation can arrive in either order, so the service must never let a report lower filled_qty.

#What do you do when the market is closed or the exchange is down?

The order service knows the trading calendar, so outside market hours it either rejects market orders with a "market closed" error or queues orders the user chose to place for the next open. If the exchange connection drops during the day, the service stops sending, marks every order in flight as unknown, and reconnects. After reconnecting it queries the exchange for each open order before it resumes sending, which is the same reconciliation used after a crash.
