Design an Ad Click Aggregator

Count ad clicks per minute, fresh in seconds and exact for billing: a click log, windowed stream processing, dedup, hot ads, late events and a recount.

Someone taps an ad, lands on the advertiser's site, and that ad's counter goes up by one. The advertiser watches the counters live and is billed per click. Count too few and the platform loses money; count too many and it overcharges a customer, which is worse.

Counting gets hard at this scale: over 100,000 events a second, a few ads getting most, clicks arriving late or twice, and a number that must be fresh and exact. The steps follow A Framework for Any Design; try each "Your turn" box before you read on.

#Clarify the problem

  • Functional: record a click and redirect to the landing page; query clicks per ad per minute over any range; produce final counts for billing.
  • Non-functional: redirect adds under 50 ms; dashboard within about 10 seconds; billed counts exact, each valid click once; no accepted click lost; survives losing any one machine.
  • Out of scope: choosing which ad to show, fraud scoring (we leave a hook for it), unique-user counts, the billing system itself.

#Estimate the scale

  • Clicks: 1010 ÷ 86,400 s ≈ 116,000 a second; about 350,000 at a 3x peak.
  • Ingest: at about 300 B per raw event, 350,000 × 300 B ≈ 105 MB/s at peak. Easy for a partitioned log; impossible as single-row increments.
  • Aggregate rows: at most one per ad per minute: 106 × 1,440 = 1.44 billion a day, at about 40 bytes about 58 GB a day (a ceiling: empty minutes write no row). The average ad gets 1010 ÷ 1.44 × 109 ≈ 7 clicks a minute.
  • Partitions: if one partition and task handle 10,000 events a second (an assumption), the peak needs 35. Use 64: about 5,500 a second each, if clicks spread evenly. They do not; see hot ads.

Raw data is 50 times the minute aggregates (3 TB versus 58 GB a day). Queries read aggregates; only recounts read raw data.

Your turn: Define the API

Write the click and query endpoints. What does the click URL carry?

Compare with a model answer

The click is a GET returning a 302; the query reads a time range. The URL carries a signed impression token. The landing page is looked up by ad id, never taken from the URL, or you have an open redirect.

#Define the API Optional

Optional in the interview. Sketch the API only if the interviewer asks, if an API choice shapes the design, or if time permits. Otherwise say "I'll skip the detailed API unless you want it" and go to the data model.

GET /v1/advertisers/{id}/clicks?from=...&to=...&group_by=ad&granularity=hour

The token is the decision worth arguing. When the ad server shows an ad, it creates a random impression id and signs {impression_id, ad_id, shown_at} with a secret key (an HMAC). Checking the signature needs no database call and proves we served that impression; without it, a script can invent clicks on a competitor's ad. The impression id is also the natural key for spotting duplicates.

Your turn: Model the data

Sketch the raw event and the aggregate. Which store holds each?

Compare with a model answer

Raw events: a log, then object storage. Aggregates: one row per (ad, minute) in a columnar analytics store, where a write replaces the value instead of adding to it.

#Model the data

Records
-- click event: in the log, then in object storage (about 300 B)
impression_id   BINARY(16)   -- random, from the signed token
ad_id           BIGINT
advertiser_id   BIGINT
shown_at        TIMESTAMP    -- from the token
clicked_at      TIMESTAMP    -- event time, set by the click service
device_hash, ip, user_agent, valid (bool)
 
-- aggregate: one row per ad per minute (about 40 B)
ad_clicks_minute
  advertiser_id  BIGINT
  ad_id          BIGINT
  minute         TIMESTAMP
  clicks         BIGINT
  final          BOOLEAN      -- set by reconciliation
  ORDER BY (advertiser_id, ad_id, minute)   -- upsert replaces the row

Clicks are written once, read in order, and reread in bulk by recounts: a partitioned log (such as Kafka), copied to object storage. Queries sum clicks over a range, grouped by minute or hour: a scan of a few columns over many rows, which a columnar analytics (OLAP) store such as ClickHouse or Druid does well.

Store clicks as an absolute value that a later write replaces, never an increment, so every writer can safely retry.

Your turn: High-level design

Sketch click to dashboard. Where is a click made durable, counted, and recounted?

Compare with a model answer

A click service appends each click to a partitioned log, then redirects. A stream processor dedups, counts per ad per minute and writes to an OLAP store. A batch job recounts from the archive and overwrites with final numbers.

#High-level design

Two paths compute the same numbers: the fast stream, nearly always right, and the slower batch recount, the truth for billing. Both write one OLAP table; the batch write wins.

#Deep dives

#The counting pipeline

UPDATE ads SET clicks = clicks + 1 per click means 350,000 row writes a second. Count in memory and write totals.

The stream processor (such as Flink) keys events by ad_id, so one ad reaches one task, which counts in one-minute tumbling windows (fixed, non-overlapping). Windows use event time, the clicked_at stamp, so a backlog after an outage still lands in the right minute. Open windows are emitted every 5 seconds. The log keeps 7 days (21 TB, 63 TB with three replicas), so any consumer can rewind.

#Counting each click once

Duplicates come from double clicks, append retries after a lost ack, and processor replays.

  • Users and retries: the processor keeps every impression id seen in the last 24 hours, the longest a click stays valid (checked against shown_at). Keying by ad_id sends both copies to one task. Cost: 1010 ids a day × 16 B = 160 GB, about 2.5 GB per task over 64 partitions, in a disk-backed state store.
  • Processor crashes: log offsets, window counts and the dedup set are checkpointed together. A restart rewinds all three and replays, so state ends as if each event was processed once.
  • OLAP writes: a replay re-sends rows the store has. Each write replaces the (ad, minute) row with an absolute count, so twice changes nothing.

The log delivers at least once. What you build is exactly-once effect: dedup by a business key plus idempotent writes. "The broker gives exactly-once", with nothing about how the sink handles a replay, is a weak answer.

Deduplicating by user and ad

"Same user, same ad, same minute" drops genuine repeat clicks and still lets a bot with many device ids through. Deduplicate on the signed impression id; leave fraud to a fraud system.

#Hot ads and partition skew

Keying by ad_id puts one ad on one partition. Fine at 7 clicks a minute; not for an ad in a live final drawing 30,000 a second. The partition was sized for 10,000, so it falls behind with every other ad on it.

Split the hot key in two stages. Key a hot ad's events by (ad_id, salt), with salt = hash(impression_id) mod 8, spreading ad 42 over 8 tasks of about 3,750 a second. A second stage keyed by ad_id sums the latest partial count from each: 8 records every 5 seconds instead of 1.8 million clicks a minute. The salt comes from the impression id, not a random number, so both copies of a double click still meet in one task.

Salt only ads on a hot list, refreshed every minute. If an ad joins the list between the two halves of a double click, the stream counts both; the recount fixes it.

#Late events and the recount

Clicks spooled to disk during a log outage arrive late. The processor tracks a watermark, its estimate that "no older events will come", and keeps each minute open until the watermark is 2 minutes past it. Later events go to a side output for the recount.

The batch recount runs hourly on the hour before last, applying the same rules to the archive and carrying 24 hours of seen impression ids between runs. It overwrites the stream's rows with final = true, excluding clicks fraud has marked invalid. A click arriving after its hour is final reruns that hour, with a billing adjustment. Alert if the paths disagree by more than, say, 0.1% in an hour: one has a bug.

#Bottlenecks and failures

At 10x (3.5 million clicks a second at peak), go to 640 partitions at 5,500 a second each; dedup state stays 2.5 GB per task. Shard the OLAP store further by advertiser. Salting hot ads becomes routine.

Redirecting before the click is durable

Answering 302 and logging in the background saves a few milliseconds, but a crash in between loses a billable click without trace. Wait for the log's ack; spool to disk only when the log is down.

#Follow-up questions

#Advertisers want counts by country and device too. What changes?

Add them to the aggregate key. Rows multiply by the combinations that occur, so keep minute rows to a few dimensions and serve finer breakdowns hourly.

#How do you stop click fraud?

A separate system reads the log, scores clicks (rate per device and IP range, impossible timing) and writes verdicts the recount applies.

#Why not query the raw events directly?

A month for one advertiser can be billions of rows; minute aggregates are about 50 times smaller.

#How long do you keep minute-level rows?

About 30 days (58 GB × 30 ≈ 1.7 TB), then hourly rollups, 60 times fewer, kept for years.

#How would you run it in several regions?

Run click services and a log per region, and ship raw events to one region for the recount. The impression id, minted once, still deduplicates across regions.
