Design Top-K Trending

Find the most viewed videos of the last hour, day and month: exact versus count-min sketch counts, sliding windows, merging partitions, precomputed reads.

A video site's "Trending" tab shows the 100 most viewed videos in the last hour, day and month. It sounds like one ORDER BY and is not: billions of views a day, hundreds of millions of distinct videos, windows sliding every minute, and a page millions load.

It tests whether you do the arithmetic before reaching for a clever structure: sometimes exact counting fits, sometimes you need a sketch and its error bound. The steps follow A Framework for Any Design; try each "Your turn" box before you read on.

#Clarify the problem

  • Functional: return the top K (K ≤ 100) videos by views over the last hour, day and month, with counts.
  • Non-functional: hour and day lists refresh every minute, the month hourly; reads under 50 ms at any load; a video clearly above the 100th is never missing; month counts within about 5%.
  • Out of scope: defining a view, fraud filtering, personalised trending, arbitrary time ranges.

#Estimate the scale

Assume 5 billion views a day; 30 million distinct videos viewed an hour, 150 million a day, 500 million a month; 50 bytes per counter entry.

  • Views: 5 × 109 ÷ 86,400 s ≈ 58,000 a second; about 175,000 at 3x peaks.
  • Hour window, exact: one count map per minute (assume 2 million distinct videos a minute) plus running totals: 60 × 2 × 106 × 50 B + 30 × 106 × 50 B = 6 GB + 1.5 GB = 7.5 GB.
  • Day window, exact: one map per hour: 24 × 30 × 106 × 50 B + 150 × 106 × 50 B = 36 GB + 7.5 GB = 43.5 GB.
  • Reads: say 20,000 page loads a second at peak, all asking the same three questions.

The decision worth arguing is what the API refuses. "Top 50 for 14:00 to 15:30 last Tuesday" turns a lookup into a scan over billions of events; ad hoc ranges belong in a warehouse.

View events are pre-summed per video per server per second: a viral video watched 20,000 times a second on 500 servers becomes at most 500 events a second.

Your turn: Model the data

What state does counting keep for the hour, and what does the read side store?

Compare with a model answer

Per-minute maps and running totals in memory, partitioned by video id. One finished, sorted list per window in a key-value store.

#Model the data

State and results
Counter task state (one task per log partition, 32 partitions)
  minute_buckets : ring of 60 maps   video_id -> views in that minute
  hour_totals    : map               video_id -> sum of the 60 buckets
  hour_buckets   : ring of 24 maps   (same idea for the day)
  day_sketches   : 31 daily count-min sketches + 1 running month sketch
  candidates     : video ids whose month estimate passed a floor
  checkpoint     : state + log offsets, written to object storage every minute
 
Results (key-value store, about 10 KB per value)
  key   "trending:hour" | "trending:day" | "trending:month"
  value { as_of, version, items: [ {video_id, title, thumbnail, views} x 100 ] }

Counting state is a stream processor's keyed state, snapshotted for recovery. Results are three keys, read constantly and written once a minute: a key-value store fits. Titles are attached at build time, so reads never join.

Your turn: High-level design

Sketch the path from a view to the page. Where are counts kept, and where do partitions' answers meet?

Compare with a model answer

Views go into a log partitioned by video id. Counter tasks emit a local top 100 every minute; a merger combines the 32 lists into the global top 100. The page reads one key through a CDN.

#Deep dives

#Windows: tumbling or sliding

A tumbling window is a fixed block, 10:00 to 11:00: at 10:01 its list rests on one minute of data, and a video that peaked at 9:55 vanishes at 10:00. A sliding window, the 60 minutes up to now, moves smoothly, but done literally must forget each view exactly 60 minutes later.

Build the sliding window from 60 one-minute tumbling buckets: each minute, add the newest to the totals and subtract the oldest. The day uses 24 hourly buckets plus the current partial hour, so it also refreshes every minute; its 23-to-24-hour length goes unnoticed.

Recomputing the whole window every minute

Summing 60 buckets each minute is 60 times the work; for the day, 24 maps of 30 million entries every minute. Adjust running totals instead.

#Merging partitions into one top K

Whether merging 32 local top-100 lists is right depends on how events were partitioned.

  • By video id (our choice): partition 12 holds V7's true total. If V7 is in the global top 100, at most 99 videos anywhere beat it, so at most 99 in its partition do, and it is in partition 12's top 100. The merge is exact.
  • By server or at random: V7's views spread over all 32 partitions. It could rank 101st in every one and still be first overall, so merging local lists is wrong.

The cost is skew: a viral video loads one partition, though pre-summing keeps it to a few hundred events a second. The ad click aggregator shows the salted two-stage fix if that is not enough.

#Exact counts or a sketch

For the month, exact counts take 250 GB, mostly long tail. A count-min sketch trades a small, one-sided error for fixed memory: a grid of d rows by w counters, one hash function per row. To add a video, add to its cell in every row; to estimate, take the smallest of those cells. Collisions only add, so the estimate is never too low.

The guarantee: with width w and depth d, each estimate is at most the true count plus (e ÷ w) × N, where N is the total of all counts and e ≈ 2.718, with probability at least 1 − e−d. Each task sketches only its own partition. A month is 5 × 109 × 30 = 1.5 × 1011 views, so one task of 32 sees N ≈ 4.7 × 109. With w = 218 ≈ 262,000 and d = 5, an estimate is high by at most 2.718 ÷ 262,144 × 4.7 × 109 ≈ 48,600 views, with probability 1 − e−5 ≈ 99.3% for any one video. If the month's 100th video has at least a million views, the error is under 5% of the counts that matter. Each sketch is 5 × 218 × 8 B ≈ 10.5 MB.

A sketch answers "how many for this video?" but cannot list the top ones, so pair it with a candidate set and a heap:

  • Each view goes into today's sketch and a running month sketch. If the month estimate passes a floor, here 500,000 (half the assumed 100th place), the video joins the candidates. Estimates are never low, so it joins no later than the view that takes its true count past the floor.
  • At midnight, subtract the expired day from the month sketch, cell by cell (all sketches share hashes and width).
  • Every hour, re-estimate the candidates, drop those under the floor, and send the best 100, found with a min-heap, to the merger.

#Precomputing so a read is one lookup

At 20,000 loads a second, computing per request would redo one minute's answer 1.2 million times. The merger writes each list under one key, read through a CDN with a 30-second lifetime. A slow pipeline means an older list, never a slow page.

Each write carries its minute as a version and succeeds only if newer, so a stalled merger cannot overwrite a fresh list.

#Bottlenecks and failures

At 10x (1.75 million views a second, 10x the distinct videos), the hour state grows to 75 GB: use 320 partitions, about 234 MB per task. Exact day counts reach 435 GB, so move the day to sketches too. The merger copes with 320 lists; reads do not change.

#What a strong answer sounds like

LevelWhat the answer does
JuniorRuns GROUP BY video ORDER BY count LIMIT 100 over a views table; caches it when prompted.
MidCounts in windowed stream processing, keeps a heap for the top K, precomputes results.
SeniorAsks sliding or calendar and exact or close, does memory arithmetic per window, partitions by item for an exact merge, uses a sketch only where needed with its error bound.

#Follow-up questions

#What changes for the most searched terms?

Normalise queries. Most terms appear once, so exact maps are mostly waste: sketch the day too.

#Trending should mean rising, not just big. How?

Rank by this hour's views over the usual hourly rate, with a minimum count so 2 to 20 does not win.

#How do you add per-country lists?

Key buckets by (country, video). Memory grows with pairs that occur; the results store gets one key per country and window, still one read each.

#How do you stop people gaming the list?

Count only views that pass upstream checks, cap what one account or device adds per video per hour, and let moderation remove candidates.

#Why not a sorted set in an in-memory store?

It works for one window, as in Design a Leaderboard. Here it means 175,000 network writes a second, and expiry still needs per-minute buckets.
