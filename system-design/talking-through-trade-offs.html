Talking Through Trade-offs

A five-part sentence for every design choice, worked on SQL vs NoSQL, caching, sync vs async, consistency and push vs pull, with strong and weak scripts.

Two candidates draw the same online shop, with orders in a relational database. Asked why, the first says "SQL is more reliable." The second names the transaction an order needs, the write rate one primary handles, and the load that would make her switch. Same choice; only the second answer tells the interviewer anything, and one sentence shape produces it on demand.

#The five-part sentence

The pattern
1. Option     "I'll use X."
2. Buys       "It gives us ..."                      (the benefit, concrete)
3. Costs      "The price is ..."                     (what gets worse)
4. Fits       "That's right here because ..."        (tie it to a requirement or a number)
5. Changes    "If ... changed, I'd switch to Y."     (the condition that flips it)

Parts 3 and 5 separate candidates. The cost shows you see the whole picture. The switch condition shows the choice came from the requirements, not habit. Part 4 needs a fact from your requirements or estimates, such as a read/write ratio or "no double bookings".

#Five classic choices

#SQL or NoSQL

Frame it by access pattern: what you read and write together, and whether you need transactions across rows. See choosing a database.

#Cache or no cache

Sometimes the strongest move is to decline one: an admin tool doing 5 reads a second gains only an extra component and stale data. Strong: "Profile reads are 100 times the writes and a few profiles get most views, so I'll put a cache in front, with a 5-minute TTL and a delete on write. The cost: others may briefly see a stale profile. If writes became as common as reads, the hit rate would drop and I'd remove it."

#Synchronous or asynchronous

Ask: does the user need this step's result before we answer? A card charge, yes. The receipt email, no. Anything the user does not wait for can go through a queue, so its failures stop being the user's.

The cost: the email can arrive minutes late, and a retry can send it twice unless the worker is idempotent. If checkout crashes between marking the order paid and enqueueing, the receipt is lost; the fix is an outbox, writing the email job in the same database transaction for a relay to move to the queue. What would flip it: a login code the user is waiting for must go out right away.

#Strong or eventual consistency

Be precise. Strong (linearizable) means once a write is acknowledged, every later read sees it. Eventual means replicas converge if writes stop, with no promised bound on staleness. A replica that "lags about a second" is eventual, not strong. CAP and consistency covers the models, and why a quorum is not strong consistency.

Strong: "Two people must never get seat 14C, so a reservation is a conditional write on the primary: take the seat only if it is still free. The seat map people browse can be a few seconds stale, since the reservation itself is checked. If we went multi-region, I'd have one region own each event's seats." One feature, two operations with different needs.

#Push or pull

Push writes each post into every follower's feed (fan-out on write). Pull builds your feed from the accounts you follow when you open it (fan-out on read).

#In the interview

Use the full sentence for the three or four decisions that shape the design. For small ones a clause will do: "round robin, since the servers are identical". An honest tie is fine: "Both work at 200 a second; I'll pick what the team runs."

Expect these follow-ups:

  • "What if you're wrong about that number?" Say what breaks first and how you would notice: "at ten times the writes the primary saturates; I'd watch write latency and partition before then."
  • "Why not the other option?" Give its strength, then the cost that rules it out.
  • "Can you have both?" Sometimes, per operation, like the seat map and reservation.

#Common mistakes

Listing pros and cons, then not choosing

"SQL has transactions, NoSQL scales horizontally, both have their place." That is not a decision. Pick one and say what would make you switch.

Only naming the flaws of the option you rejected

The interviewer will ask your choice's cost anyway. Volunteering it reads as confidence.

Quick check

Which part of the five-part sentence is missing? "I'll queue the thumbnail jobs so uploads return fast. That fits, since users don't need the thumbnail right away. If users had to see the thumbnail before posting, I'd do it inline."

  1. Not quite. It names it: queue the thumbnail jobs.
  2. Right. It never says what gets worse: a post can show a placeholder for a few seconds, and failed jobs need retries.
  3. Not quite. That is the last sentence.

A candidate says "profile reads are strongly consistent because they go to a replica that lags under a second." What is wrong?

  1. Not quite. "Strong" guarantees every read sees the latest acknowledged write. Any lag breaks it.
  2. Right. Say "eventually consistent, usually under a second behind", plus read-your-writes for the owner if needed.
  3. Not quite. Asynchronous replication always allows lag; that is why it is fast.

Most users have about 300 followers; a few have 5 million. Under pure push, how many feed writes does one post by a 5-million account cost, and what do you choose?

  1. Not quite. 300 is the typical account. The large accounts drive the cost.
  2. Right. Pulling those few accounts at read time keeps push cheap for everyone else.
  3. Not quite. That slows every feed load to fix a problem a few accounts cause.
