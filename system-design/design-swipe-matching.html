Design Swipe Matching

Design a swipe-to-match dating app: recording swipes at 70,000 a second, detecting a mutual match exactly once, and building candidate stacks.

A dating app shows one face at a time. Swipe right if interested, left if not. When two people swipe right on each other, the app says "It's a match". Think Tinder.

Each piece looks trivial. At tens of thousands of swipes a second, though, inserts need a write-optimised store, the match lookup races when two people swipe together, and the stack must never repeat someone. The steps follow A Framework for Any Design. Try each "Your turn" box before reading on.

#Clarify the problem

  • Functional: a profile with photos and preferences (age range, genders, maximum distance); a stack of candidates who fit me and whom I fit; swipe left or right; match on two right swipes; list matches.
  • Non-functional: swipe in under 200 ms; exactly one match per mutual right swipe; no profile shown twice; stacks may be minutes stale; right swipes durable, left swipes may be lost.
  • Out of scope: chat (see Design a Chat App), payments, photo moderation, the ranking model.

#Estimate the scale

  • Swipes: 20 million × 100 = 2 billion a day ÷ 86,400 ≈ 23,000 a second; with a 3x evening peak, about 70,000. Every swipe is a write, which rules out a single relational primary.
  • Right swipes: if 30% are right, about 21,000 a second at peak. Only these can match.
  • Swipe history: about 50 bytes a swipe: 2 × 109 × 50 B = 100 GB a day, about 36.5 TB a year.
  • Profiles: 100 million accounts × 2 KB = 200 GB, plus photos in blob storage behind a CDN.
  • Stacks: 200 ids of 8 bytes per daily user: 20 × 106 × 1.6 KB = 32 GB of cache. Their profile cards add 20 × 106 × 2 KB = 40 GB.
Estimate: Memory for &quot;already seen&quot; filters

Each daily user has swiped on 10,000 profiles. A Bloom filter with 1% false positives needs about 9.6 bits per item. How much memory do all daily users' filters take?

You know
  • 20 million daily users
  • 10,000 swiped profiles per user
  • About 9.6 bits per item for 1% false positives

Show the working
  1. One filter: 10,000 × 9.6 bits = 96,000 bits = 12 KB
  2. All users: 20 × 106 × 12 KB = 240 GB
  3. An exact set of 8-byte ids: 10,000 × 8 B = 80 KB each, at least 1.6 TB in total

Estimate 240 GB (anything from 80 GB to 800 GB is a good answer)

About 7 times smaller than the exact set, at the price of hiding 1 in 100 unseen profiles.

Your turn: Define the API

Write the stack and swipe endpoints. How does the second swiper learn of the match at once, and what if the phone retries?

Compare with a model answer

GET /stack returns the next profiles; POST /swipes answers whether it made a match, in the same response. Swipes are keyed by (swiper, target), so a retry changes nothing.

The decision worth arguing is what the stack leaves out: whether each candidate already liked you. Sending it saves a round trip, but anyone reading the traffic could list who liked them. Keep it on the server; 200 ms is fast enough.

The swipe is idempotent by (swiper, target): a repeat or a retry returns the same result (see idempotency and retries).

Your turn: Model the data

Sketch profiles, swipes and likes. Which key answers "do they like each other?" in one atomic step?

Compare with a model answer

Swipe history keyed by swiper, for "who have I seen". Likes keyed by the pair, smaller id first, one flag per direction, so both likes live in one row that one atomic update can check.

#Model the data

Records
profiles                       -- relational, 200 GB
  user_id PK, name, birth_date, gender, bio, photo_urls,
  age_min, age_max, genders_wanted, max_distance_km,
  lat, lng, last_active_at
 
swipes                         -- wide-column, partition key swiper_id
  swiper_id, target_id, direction, created_at
  PRIMARY KEY ((swiper_id), target_id)    -- 2 billion rows a day
 
pair_likes                     -- sharded relational, key = the pair
  low_id, high_id              -- the two user ids, smaller first
  low_likes_high  BOOLEAN
  high_likes_low  BOOLEAN
  matched_at      TIMESTAMP NULL
  PRIMARY KEY (low_id, high_id)

The swipe history is append-only, write-heavy and read by swiper: a wide-column store such as Cassandra takes 70,000 writes a second across a cluster. The pair row needs an atomic read-modify-write on one key: sharded relational rows, or a key-value store with conditional updates. It grows by up to 600 million rows a day (30% of 2 billion swipes), about 9 TB a year at 40 bytes a row, so shard by a hash of the pair. Profiles are relational; their change stream feeds profile cards in the cache and a search index with a geo field for stack building.

Your turn: High-level design

Sketch serving a stack, refilling it, and recording a swipe that may match.

Compare with a model answer

A stack service reading precomputed stacks from cache; a builder querying the geo index and dropping seen profiles; a swipe service that appends to history and updates the pair row.

#High-level design

Opening the app is a cache read. Swipes go to the history for "seen" and the pair row for "matched".

#Deep dives

#Recording 70,000 swipes a second

Each swipe is a tiny append; the only read is "all swipes by this user", to rebuild a seen filter. Partition by swiper_id and cluster by target_id, so a repeated swipe overwrites one cell. A log-structured store (see indexing) appends each write to memory and a commit log, so it takes this rate on modest hardware.

Left swipes, 70% of volume, only feed the seen filter: one replica's acknowledgement is enough. Right swipes use a quorum. A partition grows by 36,500 swipes a year, under 2 MB.

#Detecting a match exactly once

Ana and Ben swipe right 3 ms apart. The obvious method writes "Ana likes Ben" under Ana's key, then reads "does Ben like Ana?" under Ben's. On lagging replicas both reads can miss: no match, ever. If both see it, both announce one.

Ben likes Ana: set my flag, match if theirs is set
-- Ana is user 12, Ben is user 91: low_id = 12, high_id = 91
INSERT INTO pair_likes (low_id, high_id, low_likes_high, high_likes_low)
     VALUES (12, 91, false, true)
ON CONFLICT (low_id, high_id) DO UPDATE
   SET high_likes_low = true,
       matched_at = CASE WHEN pair_likes.low_likes_high
                         AND pair_likes.matched_at IS NULL
                         THEN now() ELSE pair_likes.matched_at END
RETURNING matched_at;    -- not null: tell Ben "It's a match"

Why it is exact: updates on the row run in turn, only the second sees both flags, and detecting and storing the match is one write. A retry finds matched_at already set and returns the same answer; the pair key is the match id, so a redelivered event makes no second match.

Detecting the match, then saving it in a second step

If the server detects "both liked" and crashes before writing the match, nobody ever sees it: both likes are stored and no future swipe checks again. Record the match in the same atomic write or transaction that detects it.

#Building the stack

A good candidate is nearby, fits my filters, has me inside theirs, is unseen and recently active. That barely changes in an hour, so precompute it.

The builder runs one search index query: a geo filter around me (cells and neighbours, as in Design Ride Sharing), plus age, gender, the other person's age range and genders, and active in 30 days. It drops seen profiles, checks each candidate's own distance limit, ranks, and caches 200 ids. The stack service serves 20 at a time and refills below 50, so a heavy swiper never waits.

The cost is staleness: a stacked profile may be deleted since, so each batch of 20 is checked against deletions and my seen filter. Rebuild the stack when the user moves a few kilometres.

#Never showing a profile twice

The builder must drop everyone I swiped on from 1,000 candidates. The history is exact but a large read per refill.

My pick.

A Bloom filter answers "definitely not seen" or "probably seen", so its error is the safe way round. In a small town the cost is real: 1% of 1,000 candidates is 10 people never shown, so offer the exact set to users with a small pool. When a user outgrows the filter's sized count, rebuild a larger one from history; an overfull filter's false-positive rate climbs fast.

#Bottlenecks and failures

At 10x, 700,000 swipes a second, the history cluster adds nodes; partitions are per user. The pair store adds shards for 210,000 right swipes a second; pair keys hash evenly, and a popular profile's likes spread over many pair rows, so no row is hot. The geo index sees only refill load.

When this diesWhat happensWhat you do

A swipe-history nodeIts replicas take its writes.Replication factor 3; quorum writes survive one node down.
The stack builderStacks drain without refills.Refills start with 50 left, so users keep swiping while it restarts; an empty stack is built on demand.

#What a strong answer sounds like

LevelWhat the answer does
JuniorChecks one swipes table for the reverse swipe; misses the race until prompted.
MidEstimates the write rate, picks a write-optimised store, precomputes stacks from a geo index.
SeniorShows why write-then-read can miss or duplicate a match, decides it with one atomic write on a pair key, keeps "who liked me" off the client, and weighs the Bloom filter's 1% loss against its memory saving.

#Follow-up questions

#How would you add a "see who liked you" feature?

It means pair rows where their flag is set and mine is not, which needs an index by user: keep a per-user "liked by" list fed by the pair rows' change stream. Serve it from the server, only to entitled users.

#A user travels to another city. What changes?

The location update moves their geo index document and discards their stack; the next refill uses the new place. The seen filter stays.

#How do you stop a few very popular profiles from appearing in every stack?

In ranking: the builder counts impressions per profile and down-ranks those far above their share.

#A user unmatches. Can they appear again?

No. The swipe stays in history and the seen filter, and the pair row keeps both flags plus an unmatched_at time, so a retry cannot recreate the match.

#How would you shard the geo index?

By region, with maximum distance capped at, say, 100 km so a query stays in one region. Big cities get more replicas; a profile near a border goes in both regions.
