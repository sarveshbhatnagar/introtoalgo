Unique IDs

Generate unique IDs across many machines: auto-increment, UUIDs, Snowflake-style time-ordered IDs worked out bit by bit, and range allocation.

An orders table outgrows one database and is split across 4. Each database keeps its own auto-increment counter, so within a day shard 1 and shard 3 have both created order 1001. Support looks up order 1001 and finds two. The analytics job that merges all shards silently overwrites one with the other.

On one machine, unique IDs are free. Across many machines, every server must hand out IDs no other server will ever produce, ideally without asking anyone first.

#The idea

There are three ways to avoid a clash without a central counter on every request: make IDs so random that clashes are practically impossible (UUIDs), build each ID from parts that are unique on their own, such as time plus a machine number plus a counter (Snowflake-style), or hand each server a private block of numbers in advance (range allocation).

Beyond uniqueness, ask three questions. Must the ID fit in 64 bits? Should IDs sort by creation time? Is it a problem if outsiders can guess the next ID or count your orders?

Range allocation is the simplest to run when you already have a small, reliable allocator: a server asks for "the next 1,000", gets 7,000 to 7,999, and hands them out from memory. If it crashes, the unused numbers are skipped, which is harmless. The allocator is called once per thousand IDs, so it needs high availability but almost no capacity.

How unlikely is a UUID v4 clash? It has 122 random bits. By the birthday estimate, n IDs collide with probability about n² ÷ 2123. For a trillion IDs: (1012)² ÷ (1.06 × 1037) ≈ 10−13. Treat it as never, provided the random generator is a good one.

#A Snowflake-style ID, bit by bit

Split a 64-bit integer into fields. Because the timestamp sits in the highest bits, sorting IDs as numbers sorts them by time.

  • Sign, 1 bit: always 0, so the ID stays positive in languages with signed 64-bit integers.
  • Timestamp, 41 bits: milliseconds since an epoch you choose, such as your launch date. 241 ms = 2.2 × 1012 ms, about 70 years before it runs out.
  • Machine, 10 bits: 210 = 1,024 generators can run at once.
  • Sequence, 12 bits: a counter that resets every millisecond. 212 = 4,096 IDs per ms per machine, so about 4 million a second each.

Build the example: shift each field into place and add. 1,000,000,000 × 222 = 4,194,304,000,000,000. Then 37 × 212 = 151,552. Then the sequence, 5. The ID is 4,194,304,000,151,557. Reading it back is the reverse: divide by 222 for the timestamp, and so on.

The split is yours to tune. Fewer machines and more sequence bits suits a few very busy generators; a shorter timestamp in seconds lasts longer but sorts less finely.

64-bit IDs in JavaScript

JavaScript numbers are exact only up to 253. With 22 bits below the timestamp, any timestamp past 231 ms (about 25 days after the epoch) produces an ID that a browser silently rounds. Send these IDs as strings in JSON.

#Numbers worth remembering

  • 210 ≈ 1 thousand, 220 ≈ 1 million, 230 ≈ 1 billion, 240 ≈ 1 trillion.
  • A 64-bit ID is 8 bytes; a UUID is 16 bytes, or 36 characters as text. On a billion rows and their indexes, that difference is many gigabytes.
  • Snowflake-style capacity: 4,096 per ms × 1,000 ms = about 4 million IDs a second per machine.

#In the interview

IDs come up whenever data is sharded or written from many servers, and in any design that shows items in time order (feeds, chats). State the requirements first: "IDs must be unique across shards, fit in 64 bits, and roughly sort by time, so I'd use a Snowflake-style generator inside each service."

Follow-ups you should expect:

  • "What if the clock goes backwards?" Refuse or wait until it passes the last timestamp used; alert if the jump is large.
  • "How are machine numbers assigned?" From a coordination service with a lease, or from configuration. The lease must be held while generating.
  • "Can outsiders learn anything from your IDs?" Yes. Sequential IDs reveal volume, and time-based ones reveal when a record was made. Where that matters, show users a separate random public ID.
  • "Why not UUIDs?" Fine if 128 bits is acceptable; prefer a time-ordered version so index inserts stay sequential.

#Common mistakes

Random IDs as a clustered primary key

Random UUID v4 keys land all over the index, so every insert touches a different page and large tables slow down. Use a time-ordered ID when the key decides physical order.

Quick check

Your layout uses 10 machine bits and 12 sequence bits. How many IDs can one machine make in one second at most?

  1. Not quite. That is per millisecond. A second has 1,000 of them.
  2. Right. 4,096 per ms × 1,000 ms = 4,096,000.
  3. Not quite. That multiplies by all 1,024 machines too. The question asks about one.

Which ID choice fits best: 64-bit keys, sorted by time, written by 200 servers?

  1. Not quite. Every insert would wait on one database.
  2. Not quite. 128 bits and random order: fails both requirements.
  3. Right. 64 bits, time in the high bits, and 200 servers fit easily into 1,024 machine numbers.
