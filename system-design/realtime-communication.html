Realtime Communication

Push updates to users the moment they happen: polling, long polling, server-sent events and WebSockets, and how open connections reshape the design.

A chat app has 1 million people with the app open. Each phone asks "anything new?" every 5 seconds: 1,000,000 ÷ 5 = 200,000 requests a second. Only about 2,000 new messages arrive a second, so 99% of answers are "no". And a message still waits 2.5 seconds on average before anyone sees it.

The fix: keep a connection open and let the server speak first. Cheap for the network, costly for your architecture: servers now remember who is connected to them.

#The idea

HTTP is built for the client to ask and the server to answer. Realtime features need the server to send when something happens. Four ways to get there:

  • Short polling: the client asks on a timer.
  • Long polling: the server holds each request open until there is news or about 30 seconds pass; the client then asks again. Messages arriving between polls need a cursor ("everything after 9001") or they are missed.
  • Server-sent events (SSE): one HTTP response that never ends; the server writes text events into it. Server to client only. Browsers reconnect on their own and send the last event id, so the server can resume.
  • WebSocket: an HTTP request that upgrades into a two-way message channel over the same TCP connection. Reconnecting and replaying missed messages are up to you.

#How open connections change the design

With request and response, any server can answer any request. With a WebSocket, Ben's connection lives on one server for hours. Ana's message to Ben lands on Ana's server, and something must get it to Ben's. That reshapes the system:

  • Connection servers become their own tier. They only hold sockets and pass messages, so you can deploy business logic without dropping a million connections.
  • Pub/sub routes between servers. When Ben connects, his server subscribes to user:ben; anyone with a message for Ben publishes there. This replaces a shared registry ("Ben is on server 7"), and a dead server's subscriptions vanish with it.
  • The database is the source of truth. Basic pub/sub delivers at most once, only to current subscribers. Store first, so offline clients can catch up.

The random wait in step 7 matters. If server 2's 50,000 sockets all reconnect in one second, they hit the fleet like an attack. Spread over 30 seconds: 50,000 ÷ 30 ≈ 1,700 a second.

Long-lived connections bring two chores:

  • Heartbeats: ping every 30 seconds or so. A phone that loses signal never closes its socket, and proxies cut idle connections.
  • Deploys: drain a server by moving clients elsewhere a slice at a time, not killing it with everyone attached.

#Numbers worth remembering

  • Polling load = users ÷ interval in seconds.
  • An idle connection costs memory, not CPU. Assume something like 50,000 per server and say you would load test it.
  • Heartbeat load = connections ÷ interval: 2 million every 30 seconds ≈ 67,000 small messages a second.

#In the interview

Bring this up when a requirement says "instantly", "live" or "as it happens": chat, notifications, a driver's position, a shared document. Pick the transport fast, then spend your time on routing and recovery. Phrases that show judgement: "Users both send and receive, so WebSockets." "Connection servers are stateful, so I keep them thin." "Pub/sub is fire-and-forget, so the store is the truth."

Follow-ups to expect:

  • "A user has a phone and a laptop." Two connections, both subscribed to the user's channel, so both get it.
  • "How do you balance WebSockets?" Least connections, long idle timeouts, draining on deploy.
  • "Are messages in order?" Within a conversation, yes: the store assigns increasing ids and clients sort by them. Global order is not needed.
  • "What if a publish is lost while Ben is online?" His app sees 9003 after 9001 and fetches 9002. A lost last message leaves no gap, so apps also sync when opened.

#Common mistakes

Treating pub/sub as delivery

Basic pub/sub drops messages when no one is subscribed. Store first, publish second, and let clients resync by last id.

Reconnecting all at once

Instant retries turn one crashed server into a wave that knocks over the next. Use exponential backoff with random jitter.

Quick check

300,000 users keep a dashboard open that polls every 10 seconds. How many requests a second is that?

  1. Not quite. That divides by 100, not 10.
  2. Right. 300,000 ÷ 10 = 30,000 a second.
  3. Not quite. That multiplies by the interval instead of dividing.

A sports site shows live scores in the browser. Readers never send anything back. Which transport fits best?

  1. Not quite. It works, but you build reconnects and resume yourself for a one-way channel.
  2. Right. One-way push over HTTP, with reconnect and resume built in.
  3. Not quite. Scores would arrive up to a minute late.
