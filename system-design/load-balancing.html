Load Balancing

Spread requests over many servers and route around dead ones: layer 4 vs 7, algorithms, health checks, sticky sessions and a balancer that stays up.

Launch day: the API expects 3,000 requests a second at peak, and one app server handles about 1,000 before its latency climbs. So you need at least three servers. But clients know one address, and when one of those servers crashes mid-afternoon, somebody has to stop sending it traffic.

#The idea

A load balancer sits in front of many identical servers and owns the public address; it picks a server for each request or connection. That gives you two things at once: capacity, because you scale by adding servers behind it, and availability, because a dead server is taken out of the pool.

It costs an extra hop (under a millisecond inside a data center), one more component that must not fail, and a rule: any server must be able to handle any request. That rule is what "stateless" means.

#Spreading requests and surviving a crash

Run four servers, not three, so losing one still leaves enough. Each then gets 3,000 ÷ 4 = 750 requests a second. Step through round robin, then a crash.

Health checks come in two kinds. Active checks call an endpoint on a timer, as above. Passive checks watch real traffic and eject a server that returns errors or times out, which catches problems faster.

#Sticky sessions and stateless servers

If server A keeps your shopping cart in its own memory, every request from you must reach A. Balancers can do that with sticky sessions, usually a cookie naming the server. But load gets uneven, and when A dies the carts on it are gone.

The better answer is stateless servers: keep session data in a shared store (an in-memory store such as Redis) or in a signed token the client sends. Then any server can handle any request, a crash loses nothing, and you add or remove servers freely.

#When the balancer is the weak point

One balancer in front of everything is a single point of failure. The usual fix is the pair in the first diagram: an active and a standby that share a virtual IP, with the standby taking the IP when heartbeats stop. At larger scale, run several active balancers and spread clients over them with DNS returning several addresses, or with one address announced from many places (anycast). Managed cloud balancers already do this; say so rather than drawing it.

Reverse proxies and API gateways sit in the same spot. A reverse proxy receives requests on behalf of servers: it terminates TLS, compresses and caches. A layer 7 load balancer is a reverse proxy that spreads load. An API gateway is a reverse proxy with API concerns added: authentication, rate limiting, and routing /orders and /users to different services. In a diagram, one box labelled "API gateway / load balancer" is fine.

#Numbers worth remembering

  • Worst-case detection time is check interval × failures needed: 5 s × 2 = about 10 s.
  • Servers needed: peak requests ÷ per-server capacity, rounded up, plus at least one spare.
Estimate: How many app servers

How many app servers do you run so the peak is still served after one server fails?

You know
  • 2,000 requests a second on average
  • Peak is 3 times the average
  • One server handles 500 requests a second at a healthy load

Show the working
  1. Peak: 2,000 × 3 = 6,000 requests a second
  2. Servers at peak: 6,000 ÷ 500 = 12
  3. One spare for a failure: 12 + 1 = 13

Estimate 13 (anything from 6 to 40 is a good answer)

With several zones, size so losing a whole zone still leaves enough: more spare than one server.

#In the interview

Draw a load balancer as soon as you have more than one server, then name the choices it implies: "Layer 7, round robin, health checks every few seconds, and the app servers are stateless, with sessions in a shared store, so I can scale them freely."

Follow-ups to expect:

  • "What if the load balancer dies?" Active-standby pair sharing a virtual IP, or several active ones behind DNS or anycast.
  • "How do you deploy without dropping requests?" Take a server out of the pool, let in-flight requests finish (draining), update it, put it back.
  • "WebSockets behind a balancer?" Least connections, since each connection lasts hours, and plan for clients reconnecting when a server goes away.

#Common mistakes

Sizing for exactly the peak

Three servers for a load that needs three means one crash overloads the other two, and they fall over too. Always add spare capacity for the failure you expect.

Health checks that test everything

If /health fails whenever any dependency is slow, one shared hiccup marks every server down at once. Check that this server can work; let the dependencies have their own alarms.

Quick check

Health checks run every 10 seconds and a server is marked down after 3 failures in a row. It crashes while taking 400 requests a second, and the balancer does not retry. About how many requests fail?

  1. Not quite. That counts one check interval, but it takes three failed checks to remove the server.
  2. Right. Detection takes up to 10 × 3 = 30 seconds, and 400 × 30 = 12,000 requests hit the dead server.
  3. Not quite. That multiplies 400 by the 3 failures, not by the 30 seconds they take.

A chat service keeps WebSocket connections open for hours, and some users are much more active than others. Which balancing algorithm fits?

  1. Not quite. It hands out new connections evenly, but long connections end at different times, so open counts drift apart.
  2. Right. Long-lived connections pile up unevenly; sending new ones to the emptiest server keeps the count balanced.
  3. Not quite. Many users share an IP behind an office or mobile network, so some servers get far more connections.

You need to route /api/orders to one service and /api/users to another. What do you need?

  1. Not quite. It sees IPs and ports only, never the URL path.
  2. Right. It reads the HTTP request, so it can route by path.
  3. Not quite. That changes the public API instead of routing it.
