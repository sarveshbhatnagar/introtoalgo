Design an LLM Chat Service

Design a consumer AI chat product: streamed replies that survive reconnects, scarce GPU capacity, token budgets, context assembly, safety and cost.

Maya types "Plan three days in Lisbon" and the answer starts appearing word by word in under a second. She closes the app halfway, opens it on the train, and the reply is there, finished.

It looks like a chat app with a bot, but the "other person" is a pool of GPUs that is expensive, slow to grow and easy to overload; each reply takes seconds; and each request carries the conversation so far. The steps follow A Framework for Any Design; try each "Your turn" box before reading on.

#Clarify the problem

  • Functional: start a conversation, send a message, stream the reply, stop it, list and reopen past conversations, edit a message or regenerate a reply.
  • Non-functional: first words within 1 second for most requests; streaming at reading speed or faster; replies survive reconnects; no user message lost; free users throttled before paid; safety checks on everything.
  • Out of scope: training the model, file uploads, tool use and web search, voice.

#Estimate the scale

Count in tokens, not requests: a 5-token and a 2,000-token reply are one request each but cost 400 times apart. These figures are assumptions; measure your own hardware.

  • Messages: 10 million users × 10 = 100 million a day ÷ 86,400 ≈ 1,200 a second, about 3,500 at a peak of 3x.
  • Tokens per request: about 2,000 in (instructions plus history) and 500 out. A free user's budget of 10 such messages a day is 25,000 tokens; input counts because long conversations cost GPU time too.
  • Token rate: 3,500 × 500 = 1.75 million output tokens a second at peak, plus 3,500 × 2,000 = 7 million input tokens to read.
  • Open streams: at 50 tokens a second, a 500-token reply takes 10 seconds. In flight = arrival rate × duration = 3,500 × 10 = 35,000 streams at peak.
  • Storage: 400 B message + 2,000 B reply + 600 B metadata = 3 KB per exchange: 300 GB a day, about 110 TB a year.
Estimate: How many GPU replicas at peak

A model replica (one copy of the model on its GPUs) runs 40 streams at once, each at about 50 tokens a second. How many replicas cover the peak output rate?

You know
  • 3,500 messages a second at peak
  • 500 output tokens per reply
  • One replica: 40 streams × 50 tokens a second

Show the working
  1. Peak output: 3,500 × 500 = 1,750,000 tokens a second
  2. One replica: 40 × 50 = 2,000 tokens a second
  3. 1,750,000 ÷ 2,000 = 875, call it 900; the average of 1,200 a second needs 300

Estimate 900 (anything from 300 to 3000 is a good answer)

Check with streams: 35,000 ÷ 40 = 875. Reading 7 million prompt tokens a second also takes GPU time, so plan headroom.

The decision worth arguing is server-sent events over WebSockets. A streaming reply is one-way; the user's message is an ordinary POST. Server-sent events are plain HTTP, pass existing proxies, and define resume: a reconnecting client sends Last-Event-ID. A WebSocket buys two-way traffic you do not need (see real-time communication).

Your turn: Model the data

Sketch conversations and messages. How do you represent "regenerate this reply" and "edit my earlier message", and where do tokens live while a reply streams?

Compare with a model answer

Messages form a tree: a regenerated reply or edited message is a new sibling under the same parent. Tokens in flight live in a short-lived stream buffer; the finished reply is stored once.

#Model the data

Conversations, messages, usage
conversations              -- partition key: user_id
  user_id, conversation_id       PRIMARY KEY
  title          TEXT
  updated_at     TIMESTAMP       -- list newest first
  summary        TEXT NULL       -- of older turns, see deep dives
  summary_upto   message_id NULL
  current_leaf   message_id      -- the path being shown
 
messages                   -- partition key: conversation_id
  conversation_id, message_id    PRIMARY KEY   -- time-ordered ids
  parent_id      message_id NULL
  role           VARCHAR(10)     -- user | assistant
  content        TEXT
  tokens         INT
  status         VARCHAR(10)     -- streaming | complete | stopped | blocked | failed
 
usage                      -- one row per user per day
  user_id, day, tokens_in, tokens_out

Append a message, read a conversation in order, list conversations by recency: no joins, append-only, 110 TB a year. A wide-column store (such as Cassandra) keyed by conversation fits, as in Design a Chat App. The stream buffer is an in-memory log per reply (a Redis stream, say) that expires 10 minutes after the reply finishes.

#Deep dives

#Streaming that survives reconnects

Separate generating a reply from delivering it. If the reply lived only in the HTTP connection, every drop would lose a half-finished answer and its GPU time.

  • Generation writes numbered chunks into the reply's buffer, whoever is listening.
  • Delivery is any chat server reading from the client's last sequence number.
  • Retries: a POST retried with the same client_msg_id attaches to the existing stream, never making two replies (see idempotency).
  • Stop: an explicit stop frees the batch slot at once; a disconnect does not, since users expect the reply when they return.
  • Server crash: the buffer still has every chunk; another server sees the reply stuck in streaming with no heartbeat and finishes it as a continuation.

#GPU capacity: batching, admission and tiers

You cannot autoscale out of a peak: new GPU capacity takes minutes and may not exist. So manage a fixed pool:

  • Continuous batching. Each step, a replica produces one token for every stream in its batch, so 40 streams cost little more per step than one. A fixed batch waits for its longest reply; continuous batching adds requests between steps and frees a slot the moment a reply ends. The limit is memory: each stream keeps per-token state (the attention key/value cache), so an 8,000-token conversation takes about four times the room of a 2,000-token one. Long prompts are read in pieces between steps so they do not stall the batch.
  • Admission control. The router queues per tier and estimates the wait as queued tokens ÷ pool throughput. Past 10 seconds for the free tier, new free requests get 429: a fast "busy, try in 30 seconds" beats a timeout after the GPU time was spent.
  • Rate limits in tokens. A per-user token bucket counts tokens, not requests: one 8,000-token request costs what four 2,000-token ones do. Reserve input plus the output cap, then refund the difference.
  • Priority tiers. The router fills free slots from the paid queue first, keeping a fixed share for free requests so they slow but do not starve.

#Building the context

The model remembers nothing between requests: each carries the instructions and conversation so far inside a limited context window. Longer prompts cost more, delay the first word, and can make answers worse (context rot), so budget each request, here 8,000 tokens: instructions 1,000, reply cap 1,000, summary up to 500, recent turns 5,500.

A 40-turn conversation at about 600 tokens a turn is 24,000 tokens; most cannot be sent. Older turns go into a rolling summary: when recent turns pass about 4,500 tokens, a background job folds the oldest 2,000 into the summary with a small model, storing the id of the last message covered. Retrieval over old turns (Design a RAG System) can recover a dropped detail; context engineering covers the prompt side.

Order matters for cost. A model server can reuse work on a recent prompt prefix, but only if it matches token for token from the start. So put fixed instructions first, then the summary, then the turns; between summary refreshes turns are only appended, so consecutive requests share a long prefix. The router sends a conversation back to its last replica (consistent hashing on the conversation id, with a fallback when full) so the prefix is not read again. Caching whole replies rarely pays: contexts almost never match after the first turn.

#Safety in the path

Two checks, placed for cost and latency (see guardrails):

  • Input, before the queue. A small classifier checks the message, so a blocked request costs no GPU time. Treat pasted text as data, not instructions (see prompt injection).
  • Output, while streaming. Checking only the finished reply shows unchecked text for 10 seconds; checking every token is too slow. Hold each sentence until it passes, a fraction of a second. Mark passed chunks in the buffer, so a resume replays only checked text. If a later sentence fails, stop generation and send a retract event to replace what the client showed.

If the safety service is down, fail closed: pause new generations rather than ship unchecked output. A classifier outage then becomes a product outage, so run it redundantly.

Running safety checks after the GPU

Checking the input only after generation wastes GPU time on requests you will refuse anyway. Cheap checks go before the expensive step.

#Bottlenecks and failures

At 10x, 35,000 messages a second at peak, the web tier and store scale out as usual. The GPU pool needs about 9,000 replicas, which you may not be able to buy or power. Beyond the controls above, the levers are fewer tokens per reply, smaller models for more requests, and routing load to regions where it is night.

#Follow-up questions

#How do you measure whether you are meeting the latency goal?

Track time to first token and tokens per second, split into queue wait and model time, per tier. Rising queue wait with flat model time means capacity or shedding, not faster code.

#How does "regenerate" work?

It adds a sibling of the old reply under the same parent and reruns the context; the current leaf points to the new one, and the old stays reachable. Sampling makes them differ (see sampling and temperature).

#How would you add memory across conversations?

Extract a few facts per user after conversations and add relevant ones within the context budget. Users must be able to see and delete them (see memory).
