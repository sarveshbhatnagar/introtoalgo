Design an LLM Chat Service

How to design an LLM chat service: streaming replies, sharing a fixed GPU pool, building context and safety checks.

An LLM chat service lets a user send a message to a language model and read the reply as it is generated. Interviewers ask for it because the model servers behave differently from ordinary web servers: the GPUs are expensive and slow to add, each reply takes several seconds, and every request carries the whole conversation so far.

The design has to deliver a long reply over a connection that can drop, share a fixed GPU pool between free and paid users, fit a long conversation into the model's limited input and run safety checks. The steps follow A Framework for Any Design, and you should try each "Your turn" box before reading the answer.

#Clarify the problem

  • Functional requirements: a user can start a conversation, send a message, read the streamed reply, stop it, reopen past conversations, and edit a message or regenerate a reply.
  • Non-functional requirements: the first words appear within 1 second for most requests, a reply survives a reconnect, no user message is lost, free users are throttled before paid users, and all input and output passes safety checks.
  • Out of scope: training the model, file uploads, tool use, web search and voice.

#Estimate the scale

Model cost depends on the number of tokens processed, so the estimate counts tokens. The figures below are assumptions.

  • Message rate: 10 million users sending 10 messages is 100 million messages a day. Divided by 86,400 seconds, that is about 1,200 messages a second on average and about 3,500 at a peak of 3 times the average.
  • Tokens per request: a request has about 2,000 input tokens (instructions plus history) and 500 output tokens. A free user's daily budget of 25,000 tokens covers about 10 such messages, and input tokens count because they cost GPU time too.
  • Token rate at peak: 3,500 × 500 is 1.75 million output tokens a second.
  • Open streams: a model replica generates about 50 tokens a second per stream, so a 500-token reply takes 10 seconds. The streams open at once are the arrival rate times the duration: 3,500 × 10 = 35,000 at peak.
  • Storage: one exchange needs about 400 B for the message, 2,000 B for the reply and 600 B of metadata, which is 3 KB. That is 300 GB a day and about 110 TB a year.
Estimate: How many GPU replicas at peak

A model replica (one copy of the model on its GPUs) runs 40 streams at once, each at about 50 tokens a second. How many replicas cover the peak output rate?

Your turn: Define the API

Write the endpoints for sending a message and streaming the reply. What happens when the connection drops halfway through a reply, and what does an overloaded server return?

Compare with a model answer

Sending a message is a POST that is answered with a server-sent event stream of numbered chunks, and a resume endpoint accepts the id of the last chunk the client saw. A client-generated message id makes retries safe. An overloaded server returns 429 with a Retry-After header.

The API decision worth arguing is server-sent events instead of WebSockets. Streaming a reply sends data in one direction only. Server-sent events are plain HTTP, so they pass through existing proxies, and they define resuming, because a reconnecting browser sends the Last-Event-ID header. A WebSocket would add two-way traffic that this product does not need (see real-time communication).

Your turn: Model the data

Sketch the conversation and message records. How do you represent "regenerate this reply" and "edit my earlier message", and where do the tokens live while a reply is still streaming?

Compare with a model answer

Messages form a tree, so a regenerated reply or an edited message becomes a new sibling under the same parent. Tokens that are still being generated live in a short-lived stream buffer, and the finished reply is stored once in the message table.

#Model the data

Conversations, messages, usage

  user_id, conversation_id       PRIMARY KEY

  updated_at     TIMESTAMP       -- used to list newest first
  summary        TEXT NULL       -- summary of older turns, see deep dives
  summary_upto   message_id NULL
  current_leaf   message_id      -- the branch the user is viewing
 
messages                   -- partition key: conversation_id
  conversation_id, message_id    PRIMARY KEY   -- time-ordered ids
  parent_id      message_id NULL
  role           VARCHAR(10)     -- user | assistant
  content        TEXT
  tokens         INT
  status         VARCHAR(10)     -- streaming | complete | stopped | blocked | failed
 
usage                      -- one row per user per day
  user_id, day, tokens_in, tokens_out

The access patterns are to append a message, to read one conversation in order and to list a user's conversations by recency. None needs a join, and the data grows by about 110 TB a year. A wide-column store such as Cassandra, keyed by conversation, fits this pattern, as it does in Design a Chat App. The stream buffer is an in-memory log for each reply that expires 10 minutes after the reply finishes.

Your turn: High-level design

Sketch the components between the user's phone and the GPUs. Where are token budgets checked and context built, what chooses the replica, and how do tokens travel back to the phone?

Compare with a model answer

A gateway checks the token budget. A chat service saves the message, builds the context and runs the safety checks. An inference router queues requests by tier and places them on replicas, and the tokens return through a stream buffer.

#High-level design

#Deep dives

#Streaming a reply so that it survives reconnects

A reply takes about 10 seconds to generate, and mobile connections drop often. If generation is tied to the HTTP connection, a dropped connection loses the half-finished reply and wastes the GPU time already spent on it.

The fix is to separate generating a reply from delivering it. Generation writes numbered chunks into a per-reply buffer, whether or not anyone is listening. Delivery is any chat server forwarding chunks from that buffer. A reconnecting client sends the number of the last chunk it saw, and whichever server receives the request replays everything after it and then follows the live stream.

Three details matter. First, a retried POST with the same client_msg_id attaches to the existing reply instead of creating a second one (see idempotency). Second, a stop request frees the replica's batch slot immediately, but a disconnect does not, because the user usually returns for the reply. Third, if a chat server crashes, the buffer still holds every chunk, so another server that finds the reply stuck in the streaming state with no heartbeat can finish delivering it.

#Sharing a fixed GPU pool

You cannot autoscale out of a traffic peak, because new GPU capacity takes minutes to start and may not exist, so the system must decide who is served when demand exceeds a fixed pool. Four mechanisms work together.

Continuous batching is how one replica serves many streams. In each step the replica produces one token for every stream in its batch, so 40 streams cost little more per step than one. Continuous batching adds new requests between steps and frees a slot the moment a reply ends, instead of waiting for the longest reply in a fixed batch. The limit is memory: each stream keeps per-token state in the attention key/value cache, so an 8,000-token conversation takes about four times the memory of a 2,000-token one.

Admission control limits how much work enters the pool. The router keeps a queue per tier and estimates the wait as the queued tokens divided by the pool's throughput. When the estimated wait for the free tier passes 10 seconds, new free requests receive a 429 response with a retry time. An immediate "busy" answer is better than a timeout that arrives after the user has waited.

Token-based rate limits keep any one user from taking the pool. A per-user token bucket counts tokens and not requests. The gateway reserves the input tokens plus the output cap when the request arrives and refunds the difference when the reply ends.

Priority tiers decide who is served first. The router fills free slots from the paid queue first but reserves a fixed share for free requests, so free users slow down but are not starved.

#Building the context for each request

The problem is that the model remembers nothing between requests, so each request must carry the instructions and the conversation so far inside a limited context window. Longer prompts cost more, delay the first word and can make answers worse (see context rot), so each request gets a fixed budget. Here the budget is 8,000 tokens: 1,000 for instructions, 1,000 for the reply, 500 for a summary and 5,500 for recent turns.

A 40-turn conversation at about 600 tokens a turn is 24,000 tokens, so most of it cannot be sent. There are three ways to handle that.

Truncation drops the oldest turns. It is trivial to build, but the model forgets everything early in the conversation, including the user's original goal.

A rolling summary keeps the gist of the old turns. When the recent turns pass about 4,500 tokens, a background job folds the oldest 2,000 tokens into the stored summary with a small model and records the last message it covered. This keeps the main facts for the price of an occasional extra model call, although the summary can lose details.

Retrieval over old turns indexes every turn and adds the most relevant ones to the prompt. It can recover a detail that a summary dropped, but it needs an index and adds latency (see Design a RAG System). A rolling summary is the right default for most chat products, with retrieval added only when users expect exact recall of old details.

Prompt order affects cost. A model server can reuse the work it did on a recent prompt prefix, but only if the new prompt matches the old one token for token from the start. For that reason the prompt puts the fixed instructions first, then the summary, then the turns, so that consecutive requests share a long prefix between summary refreshes. The router also sends a conversation back to the replica that served it last, using consistent hashing on the conversation id.

#Where to run the safety checks

Every message and every reply must be checked (see guardrails), but a check in the wrong place either delays every user or lets harmful text reach the screen.

The input check runs before the request enters the queue. A small, fast classifier reads the message, so a blocked request uses no GPU time.

For the output check there are three placements. Checking only the finished reply is simple, but the user has already read up to 10 seconds of unchecked text. Checking every token is too slow and too noisy for a classifier to judge. The compromise is to hold each sentence back until it passes the classifier, which adds a fraction of a second. Only chunks that passed are replayed to a resuming client. If a later sentence fails, the service stops generation and sends a retract event that makes the client replace what it showed.

If the safety service is down, the system fails closed and pauses new generations. This turns a classifier outage into a product outage, so the classifier runs redundantly.

#Bottlenecks and failures

At 10 times the load, or 35,000 messages a second at peak, the gateway, chat service and store scale out. The GPU pool is the real limit: it would need about 8,750 replicas, which may be impossible to buy or power. The remaining levers are shorter replies and smaller models.

#Follow-up questions

#How do you measure whether you are meeting the latency goal?

Track the time to the first token and the tokens per second for each tier, and split the first figure into queue wait and model time. If queue wait rises while model time stays flat, the problem is capacity and not code speed.

#How does regenerating a reply work?

The service adds a new sibling of the old reply under the same parent message and runs the context-building step again. The current leaf then points to the new reply, and the old one stays reachable as another branch.

#What happens when the user presses stop?

The client calls the stop endpoint, and the router frees the replica's batch slot at once. The text generated so far is saved with the status stopped. The user is charged only for the tokens actually produced, so the gateway refunds the rest of the reserved budget.

#How would you add memory across conversations?

After a conversation ends, a background job extracts a few facts about the user and stores them, and the most relevant ones are added to later prompts within the context budget. Users must be able to see and delete these facts (see memory).
