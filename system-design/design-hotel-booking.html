Design Hotel Booking

How a hotel booking system searches availability, claims several nights in one transaction, holds rooms during payment and handles overbooking.

A hotel booking site lets guests search for places to stay by location, dates and number of guests, look at a listing, and book one or more rooms for a range of nights. It is hard to design for two reasons. A stay covers several nights, so one booking has to claim several inventory rows at once without ever selling a night twice. And guests search and browse far more often than they book, so most of the load comes from reading availability that keeps changing.

The steps below follow A Framework for Any Design.

#Clarify the problem

  • Functional: search by place, dates and number of guests; view a listing with photos, prices and a calendar; book one or more rooms of a type for a range of nights; pay; cancel.
  • Non-functional: no night is ever sold beyond its limit, so inventory needs strong consistency; search responds within 300 ms and may lag behind bookings by a few seconds; listing pages respond within 200 ms; a hold lasts 15 minutes; a confirmed booking is never lost.
  • Out of scope: reviews, host payouts, messaging, price setting and loyalty programmes.

#Estimate the scale

A day has 86,400 seconds, and we assume the busiest hour runs at 5 times the average rate.

  • Bookings: 500,000 ÷ 86,400 is about 6 a second, and about 30 a second at peak. One database primary can handle this.
  • Searches: 500,000 × 100 = 50 million a day, which is about 600 a second and 3,000 a second at peak.
  • Listing views: 500,000 × 200 = 100 million a day, which is about 1,200 a second and 6,000 a second at peak.
Estimate: Inventory rows for a year ahead

Inventory is stored as one row per room type per night, for the next 365 nights. How much space do those rows take?

You know
  • 1 million properties
  • 2 room types per property on average (a home is one room type with one unit)
  • 365 nights ahead
  • About 50 bytes per row

Show the working
  1. 1,000,000 × 2 = 2 million room types
  2. 2,000,000 × 365 = 730 million rows
  3. 730 × 106 × 50 B ≈ 36.5 × 109 B, about 37 GB

Estimate 37 GB (anything from 10 GB to 150 GB is a good answer)

This fits on one machine, so the size of the data is not a reason to partition it.

Your turn: Define the API

Write the endpoints for search, a listing page and booking. How do you write the dates of a stay, and what does booking return when one of the nights has just sold out?

Compare with a model answer

Search and listings are GET requests. Booking is a POST that creates a held reservation, and a second call pays for it. A stay is written as a check-in date and an exclusive check-out date in the property's local calendar, and a night that has just sold out returns 409 Conflict.

The API decision worth explaining is how to write the dates. A stay is two plain dates in the property's own calendar, with no time zone, and it covers the nights from check-in up to but not including check-out, so a stay from 12 June to 15 June uses the nights of the 12th, 13th and 14th.

Your turn: Model the data

Sketch the tables for room types, inventory and reservations. How does a booking for three nights claim all three nights at once?

Compare with a model answer

Inventory has one row for each room type and night, with a total and a reserved count. One transaction adds to the reserved count on every night that still has room, and it commits only if every night was changed.

  room_type_id   BIGINT

  total_units    SMALLINT
  overbook_limit SMALLINT       -- extra units the hotel allows; 0 for homes
  reserved       SMALLINT       -- held + confirmed
  price_cents    INT
  PRIMARY KEY (property_id, room_type_id, night)
 
reservations
  reservation_id BIGINT
  property_id    BIGINT
  room_type_id   BIGINT
  user_id        BIGINT
  check_in       DATE
  check_out      DATE           -- exclusive
  rooms          SMALLINT
  status         VARCHAR(10)    -- held | paying | confirmed | expired | cancelled
  held_until     TIMESTAMP
  total_cents    INT
  idem_key       VARCHAR(64) UNIQUE
  PRIMARY KEY (property_id, reservation_id)

A hotel sells a room type, not a specific room such as room 214, because the front desk assigns the actual room at check-in. Inventory is therefore a count for each room type and night. A home is a room type with total_units = 1.

A booking changes several rows of one property, and all of those changes must succeed or none of them, so the data belongs in a relational database with transactions. Every key starts with property_id, so partitioning by property later never splits one booking.

Your turn: High-level design

Sketch search, listings and booking. Where does search get its availability data, and how does it learn about new bookings?

Compare with a model answer

A search index holds each listing together with its sold-out nights, and it is updated from the inventory change stream. Listing pages are mostly served from a CDN. A booking service is the only writer of inventory, and it calls the payment processor.

#High-level design

#Deep dives

#Reserving several nights at once

A stay of three nights needs three inventory rows to each have room, and the three claims must succeed or fail together, or a guest could end up with a booking that has a gap in it. There are two ways to do this.

Nightly counts with a conditional update. Each night has a row with a limit and a reserved count. One UPDATE statement adds to the reserved count on every night in the range that still has room, and the application checks how many rows changed. If the number equals the number of nights, the transaction commits. If it is smaller, at least one night was full, and the transaction rolls back. This works for hotels with many rooms and for homes with one.

Date ranges with an overlap constraint. Each booking is stored as a range of dates, and the database rejects a new range that overlaps an existing one for the same room. No nightly rows are needed, but the constraint only says yes or no for one unit. It cannot count 30 rooms of a type, so it fits only a product made of single-unit homes.

Claim one room of type 42 for 12 to 15 June
BEGIN;
UPDATE inventory
   SET reserved = reserved + 1
 WHERE property_id = 501 AND room_type_id = 42
   AND night >= '2027-06-12' AND night < '2027-06-15'
   AND reserved + 1 <= total_units + overbook_limit;
-- The statement must change 3 rows (the nights 12, 13 and 14).
-- If it changes fewer, run ROLLBACK and return 409.
INSERT INTO reservations (..., status, held_until)
     VALUES (..., 'held', now() + interval '15 minutes');
COMMIT;

This is safe because an updated row stays locked until its transaction commits, so a second transaction that wants the same row waits. In PostgreSQL at the default read committed level, the waiting update then re-checks its WHERE condition, finds the night full, and skips that row, so the row count comes back short and the application rolls back. At stricter isolation levels the database raises a serialization error instead, which also becomes a 409 (see transactions and isolation). Two overlapping stays can lock the same rows in different orders and deadlock, so the application retries a transaction that the database aborts for that reason.

Counting the check-out night

A stay from the 12th to the 15th uses three nights, not four. Writing night <= check_out blocks a night the guest never sleeps in, so a guest who wants to arrive on the 15th would see the room as taken. Use the half-open range everywhere: in the claim, the release, the search filter and the price total.

#Searching by availability

A search combines a location, a number of guests and the availability of every night in the stay, at about 3,000 searches a second at peak. The question is where the availability part comes from. There are three options.

Query the inventory database directly. The answer is always exact, but each search scans many listing-nights on the database that handles bookings, so it only suits a small site.

Search without availability, then check each result. The index holds only static data such as location and capacity, and availability is checked afterwards. In a busy week most top results are full and must be discarded.

Keep sold-out nights in the index and recheck the page. Each room type's document in the search index lists the nights on which it is sold out. A room type matches if none of the stay's nights is in that list, which is one "must not match" filter next to the geographic filter (see Design Proximity Search). The change stream updates the index only when a night's free count reaches zero or leaves zero, so most bookings do not touch it, and it applies changes in log order.

The sold-out list does not say how many rooms are free, so a family that needs three rooms may be shown a hotel with one left. Search therefore rechecks the 25 results it is about to show with one batched read from the replica, which is 25 room types × 3 nights = 75 rows, and drops any that fail.

#Holds, payment and expiry

The booking must reserve the nights before it charges the card, so that a guest never pays for nights that cannot be claimed. The flow is the same as in ticket booking: the reservation is held for 15 minutes, it moves to a paying status that the sweeper leaves alone, and the charge uses an idempotency key (Design a Payment System covers payments whose result is unknown). The difference for hotels is how an expired hold is released.

Releasing an expired hold needs a writer. In ticket booking each seat row carries its own expiry time, so an expired hold simply reads as free. Here the inventory row holds only a count, which cannot say which holds are stale, so a sweeper job releases them. It runs UPDATE reservations SET status = 'expired' WHERE reservation_id = 88002 AND status = 'held' AND held_until < now(), and only if that changed one row does it subtract from the reserved count of each night, in the same transaction.

#Overbooking on purpose and by accident

Some guests never arrive, so hotels sell slightly more rooms than they have, for example 105 rooms for a 100-room hotel. The overbook_limit column lets each hotel set its own margin for each room type, with 0 for homes, and the same conditional update enforces it exactly.

Accidental overbooking is the larger risk. Hotels often sell the same rooms on several sites, and no transaction on our side stops two sites from selling the last room in the same minute. The system should push bookings to other channels within seconds.

#Bottlenecks and failures

At ten times the load, search reaches 30,000 requests a second, and the search index is the first thing to scale. Shard it by region, because every query names a place, and add replicas. The 30,000 rechecks a second then need more inventory replicas. Bookings at 300 a second still fit on one primary. Partitioning by property_id gives more headroom.

LevelWhat the answer does
JuniorUses one database for both search and booking, and checks whether the room is free before inserting the booking, adding a transaction only when prompted.
Mid-levelModels nightly inventory, claims the whole stay in one transaction, and adds holds and idempotent payment.
SeniorRecognizes that reads are the scale problem, separates a stale search copy from the exact check at booking, releases counted holds safely, and treats overbooking across sites as a business process as well as a technical one.

#Follow-up questions

#Prices change per night. How do you show the total?

Add up the nightly prices for the stay and copy the total onto the reservation when the hold is created. A later price change then does not alter what the guest agreed to pay.

#A hotel takes 5 rooms out for repairs. What happens?

Lower total_units on those nights in one transaction. If reserved is now higher than the limit on some night, do not cancel anyone automatically. Send those bookings to the relocation process instead, because cancelling a confirmed guest is a business decision.

#Why not lock the night rows with SELECT FOR UPDATE, or use a version column?

Both work, but they cost more. With SELECT ... FOR UPDATE the application reads the nights, checks the counts and then writes, so the locks are held across a round trip to the application, and popular nights become a queue. With a version column the update fails whenever another booking touched the row since it was read, so a popular night causes many retries. The single conditional update checks and changes the rows in one statement, which keeps the locks as short as possible.

#The guest double-clicks, or the client retries after a timeout. How do you avoid two reservations?

The client sends an idempotency key, and the reservations table has a unique constraint on it. The claim and the insert run in one transaction, so a duplicate request fails on the constraint and rolls back its claim. The service then returns the reservation that already exists for that key.

#How does cancellation work?

In one transaction the service changes the status from held or confirmed to cancelled and subtracts the rooms from the reserved count of every night in the stay. It does this only if the status change affected a row, so a repeated cancel does nothing. The refund follows the property's cancellation policy.
