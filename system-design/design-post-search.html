Design Post Search

Design keyword search over a social network's posts, sorted by recency or likes: fast indexing, like-count tiers, time-sharded indexes and query caching.

Something happens in your city and you type "ferry strike" into a social app's search box. You expect posts from the last few minutes, newest first, or the most-liked ones if you flip the sort. Think Twitter search: keywords over a huge, fast-moving stream of short posts.

The hard part: the index is written far more than searched, and one sort depends on likes, which change 116,000 times a second. This builds on Search Systems (inverted index, analysers, feeding an index) and follows A Framework for Any Design.

#Clarify the problem

  • Functional: search public posts by keywords (all must match); sort by newest or most liked, optionally within a time window; page through results.
  • Non-functional: new posts searchable within 10 seconds; 500 ms at the 99th percentile; like order may lag about a minute; deleted posts gone within seconds; search stays up if parts of the index are down.
  • Out of scope: typos, phrases, personalisation, private posts, autocomplete (see Design Typeahead Search).

#Estimate the scale

A day is 86,400 seconds; peaks are 3x.

  • New posts: 500 million ÷ 86,400 ≈ 5,800 a second, about 17,000 at peak.
  • Likes: 10 billion ÷ 86,400 ≈ 116,000 a second, 20 per post on average.
  • Searches: 200 million ÷ 86,400 ≈ 2,300 a second, about 7,000 at peak.
  • Writes per search: (5,800 + 116,000) ÷ 2,300 ≈ 53, about 50.
Estimate: Index growth per day

How much does the inverted index grow each day?

You know
  • 500 million posts a day
  • About 30 tokens per post
  • About 5 bytes per posting, compressed

Show the working
  1. Postings: 500 × 106 × 30 = 1.5 × 1010 a day
  2. 1.5 × 1010 × 5 B = 7.5 × 1010 B = 75 GB a day
  3. Last 7 days: 7 × 75 = 525 GB. One year: 75 GB × 365 ≈ 27 TB

Estimate 75 GB (anything from 25 GB to 250 GB is a good answer)

A week fits in memory (525 GB × 3 replicas ≈ 1.6 TB); a year does not. Hence hot and cold tiers.

Estimate: Rewriting the index on every like

If each like rewrote its post's index document, how many rewrites a second is that on average?

You know
  • 10 billion likes a day
  • A day is 86,400 seconds

Show the working
  1. 10 × 109 ÷ 86,400 ≈ 116,000 a second
  2. That is 20 times the rate of new posts

Estimate 116 thousand/s (anything from 40 thousand/s to 400 thousand/s is a good answer)

Each update deletes and re-inserts the whole document. The second deep dive avoids this churn.

Your turn: Define the API

Write the search endpoint. How does the client get the next page, for each sort?

Compare with a model answer

One GET with query, sort and optional time window. Newest first: the cursor is "older than post id X". Most liked: counts move, so the cursor names a short-lived snapshot of the ranked list.

#Define the API Optional

Optional in the interview. Sketch the API only if the interviewer asks, if an API choice shapes the design, or if time permits. Otherwise say "I'll skip the detailed API unless you want it" and go to the data model.

HTTP API
GET /v1/search?q=ferry+strike&sort=recent&limit=20&cursor=...
GET /v1/search?q=ferry+strike&sort=likes&since=2026-10-15&limit=20
  200 { "results": [ { "post_id": "1849...", "author": "...", "text": "...",
                       "likes": 1532, "created_at": "..." } ],
        "next_cursor": "...", "partial": false }
  400 Bad Request     empty query, or more than 10 words
  410 Gone            cursor snapshot expired; start again

The decision worth arguing is pagination. For sort=recent, post ids are time-ordered (see Unique IDs), so the cursor is "ids smaller than the last one shown" and new posts never shift a page. For sort=likes, a post can gain 500 likes between pages, so the server ranks once and keeps the ordered ids for 10 minutes. partial says some shards timed out: a degraded answer beats an error.

Your turn: Model the data

What does the index store per post, and where do like counts live so the likes sort works without rewriting the index?

Compare with a model answer

The index stores post id, tokens and a coarse like tier. Exact counts live in a key-value store, read at query time. The posts database owns text and deletion.

Your turn: High-level design

Sketch how a post and a like reach the index and count store, and how a search is answered.

Compare with a model answer

Posts and likes arrive as events. Indexers add posts to today's index; an aggregator batches likes into the count store and tells indexers only when a post changes tier. Search checks a cache, fans out to shards, reads counts for the likes sort, and fetches text.

#High-level design

#Deep dives

#Indexing a firehose

Postings lists are sorted and compressed: cheap to read, expensive to edit. So the indexer never edits them. It buffers new posts and writes a small, immutable segment every second; a search reads all segments of a shard. A background job merges small segments into bigger ones, like the log-structured storage in a key-value store. Deletes go on a list of dead ids and are removed during merges.

Time-ordered ids pay off twice: new posts append to the end of every list, and a newest-first query walks lists backwards and stops early.

At peak, 17,000 posts × 30 tokens is about 510,000 postings a second across today's shards.

#Sorting by likes without rewriting the index

Rewriting a document per like is 116,000 index updates a second. Separate "roughly how popular" from "exactly how many".

A post with 1 million likes changes tier 6 times, not a million. Even if every post crossed two boundaries, that is 2 × 5,800 = 11,600 updates a second, a tenth of the like rate.

A likes query searches the highest tier first. Say "ferry strike" matches 4 posts in tier 4 and 150 in tier 3. Every lower-tier post has fewer likes, so those 154 are the only possible top 20: fetch their exact counts in one batch, sort, return 20. Lower tiers are never read.

A broad word over 30 days can put 50,000 matches in one tier. Then each shard sends only its newest few hundred from that tier: bounded work, approximate order. Finer tiers (half powers of ten) shrink that case for twice the updates.

Counts are batched as in Design Photo Sharing: sum per post each second, and store the last applied offset with the count so a replay cannot add twice.

#Sharding the index

Split by time first, then by document: each day gets its own index, sharded by hash of post id as Search Systems recommends. Time first means:

  • All writes go to today's index, which can sit on more machines.
  • Newest-first queries read only the latest days.
  • An old day never gets new posts, so it merges into one large segment on cheaper machines.

The cost is fan-out: a year-long query reads 365 day indexes times their shards. So older days roll into week and month indexes, and likes queries default to 30 days.

With 20 shards, the slowest sets the latency. If each is slow 1% of the time, a query waiting for all 20 is slow 1 − 0.9920 ≈ 18% of the time. Hence the hedged request after 50 ms.

#Hot and cold data, and caching

The recent 7 days (525 GB) live in memory with 3 replicas, because nearly every newest-first query ends there. Older data, about 27 TB a year, lives on SSDs with fewer replicas. If it is down, return recent results with partial: true.

Queries are skewed: in a news event, thousands type the same words. Cache the ranked ids, keyed by normalised query, sort and window, for 15 seconds. Also cache per-shard results for days that are over for an hour: they change only through deletes and tier moves. A deep page then costs one live query on today's shards. Deleted posts are filtered at text fetch, so no cached list shows one.

Treating search like a read-heavy service

Here writes outnumber searches 50 to 1. Ignore the 116,000 likes a second and the index spends its capacity on rewrites. Start from the write path.

#Bottlenecks and failures

At 10x (5 billion posts a day), today's index takes 170,000 posts a second at peak: about 10 times the shards, and 5 TB of memory for 7 days. The like stream reaches 1.2 million events a second; partitioned by post id, aggregators scale out. Fan-out latency hurts first: fix it with larger rolled-up old indexes and narrower default windows.

#What a strong answer sounds like

LevelWhat the answer does
JuniorPuts posts in a search engine, sorts in the query, adds a cache.
MidFeeds the index from a change stream, shards by document, and keeps fast-changing like counts outside the index.
SeniorLeads with the 50-to-1 write ratio, shards by time then document, stops early for newest-first, uses tiers for likes with the arithmetic, and explains tail latency from fan-out.

#Follow-up questions

#How do you add relevance ranking?

Fetch a few hundred candidates per shard by a cheap score (text match, tier, recency), then re-rank the merged list with a richer model. Expensive scoring touches only a few hundred posts.

#A post is deleted. How fast does it disappear?

Immediately for users: deleted ids are filtered at text fetch. The index entry is marked dead within seconds and removed at the next merge.

#How would you search hashtags or a single user's posts?

A hashtag is another token. "From this user" is an author_id field plus a query filter.

#How do you change the analyser, say to add stemming?

Build new indexes alongside the old, newest days first, from the posts database, then switch reads one day at a time. Per-day indexes make this easy.

#Why not use the database's full-text search?

At 75 GB of new index a day and 5,800 inserts a second, one database's text index cannot keep up or split by time. For a few million posts it would be the right first answer.
