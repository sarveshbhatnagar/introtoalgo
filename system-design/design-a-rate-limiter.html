Design a Rate Limiter

Design a distributed API rate limiter: rules per user and per IP, a shared counter store with atomic updates, races, and failing open or closed.

A rate limiter sits in front of an API and says "no" to clients that send too much. Every request asks "may this one through?", and the answer must come back within a millisecond or two, from any of dozens of gateway servers that agree on each client's count.

It is small yet touches shared state, atomic updates, races, clocks, and dependency failure. Rate Limiting covers the algorithms; this case study builds the service, following A Framework for Any Design.

#Clarify the problem

"Design a rate limiter" can mean a class in one process or a company-wide service. Find out which before you say "token bucket".

  • Functional: limit per API key, IP and account, with rules by endpoint and plan; reject excess with 429 and a retry time; change rules without a deploy.
  • Non-functional: under 2 ms added at p99; the API stays up if the limiter is down; counts shared across gateways, within a few percent; rule changes apply within about 10 seconds.
  • Out of scope: billing, usage dashboards, bot detection beyond simple limits.

#Estimate the scale

A day has 86,400 seconds. Assume peaks of 3x the average, and that each request is checked against two rules (its API key and its IP).

Estimate: Counter store load at peak

How many counter operations per second must the shared store handle at peak?

You know
  • 1 billion API requests a day
  • Peak is 3x the average
  • Each request is checked against 2 rules, one store operation each

Show the working
  1. Average: 109 ÷ 86,400 s ≈ 11,600, call it 12,000 a second
  2. Peak: 12,000 × 3 = 36,000 a second
  3. Store operations: 36,000 × 2 = 72,000 a second

Estimate 72 thousand/s (anything from 30 thousand/s to 200 thousand/s is a good answer)

An in-memory node does about 100,000 simple operations a second, but each check runs a script: plan for 50,000 a node and 4 shards.

Estimate: Memory for every counter

How much memory do the counters need if every client is active at once?

You know
  • 10 million API keys and 10 million IP addresses
  • One token bucket per key or IP
  • About 100 bytes per bucket, with key and overhead

Show the working
  1. Buckets: 10 million + 10 million = 20 million
  2. 20 × 106 × 100 B = 2 × 109 B = 2 GB

Estimate 2 GB (anything from 500 MB to 10 GB is a good answer)

Memory is not the problem; operations per second and latency are.

#Define the API

What clients see, and the internal calls
Every response from the API:
  X-RateLimit-Limit: 100        bucket size for the tightest rule
  X-RateLimit-Remaining: 36     tokens left after this request
 
Rejected request:
  429 Too Many Requests
  Retry-After: 1                seconds until a token is available
  body: { "error": "rate_limited", "rule": "key-free-plan", "retry_after_s": 1 }
 
Gateway to counter store, one atomic call per rule:
  take(key, capacity, refill_per_sec, cost = 1)
    -> { allowed, remaining, retry_after_ms }
 
Operators:
  PUT /admin/rules/{rule_id}    body: the rule (see the data model)
  400 if the rule is invalid; gateways pick up changes within 10 s

The decision to argue: 429 means "you sent too much"; 503 means "we are overloaded". Use 429 for limits, so a well-behaved client reads Retry-After and slows down. Keep 503 for load shedding. Mixing them up makes clients retry at the wrong times.

Your turn: Model the data

What records exist, how big are they, and who reads them how often? Pick a kind of store for each.

Compare with a model answer

Rules: a few hundred records, read constantly, changed rarely; every gateway holds them in memory. Counters: 20 million tiny records written on every request; an in-memory key-value store.

#Model the data

Rules (config store) and counters (in-memory store)
rule
  rule_id          "key-free-plan"
  match            endpoint pattern and plan, e.g. "/v1/*", plan = free
  key_by           api_key | ip | account
  capacity         100            burst size
  refill_per_sec   10             long-run rate
  on_store_down    open | local | closed
 
counter            key = "rl:{rule_id}:{subject}"   e.g. "rl:key-free-plan:k_8f3a"
  tokens           float, 8 bytes
  last_refill_ms   integer, 8 bytes
  TTL              capacity / refill_per_sec = 100 / 10 = 10 s

Rules are a few hundred records in any durable config store; gateways poll them into memory every 10 seconds.

Counters are updated on almost every request and needed in about half a millisecond: an in-memory key-value store (such as Redis) that runs small scripts atomically and expires keys. Durability barely matters: a lost counter just gives one client a fresh bucket.

The TTL is a neat trick: a bucket idle for capacity ÷ rate = 10 seconds is full again, and a missing key counts as full, so expiry frees memory without changing any answer.

#High-level design

The limiter is a library in each gateway; a separate service would add a hop to every request and a fleet to run. The counter store has 4 shards by key, each with a replica.

#Deep dives

Interviewers push on four places: the algorithm, the shared counter, store failure, and the key you limit by.

#Choosing the algorithm per rule

Pick per rule, by what it protects.

Which algorithm for which rule
OptionGood atBad atPick it when
Token bucket Usual defaultAllows short bursts, holds the long-run rate. Two numbers per key, one atomic script.A full bucket lets a whole burst through at once.General per-key and per-IP API limits. My default here.
Sliding window logExact count over the window.One timestamp per request per key, so memory grows with the limit.Small limits that must be exact: 5 login attempts per account per 15 minutes.
Fixed window counterOne integer and an expiry. Cheapest possible.Up to twice the limit across a window edge.Coarse quotas where the edge does not matter: 100,000 calls a day.

If the backend cannot absorb bursts at all, a leaky bucket that queues requests fits better.

#A shared counter with atomic updates

Twenty gateways each counting alone would let a client spread across them get up to twenty times its limit. So each key's count lives on one shard, chosen by consistent hashing so adding a shard moves few keys. The danger is splitting the check from the update:

The atomic take, run inside the counter store
take(key, capacity, rate, cost):
  now = store's own clock, in ms
  tokens, last = read key            (missing key: tokens = capacity, last = now)
  tokens = min(capacity, tokens + (now - last) / 1000 * rate)
  if tokens >= cost:
      tokens = tokens - cost
      allowed = true
  else:
      allowed = false
  write key = (tokens, now), expire after capacity / rate seconds
  return allowed, floor(tokens), time until tokens >= cost

Two details show you have built one:

  • Use the store's clock. Gateway clocks drift; if A's is behind B's, now - last goes negative and the refill math breaks.
  • Never retry a timed-out take. The store may have taken the token before the reply was lost, so a retry charges twice. Treat a timeout as "store down" for that request.

#Failing open or closed

Decide per rule what the gateway does when the counter store is unreachable.

When the counter store cannot answer
OptionGood atBad atPick it when
Fail openA limiter outage never becomes an API outage.No protection until the store is back; one abusive client can hurt everyone.Low-risk endpoints where the backend has headroom.
Fall back to local limits Usual defaultStill available, still roughly limited.A client pinned to one gateway gets only that gateway's share of its limit.General API limits. My default.
Fail closedNo request skips the limit, ever.A store outage rejects every request on that endpoint.Login, password reset, SMS sending: where an unlimited attacker costs more than a short outage.

Local fallback: the free plan refills 10 a second, so each of 20 gateways allows 10 ÷ 20 = 0.5 a second for that key in its own memory. A client spread evenly still gets 20 × 0.5 = 10 a second. The right choice differs by endpoint, hence on_store_down on each rule.

#Per-user and per-IP rules together

A request can match several rules: IP, API key and endpoint. Allow only if all allow, and return the longest Retry-After. Check per IP first, so a flood is rejected before a second store call.

  • IP alone is a poor identity. An office or mobile carrier can put thousands of users behind one address. Use IP for anonymous traffic and floods, the key or account once known.
  • IPv6 needs a prefix. One home often gets a whole /64 block; limit by that prefix, or a client rotates through endless addresses.
  • Login needs two keys: per IP (one attacker, many accounts) and per target account (many IPs, one account). Either alone misses an attack.

#Bottlenecks and failures

At 10x (360,000 requests a second at peak), the store sees 720,000 operations a second: at about 50,000 per shard, run 16 shards. A key that moves simply starts as a full bucket. Gateways hold only rules and a deny cache, so add more.

The first thing to break is usually a hot key: one abusive client at 50,000 requests a second lands every check on one shard. The tracer's deny cache handles it, and a local per-IP pre-limit drops obvious floods before the store.

A big customer allowed 20,000 requests a second is a hot key the deny cache cannot help, since those requests pass. Let each gateway take tokens in batches of 50 and spend them locally: 50 times fewer store calls, at the cost of a few tokens stranded on a gateway.

When this diesWhat happensWhat you do
A gateway nodeIts in-flight requests fail.The load balancer removes it. Counters are shared, so nothing is lost.
A counter shard primaryIts keys time out for a few seconds until the replica is promoted.on_store_down applies. Replication is asynchronous, so the last few hundred ms of decrements are lost: a few extra requests, once.
The whole counter storeNo shared counts.Local limits for most rules, fail closed for login. Alert.

A limiter that can take the API down

If every request waits on the counter store with no timeout or fallback, the limiter is a single point of failure for the whole API. "We'll make the store highly available" is not an answer: everything goes down. Set a timeout far below the latency budget and a failure behaviour per rule.

#What a strong answer sounds like

Most candidates know the token bucket. Levels differ on fleets, races and failure.

LevelWhat the answer does
JuniorOne algorithm, in one process. Needs prompting to see that gateways counting alone multiply the limit.
MidShared counter store, atomic check, 429 with Retry-After, an estimate of store load.
SeniorPicks the algorithm and failure mode per rule, uses the store's clock, never retries a timed-out take, handles hot keys, and says how loose limits get during failures.

#Follow-up questions

#How do you limit across several regions?

A cross-region store adds tens of milliseconds to every request. Give each region its own counters and split the limit by traffic share, or sync counts every second and accept a small overshoot.

#How would you limit by cost instead of by request?

Pass cost to the take call: a bulk export takes 10 tokens, a read takes 1. If the cost is only known afterwards, take an estimate up front and charge the difference.

#How do you roll out a new, stricter limit safely?

Run it in shadow mode: log who it would reject but let them through. After a few days, warn the customers it hits, then enforce.

#Why not just put the limit in the load balancer?

Many load balancers can limit per IP, a good first layer against floods, but they do not know the API key or plan. Use both.
