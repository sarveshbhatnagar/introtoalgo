Binary Search Trees

Keep values in a tree where smaller goes left and bigger goes right, so search, insert and delete each follow one path. Traced, with JS and Python code.

A game server keeps its players sorted by score, so it can show each player the rival ranked just above them. A sorted array is great for that: binary search finds any score in about 20 steps among a million players. But players finish games all the time, and every new score has to be squeezed into the right place. In an array, that means shifting every item after it one slot to the right. Up to a million moves, for one insert.

You want the fast search of a sorted array without the expensive shifting. A binary search tree gives you both, as long as it keeps a sensible shape.

#The rule: smaller left, bigger right

A binary search tree (BST) is a binary tree with one rule, which holds at every node:

  • every value in the node's left subtree is smaller than the node's value, and
  • every value in its right subtree is bigger.

Look at the root. Everything smaller than it is somewhere on the left, everything bigger is on the right. So one comparison at the root throws away a whole side of the tree. That is binary search, built into the shape of the data instead of into array indexes.

You have already met one consequence. An inorder traversal visits the left subtree, then the node, then the right subtree. In a BST that means smaller values, then this one, then bigger values: the whole tree in sorted order.

#Search and insert follow one path

To find a value, start at the root and compare. Equal: found. Smaller: go left. Bigger: go right. If you step onto an empty child, the value is not in the tree.

Insert is the same walk. You search for the new value, and when you fall off the tree, the empty spot where you landed is exactly where it belongs. No other node moves.

// TreeNode is the same class as in Binary Trees.
function contains(node, val) {
  while (node !== null) {
    if (val === node.val) return true;
    node = val < node.val ? node.left : node.right; // throw away one side
  }
  return false;
}
 
// Returns the root of the tree with val added.
function insert(node, val) {
  if (node === null) return new TreeNode(val); // found the empty spot
  if (val < node.val) node.left = insert(node.left, val);
  else if (val > node.val) node.right = insert(node.right, val);
  return node; // a duplicate is ignored
}
 
let root = null;
for (const v of [40, 20, 60, 10, 30, 50, 70, 35]) root = insert(root, v);
contains(root, 35); // true
contains(root, 33); // false

insert returns the root of the updated subtree and the parent stores it back with node.left = …. That one habit handles the empty tree, where the new node becomes the root, with no special case.

Two more questions come free. The smallest value is the leftmost node: keep going left until you cannot. The largest is the rightmost.

#Delete: three cases

Removing a value is the only tricky operation, because the tree must stay valid. First find the node, then look at how many children it has.

  1. No children: just remove it.
  2. One child: the child moves up into its place. Everything under it was already on the correct side of the parent, so the rule still holds.
  3. Two children: you cannot leave a hole with two subtrees hanging from it. Instead, find the next bigger value, called the successor. It is the leftmost node of the right subtree. Copy it into this node, then delete it from the right subtree. The successor has no left child (otherwise it would not be leftmost), so that second delete is case 1 or 2.
// Returns the root of the tree with val removed.
function remove(node, val) {
  if (node === null) return null; // val is not in the tree
  if (val < node.val) node.left = remove(node.left, val);
  else if (val > node.val) node.right = remove(node.right, val);
  else {
    if (node.left === null) return node.right; // 0 or 1 child:
    if (node.right === null) return node.left; // the child moves up
    let next = node.right;                     // 2 children: find the
    while (next.left !== null) next = next.left; // next bigger value
    node.val = next.val;                       // copy it here
    node.right = remove(node.right, next.val); // and remove the copy
  }
  return node;
}

#Cost depends on the height

Search, insert and delete each walk one path from the root down, so each costs O(h), where h is the height. In a bushy tree, h is about log₂ n: 20 levels for a million values. That beats the sorted array, whose search is O(log n) but whose insert is O(n).

The catch: a BST's shape depends on the order you insert values. Insert 10, 20, 30, 40, 50 in that order and each new value is bigger than everything so far, so it always goes right. You get the stick from Binary Trees, with height n. Searching it is no faster than scanning a list.

ApproachTimeSpaceWhy
Sorted arrayO(log n) search, O(n) insertO(n)Insert and delete shift items over.
BST, bushy shapeO(log n)O(n)Search, insert and delete walk one path of about log₂ n nodes.
BST, worst shapeO(n)O(n)Sorted inserts build a stick, and the path is the whole tree.
Key idea

Every BST operation walks one root-to-leaf path. It is fast exactly when the tree is short.

Fixing that worst case is the job of balanced trees, which reshape themselves after each change so the height stays O(log n) whatever the insert order.

#Common mistakes

Checking only a node's direct children

A tree can pass "left child smaller, right child bigger" at every node and still break the rule. In the figure below, 45 is a fine right child of 20, but it sits in 40's left subtree, where everything must be smaller than 40. A search for 45 goes right at the root and never finds it. To validate a BST, pass down the allowed range: going left lowers the upper limit, going right raises the lower limit. Or check that the inorder traversal is strictly increasing.

Forgetting to store the returned subtree

Writing insert(node.left, val) without node.left = … builds the new node and then drops it. The same goes for root = insert(root, val) at the top: without it, the first insert into an empty tree is lost.

Not deciding about duplicates

The code above ignores a value that is already there, which is right for a set. If you need counts, store a count in each node. Do not let equal values go to either side at random, or searches will miss them.

In the real world

You rarely write a BST by hand at work. Ordered maps such as Java's TreeMap and C++'s std::map are balanced BSTs underneath. You reach for one when you need a sorted collection that changes often, with questions like "smallest key above 500".

#Check yourself

Quick check

In the tree from the first trace (root 40, then 20 and 60, then 10, 30, 50, 70), where does 55 go?

  1. Not quite. 55 is bigger than 50, so it goes right of 50, not left.
  2. Right. 55 > 40: go right to 60. 55 < 60: go left to 50. 55 > 50: go right, which is empty. Place it there.
  3. Not quite. At 60, 55 is smaller, so the walk goes left to 50 and never reaches 70.

You insert the values 1, 2, 3, …, 1,000 into an empty BST in that order. How many comparisons does a search for 1,000 take?

  1. Not quite. That would be true for a bushy tree. Sorted inserts always go right, so the tree is a stick.
  2. Right. Each value became the right child of the previous one. The tree is a path of 1,000 nodes, and 1,000 is at the bottom.
  3. Not quite. The root is 1, the first value inserted, not 1,000.

You delete a node with two children. Which value replaces it?

  1. Not quite. The right child may have a smaller value below it on the left. Then the rule breaks.
  2. Right. That is the next bigger value. It is larger than everything on the left and smaller than everything else on the right.
  3. Not quite. Everything else on the right would then be smaller than the new value, but it sits on the right side.

#What to practise next

A BST answers "is this value here?" and "what comes next in order?". Often you only care about the smallest or the most urgent item. For that there is a simpler, faster structure: Heaps and Priority Queues.
