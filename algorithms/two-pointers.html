Two Pointers

Use two indexes that move toward each other or side by side to turn O(n²) pair searches into one O(n) pass. Traced by hand, with JS and Python code.

You have a gift card worth exactly 16 and a price list sorted from cheapest to most expensive: 2, 4, 5, 8, 11, 15. You want two items that use the card exactly, with nothing left over.

The obvious way is to try every pair. That works, but it is O(n²): with 10,000 prices it is about 50 million checks. Because the list is sorted, there is a much better way. Put one finger on the cheapest item and one on the most expensive, and move them toward each other.

#The idea: one finger on each end

Call the left finger L and the right finger R. Add the two prices they point at.

  • If the sum is exactly the target, you are done.
  • If the sum is too big, move R one step left. That is the only move that makes the sum smaller.
  • If the sum is too small, move L one step right. That is the only move that makes the sum bigger.

Every step either finds the answer or moves a finger inward. The fingers can only meet once, so you check at most n pairs instead of all of them.

#Why it is safe to throw a value away

This is the part people skip, and it is the part that makes the method correct. When you move a finger, you are claiming that the value you leave behind cannot be part of any answer.

Look at step 2. The sum 2 + 15 was too big. Every other price is at least 2, because the list is sorted. So 15 plus anything left is at least 17. No partner exists for 15, and dropping it loses nothing.

Step 3 is the mirror image. The sum 2 + 11 was too small, and 11 is now the largest price still in play. So 2 plus anything left is at most 13. Nothing can rescue 2, so it goes.

Key idea

Two pointers works when each comparison tells you, for certain, that one of the two values can be discarded. Sorted order is what gives you that certainty.

#The code

// prices is sorted from low to high.
// Returns the two positions, or [] if no pair works.
function pairWithSum(prices, target) {
  let left = 0;
  let right = prices.length - 1;
  while (left < right) {
    const sum = prices[left] + prices[right];
    if (sum === target) return [left, right];
    if (sum > target) right--; // too big: drop the largest
    else left++;               // too small: drop the smallest
  }
  return [];
}
 
pairWithSum([2, 4, 5, 8, 11, 15], 16); // [2, 4]
# prices is sorted from low to high.
# Returns the two positions, or [] if no pair works.
def pair_with_sum(prices, target):
    left, right = 0, len(prices) - 1
    while left < right:
        total = prices[left] + prices[right]
        if total == target:
            return [left, right]
        if total > target:
            right -= 1  # too big: drop the largest
        else:
            left += 1   # too small: drop the smallest
    return []
 
pair_with_sum([2, 4, 5, 8, 11, 15], 16)  # [2, 4]

Note the condition left < right, not left <= right. When the two fingers meet, they point at the same item, and an item cannot pair with itself.

#Three shapes of the same idea

"Two pointers" is a family. The pair-sum version moves the pointers toward each other, but the same trick shows up in two other shapes.

Same direction. A slow pointer marks where the next item you want to keep goes. A fast pointer scans ahead. This lets you clean up an array in place without a second array. Here it removes repeated values from a sorted list and returns how many unique values are left at the front:

function removeDuplicates(nums) {
  if (nums.length === 0) return 0;
  let slow = 0; // nums[0..slow] holds the unique values so far
  for (let fast = 1; fast < nums.length; fast++) {
    if (nums[fast] !== nums[slow]) {
      slow++;
      nums[slow] = nums[fast];
    }
  }
  return slow + 1;
}
// [1, 2, 2, 2, 5, 5] becomes [1, 2, 5, ...] and returns 3
def remove_duplicates(nums):
    if not nums:
        return 0
    slow = 0  # nums[0..slow] holds the unique values so far
    for fast in range(1, len(nums)):
        if nums[fast] != nums[slow]:
            slow += 1
            nums[slow] = nums[fast]
    return slow + 1
# [1, 2, 2, 2, 5, 5] becomes [1, 2, 5, ...] and returns 3

Two lists. One pointer walks each sorted list, and at every step you take the smaller value and advance that pointer. That is the merge step at the heart of merge sort.

Tip

The inner loop in the same-direction pattern can look like a nested loop. It is not. slow only ever moves forward, and so does fast. Count the total moves of each pointer over the whole run: at most n each, so O(n).

#Common mistakes

Using it on unsorted data

On [8, 2, 15, 4], "sum too big, move right pointer left" means nothing, because the item to the left is not smaller. The discard argument breaks and you will miss answers. Sort first, or use a hash map instead, as in Matching Receipts.

Returning positions after sorting

If the problem asks for positions in the original list and you sort it first, the positions change. Sort pairs of (value, original position) instead, or use a hash map.

A pointer that never moves

Every branch of the loop must move at least one pointer, or the loop runs forever. When you write the if and else, check that each one changes left or right.

In the real world

Merging two sorted streams, like two sorted log files or two sorted search result lists, uses the two-lists shape directly. It is how databases join sorted tables without comparing every row to every row.

#Check yourself

Quick check

Prices [3, 5, 9, 14], target 12. L is on 3 and R is on 14. The sum is 17. What should happen next?

  1. Not quite. That makes the sum bigger, and it is already too big.
  2. Right. 17 is too big. 14 plus the smallest remaining price is already over 12, so 14 can never be part of the answer. Drop it.
  3. Not quite. You only know for sure that 14 is useless. 3 might still pair with 9, which it does: 3 + 9 = 12.

Why does pair-sum with two pointers need the list to be sorted?

  1. Not quite. Sorting does not change how many steps the loop takes. It changes whether the steps are correct.
  2. Right. Right. Sorted order guarantees the next item to the left is smaller and the next to the right is bigger. That is what lets you discard values safely.
  3. Not quite. That helps other problems, like removing duplicates, but it is not why pair-sum works.

The same-direction version has a for loop over fast and moves slow inside it. What is its time complexity?

  1. Not quite. There is no loop inside the loop. slow moves by one at most once per iteration.
  2. Right. fast visits each item once and slow never moves backwards, so the total work is proportional to n.
  3. Not quite. Nothing is sorted or halved here.
