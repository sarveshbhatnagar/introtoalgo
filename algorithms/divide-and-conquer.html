Divide and Conquer

Split a problem into halves, solve each half the same way, then combine. Count disagreements between two rankings fast and read the cost of any split.

You and a friend each rank the same six films. You want one number that says how much you disagree. A natural one: count the pairs of films you put in opposite order. If you rank Film A above Film B and your friend ranks B above A, that pair is one disagreement.

Number the films 1 to 6 in your order. Then write your friend's list, favourite first, using your numbers: [3, 6, 5, 1, 4, 2]. A disagreement is any bigger number that appears before a smaller one. Checking every pair works, but that is n(n − 1) / 2 comparisons, about 45 billion for a catalogue of 300,000 films. Divide and conquer does it in O(n log n).

#The idea: split, solve, combine

You have already met this pattern twice. Binary search throws away half the range and solves the other half. Merge sort sorts each half and merges them. Both follow the same three steps:

  1. Divide the input into smaller parts, usually two halves.
  2. Conquer each part by calling the same function on it.
  3. Combine the answers for the parts into the answer for the whole.

The first two steps are almost free to write. All the thinking goes into the combine step: given the answers for each half, what is still missing, and how do you get it cheaply?

Key idea

Divide and conquer pays off when the combine step is cheap. Ask: once both halves are solved, what work is left that crosses the split?

#Counting disagreements

Split the list into [3, 6, 5] and [1, 4, 2]. Every disagreement is one of three kinds: both numbers in the left half, both in the right half, or one in each. The recursive calls count the first two kinds. The combine step only has to count the pairs that cross the middle.

Counting crossing pairs one by one would still be slow. Here is the trick: the crossing count does not depend on the order inside each half. So you are free to sort each half first, and the recursion can hand back sorted halves for nothing, because merging them is exactly what merge sort does anyway.

During the merge, every left item came before every right item in your friend's list. So when a right item is smaller than the front of the left half, it is also smaller than everything still waiting there, and each of those is a disagreement. Add how many are waiting, in one step.

// Returns [sorted copy of a, number of disagreements in a].
function sortAndCount(a) {
  if (a.length <= 1) return [a, 0];
  const mid = Math.floor(a.length / 2);
  const [left, leftCount] = sortAndCount(a.slice(0, mid));
  const [right, rightCount] = sortAndCount(a.slice(mid));
  const merged = [];
  let i = 0, j = 0, cross = 0;
  while (i < left.length && j < right.length) {
    if (left[i] <= right[j]) {
      merged.push(left[i++]);
    } else {
      cross += left.length - i; // right[j] jumps every waiting left item
      merged.push(right[j++]);
    }
  }
  while (i < left.length) merged.push(left[i++]);
  while (j < right.length) merged.push(right[j++]);
  return [merged, leftCount + rightCount + cross];
}
 
sortAndCount([3, 6, 5, 1, 4, 2])[1]; // 10
# Returns (sorted copy of a, number of disagreements in a).
def sort_and_count(a):
    if len(a) <= 1:
        return a, 0
    mid = len(a) // 2
    left, left_count = sort_and_count(a[:mid])
    right, right_count = sort_and_count(a[mid:])
    merged = []
    i = j = cross = 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:
            merged.append(left[i])
            i += 1
        else:
            cross += len(left) - i  # right[j] jumps every waiting left item
            merged.append(right[j])
            j += 1
    merged.extend(left[i:])
    merged.extend(right[j:])
    return merged, left_count + right_count + cross
 
sort_and_count([3, 6, 5, 1, 4, 2])[1]  # 10

Note the <=. When two values are equal, take the left one first. They are not a disagreement, so nothing should be counted for them.

#Reading the cost of any split

You do not need a formula to price a divide and conquer algorithm. Draw the tree of calls and add up the work level by level. Two things decide the answer: how many smaller calls each call makes, and how much the combine step costs.

Each call makesCombine costsTotalExample
1 call on halfO(1)O(log n)binary search, fast power below
1 call on halfO(n)O(n)finding the median by partitioning as in quicksort and keeping only the side that holds it (quickselect), on average: n + n/2 + n/4 + … ≈ 2n
2 calls on halvesO(1)O(n)largest value by splitting in two
2 calls on halvesO(n)O(n log n)merge sort, counting disagreements

#One half is enough: fast power

Sometimes the two halves are the same problem, so you solve it once. To compute 3¹³, note that 3¹³ = 3⁶ × 3⁶ × 3. And 3⁶ = 3³ × 3³, and so on. Each call halves the exponent and does one or two multiplications.

// x to the power n, for a whole number n >= 0
function power(x, n) {
  if (n === 0) return 1;
  const half = power(x, Math.floor(n / 2)); // solve the half once
  return n % 2 === 0 ? half * half : half * half * x;
}
 
power(3, 13); // 1594323
# x to the power n, for a whole number n >= 0
def power(x, n):
    if n == 0:
        return 1
    half = power(x, n // 2)  # solve the half once
    return half * half if n % 2 == 0 else half * half * x
 
power(3, 13)  # 1594323

The exponent goes 13, 6, 3, 1, 0: five calls and 7 multiplications, where a plain loop needs 12. For an exponent of a billion, 31 calls. That is the first row of the table: one call on half, constant combine, O(log n).

#Common mistakes

A combine step that is too slow

If you count the crossing pairs with a nested loop over both halves, the combine costs O(n²) and the whole algorithm is O(n²) again: you split for nothing. The speed comes entirely from a cheap combine, here the sorted halves.

Solving the same half twice

Writing power(x, Math.floor(n / 2)) * power(x, Math.floor(n / 2)) makes two calls where one would do. The tree then has two branches per level and the cost climbs back to O(n). Store the result in a variable and reuse it.

A split that does not shrink

With one item, mid is 0, so one "half" is empty and the other is the whole list again. Without the length <= 1 base case, the function calls itself on the same list forever.

Tip

If the parts overlap, so the same smaller problem is solved many times, divide and conquer can become exponential. The naive Fibonacci in Recursion is the classic case. That is the signal to switch to dynamic programming.

#Check yourself

Quick check

During a merge, the left half is [2, 7, 9] with i on 7, and the right half's next item is 4. How many disagreements does taking 4 add?

  1. Not quite. 4 jumps over every item still waiting on the left, not only the one at the front.
  2. Right. 7 and 9 are still waiting, both are bigger than 4, and both came earlier in the list. 2 was already taken, so it does not count.
  3. Not quite. 2 was already merged, and 2 is smaller than 4 anyway, so that pair is in the right order.

An algorithm splits into two halves, recurses on both, and combines in O(1). What is its total cost?

  1. Not quite. That is for one call per level. With two calls, the number of calls doubles on each level.
  2. Right. 1 + 2 + 4 + … + n calls, each O(1), is about 2n.
  3. Not quite. That needs O(n) work on every level. Here the top levels do almost nothing.

Why does counting disagreements sort each half first?

  1. Not quite. The answer is a count. Sorting is a tool to make the crossing count cheap.
  2. Right. Right. Order inside a half does not affect which pairs cross, and sorted order lets one step count a whole batch of them.
  3. Not quite. Those were already counted by the recursive calls before sorting. Sorting does not lose them.
