Quicksort

Pick a pivot, move smaller items left and bigger items right, and repeat on each side. Learn partitioning, why pivots matter, and quicksort's worst case.

A photographer wants a class of children lined up by height. She does not compare everyone with everyone. She picks one child, Sam, and says: "Shorter than Sam, stand on his left. Taller, on his right." Nobody on the left is sorted yet, nobody on the right is sorted yet, but Sam is now standing exactly where he belongs in the final line.

Then she does the same thing with the group on the left, and the group on the right. Each round puts at least one more child in their final place, and the groups keep shrinking. That is quicksort.

#The idea: partition around a pivot

Quicksort has three steps:

  1. Pick a pivot, one item from the range.
  2. Partition: rearrange the range so every item smaller than the pivot comes before it and every other item comes after it. The pivot lands in its final position.
  3. Recurse on the part before the pivot and the part after it.

Compare it with merge sort. Merge sort splits without looking at the values, then does its real work when merging. Quicksort does its real work while splitting, and then there is nothing to combine: once both sides are sorted, the whole range is sorted. It also sorts in place, inside the original array.

#Partitioning, traced

The partition step is the heart of quicksort, so trace it carefully. This version uses the last item as the pivot. A boundary b marks where the next small item should go: everything left of b is smaller than the pivot. Pointer j scans the range once.

#The code

The partition below is the one you just traced, with one addition: it first picks a random item and swaps it to the end, so the pivot is random instead of always the last item. The next section explains why.

function quickSort(a, lo = 0, hi = a.length - 1) {
  if (lo >= hi) return a; // 0 or 1 items: sorted
  const p = partition(a, lo, hi);
  quickSort(a, lo, p - 1);  // the pivot at p is already final
  quickSort(a, p + 1, hi);
  return a;
}
 
function partition(a, lo, hi) {
  const r = lo + Math.floor(Math.random() * (hi - lo + 1));
  [a[r], a[hi]] = [a[hi], a[r]]; // random pivot, moved to the end
  const pivot = a[hi];
  let b = lo; // a[lo..b-1] holds items smaller than the pivot
  for (let j = lo; j < hi; j++) {
    if (a[j] < pivot) {
      [a[b], a[j]] = [a[j], a[b]];
      b++;
    }
  }
  [a[b], a[hi]] = [a[hi], a[b]]; // pivot into its final slot
  return b;
}
 
quickSort([7, 2, 9, 4, 1, 6]); // [1, 2, 4, 6, 7, 9]
import random
 
def quick_sort(a, lo=0, hi=None):
    if hi is None:
        hi = len(a) - 1
    if lo >= hi:  # 0 or 1 items: sorted
        return a
    p = partition(a, lo, hi)
    quick_sort(a, lo, p - 1)  # the pivot at p is already final
    quick_sort(a, p + 1, hi)
    return a
 
def partition(a, lo, hi):
    r = random.randint(lo, hi)
    a[r], a[hi] = a[hi], a[r]  # random pivot, moved to the end
    pivot = a[hi]
    b = lo  # a[lo..b-1] holds items smaller than the pivot
    for j in range(lo, hi):
        if a[j] < pivot:
            a[b], a[j] = a[j], a[b]
            b += 1
    a[b], a[hi] = a[hi], a[b]  # pivot into its final slot
    return b
 
quick_sort([7, 2, 9, 4, 1, 6])  # [1, 2, 4, 6, 7, 9]

#Good pivots and bad pivots

Partitioning a range of n items costs O(n): one scan. What matters is how evenly the pivot splits the range.

If the pivot lands near the middle every time, each level halves the work, just like merge sort. There are about log n levels with O(n) work each, so the total is O(n log n).

Now take an array that is already sorted and always use the last item as the pivot. The pivot is the biggest item, so the "smaller" side gets everything else and the "bigger" side is empty. Each level removes just one item. That is n + (n − 1) + … + 1 steps, which is O(n²), and the recursion goes n calls deep.

A random pivot fixes this in practice. No particular input can force bad pivots, because the choice is made fresh every run. The chance of hitting the worst case on a large array is so small that the expected cost is O(n log n) on every input.

ApproachTimeSpaceWhy
Average (random pivot)O(n log n)O(log n)About log n levels of O(n) partitioning. Space is the recursion stack.
Worst caseO(n²)O(n)Every pivot is the smallest or largest item, so each level removes only one.
Key idea

Partitioning puts the pivot in its final place in one O(n) pass. Quicksort is fast when pivots split the range roughly in half, and a random pivot makes that the expected case on any input.

Quicksort is not stable. The swaps in the partition throw items over each other: in the trace, 7 was thrown from slot 0 to slot 1, then to slot 3, then to slot 5. If two items had the same key, nothing would keep them in their original order.

#Common mistakes

Always picking the first or last item

It works on random data and falls apart on data that is already sorted or reversed, which is common in real life: log files, IDs, timestamps. Pick a random pivot, or the median of the first, middle and last items.

Including the pivot in the recursive call

Recurse on [lo, p − 1] and [p + 1, hi]. If you recurse on [lo, p] and the pivot is the largest item, that call gets the same range again and never stops.

Many equal items

If every item is the same, a[j] < pivot is never true, so every partition puts everything on one side. That is the O(n²) case again, even with a random pivot. The fix is a three-way partition: split into smaller, equal and bigger, and only recurse on smaller and bigger.

Tip

If you only need the k-th smallest item, partition once and recurse into the one side that contains position k. That is quickselect, and it runs in O(n) on average because the range shrinks every step without ever branching in two.

In the real world

C++'s std::sort is usually an introsort: quicksort, with insertion sort for tiny ranges and a switch to heap sort if the recursion gets suspiciously deep. You get quicksort's speed with an O(n log n) guarantee.

#Check yourself

Quick check

You partition [3, 8, 1, 5] using the last item, 5, as the pivot, with the code from the trace. Where does 5 end up?

  1. Right. Two items, 3 and 1, are smaller than 5, so they fill slots 0 and 1, and the pivot goes into slot 2. The result is [3, 1, 5, 8].
  2. Not quite. The pivot starts at index 3, but 8 is bigger, so 5 has to move left of it.
  3. Not quite. That would mean only one item is smaller than 5. Both 3 and 1 are.

Quicksort with the last item as pivot gets [1, 2, 3, …, 1000]. Roughly how many comparisons does it make?

  1. Not quite. That is n log n, the cost with good pivots. Here every pivot is the largest item.
  2. Right. Each partition removes only the pivot, so the scans are 999 + 998 + … + 1, which is about n²/2.
  3. Not quite. Even one level of partitioning already costs 999 comparisons.

Which is true of quicksort but not of merge sort?

  1. Right. Partitioning only swaps items inside the array. Merge sort needs an O(n) buffer for its merges.
  2. Not quite. It is the other way round: merge sort is stable and quicksort is not.
  3. Not quite. Merge sort is. Quicksort's worst case is O(n²).

#What to practise next

Partition [5, 9, 2, 7, 3] by hand around its last item, 3: you should get [2, 3, 5, 7, 9] with the pivot at index 1. Then read Heap Sort, which guarantees O(n log n) in place, with no bad inputs at all.
