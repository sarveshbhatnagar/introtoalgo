Binary Search on the Answer

How to binary search over the possible answers instead of an array, how to recognise these problems, and what interviewers ask about them.

Binary search on the answer is used for problems that ask for the smallest or largest value satisfying some condition, when checking whether one particular value satisfies the condition is easy. Instead of searching an array, you search the range of possible answers, and the check takes the place of the comparison with a[mid]. It reduces a problem that seems to need every possibility to be tried to about log₂ of the range size checks.

Without it, you would try the candidate answers one at a time from the smallest upward, and each try costs a full check. When the answer can be anywhere up to a billion, that is far too slow, while binary search needs about 30 checks.

#How binary search on the answer works

The technique applies when the candidate answers can be split into a block of "no" values followed by a block of "yes" values, where "yes" means the candidate satisfies the condition. If a candidate works, every larger candidate must work as well. This is called being monotone. The answer you want is then the first "yes", and finding the first "yes" in a sorted run of no and yes is exactly the lower-bound search from Binary Search. The positions are candidate answers instead of array indexes, and the comparison is a function call instead of a read from the array.

To use it you need three things:

  1. Bounds. A lo that is the smallest candidate worth considering, and a hi that is certain to be a "yes".
  2. A fast check. A function that takes a candidate and returns yes or no, usually with one greedy pass over the input.
  3. Monotonicity. A reason why a "yes" for x implies a "yes" for x + 1. You should be able to state this reason in one sentence before you write any code.

#Worked example: the smallest daily limit

You have six podcast episodes to listen to in order, of 40, 25, 60, 30, 45 and 20 minutes. You listen to whole episodes only and want to finish in at most 3 days. What is the smallest daily listening limit that makes this possible?

Checking a limit is easy. Fill each day with episodes until the next one would go over the limit, then start a new day, and count the days. With a limit of 80 this gives 40 + 25, then 60, then 30 + 45, then 20, which is 4 days, so 80 is too small. Filling each day as far as possible is correct because it never leaves a later day with more work than any other way of splitting the list would.

The candidates are monotone. A limit below 60 can never work, because the 60-minute episode would not fit in any day. The total of 220 always works, because everything fits in one day. And a larger limit never needs more days than a smaller one. So the limits from 60 to 220 go from "no" to "yes" once.

#Code

The code is split into a reusable firstYes search and the check that belongs to this problem. firstYes works for any problem whose answers go from no to yes, as long as hi is a "yes".

// Smallest x in [lo, hi] with isYes(x) true.
// isYes must go no, ..., no, yes, ..., yes, and isYes(hi) must be true.
function firstYes(lo, hi, isYes) {
  while (lo < hi) {
    const mid = lo + Math.floor((hi - lo) / 2);
    if (isYes(mid)) hi = mid; // mid works: the answer is mid or smaller
    else lo = mid + 1;        // mid fails: the answer is bigger
  }
  return lo;
}
 
// Assumes limit >= the longest episode.
function daysNeeded(episodes, limit) {
  let days = 1, today = 0;
  for (const minutes of episodes) {
    if (today + minutes > limit) { days++; today = 0; } // start a new day
    today += minutes;
  }
  return days;
}
 
function smallestDailyLimit(episodes, maxDays) {
  const lo = Math.max(...episodes);
  const hi = episodes.reduce((sum, m) => sum + m, 0);
  return firstYes(lo, hi, (limit) => daysNeeded(episodes, limit) <= maxDays);
}
 
smallestDailyLimit([40, 25, 60, 30, 45, 20], 3); // 90
# Smallest x in [lo, hi] with is_yes(x) true.
# is_yes must go no, ..., no, yes, ..., yes, and is_yes(hi) must be true.
def first_yes(lo, hi, is_yes):
    while lo < hi:
        mid = lo + (hi - lo) // 2
        if is_yes(mid):
            hi = mid      # mid works: the answer is mid or smaller
        else:
            lo = mid + 1  # mid fails: the answer is bigger
    return lo
 
# Assumes limit >= the longest episode.
def days_needed(episodes, limit):
    days, today = 1, 0
    for minutes in episodes:
        if today + minutes > limit:  # start a new day
            days += 1
            today = 0
        today += minutes
    return days
 
def smallest_daily_limit(episodes, max_days):
    lo, hi = max(episodes), sum(episodes)
    return first_yes(lo, hi, lambda limit: days_needed(episodes, limit) <= max_days)
 
smallest_daily_limit([40, 25, 60, 30, 45, 20], 3)  # 90

#Variants

#Finding the largest value that works

Some problems reverse the pattern: the answers go yes, …, yes, no, …, no, and you want the last "yes". Do not write a second template for this. Search for the first "no" with firstYes and subtract 1. For example, the integer square root of 30 is the largest x with x × x ≤ 30. The first x with x × x > 30 is 6, so the answer is 5.

Largest value that works
// Largest x with x * x <= n, for n >= 0.
function intSqrt(n) {
  // n + 1 is surely a "no", because (n + 1)² > n.
  return firstYes(0, n + 1, (x) => x * x > n) - 1;
}
 
intSqrt(30); // 5
# Largest x with x * x <= n, for n >= 0.
def int_sqrt(n):
    # n + 1 is surely a "no", because (n + 1)² > n.
    return first_yes(0, n + 1, lambda x: x * x > n) - 1
 
int_sqrt(30)  # 5

This is also the way to handle "maximise the minimum" problems, such as placing k items on a line so that the smallest gap between any two is as large as possible. The check is "can I place all k items with every gap at least d?". It is true for small d and false for large d, so you search for the first d where it fails and subtract 1.

#Answers that are real numbers

When the answer is a real number, such as a speed or a length, there is no mid + 1 to step to, so the integer template does not apply. Keep the same idea but move the bounds to mid in both cases, and stop after a fixed number of iterations (100 is plenty for doubles) or when hi - lo is smaller than the precision the problem asks for. Do not loop on lo < hi with floating-point numbers, because the loop may never end.

#When the technique does not apply

It does not apply when the check is not monotone, which means the answers do not change from no to yes only once. For example, "can I finish in exactly 3 days?" gives no for tiny limits, yes for some limits, and no again for huge limits that finish in 1 day. Asking for "at most 3 days" fixes this. It also does not apply when you cannot bound the answer, or when a direct formula or a single greedy pass already gives the answer, because then the search adds work without saving any.

#Pitfalls

A lower bound that is too low

If you start lo at 1 and call daysNeeded(episodes, 50), the 60-minute episode cannot fit anywhere, but the check puts it in a day of its own and silently exceeds the limit. The check is only correct from 60 upward. Set lo to the smallest value for which the check is valid, here the longest episode.

An upper bound that is not a yes

firstYes never tests hi. It returns hi when every other candidate fails. If your hi might not satisfy the condition, for example when the problem may have no solution, the function returns a wrong answer without warning. Either choose a hi that always works, or check isYes on the returned value afterwards.

Writing a search for the last yes by hand

A search for the last "yes" that sets lo = mid with a mid rounded down loops forever once hi = lo + 1, because mid equals lo and nothing changes. Search for the first "no" with firstYes and subtract 1, as in the square root example.

A check that is too slow or too loose

The total cost is the number of checks times the cost of one check. If the check is O(n²), the whole solution is O(n² log R). Also, the check must test the real condition. A greedy check that is not actually optimal can say "no" for a value that does work, and then the search returns a number that is too large.

#In the interview

The signals are in the wording of the problem. Look for "the minimum possible largest sum", "the smallest speed that finishes in time", "the largest size such that at least k pieces fit", or "the minimum capacity needed to ship within d days". Another clue is a huge range of possible answers, up to 10⁹ or more, together with a simple way to verify one candidate. Many problems of this type are classic ones, such as splitting an array into k parts with the smallest largest sum, or the slowest eating speed that finishes all piles in h hours. They all use the same template with a different check.

Interviewers usually focus on two things: whether you can state why the answers are monotone, and whether your bounds and your check are correct. Expect these questions.

  • "Why can you binary search here? The input is not sorted." The thing being searched is the range of candidate answers, not the input. If a value works, every larger value works too, so the candidates are ordered by yes and no, and that is all binary search needs.
  • "How did you choose the bounds?" The lower bound is the smallest value for which the check is meaningful, such as the longest single item. The upper bound is a value that certainly works, such as the total of all items. A looser bound only costs one or two extra checks, because the cost grows with the logarithm of the range.
  • "Why is the greedy check correct?" Filling each day as full as possible leaves the least work for the remaining days. Any other way to split the list can be changed into the greedy one without using more days, so the greedy count is the minimum for that limit.
  • "Can anything overflow?" In languages with fixed-size integers, the sum of all items can exceed 32 bits, so use a 64-bit type for hi and for the running total in the check. Computing mid as lo + (hi - lo) / 2 avoids overflow in lo + hi.
  • "What is the complexity?" It is O(n log R), where n is the cost of one check and R is the size of the range of candidates. For limits up to 10⁹ that is about 30 passes over the input.
  • "What if the answer is a decimal?" Halve the interval a fixed number of times, or until it is narrower than the required precision, and move the bounds to mid instead of mid + 1.
  • "Is there another way to solve this?" A dynamic programming solution exists for the splitting problem and takes O(n² × k) time, which is slower for large inputs. Binary search on the answer is the expected solution when the limits are large.
Quick check

The episodes are [40, 25, 60, 30, 45, 20] and the limit is 100 minutes. How many days does the greedy check need?

  1. Right. 40 + 25 = 65, and adding 60 would make 125. Then 60 + 30 = 90, and adding 45 would make 135. Then 45 + 20 = 65.
  2. Not quite. Day 1 cannot take the 60 after 65 minutes, and the remaining 155 minutes do not fit in one more day.
  3. Not quite. That is what a limit of 80 needs. At 100, the episodes 60 and 30 share a day.

The candidate answers run from 1 to 1,000,000,000. About how many checks does binary search on the answer need?

  1. Right. Each check halves the range, and 230 is just over a billion.
  2. Not quite. log₂ of 109 is about 30, not 1,000.
  3. Not quite. That is trying every candidate. Monotone answers let you discard half of the range with each check.

Which question can you binary search on?

  1. Right. A bigger limit never needs more days, so the answers go no, …, no, yes, …, yes.
  2. Not quite. A very large limit gives 1 day, so the answers go no, yes and then no again, with no single switch.
  3. Not quite. The answers alternate, so one check tells you nothing about the neighbouring values.

You want the largest x for which a check is true, and the answers go yes, …, yes, no, …, no. What do you do with firstYes?

  1. Right. The last yes is the value just before the first no.
  2. Not quite. This loops forever when hi = lo + 1, because mid stays equal to lo.
  3. Not quite. The first yes is the smallest value, which is the opposite end of the yes block.
