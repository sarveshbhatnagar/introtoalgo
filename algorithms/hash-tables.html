Hash Tables

See how a hash table turns any key into a bucket number, how it handles collisions, and when a map turns an O(n²) search into one O(n) pass.

At a theatre coat check, you get ticket 37 for your coat. When you come back, the attendant walks straight to hook 37 instead of searching every hook.

An array works like that, but only when the "ticket" is a small whole number. Usually you look things up by a username, a word or a product code. A hash table gives any key its own ticket number, so you find it just as fast.

#From key to bucket

A hash table is an array of buckets. A hash function turns the key into a whole number, always the same for the same key. That number modulo the bucket count picks the bucket.

A simple, deliberately weak hash for strings: add up the character codes. For "owl": 111 + 119 + 108 = 338. With 5 buckets, 338 % 5 = 3, so every lookup of "owl" goes straight to bucket 3.

#Collisions, and why they are fine

With endless possible keys and only 5 buckets, two keys will sometimes share a bucket: a collision. "ant" sums to 323, and 323 % 5 is also 3.

The common fix is chaining: each bucket holds a short list of [key, value] pairs. To look up a key, hash it, go to its bucket, and compare keys along the list. Step through a table of how many of each animal a zoo has.

Real languages use a far better hash function, but the structure is the same:

class TinyMap {
  constructor(size = 5) {
    this.buckets = Array.from({ length: size }, () => []);
  }
  bucketFor(key) {
    let sum = 0;
    for (const ch of key) sum += ch.charCodeAt(0); // weak hash, for teaching
    return this.buckets[sum % this.buckets.length];
  }
  set(key, value) {
    const bucket = this.bucketFor(key);
    for (const pair of bucket) {
      if (pair[0] === key) { pair[1] = value; return; } // update
    }
    bucket.push([key, value]); // new key: add to the chain
  }
  get(key) {
    for (const [k, v] of this.bucketFor(key)) {
      if (k === key) return v;
    }
    return undefined; // not found
  }
}
class TinyMap:
    def __init__(self, size=5):
        self.buckets = [[] for _ in range(size)]
 
    def bucket_for(self, key):
        total = sum(ord(ch) for ch in key)  # weak hash, for teaching
        return self.buckets[total % len(self.buckets)]
 
    def set(self, key, value):
        bucket = self.bucket_for(key)
        for pair in bucket:
            if pair[0] == key:
                pair[1] = value  # update
                return
        bucket.append([key, value])  # new key: add to the chain
 
    def get(self, key):
        for k, v in self.bucket_for(key):
            if k == key:
                return v
        return None  # not found

#Keeping the chains short

Lookups are fast only while chains stay short. Two things keep them short:

  • A good hash function spreads keys evenly. Adding codes is weak: "cat" and "act" always collide. Real hash functions mix every bit of the key, so similar keys land in unrelated buckets.
  • The table grows. When the load factor (entries ÷ buckets) passes a limit such as 0.75, the table makes about twice as many buckets and re-inserts every entry, because % bucketCount now gives different answers. That O(n) step is rare, like a growing array's copy.

Then a chain holds about one entry on average, so get, set and delete are O(1) on average. If every key lands in one bucket, a lookup walks all n entries: O(n).

ApproachTimeSpaceWhy
get, set, delete (average)O(1)O(n) for the tableChains hold about one entry.
get, set, delete (worst case)O(n)Every key in one bucket.
ResizeO(n) onceRare, so inserts stay O(1) amortized.

#Turning O(n²) into O(n)

You rarely write your own: JavaScript has Map and Set, Python has dict and set. The skill is noticing when to reach for one.

To count how often each word appears, the direct approach scans the whole list for each word: O(n²). With a map, you walk the list once and bump a counter per word.

function countWords(words) {
  const counts = new Map();
  for (const word of words) {
    counts.set(word, (counts.get(word) ?? 0) + 1); // O(1) on average
  }
  return counts;
}
 
countWords(["red", "blue", "red", "green", "blue", "red"]);
// Map { "red" => 3, "blue" => 2, "green" => 1 }
def count_words(words):
    counts = {}
    for word in words:
        counts[word] = counts.get(word, 0) + 1  # O(1) on average
    return counts
 
count_words(["red", "blue", "red", "green", "blue", "red"])
# {'red': 3, 'blue': 2, 'green': 1}

Whenever an inner loop only searches ("have I seen this?", "how many so far?", "where is the partner for this value?"), a map can remember the answer instead. Each question then costs O(1), paid for with O(n) extra memory.

Key idea

A hash table turns a key into a bucket number, so finding a key costs about as much as reading one array slot. When an inner loop is only searching, replace it with a lookup.

#Common mistakes

Using arrays or objects as keys

In JavaScript, map.set([1, 2], "x") then map.get([1, 2]) returns undefined: a Map compares object keys by identity, and these are two different arrays. In Python, a list cannot be a key. Use a string key like "1,2", or a tuple in Python.

Plain objects turn keys into strings

A JavaScript object converts every key to a string, so obj[1] and obj["1"] are the same entry, and "constructor" already looks present. Use Map when keys come from data.

Treating O(1) as a promise

O(1) is the average. A poor hash function, or input built to collide, makes every lookup O(n). That is why Python mixes a random value into string hashes each time it starts.

In the real world

A web cache finds a saved page by its address with a hash table, and a compiler keeps its variable names in one.

#Check yourself

Quick check

Using the sum-of-character-codes hash with 5 buckets, which key always lands in the same bucket as "cat"?

  1. Right. Same letters, same sum (312), same bucket. That is why adding codes is a weak hash.
  2. Not quite. 99 + 97 + 114 = 310, and 310 % 5 = 0, not cat's 2.
  3. Not quite. 99 + 111 + 119 = 329, and 329 % 5 = 4. Different bucket.

A badly chosen hash function sends all n keys to the same bucket. What does a lookup cost now?

  1. Not quite. Finding the bucket is O(1), but its chain holds every entry.
  2. Right. The table is now one long list, compared key by key.
  3. Not quite. An unsorted chain has nothing to halve.

A loop over n orders checks bannedIds.includes(order.customerId), where bannedIds is an array of n IDs. What makes the whole check O(n)?

  1. Not quite. Sorting plus binary search gives O(n log n), not O(n).
  2. Right. Building the set is O(n), and each has is O(1) on average. Total O(n).
  3. Not quite. indexOf scans too: O(n²) overall.
