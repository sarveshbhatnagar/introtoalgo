Math for Algorithms

The little math algorithms really use: logarithms as halving, powers of two, the 1 + 2 + ... + n sum, counting pairs, and modulo for wrap-around.

A knockout tournament starts with 64 teams. In every game the loser goes home. How many rounds until there is a champion, and how many games in total? Compare that with a league, where each team plays every other team once.

The answers are 6 rounds, 63 games and 2,016 games. Each takes seconds with the right idea, and the same ideas estimate an algorithm's cost.

#Halving: logarithms

Each round halves the teams: 64, 32, 16, 8, 4, 2, 1. That is 6 halvings. The times you can halve n before reaching 1 is the logarithm base 2 of n, written log₂ n. So log₂ 64 = 6.

Read backwards: 2⁶ = 64. A logarithm asks "which power of 2 gives me n?"

When n is not a power of 2, halving with whole numbers rounds down each time. Step through it for 100.

Logarithms grow very slowly, which is why halving the work each step, as binary search does, is so fast.

Remember one anchor: 2¹⁰ = 1,024, about a thousand. Every factor of 1,000 adds about 10.

The base does not matter in Big-O

log₂ n is about 3.32 times log₁₀ n, a constant factor, so Big-O just says O(log n).

#Doubling: powers of two

Doubling explodes as fast as halving shrinks. If you can include or leave out each of n items, there are 2 choices per item: 2ⁿ ways in total. 3 toppings give 2³ = 8 possible pizzas, counting the plain one. 30 toppings give over a billion.

So trying every subset only works for about 20 to 25 items. The naive Fibonacci in Recursion was slow for the same reason: its calls multiplied by about 1.6 each time n went up by 1.

Count the tournament games round by round: 32 + 16 + 8 + 4 + 2 + 1 = 63. A halving sum always lands just under twice the biggest term: 1 + 2 + 4 + ... + 2ᵏ = 2ᵏ⁺¹ − 1.

Faster: every game sends one team home, and 63 must go home to leave one. Counting what each step removes is often easier than adding up steps.

In the real world

The halving sum is why appending to a JavaScript array or Python list is cheap. When full, it copies everything into one twice the size. The copies cost 1 + 2 + 4 + ... + n, less than 2n in total, so each append is O(1) on average. Arrays covers this.

#Adding up 1 + 2 + ... + n

This sum appears whenever an inner loop gets one step longer (or shorter) each time. Write it twice, forward and backward, and pair them up.

Each of the n rows adds up to n + 1. So:

1 + 2 + ... + n = n(n + 1) / 2. For n = 100 that is 100 × 101 / 2 = 5,050.

What matters is the shape: about n²/2. An inner loop that runs 1, 2, 3, ... up to n times is O(n²).

#Counting pairs

In the league, each of 64 teams plays 63 others: 64 × 63 = 4,032. That counts every game twice, so divide by 2: 2,016. In general, n things make n(n − 1) / 2 pairs, the count from the pair loop in Big-O Notation. That is why "check every pair" is O(n²).

Orders grow even faster. 3 people line up in 3 × 2 × 1 = 6 orders, written 3! ("3 factorial"). 10 people have 10! = 3,628,800. Trying every order is limited to about 10 items.

#Remainders: modulo

Six friends sit at a round table in seats 0 to 5. A card moves 4 seats clockwise from seat 3. There is no seat 7: seat 6 is seat 0 again, so it lands on seat 1.

That wrapping is modulo, written %: the remainder after division. 7 % 6 is 1, because 7 = 1 × 6 + 1. Use it whenever something wraps around:

  • Circular positions: (i + k) % n for seats, clocks, circular buffers, weekdays.
  • Even or odd: x % 2 is 0 for even numbers.
  • Last digit: x % 10. With dividing by 10 and rounding down, it peels off digits one at a time.
  • Huge answers: counting problems often say "return the answer modulo 1,000,000,007" because the exact number is too big to store. Taking the remainder after each addition or multiplication gives the same final remainder.

#The code

// Halvings until n reaches 1: about log2(n)
function countHalvings(n) {
  let steps = 0;
  while (n > 1) {
    n = Math.floor(n / 2); // JS division gives decimals
    steps++;
  }
  return steps;
}
 
// 1 + 2 + ... + n, no loop needed
const sumTo = (n) => (n * (n + 1)) / 2;
 
// Move k seats around a table of n seats; k may be negative
const moveSeat = (i, k, n) => (((i + k) % n) + n) % n;
 
countHalvings(100); // 6
sumTo(100);         // 5050
moveSeat(3, 4, 6);  // 1
moveSeat(1, -3, 6); // 4
# Halvings until n reaches 1: about log2(n)
def count_halvings(n):
    steps = 0
    while n > 1:
        n //= 2  # whole-number division
        steps += 1
    return steps
 
# 1 + 2 + ... + n, no loop needed
def sum_to(n):
    return n * (n + 1) // 2
 
# Move k seats around a table of n seats; k may be negative
def move_seat(i, k, n):
    return (i + k) % n  # Python's % is never negative here
 
count_halvings(100)  # 6
sum_to(100)          # 5050
move_seat(3, 4, 6)   # 1
move_seat(1, -3, 6)  # 4

#Common mistakes

Negative numbers and %

In JavaScript, -2 % 6 is -2, not 4: the result takes the sign of the left side. Moving backwards then gives an out-of-range index. Add n and take % n again, as moveSeat does. Python's % already returns 4, so this bug bites when porting Python to JavaScript.

Division that is not whole

7 / 2 is 3.5 in both languages. Use Math.floor(7 / 2) or 7 // 2 to get 3. A middle index of 3.5 reads undefined in JavaScript and raises an error in Python.

Numbers that grow too big

JavaScript numbers are exact only up to about 9 × 10¹⁵; beyond that they quietly lose their last digits. Python integers never overflow but get slow when enormous. If a count can grow like 2ⁿ or n!, expect to return it modulo a number, and take the remainder at every step.

#Check yourself

Quick check

You halve a list of 1,000,000 items again and again until 1 item is left. About how many halvings is that?

  1. Right. 2¹⁰ is about a thousand, so 2²⁰ is about a million.
  2. Not quite. That is the square root of a million. Halving shrinks much faster.
  3. Not quite. That is the size after one halving, not the number of halvings.

An inner loop runs 1 time, then 2 times, then 3 times, up to 100 times. How many times does its body run in total?

  1. Not quite. That is only the last pass.
  2. Not quite. That is 100 × 99 / 2, the pairs among 100 things. The passes go up to 100, so use n(n + 1) / 2.
  3. Right. 100 × 101 / 2 = 5,050, about n²/2, so the loop is O(n²).

Seats are numbered 0 to 4 around a table. In JavaScript, what does (0 - 1) % 5 give?

  1. Not quite. That is what Python gives. JavaScript keeps the sign of the left side.
  2. Right. JavaScript keeps the sign of the left side. Use ((0 - 1) % 5 + 5) % 5 to get 4.
  3. Not quite. The remainder of −1 divided by 5 is not 1 in any convention.
