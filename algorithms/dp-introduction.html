Introduction to Dynamic Programming

Turn a slow recursive solution into a fast one: remember answers with memoisation, then fill a table bottom-up. One example, start to finish.

You are building the change dispenser for a ticket machine. It has coins worth 1, 4 and 5, as many of each as it needs. A customer is owed 8. The machine should hand over as few coins as possible.

The obvious rule is "always take the biggest coin that fits". That gives 5, then 1, 1, 1: four coins. But 4 + 4 is only two coins. Taking the biggest coin first looked safe and was wrong, the same trap you saw in Greedy Algorithms. To get the right answer you have to consider every first coin. That is where this lesson starts.

#Version 1: honest, slow recursion

Think about the first coin the machine hands over. It is a 1, a 4 or a 5. Whichever it is, what remains is the same problem with a smaller amount. If you owe 8 and hand over a 4, you now owe 4.

So the fewest coins for 8 is one coin plus the best of three smaller answers: the fewest coins for 7, for 4, or for 3. Each of those breaks down the same way, until you reach 0, which needs no coins at all.

Slow: try every first coin
// Fewest coins that add up to amount (Infinity if impossible).
function fewestCoins(amount, coins) {
  if (amount === 0) return 0;
  let best = Infinity;
  for (const coin of coins) {
    if (coin <= amount) {
      best = Math.min(best, 1 + fewestCoins(amount - coin, coins));
    }
  }
  return best;
}
 
fewestCoins(8, [1, 4, 5]); // 2
import math
 
# Fewest coins that add up to amount (math.inf if impossible).
def fewest_coins(amount, coins):
    if amount == 0:
        return 0
    best = math.inf
    for coin in coins:
        if coin <= amount:
            best = min(best, 1 + fewest_coins(amount - coin, coins))
    return best
 
fewest_coins(8, [1, 4, 5])  # 2

This is correct. For 8 it makes 35 calls. For 30 it makes 255,904 calls. There are only 31 different amounts between 0 and 30, so almost all of that work is repeated.

You saw the same waste with Fibonacci in Recursion. Two things are true here, and together they are the signal for dynamic programming:

  • The big answer is built from smaller answers. The best way to pay 8 is one coin plus the best way to pay what is left.
  • The smaller problems repeat. Different paths through the recursion keep landing on the same amount.

#Version 2: remember answers (memoisation)

The fix is small. Keep a map from amount to answer. Before working anything out, check the map. After working it out, store it. Each amount is now solved once; every later visit is a single lookup.

Memoised: same recursion, plus a map
function fewestCoinsMemo(amount, coins, memo = new Map()) {
  if (amount === 0) return 0;
  if (memo.has(amount)) return memo.get(amount); // solved before
  let best = Infinity;
  for (const coin of coins) {
    if (coin <= amount) {
      best = Math.min(best, 1 + fewestCoinsMemo(amount - coin, coins, memo));
    }
  }
  memo.set(amount, best); // remember for next time
  return best;
}
def fewest_coins_memo(amount, coins, memo=None):
    if memo is None:
        memo = {}
    if amount == 0:
        return 0
    if amount in memo:  # solved before
        return memo[amount]
    best = math.inf
    for coin in coins:
        if coin <= amount:
            best = min(best, 1 + fewest_coins_memo(amount - coin, coins, memo))
    memo[amount] = best  # remember for next time
    return best

For 30, the call count drops from 255,904 to 84. The logic did not change at all. You only stopped throwing answers away.

#Version 3: fill a table from the bottom

Memoisation still works top-down, from 8 toward 0. But every amount only depends on smaller amounts. So you can skip the recursion and work upward: solve 0, then 1, then 2, and so on. By the time you reach any amount, everything it needs is already in the table. This is called tabulation.

Tabulation: a loop instead of recursion
function fewestCoinsTable(amount, coins) {
  const best = new Array(amount + 1).fill(Infinity);
  best[0] = 0;
  for (let a = 1; a <= amount; a++) {
    for (const coin of coins) {
      if (coin <= a) best[a] = Math.min(best[a], 1 + best[a - coin]);
    }
  }
  return best[amount]; // Infinity means "cannot be paid"
}
 
fewestCoinsTable(8, [1, 4, 5]); // 2
def fewest_coins_table(amount, coins):
    best = [math.inf] * (amount + 1)
    best[0] = 0
    for a in range(1, amount + 1):
        for coin in coins:
            if coin <= a:
                best[a] = min(best[a], 1 + best[a - coin])
    return best[amount]  # math.inf means "cannot be paid"
 
fewest_coins_table(8, [1, 4, 5])  # 2

Memoisation and tabulation do the same work. Memoisation is often easier to write first, because it is your recursion plus three lines. Tabulation has no recursion, so it cannot overflow the call stack on a large amount, and it is usually a little faster.

#The five-step recipe

Every dynamic programming solution in this module is written the same way. Get these five answers down in words before you write any code:

  1. State. What does one cell of the table mean? Here: best[a] is the fewest coins that add up to exactly a.
  2. Recurrence. How is a cell built from smaller cells? Here: best[a] = 1 + min(best[a − coin]) over every coin that fits.
  3. Base cases. Which cells do you know without asking anything? Here: best[0] = 0.
  4. Order. Which way do you fill the table so each cell's inputs are ready? Here: from 0 upward.
  5. Answer. Which cell holds the result? Here: best[amount].
Key idea

Dynamic programming is recursion that never solves the same subproblem twice. Find the state, write the recurrence, and either remember answers as you recurse or fill the table in an order where every answer you need is already there.

Step 1 is where the thinking happens. If you cannot say in one sentence what a cell means, the recurrence will not come. The other four steps usually follow from it.

ApproachTimeSpaceWhy
Plain recursionExponentialO(A)A is the amount and k the number of coins. Up to k calls per call and up to A levels deep, so up to about kA calls.
MemoisationO(A × k)O(A)Each amount is solved once and tries k coins. The map and the call stack both hold up to A entries.
TabulationO(A × k)O(A)The same A × k steps in two plain loops. No call stack.

The rule of thumb for any DP: time = number of cells × work per cell. Here there are A + 1 cells and each one tries k coins.

#Common mistakes

Starting the table at 0 instead of ∞

If every cell starts at 0, min(best[a], …) keeps the 0 and every answer comes out as 0. Start "fewest" problems at ∞ so any real option beats it. ∞ also handles amounts that cannot be paid: with coins 4 and 5, best[3] stays ∞, and 1 + ∞ is still ∞.

A memo that is created fresh on every call

If you write const memo = new Map() inside the function body, each call gets its own empty map and nothing is ever reused. The memo must be shared by every call for the same input: pass it along, as above, or keep it outside. In Python, never write memo={} as a default argument: that one dictionary survives between separate calls, so answers for one set of coins leak into the next.

Filling the table in the wrong order

If a cell reads best[a − coin], that cell must be filled first. Loop over amounts downward and best[8] reads best[7], best[4] and best[3] while they are still ∞, so it comes out as ∞ instead of 2. When you write the loop, point at one cell and check that every cell it reads has already been computed.

In the real world

Spreadsheets recalculate formulas in an order where every cell's inputs are ready first, and build tools cache the result of every step they have already done. Both are the same "solve once, reuse" idea at work.

#Check yourself

Quick check

Coins are 1, 3 and 4. Using the table, what is best[6]?

  1. Not quite. That is the greedy answer, 4 + 1 + 1. The table also tries starting with a 3, which leaves 3, and best[3] is 1.
  2. Right. 3 + 3 = 6. In the table: coin 3 leaves 3, and best[3] = 1, so 1 + 1 = 2. No single coin is worth 6, so 2 is the minimum.
  3. Not quite. That would need a coin worth 6. Only best[0] plus one coin can give 1.

Why is memoised recursion so much faster than plain recursion here?

  1. Not quite. It tries exactly the same coins. The saving comes from not repeating whole subproblems.
  2. Right. Plain recursion solves amount 3 many times over. With a memo, the second visit is a single lookup, so the total work is about amounts × coins.
  3. Not quite. That is tabulation. Memoisation still recurses; it just stops early when the answer is known.

In the five-step recipe, which step decides the direction of the loop?

  1. Not quite. The state says what a cell means. It does not say which cell to fill first.
  2. Not quite. Base cases are where the filling starts from, but the loop direction comes from what the recurrence reads.
  3. Right. The order makes sure every cell a cell depends on is already filled. Here each amount reads smaller amounts, so you go upward.

#What to practise next

The coin table was one row of cells, each looking back at a few earlier cells. That shape covers a whole family of problems, from choosing work shifts to counting ways up a staircase, and it is the subject of 1D Dynamic Programming. Use the five steps there on purpose, even when the answer looks obvious. To practise the coin table itself, try Cookie Box Order.
