Knapsack

Choose which items to pack under a weight limit for the most value. Fill the item-by-capacity table, read back the chosen items, then shrink it to one row.

You sell at a weekend market and carry your goods on a bike trailer that holds 5 kg. You have three things you could bring: a box of honey (2 kg, profit 4), a wheel of cheese (3 kg, profit 7) and a crate of jam (4 kg, profit 10). Each one comes whole or not at all. What should you load?

Jam earns the most per kilo, 2.5, so a common rule takes it first. Then 1 kg is left and nothing fits: profit 10. Honey and cheese together weigh exactly 5 kg and earn 11. With 3 items you could check all 8 combinations. With 40 items there are over a trillion. This is the 0/1 knapsack problem: every item is either in (1) or out (0).

#Why one index is not enough

In 1D Dynamic Programming the state was "the best answer for the first i days". Try that here: "the best profit from the first i items". To decide whether to add item i, you need to know how much space the earlier items used, and that number is not in the state. Two packings with equal profit can leave different room.

So put the space into the state too. That gives a table with one row per item and one column per amount of space, the same kind of table you filled in DP on Grids.

#The five steps

  1. State. best[i][w] is the most profit you can make using only the first i items, with at most w kg of space.
  2. Recurrence. Item i is either left out or packed. Leave it out and you get best[i − 1][w]. Pack it, if it fits, and you get its value plus the best you can do with the earlier items in the space that remains: value[i] + best[i − 1][w − weight[i]]. Take the larger.
  3. Base cases. best[0][w] = 0 for every w: with no items you earn nothing.
  4. Order. Each cell reads only the row above. Fill row by row.
  5. Answer. best[n][W]: all items allowed, full capacity.

The "take" arrow always comes from the row above. That is what stops an item being used twice: once you pack the cheese, the rest of the space can only hold items from earlier rows.

#The code

Item-by-capacity table
function bestProfit(weights, values, capacity) {
  const n = weights.length;
  const best = Array.from({ length: n + 1 }, () => new Array(capacity + 1).fill(0));
  for (let i = 1; i <= n; i++) {
    const weight = weights[i - 1]; // row i is item i - 1 in the arrays
    const value = values[i - 1];
    for (let w = 0; w <= capacity; w++) {
      best[i][w] = best[i - 1][w]; // skip the item
      if (weight <= w) {
        best[i][w] = Math.max(best[i][w], value + best[i - 1][w - weight]); // take it
      }
    }
  }
  return best[n][capacity];
}
 
bestProfit([2, 3, 4], [4, 7, 10], 5); // 11

#One row is enough, if you go backwards

Each row only reads the row above, so you can keep a single array and overwrite it item by item. There is one catch. The "take" option reads best[w − weight], a cell to the left. If you loop w upward, that cell has already been overwritten for the current item, and you end up packing the item twice. Loop w downward and every cell you read on the left still holds the old row.

One row, filled right to left
function bestProfitOneRow(weights, values, capacity) {
  const best = new Array(capacity + 1).fill(0);
  for (let i = 0; i < weights.length; i++) {
    // High to low, so best[w - weights[i]] is still from the previous item.
    for (let w = capacity; w >= weights[i]; w--) {
      best[w] = Math.max(best[w], values[i] + best[w - weights[i]]);
    }
  }
  return best[capacity];
}
def best_profit_one_row(weights, values, capacity):
    best = [0] * (capacity + 1)
    for weight, value in zip(weights, values):
        # High to low, so best[w - weight] is still from the previous item.
        for w in range(capacity, weight - 1, -1):
            best[w] = max(best[w], value + best[w - weight])
    return best[capacity]
Key idea

When a choice uses up a shared resource, put the amount of resource left into the state. The table then has one dimension for "which items have I considered" and one for "how much room is left".

ApproachTimeSpaceWhy
Try every subsetO(2ⁿ × n)O(n)Each of n items is in or out, and each subset takes up to n steps to add up.
Full tableO(n × W)O(n × W)One cell per item and capacity, two options per cell. You can walk back to list the items.
One rowO(n × W)O(W)Same work. You can no longer walk back to list the items.

The cost depends on the capacity W as well as on the number of items. Three items and a 5 kg limit is 4 × 6 = 24 cells. Write the same weights in grams and the limit becomes 5,000 g: 4 × 5,001 cells for the same answer. With 20 items and a capacity in the billions the table is hopeless, while trying all 2²⁰ (about a million) subsets is quick.

#Common mistakes

Looping upward in the one-row version

With honey alone (2 kg, profit 4) and 4 kg of space, an upward loop sets best[2] = 4, then best[4] = 4 + best[2] = 8: two boxes of honey from one. That is the right answer to a different problem, where every item comes in unlimited copies. The coin table in Introduction to Dynamic Programming is that unlimited-copies problem: best[a − coin] may already use the same coin, and that is allowed, so its loop goes upward on purpose.

Packing by profit per kilo

Sorting by value per weight and packing greedily is correct only if you may cut items into pieces, like pouring out part of a sack of rice. For whole items it can strand space, as the jam did. See Greedy Algorithms for when a greedy rule is safe.

Mixing up row numbers and item positions

Row 0 of the table means "no items", so row i describes the item at position i − 1 in the input arrays. Reading weights[i] instead is an off-by-one error that skips the first item and runs past the last.

In the real world

The same shape appears whenever a budget is spent on all-or-nothing choices, such as picking features that fit a team's hours for a release.

#Check yourself

Quick check

Items: (1 kg, profit 3) and (3 kg, profit 5). Capacity 3 kg. What is best[2][3]?

  1. Not quite. That packs both items, which weigh 4 kg together. Only 3 kg fits.
  2. Right. Skip the 3 kg item: best[1][3] = 3. Take it: 5 + best[1][0] = 5 + 0 = 5. The larger is 5.
  3. Not quite. That is the skip option. Taking the 3 kg item on its own earns more.

Why does the "take" option read best[i − 1][…] and not best[i][…]?

  1. Not quite. Cells to the left in row i are already filled. Reading them would be possible, and wrong.
  2. Right. The remaining space may only be filled with earlier items. Reading row i would let item i appear again.
  3. Not quite. Both reads cost the same. The choice of row changes what problem you are solving.

A packing problem has 30 items and a capacity of 50. Roughly how many cells does the full table have?

  1. Right. (30 + 1) × (50 + 1) = 1,581 cells, each filled with one comparison.
  2. Not quite. That is roughly 2³⁰, the number of subsets you would check by brute force.
  3. Not quite. The table multiplies items by capacities; it does not add them.
